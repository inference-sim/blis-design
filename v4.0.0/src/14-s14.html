14Versions and releases

This section is about the versions of the code the design describes. The design’s own version is numbered by the rule named in §1.

14.1 Version schemes

An engine module models one upstream commit: a release tag, or any commit on the upstream’s main or a release branch (LIF-5). inference-sim is the one tagged release. Every other repository is pinned by commit.

Only inference-sim has release versions; everything else is identified by a commit.

What a release guarantees about an engine module

A release of inference-sim, for each engine module:

  • models the upstream commit its Upstream record names, and no other;
  • passed that commit’s oracle tiers, its field list and surface list checks, and every invariant whose registry status is ci (§13.1);
  • differs from the previous release that models the same commit only by BLIS-side changes: bug fixes, newly modelled features, contract or substrate updates. They may change prices or decisions. The release notes list the pull requests merged between the two releases, say whether prices or decisions changed, and include the price-change report (§13.3);
  • holds only files ported from that commit or original to BLIS.

The pseudo-version Go derives for a router fork commit only orders commits and says nothing about the llm-d release modelled.

A detail of Go’s version ordering

To Go, -blis.N is a pre-release suffix. So vA.B.C-blis.1 sorts before vA.B.C, and go get …@latest prefers any plain release over every pre-release. Three rules follow for the router fork:

  • It never tags a plain v<upstream>; an optional tag always has a -blis.N suffix, with N from 1.
  • Pins name exact commits. A lint checks the version each build actually selects, not the text of go.mod (LIF-2).
  • A plain tag made earlier stays (LIF-1) and makes @latest wrong for that module. A retract line cannot fix this, because Go reads retractions only from the latest release version; an exclude line in inference-sim’s go.mod does (X11).

14.2 Lifecycle invariants

  • LIF-1 A tag names one commit forever, and a pinned commit stays on its branch forever. Tags are never moved or deleted; a mistake gets a new tag. A main or release branch that a release pins is never rewritten.Maintainer practice (§4.2): a tag rule on v* in inference-sim blocks updating and deleting a tag, and branch protection blocks force-pushes to main and release branches in every repository.
  • LIF-2 In every build, the router fork resolves to the commit stack.json records, through inference-sim’s one replace directive (X11). One Go toolchain version is named in substrate/contracts/toolchain. No module BLIS writes declares a go version above it. Every CI job sets GOTOOLCHAIN=local and installs exactly that version, so no build downloads a toolchain. When upstream llm-d raises the router fork’s go line, a maintainer raises the toolchain file first, in the same change. Documented version strings are generated (X23).Checked by: selected-version lint (go list -m all), which for the router reads the replace target, not the placeholder version on the require line; a check that no module declares a go version above contracts/toolchain; a CI step that fails if go version differs from it; a test of every engine and router package against the versions the simulator selects.
  • LIF-3 A maintainer with write access cuts each inference-sim release, from a commit where every required check passed, with an annotated tag on that commit. The release notes list the pull requests merged since the previous release and the price-change report, and name the upstream commit each engine module models (SIM-3).Maintainer practice (§4.2): inference-sim’s settings let only people with write access create tags; branch protection requires the checks before a merge; the maintainer writes the notes from the generated list and report (§13.6).
  • LIF-5 An engine module models one upstream commit. Its Upstream record names that commit and the release it descends from, every ported file names that same commit, and no code for another commit remains except a model backport the record lists (VLM-2). An adapter file derived from a package the oracle’s lock pins also names that package’s version. The modelled commit’s package depends on no package kept only for another commit.Checked by: a test that lists the dependencies of the engine’s entry package with go list -deps and fails on any package kept for another commit; the provenance lint, which refuses a ported file that names another commit; the oracle tiers (§7.4).
  • LIF-6 Each inference-sim release runs exactly one upstream commit of each engine and one llm-d release, and lists them in stack.json. A scenario states no upstream version, of an engine or of llm-d: the build fixes them, and every Result records them. A user who needs a particular upstream commit chooses the inference-sim release that runs it, as its stack.json and release notes state, and inference-sim version prints the commits a build runs. A scenario that states a version field is refused as an unknown field (X1, SIM-2).Checked by: a refusal test of a scenario that states a version field; a test that every Result records the commits in stack.json.
  • LIF-7 A deprecated feature is removed by the first release after its deprecation that may break compatibility: a MAJOR release, or a MINOR release while inference-sim is at v0. An engine module also removes deprecated code when it moves to a new upstream commit. Removal takes with it every code path, flag, field, test and document that existed only for that feature. Each deprecation is recorded where the feature is defined, with the release that deprecated it. Nothing in this design depends on a deprecated feature, and no directory keeps code that none of the binaries BLIS ships can reach.Checked by: a whole-program dead-code check from the main packages of every binary BLIS ships, with test files not counted as reaching code; upstream files in the router fork, and the interfaces in contracts/, are exempt. Maintainer practice (§4.2): the maintainer cutting a MAJOR release, or a MINOR one at v0, reads the deprecation notices and removes the features they name.

14.3 The SGLang engine module

engines/sglang is an engine module like engines/vllm (§5.2). It does not port SGLang’s own router, because llm-d is the router in the llm-d stack.

14.4 Release branches

inference-sim has a main branch, which models the newest upstream commit of each engine BLIS supports, and release branches release-vX.Y. When an engine module moves to a new upstream commit, inference-sim cuts release-vX.Y from its last release that ran the old commit.

A fix needed on the old commit is made first on the main branch if the main branch needs it too, then cherry-picked to the release branch; otherwise it is made on the release branch alone. A PATCH release from the release branch ships it. Only the release before the newest is supported this way, and its branch closes when inference-sim next moves an engine or llm-d to a new upstream commit.

The router fork keeps a branch release-<llm-d release> for the same purpose, cut from the last commit that modelled the old llm-d release, and the release branch of inference-sim pins it.
