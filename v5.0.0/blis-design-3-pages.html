The BLIS design in three pages

This summarises the BLIS target design for engineers who already know llm-d and vLLM. The design is the authority, and each claim below links to the section that states it. Terms are defined in the glossary (Appendix B), and Appendix C maps v1.0.0 rule identifiers to this version.

What BLIS is

BLIS simulates an LLM serving cluster. It runs the router of llm-d, hosted in simulated time with no change to any routing decision (§5.3), and Go ports of the vLLM and SGLang engines (§5.2). Each port covers the engine’s scheduling, KV-cache management, KV transfer and tiering, and how it resolves settings and chooses kernels (§7.1). It is tested step by step against the engine’s own Python code (§7.2). A cost model, built from published hardware facts and fitted coefficients, prices every step (§6.1).

A user configures BLIS with the upstream’s own field names, types and defaults. An unknown or unsupported field is refused by its upstream name (§4).

One idea organises the design: the engine decides what runs, the cost model says how long it takes, and the cost model sees physical units, never the engine’s vocabulary (§6.1).

The components, one owner for every fact

inference-sim holds everything built into the simulator: the substrate, one directory per engine module, and the simulator. They form one Go module, with import-graph checks at the directory boundaries. The router fork keeps llm-d’s router close to upstream and depends on no BLIS code, and the two applications stay separate (§2.1).

Every fact has one owner. To place a fact, ask what it depends on: an engine’s upstream commit, an llm-d release, or the simulator’s own design. If none, it is true of the hardware, the model, the physics or the data, and belongs in the substrate. A check: would a second engine need the same edit? If not, it belongs in an engine module (§2.2).

One simulated step

Once per pool, the engine module resolves its configuration as the upstream does, lowers the model to kernels, sizes its KV budget, and hands the cost model a PoolPlan. At each step the scheduler forms a StepShape, padded as the upstream pads it, and asks the cost model for its price through an Environment that the simulator supplies. The engine reports the step done with its metrics and KV events; the simulator advances simulated time and delivers them to the router (§6.3). The cost model turns each KV move into the bytes each link must carry, and the simulator shares each link among the overlapping transfers, the only resource arithmetic it does (§6.2).

Lowering happens only in engine modules; the catalog’s deriver writes checkpoint facts and nothing else. The cost model sees physical units, never an engine’s settings, and the substrate holds no engine name (§6.1). A kernel coefficient is keyed by the kernel implementation that runs. An engine-path cost, such as host or launch time, is keyed by the identity of the code that does the work, supplied by the engine module (§9.2).

Engines model an upstream commit

An engine module models one upstream commit: a release tag, or any commit on the upstream’s main or a release branch. A build runs one commit of each engine, and a scenario states no upstream version; to model another commit, use the release that runs it (§7.1). An engine upgrade ports the diff of the code a module models, regenerates its lists and runs every test tier again (§12.4). Model support is work in one module for a model whose engine-facing code an upgrade does not port (§12.5). A model backport applies the upstream commits that add a model onto the modelled commit; it carries model code only, and an upgrade drops it once the new commit contains it (§7.1).

Each upgrade generates a report of what the new commit changes and which models it supports, with what each lacks (§12.4). Maintainer practice: a maintainer with write access decides an on-demand upgrade and records it in an issue (§7.1). A new engine, such as TRT-LLM, meets the same bar: it ports the upstream’s scheduling and KV-cache code, checked by an oracle, a harness that runs the upstream code, through its bindings for C++ (§12.6).

The discrete-event core

BLIS takes its terms from Parallel DEVS, the Discrete Event System Specification. Simulated time moves from one event to the next. The model components (an engine instance, the router, a link, a client) interact only through timestamped messages, and none reads another’s state. The router learns of an engine only from the metrics and KV events it sends, after the configured delay (§8.1).

An instant is processed in three phases: every model component with an internal event runs its output function; each model component receives all the messages addressed to it at that instant, sorted by (time, round, class, sender, the sender’s own send count); each then makes exactly one transition: internal if only its own event is due, external if only messages arrived, confluent if both. No global counter enters the order (§8.2). Time is an integer number of microseconds, and every random draw comes from a substream named by model component, purpose and entity (§8.3, §8.4). For fixed inputs the output is identical byte for byte across runs, thread counts and platforms (§4).

Outputs are estimates: one run by default, or a mean over replications with a confidence interval on request. A comparison declares a configuration better or worse only with an interval; otherwise it is not distinguished (§8.8). Verification checks the code against the model; validation, the model against the real system (§8.9).

Where numbers come from, and how much to trust them

For each lookup the cost model uses the entry of smallest rank: measured, calibrated, transferred, literature, vendor_spec, roofline, assumed. When the coefficient registry has no exact entry, as for an engine commit whose code differs, the lookup falls back down the ranks to the most trusted entry for that chip, and the point (one scored run) names the method. New entries are required only for a new primitive family (§9.2). Every price records the least trusted method it used (§9.4). No rule requires a new GPU or cluster experiment; the fallback prices a measurement no source holds (§10.4).

The data ledger gives each external data unit exactly one role: fit, select, validate, held or anchor. A role is computed from the partition secret, once for each group of near-copies, so a point that fitted a value cannot judge it (§10.2). Accuracy is reported only on held-out units (held and anchor). Held units come only from InferenceX, anchor units from InferenceX and configiq; every other source is training data. A new source draws training roles only (§10.4). Each run’s settings come from its own records; a value no record holds is a named substitution on the point, and it lowers the grade (§10.4).

The dashboard gives each point one grade. G1: the run’s engine commit is the modelled commit and every condition for exactness holds. G2: the same, with named substitutions. G3 and G4: another commit, with the ported code unchanged or changed. G5: not scored, for a listed reason (§11.3, §11.4). The dashboard copies the run’s recorded configuration unchanged and keeps no table of modelled settings (§11.2). Coverage is a funnel for each source, with no age limit, and accuracy can be sliced by any recorded attribute (§11.6, §11.9). A ranked backlog directs the work (§11.6).

How the project stays correct

Every rule has an identifier and one of three kinds (§4.2). An automated rule is a deterministic check that protects correctness or accuracy: an import-graph lint, a conformance, differential, mutation, metamorphic or property test, or a data validator. A maintainer practice is a rule about process (review, approval, merge, issue handling, release notes), kept with branch protection, required reviews and signed commits; no program audits it. Agent guidance is followed by an agent that writes or reviews a change. Tests are behavioural, never tests of source text, order or hashes (X13, §7.4). The checks that run are in §13.3 to §13.5.

For each modelled commit, the engine module generates a surface list from the upstream’s own registration tables. Every connector, tier, KV-cache manager, speculative method, policy, metric and event type has one status: modelled with evidence, refused by name with an issue, or out of scope for one of three listed reasons. Every configuration field is modelled, proven inert, or not modelled with an issue (§5.2). CI fails while any item has none (§7.5, §4). A run that loaded code the upstream does not ship is not scored (§11.4). Each release records in stack.json the upstream commit each engine models (§5.4).
