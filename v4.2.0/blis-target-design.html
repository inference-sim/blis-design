BLIS Target Design

How BLIS is divided into components, what each one owns, the rules that keep them correct, and how we upgrade them when vLLM, SGLang, llm-d or our data change.

Status Standing design: true for every release Scope the llm-d stack, with vLLM or SGLang as the engine Companion each release has its own release plan, which schedules the work this design requires

What BLIS is. BLIS simulates an LLM serving cluster. It runs two kinds of code: the router of llm-d, a Kubernetes-based stack that routes requests to vLLM or SGLang engines, unchanged; and Go engine modules, each a port of one vLLM or SGLang engine. Each covers the engine’s scheduling, its KV-cache management, its KV transfer and tiering, and how it resolves its settings and chooses its kernels (§7.1). Each is tested step by step against the engine’s own code. A cost model, built from published hardware facts and fitted coefficients, prices every step. This document describes the shape BLIS has, the rules that keep it correct, and how those rules are checked. What a particular release does to reach it is in that release’s plan; §1 explains how the two documents relate.

The main ideas.

  1. One repository, inference-sim, holds the simulator, the engine modules and substrate/, which holds everything that is true whatever engine runs: the shared contracts, the published facts, the fitted coefficients and the cost model. The router fork is a separate repository. Every kind of work has one owner (Table 1, §2.2).
  2. Engines hand the cost model a fully resolved description of what runs, so the cost model does not depend on which engine produced it.
  3. Each engine module models one upstream commit and has a list of that commit’s features, generated from the upstream’s own source. Each feature is modelled, refused by name, or declared out of scope, and CI fails while any feature has no status.
  4. Every coefficient the cost model needs has a value, labelled by how it was obtained: measured, calibrated, transferred, taken from published work, or assumed. Coverage can then grow without hiding how good each estimate is.
  5. The simulator follows explicit rules for a discrete-event simulation and for analysing its output, so its reported values are reproducible and carry their uncertainty (§8).

1How to read this document

Words. MUST, MUST NOT and SHOULD mean what they mean in RFC 2119. An invariant is a statement about the code that every merged pull request and every release keeps true. Upstream means vLLM, SGLang or llm-d, whichever the sentence is about. Appendix B defines every term.

Components. A component is a part of the BLIS code with one owner. Table 1 (§2.2) lists them all, and says what each may import and what it must never contain. A component is a directory of inference-sim or a repository of its own. These words have fixed meanings:

  • BLIS code lives in four repositories: inference-sim, the router fork, accuracy-dashboard and blis-config-search.
  • inference-sim is one Go module, and its directories substrate/, engines/, sim/ and cmd/ are packages of it.
  • An engine module is one directory under engines/: the Go port of one upstream engine, at one upstream commit. The word is never used for a Go module. The commit it ports is its modelled commit (§7.1).
  • The simulator is the code in sim/ and cmd/. The substrate is substrate/, and its parts are named by directory (§3). A rule that says inference-sim means the repository; a rule that says the simulator means sim/ and cmd/.
  • The router fork is llm-d’s router code, made runnable in simulated time and kept in a repository of its own (§2.1). The hosting contract is the interface through which the simulator runs it. It lives in the router fork (§5).

§8 uses the word “component” for a part of the simulated system, such as an engine instance or a link, and defines it there.

Registries. Three things in this design are called registries, and the word is never used alone. The coefficient registry is the fitted and assumed coefficients, with their provenance (substrate/registry/, the --registry flag); it is what --catalog is paired with. The invariant registry is the project’s rules, each with its statement, checks and status (substrate/contracts/invariants/, §13.1). The metric registry is the definition of every metric a Result may report (contracts/metrics, §8.7). An upstream’s own tables are called registration tables, and engines are said to register a factory.

Identifiers. Every invariant has a short identifier, such as X3 or SUB-4. Appendix C maps each identifier of version 1.0.0 to its place in this version. The prefixes are:

Versions of this design and the release plans. This design has a version number. The rule for numbering and tagging versions is in the README of blis-design, and is stated nowhere else. Two short companions. A page is a standard print page (US Letter, 0.9 inch margins, 10.5 point text). A summary does not grow when the design does. It links every claim to the section that states it, and defers to the design where they differ. A section a summary cites keeps its number.

Citations. A claim about upstream code cites the upstream source at a pinned commit, in the form X23 gives. The commits are the ones stack.json records for each engine module and for the llm-d router. When an engine module moves to a new modelled commit, the citations that describe its behaviour move with it. A claim drawn from reading code that a recorded run has not confirmed is marked inferred.

2The shape of the system

2.1 One simulator repository, one router fork, two applications

inference-sim holds everything that is built into the simulator: substrate/, engines/vllm/, engines/sglang/ and the simulator itself (sim/, cmd/). They are packages of one Go module.

Three repositories stay separate:

  • The router fork is llm-d’s router, kept close to upstream. It owns the hosting contract and depends on no BLIS code, so inference-sim can import it without a cycle.
  • accuracy-dashboard scores simulations against measured runs. A scorer independent of the simulator can be audited.
  • blis-config-search searches configurations.

Pins between repositories are exact commits (X11). The checks of Table 1 keep the boundaries between the directories of inference-sim.

2.2 Where a fact belongs

Every fact, rule and value has one owner. To find it, ask what the fact depends on:

  • An engine’s upstream commit, such as vLLM’s default fraction of GPU memory: the engine module that models that engine.
  • An llm-d release, such as how its prefix-cache scorer ranks endpoints: the router fork.
  • The simulator’s own design: the simulator.
  • The hardware, the model, the physics or the data, whatever engine runs, such as H200 memory bandwidth or the speed of one attention kernel: the substrate.
  • The user’s configuration, such as the node count or the scorer weights: the scenario, copied verbatim.

Work has one owner as well. Another component calls the owner’s command or imports its package, so a fitting script that wants an end-to-end reported value (§8.7) runs the dashboard’s scoring harness and writes no scorer of its own.

Other sections cite them and do not restate them. The import-graph lint (go list, required in CI) and the path-reference lint of X7 enforce the rows for every directory component.

3The substrate

3.1 Why the parts live together

The substrate is the directory substrate/ of inference-sim. It has parts for contracts, the catalog with its ledger, the coefficient registry, the cost model, the validators and the loader. They change together:

  • A model whose architecture is already supported needs only a catalog entry. A model with something new in its architecture usually needs a new data field, a catalog entry, new coefficients and a change to the cost model, all at once.
  • The validators check the data, and the cost model is tested against the data.

Such a change is one pull request, one review and one release, and it can include the engine module and the simulator change that use it. Each release embeds its own data, which is small enough to compile into the program.

3.3 Data: a path first, the embedded copy as the default

The catalog and the coefficient registry reach a running program in one of two ways. Both are always available, and every run records which one it used.

  • A path. --catalog <dir> and --registry <dir> (or BLIS_CATALOG and BLIS_REGISTRY) name directories with the same layout as substrate/catalog/ and substrate/registry/. When a path is given, the run uses that directory instead of the embedded copy. Recalibration uses this. A fitting script writes candidate coefficients to a directory, and the released simulator scores them with no rebuild.
  • The embedded copy. When no path is given, the run uses the data compiled into the simulator with go:embed. A release therefore carries the exact data it was tested with, and a user of a released binary needs no checkout. inference-sim cannot be installed with go install …@version, because Go refuses that for a module whose go.mod has a replace directive, and inference-sim carries one for the router fork (X11). So each release ships signed binaries for the supported platforms, with the provenance and bill of materials of X21. A source build needs a checkout at the tag.
  • What stays fixed. A model runs only if it is in the catalog in use, and it is resolved from its graph.yaml. A missing model is refused with the catalog’s source (the embedded release, or a path) and the relative path its entry belongs at. No run creates or changes catalog or coefficient registry files, no run fetches anything from the network, and the deployment always comes from a required scenario.

Private additions. To run a private model against a pinned catalog and coefficient registry, --catalog-overlay <dir> and --registry-overlay <dir> add entries to the data in use. An entry is identified as follows:

  • In the catalog, a whole model directory (models/<name>/), or a whole hardware, device, network or workload file.
  • In the coefficient registry, one coefficient, identified by its set, its name, its scope and its method.

An overlay entry with the same identity as an existing entry replaces it; any other entry is added. The combined data are then validated in full, including the rules that each lookup has at least one entry (VAL-2) and at most one per rank (VAL-4). An overlay may not contain ledger files.

Which files count as data

The file patterns are defined once, in the top-level package of substrate/ (data.go). It must sit there, because Go’s go:embed can only embed files at or below the package’s own directory. The patterns are: hardware, devices, networks, workloads, measurement sources, each model’s model.yaml and graph.yaml, every coefficient set, and acceptance and routing profiles. The ledger is not runtime data: pricing never reads it, and it is large. Secret-holding jobs (§10.2), including those in accuracy-dashboard, read it from a checkout of inference-sim at the commit they build. No part of it is embedded.

The go:embed directive must list literal patterns. A path is read with the same patterns, so the load test of SUB-9 shows any difference between them. The loader refuses anything that would make the data ambiguous:

  • a file under a data directory that matches no pattern, such as coefficients/x.yml where .yaml is expected. Ignoring it would silently drop a candidate’s change.
  • a symbolic link;
  • a data file containing a carriage return;
  • two paths that differ only in letter case.

The data directories are exactly those the patterns in data.go name. Files outside them, such as scripts and documents, are ignored. Two things inside them are ignored by name: a model directory’s config.json, and everything under catalog/ledger/. The check that graph.yaml’s recorded derived_from hash matches config.json runs in the validators, in CI, not in the loader. So a path load and an embedded load validate the same files in the same way (SUB-9).

Recording what was used

Every run computes a content hash for each of the catalog and the coefficient registry. It lists every data file as <sha256 of the file's bytes> <path relative to the catalog or coefficient registry directory, with forward slashes>, sorts the lines by path in byte order, ends every line, including the last, with a line feed, and takes the SHA-256 of the result. The loader refuses carriage returns, so the hash is the same on every machine. The Result document records, for each of the catalog and the coefficient registry:

  • its source: embedded or path;
  • its content hash;
  • the hash of each overlay, and the hash of the combined data. With no overlay the combined hash is the base hash. Otherwise it is the SHA-256 of the line <base hash> base followed by one line <overlay hash> overlay for each overlay in the order applied, each line ending in a line feed, so it names the base and every overlay and their order.

It also records the build the simulator came from: the inference-sim release tag, or the commit it was built from.

A run is exactly pinned when all of these hold:

  • the simulator is an inference-sim release tag or a full commit of it, and its stack.json names the router fork commit and the upstream commit each engine module models (X11);
  • the catalog and coefficient registry hashes equal the embedded hashes of that commit;
  • no overlay is used, and the simulator was built from a committed tree with no uncommitted change.

Every other run is experimental. Only exactly pinned results are published (X8). A tag names a release, which the dashboard scores once (COV-9); a commit pin is not a release, and a published number records its commit.

Checking data at load

Whatever its source, the data is validated when it is loaded, by the same validators CI runs. That includes the checks between the catalog and the coefficient registry, for example that every chip a coefficient names exists in the catalog in use.

Each run also reports which coefficient registry entries were selected (a lookup returned them), and which coefficient files were never loaded. The report covers every reader behind the Environment, including acceptance and routing profiles. The landing gate uses this report (VAL-6).

The ledger in a candidate

A candidate may add data units. The gate and select jobs compare the candidate’s units, by unit_id, with the ledger at the pull request’s merge base, and draw the role of each new unit. A unit_id present at the merge base but absent from the candidate is refused unless an alias table or a new partition version covers it (D4); a unit whose identifying fields changed is refused this way, because its unit_id hashes those fields. Roles are never read from a file (D4), so a candidate cannot change which units are held out.

3.4 Checks by directory

CI is filtered by path: a change to one directory runs that directory’s checks, so a catalog-only change does not run the cost model’s slow race suite. Any change also runs the cross-directory checks (the validators against the data, the cost model against the embedded data), which are the reason the parts live together. 4.2 Three kinds of rule

Every invariant is kept in one of three ways. The design says which, so that a rule with no program behind it is a stated decision.

The three kinds of rule differ in who keeps them: a program, a person with write access, or an agent.
KindKept byExamples
AutomatedA named, deterministic check that fails the pull request, the nightly run or the release.The import-graph check (X7), the field-list completeness check (VLM-3), the conformance suites, the lints.
Maintainer practiceA person with write access. The hosting service enforces the rule where it offers a setting. The test. A rule is automated when a program can decide it from the repository’s own contents and what it imports, the same way each time. A rule about who holds a permission, about a repository’s settings, or about an act only a person can perform is a maintainer practice. A rule that shapes how a change is written or judged, and that a program cannot decide, is agent guidance. A rule can be more than one kind: a person signs a commit, and an agent follows the convention that words its message.

Lints. A lint reads source text, headers or the import graph. It checks where code lives and how it is written, so it is automated for architecture: the import graph, licence and provenance headers, generated-file freshness. A lint never stands as the only check of a correctness invariant. Determinism, independence from the clock and neutrality of the cost model each have a behavioural test (X6, SUB-11), and a lint is called a lint, never a test.

Dependency direction holds for all three. An automated check reads only its own repository and what it imports (X7). A check in one repository never reads the settings, branches, issues or workflows of another. A practice is kept in the repository it concerns.

6The boundary between engines and the cost model

6.1 The rule

Only an engine module knows its upstream, so only it works out the engine’s behaviour: defaults, backend choices, sharding, fusion, padding and graph-capture sizes. That work is lowering, and it lives only in engine modules (X3, SUB-15). The one exception, the choice a third-party transport library makes, is data keyed on the library (below). A move is one movement of KV. engine.Transfer is the engine’s report of a move, and plan.Transfer is the cost model’s input for it. The cost model receives three plain objects in physical units (bytes, tokens, ranks): a PoolPlan, a StepShape, and, for each move, an engine.Transfer whose Move field is a plan.Transfer stating the catalog device, the node and rack at each end, and the direction. The cost model never sees an engine’s settings and never applies an engine’s rules (X2, SUB-6).

The forms a move takes. A KV move is not always a plain copy over one link, so the Move also states its form, from the closed list below, and these fields of plan.Transfer:

  • the memory at each end: GPU, host, or a named catalog storage device;
  • for a storage device reached over the network, or a move between nodes, the protocol: RDMA or TCP;
  • for a copy between GPU and host memory, the copy mechanism: the GPU’s copy engines, or a copy kernel that runs on its streaming multiprocessors;
  • the staging buffer, if the bytes pass through one, and the chunk size the move is pipelined in;
  • for storage, whether IO is buffered (through the operating system’s page cache) or unbuffered (O_DIRECT), and whether the upstream syncs a write to the device before it counts the write as done;
  • the size of one request, and how many requests the engine keeps in flight;
  • the bytes it registers with the network for the first time.

A move that states no form is priced from its Kind and Tier: copy for host memory, storage for a storage device, and the form its endpoints imply for a peer. The engine states the form, as its upstream chooses it. Where a transport library makes the choice, as UCX does under NIXL, the engine gets it from one table in contracts/transport, described below. The cost model never picks a form or falls back between forms (SUB-6).

The cost model prices each form as a sequence of legs. A leg is a copy over one path that the catalog states: within a node, the link between a GPU and host memory, host memory itself, the NVLink domain, the PCIe path between two devices, or a storage device’s own link; between nodes, the NIC at each end and each switch tier between them (SUB-17). One leg of b bytes, sent as n requests with q in flight, takes ⌈n/q⌉ × base latency + b / rate, with the rate held to the catalog peak of the leg’s link (SUB-5). A memory layout reaches the price only through the request size and count it gives. How a value is obtained follows §9.

A storage plugin maps to the form it implements, and the module’s surface list records the mapping. A storage device reached over the network is a catalog storage device with a network attachment: the catalog states the rack or switch it hangs from, or that it sits outside the cluster behind a stated uplink. Its coefficients are its own.

Staging. Any form may name a staging buffer in host memory, which adds a leg between the buffer and the GPU at each end that uses one. The buffer is one of the plan’s Buffers, so its size is the size the upstream allocates. A move with more than one leg goes through its buffer in chunks of the size the engine states. If the buffer holds two chunks or more, the legs overlap: the move takes the first chunk’s time through every leg, plus the slowest leg’s time for each later chunk. If it holds one chunk, each chunk passes through every leg before the next starts, so the legs run one after the other. When the upstream keeps the bytes in a tier between two legs, those are two moves, each reported on its own, such as a copy and then a storage move.

Buffered and unbuffered IO. Unbuffered IO (O_DIRECT) goes between the device and the buffer. Each request is rounded up to the device’s logical block size, a catalog fact. Buffered IO also copies the bytes through the page cache, so the storage leg carries one more copy in host memory, priced at host_copy_rate. A buffered read is priced as a read from the device. A buffered write is done when its bytes are in the page cache, unless the move states that the upstream syncs it, citing the call, in which case it is done when the device write is. The writeback that follows is demand on the device’s link after the move ends, and the simulator shares it like any other. A page-cache hit depends on what the node did before, which no engine decides, so it is not priced.

Who chooses the transport. A transport library outside the engine’s code chooses some forms. Under NIXL, UCX picks a transport from the hardware it finds and its own settings; NCCL picks a path from its own topology search. That code is neither engine’s, so no engine module ports it (VLM-2), and the cost model may not resolve it (SUB-6). The choice is split in two. The table is data: entries in catalog/transport, keyed on the library and its version, the library settings the engine’s field list classifies (VLM-3), and catalog facts: whether the two ends share a node or an NVLink domain, the NIC, and whether it supports GPUDirect RDMA. Each entry gives the form and cites the library’s selection code at that version (SUB-22). The selection is one function in contracts/transport, which reads the table through an optional interface (SUB-1). The engine passes the library, its settings and the endpoints, and states the form the function returns.

How the simulator advances a move. The cost model returns the bytes each leg places on each link, and the move’s fixed latency: its base latencies, the pipeline’s first chunk, and any registration. The simulator shares each link among the moves on it (SIM-13). A pipelined move then advances at the rate of its slowest leg after sharing, and a move whose buffer holds one chunk at 1 / Σ(1 / ri), where ri is each leg’s rate after sharing. Both rules are part of the link sharing that X3 allows the simulator (SUB-21).

6.2 The plan and the step shape

Both are defined in substrate/contracts/engine, and a field added later keeps its zero value meaningful (SUB-1).

// PoolPlan is fixed for the life of one engine pool.
type PoolPlan struct {
    Hardware string         // catalog chip name
    Fabric   string         // catalog network name; "" on one node
    Layout   Layout         // tensor, pipeline, data, expert and context parallel widths, and rank placement
    Layers   []LoweredLayer // one entry per (layer, primitive)
    KV       []KVGroup      // per cache group: bytes per page, tokens per page, full or sliding window
    KVBudget []int64        // bytes per rank available for KV, one value per pipeline stage
    Tiers    []KVTier       // the KV tiers below GPU memory, as the engine resolved them
    Graphs   GraphPolicy    // CUDA-graph buckets, keyed by token count or by batch size; carries CodeID
    Drafts   DraftPolicy    // speculative decoding: chain length, or tree (top-k × steps)
    DraftLayers []LoweredLayer // the draft model's layers
    Host     HostPlan       // per-request and per-token host work (admission, sampling, detokenizing); carries CodeID
    Weights  []ResidentTensor // per rank: shape, stored data type and sharding, after weight post-processing
    Buffers  []Buffer       // engine-chosen buffers and workspaces, sized as the upstream sizes them
    InFlight int            // most steps in flight at once; 1 without asynchronous or overlap scheduling
}

type LoweredLayer struct {
    Layer      int          // index in the model graph
    Stage      int          // pipeline stage that runs it
    Primitive  string       // from a fixed list: "attention.decode", "gemm", "moe.grouped_gemm", "all2all", …
    KernelImpl KernelImpl   // what executes it; the coefficient registry looks coefficients up by this
    Shape      PrimitiveShape
    Collective *Collective  // group, bytes, and whether it crosses nodes
}

type KernelImpl struct {
    Library  string         // from a fixed list of kernel-library names in contracts
    Variant  string         // the library's own exported kernel name; an engine's backend names map to it in the engine's lowering
    CodeHash string         // hash of source and target GPU architecture, or of a binary library (below)
}

type KVTier struct {
    Device   string         // catalog device name, e.g. host DRAM, local NVMe
    Bytes    int64          // capacity per rank, as the engine sized it
    Shared   bool           // one copy per node rather than one per rank
}

// StepShape is one engine step on the data-parallel ranks that run in lockstep, already padded by the engine.
type StepShape struct {
    Mode      StepMode      // Mixed, PrefillOnly, DecodeOnly, Verify, KVArrived or Idle
    Ranks     []RankStep    // per data-parallel rank in the lockstep group: each request's scheduled and cached tokens
    Padded    []PaddedShape // per rank: the shape actually launched (graph bucket, padding)
    Drafts    DraftShape    // tokens drafted and verified this step
    Stage     int           // pipeline stage; 0 without pipeline parallelism
}

PrefillOnly is a step of prefill tokens, with or without a cached prefix. KVArrived is a P/D decode merge, as SGLang does it: KV arrived from the prefill pool, so the step runs no forward pass. It still has scheduler and host cost, which the cost model prices. Each engine module maps its step kinds to these modes.

HostPlan and GraphPolicy each carry CodeID string, the identity of the upstream code that does that work. The engine module computes it, and the cost model uses it only as a lookup key (SUB-6). A coefficient keyed by an identity is exact for that code and no other. When an upgrade changes the code, the new identity gets a transferred entry from the old one, with the per-function difference as its rule (§9.2).

PaddedShape also records how the step launches: a full CUDA-graph replay, a piecewise replay with some layers run eagerly, or a fully eager run. These have different costs, so the engine states which one applies.

Six rules follow:

  • The engine pads the batch, and the cost model prices the padded shape. Each engine reports the shape it launches in Padded. When data-parallel ranks run in lockstep, padding depends on every rank’s tokens in the same step, so a StepShape describes all the ranks that run in lockstep. The engine decides which ranks those are, as its upstream does; where the ranks are independent engines, each StepShape has one rank.

  • The engine names the exact kernel implementation. An engine picks an attention backend per chip and model, and a backend may force a page size. The engine’s lowering records that choice in KernelImpl, and the coefficient registry prices that exact implementation. Library is a fixed list of kernel-library names. A library that an engine ships with its own code is named by the repository name, and that is the only place an engine name appears in a coefficient key (X2).

    The coefficient registry’s lookup key uses a hash of the kernel’s source (the kernel hash, CodeHash), not a package version. A coefficient lists the kernel hashes it is valid for, so a version bump that leaves a kernel unchanged needs no substrate change. A kernel whose source changed gets a new key, and the substrate must supply a value for it (§9). For a kernel built from source, the hash covers the source and the target GPU architecture. Libraries shipped only as binaries, such as cuBLAS, cuDNN and FlashInfer’s precompiled kernels, are keyed by the SHA-256 of the shipped library file together with the target GPU architecture.

    Two things change a kernel’s speed without changing its source. A compiler or CUDA toolkit change: the engine records the toolkit version with each kernel implementation, the entry stays, and the landing gate (VAL-6) shows whether the old value still holds. A tuned-configuration file, such as a per-GPU table of launch parameters: the lowering selects the file the upstream selects for the plan’s shape, data type and device, and the SHA-256 of the selected file or entry is part of CodeHash, so a change is a new key and falls back as in §9.2. Autotuned launch configurations and library heuristics are part of measured behaviour and are not a key.

    Each engine module ships a generated table, kernel_impls.json, of every kernel implementation it can emit, for its modelled commit’s library versions and every library version seen in InferenceX runs. The substrate reads it only through its generated copy (X7). If a lookup has no entry for an exact implementation, the cost model takes the most trusted entry §9.2 offers for that chip, at worst the primitive family’s roofline or assumed entry, and the price records that method (VAL-3).

  • The engine decides which KV blocks move between tiers, and the substrate prices each move. Which blocks move between GPU memory, host memory and storage, when, and under which policy, is engine behaviour. The engine reports each move as an engine.Transfer. The cost model turns each transfer into a demand: bytes per link, from catalog device facts and coefficient registry tier coefficients. The engine returns its transfers to the simulator with each step. For each one the simulator calls env.DemandFor, which refuses a transfer whose report and Move disagree or that its plan cannot make, then asks env.TransferDemand(engine.Plan(), t.Move) for the bytes each link must carry. An engine that starts a transfer implements engine.Planned, whose Plan() returns the PoolPlan the transfer is priced against. The engine states a peer’s node and rack from engine.Request.Peer, which a host must set on a request that pulls KV from a peer. A move that spans nodes, or that carries a different token count for each KV cache group, states them in the optional fields Nodes and Groups (§6.3).
  • Sharing a link over time is the simulator’s job. Dividing a link’s bandwidth among concurrent transfers depends on when they happen, so it belongs to the simulator’s event loop (X3, SIM-13).

  • A transfer can be consumed layer by layer, overlapped with the step that uses it. A connector or a tier may move KV layer by layer. In vLLM, each attention layer calls the connector before it runs, to wait for its loaded KV, and after it, to start its save. In SGLang, HiCache loads host KV one layer at a time. The engine states this with the field Parts of engine.Transfer. Each part is one plan.Transfer with the range of layers it carries, numbered within the pipeline stage that runs them, and, for a load, the layer whose compute waits for it, or, for a save, the layer after whose compute it may start. The engine also states whether the step’s end waits for its layer-wise saves. A step whose launch mode, as PaddedShape records it, does not run the per-layer calls states no parts, and the engine cites the upstream condition.

    The cost model sizes each part from the plan’s KV groups, prices it as a move (§6.1), and returns the step’s compute time per layer in its StepEstimate. A layer that runs while a copy is in flight beside it runs at a share of its rate, the coefficient layered_transfer_compute_efficiency, keyed on chip, link and copy mechanism (copy engine or copy kernel), measured by timing a layer’s kernels with and without a concurrent copy. The simulator moves each part over its links, shared as for any transfer, and sends the engine a transfer-complete message for each part when it arrives (SIM-15). The engine ends the step, as it combines pipeline stages: layer i starts when layer i−1 has ended and every part it waits for has arrived, the step ends when its last layer ends, or later if it waits for its saves, and each arrival recomputes the engine’s time advance (§8.3). One suite in contracts/conformance checks this timing rule for every engine; VLM-8 and SGL-7 add each engine’s wait point. A transfer with no parts is consumed whole.

  • The engine combines pipeline stages. With pipeline parallelism the engine emits one StepShape per stage. The cost model prices each stage alone. How stages overlap, and where bubbles occur, is the engine’s batch-queue behaviour, so the engine combines the stage times and reports them to the simulator.

6.3 How an engine is built: two phases

An engine cannot size its KV cache without the memory its weights, activations and buffers take, which is the cost model’s arithmetic; the cost model cannot price a step without the engine’s plan. inference-sim breaks the loop by giving the engine an environment when it builds it:

// substrate/contracts/engine: what an engine may ask of the substrate while it is built and run.
type Environment interface {
    Graph(model string) (*model.Graph, error)          // the catalog's model graph
    Chip(name string) (*hardware.Chip, error)          // catalog hardware facts
    Memory(partial PoolPlan) (kernel.MemoryBreakdown, error) // weights, activations, buffers; per stage
    Price(plan PoolPlan, step StepShape) (kernel.StepEstimate, error)
    TransferDemand(plan PoolPlan, t plan.Transfer) (kernel.TransferDemand, error) // t is an engine.Transfer's Move; plan is the engine's Plan()
    Acceptance(model, drafter, workload string) (acceptance.Profile, error)
}

// engine.New builds an engine for one pool.
func New(spec Spec, env Environment) (Engine, error)

plan.Transfer is the move as the cost model receives it: the tokens moved, the two ends, the direction, and the catalog device of a tier. Each end is a plan.Endpoint, a node and a rack, both numbered within the pool the end belongs to: the node from the pool’s first node, the rack from its lowest rack. It is defined in substrate/contracts/engine/plan, with PoolPlan.

A move that spans nodes, and a move in a hybrid model. Two facts about a real move do not fit one pair of endpoints and one token count, so plan.Transfer has two optional fields for them.

Node moves. A pool may span several nodes, and each node’s workers then move their own share of the KV at the same time. The engine states this with Nodes, a list of plan.NodeMove. Each entry is one node’s move: the node and rack it starts from and the node and rack it lands on, numbered as above, for the move’s tokens. The cost model finds each entry’s bytes from the plan, as the KV of the ranks that sit on that node, prices each entry over its own path, and adds the results into one demand: a link that two entries use carries the sum of their bytes, and each node’s NIC carries only its own. The entries run together, so the move’s fixed latency is the largest of theirs. An entry that leaves and lands on the same node uses no NIC (SUB-17). When Nodes is empty, the move is the single From and To; otherwise they are the first entry, and the report is refused if they differ from it.

Group sizes. A hybrid model keeps several KV cache groups: a sliding-window group keeps only its window, a full-attention group keeps every token. A move may therefore carry a different token count for each group. The engine states it with Groups, a list of plan.GroupMove: the index of a KV group in the plan’s KVGroups, and the tokens that group moves. The cost model rounds each group up to the pool’s page size and sums the groups’ bytes. Tokens stays the largest count among the groups, and the report is refused if any group’s count exceeds it. When Groups is empty, Tokens applies to every group.

Both fields are additive and optional (SUB-1). An engine whose upstream moves bytes per node or per group states them, so that the host prices every move through env.DemandFor with no per-engine hook. The conformance suite covers a two-node pool and a two-group hybrid model (SUB-17).

Construction then runs in two phases:

  1. Plan. The engine resolves its configuration and lowers the model into a partial PoolPlan, one whose KV budget is still empty. The partial plan carries the engine’s own profiling step shape (in vLLM, the shape its memory profiling run uses; in SGLang, the shape behind its reserve formula) and the set of graphs it will capture. The engine states the resident weights and the buffers it chooses in the partial plan. env.Memory sums their bytes, and sizes the activations of the profiling shape and the graph pools. The profiling shape is engine policy; the cost model only sizes it. The engine then applies its upstream’s budget rule and fills in KVBudget.
  2. Run. Each step, the engine forms a StepShape and asks env.Price for its time.

inference-sim implements Environment using the substrate’s cost model and data loader. Engine tests use a small reference implementation in contracts/conformance, which prices from fixed test values.

7.6 Port a shared framework before the features built on it

Connectors, tiers and KV-cache managers are built on shared frameworks. Porting one framework completely, with recorded traces of its contract, makes each further connector, tier or manager a smaller change. A module therefore ports a framework as a unit before the features built on it.

A framework’s interface is the abstract class or classes that its features implement or call. A framework’s traces are taken at that interface and are of two kinds. A recorded trace is the sequence of interface calls that a real feature makes while the oracle runs a scenario. The port receives the same calls, and its answer to each is compared with the upstream’s. A direct trace is a sequence of calls made by a driver the module writes, including orderings that no existing feature makes. Recorded traces keep the call mix realistic; direct traces test the contract itself. A part of a framework that reads the clock is traced with the clock replacement of FID-1. A part that does its work in threads, as HiCache’s controller does its backups, loads and prefetches, is run by the step-driven runner of FID-1, so that its decisions are traced in a fixed order.

8Simulation method

BLIS is a discrete-event simulator. Its clock is virtual time: it jumps from one event, such as a request arriving or a step ending, to the next, and never follows the wall clock. Between events, state either stays fixed or changes at a known constant rate. This section states the rules a run follows, whatever engine it runs. It takes its terms from Parallel DEVS, the Discrete Event System Specification of Bernard Zeigler. The table gives each term and its meaning in BLIS.

8.1 Model components and how they couple

Each model component changes its state only through its three transitions, and sends messages only through its output function. The output function runs on the state just before an internal or confluent transition, and every message it sends carries that instant’s time. An external transition sends nothing. A model component that must answer at once, as the router answers a request, schedules an internal event with a time advance of zero and sends its answer one round after the message that caused it (§8.2).

A link is the one model component whose state changes between events. Its state is the set of transfers in progress and the bytes each has left, and its time advance is the earliest time a transfer finishes under the current sharing. Every start or end of a transfer, and every step that starts or ends a cross-domain collective, is an event that recomputes the rate of every other transfer on the link.

Model components interact only through messages, and none reads another’s state. The router learns about an engine only through the metrics and KV events the engine sends, at the times it sends them, after the delay the deployment’s scrape and event-delivery settings impose.

Within a model component, nothing depends on goroutine scheduling, the system clock or the order of iteration over a map. Concurrency inside a model component runs on the simulated runtime, which serialises it (RTR-7).

8.2 One instant

Many events fall at one simulated instant, for example a step ending as a metrics scrape is due. An instant is a sequence of rounds. BLIS processes each round as Parallel DEVS defines an instant, in three phases:

  1. Every model component whose internal event falls at this instant runs its output function.
  2. Each model component receives the bag of every message addressed to it at this instant. BLIS sorts the bag by the key below, so a transition that reads it in order is deterministic.
  3. Each model component then makes exactly one transition: confluent if it had both an internal event and messages, internal if only the first, external if only the second.

So no model component sees another’s state change from the same round before making its own. A message sent by an output function in phase 1 of round r is in the bags of phase 2 of the same round, and carries r in its key. A model component whose transition in round r leaves a time advance of zero is imminent in round r+1, and its answer is delivered in round r+1, one round after the message that caused it. The instant ends when a round has no imminent model component and no message. Messages and internal events are keyed as DEV-2 states. A model component’s index is its position in the scenario’s declared order, never a map or hash order, so renaming an instance leaves the Result unchanged. The order of internal events at one instant has no effect, because all outputs are gathered before any transition. The class is a fixed order of message kinds, such as “transfer complete” before “new request”. Each class’s position is stated with its reason, and a change to the order is a change to the model (§8.9).

A model component’s confluent transition says what it does when its own event and a message coincide. For an engine it follows from where the upstream’s loop reads its input queue, not from a choice BLIS makes, except where that order is a race between threads. A request that arrives while a step runs waits until the engine next reads its input. Where the upstream schedules the next batch while the current one runs, a request that arrives during a step first joins the step after the next. Each engine declares, for each kind of external input, the step boundary at which it takes effect and whether it arrives during a step or as one ends (DEV-3). Where the upstream’s order is a race, the declaration says so and names the order BLIS uses.

8.3 Time and progress

Simulated time is an integer number of microseconds. A duration that the cost model prices or a link computes is converted to microseconds once, by one rule: round to the nearest microsecond, with a minimum of one microsecond for any positive duration, so that rounding never creates a zero-time cycle. A link keeps each transfer’s remaining bytes as integers and carries the rounding remainder to its next event, so that the bytes moved are conserved. Two events that rounding makes simultaneous are ordered by the key (§8.2). Arithmetic whose result reaches the order of events or the Result gives the same bits on every supported platform (X6).

The future event list is a priority queue of internal events, ordered by time and then by the key (§8.2). A model component changes its own next event only by recomputing its time advance after a transition. The event it no longer wants is marked stale by a generation number, and dropped when it reaches the front of the queue, so it cannot affect the result wherever it sits.

Simulated time must advance; DEV-5 bounds zero-time cycles and steps that change no state.

8.4 Random numbers and determinism

Every random draw comes from a substream named by model component, purpose and entity: for example, client 3, prompt length, request 17. The substream’s seed is the SHA-256 of the scenario seed and that name. Streams for different seeds are treated as independent. The generator’s name and version are part of the experimental frame, because a new generator changes every draw.

A run is determined by its scenario, seed and build (X6).

The named substreams give common random numbers: two runs that differ only in configuration give the same requests the same random inputs. Some draws depend on how the system responds, for example a retry after a timeout, or a router’s tie-break. They use their own substreams and do not line up between configurations. Comparisons therefore still need replications and intervals (§8.8).

8.5 Input models

Every distribution the workload generator draws from names its family, its parameters, how they were estimated, and the trace they were estimated from, and is compared with held trace data by the two-sample Kolmogorov-Smirnov distance, which must not exceed a bound stated with the distribution (for example 0.02 at samples above 10,000). The Result’s frame report includes a quantile-quantile comparison; any significance level is Holm-corrected over the distributions tested. Where a dependence matters, it is modelled, not assumed away: output length against prompt length, the burstiness of arrivals, and the structure of sessions.

A trace records the causes of each arrival, not only its time: which session a request belongs to, and how long the client waited after the previous response. Replaying a trace under another configuration recomputes the arrivals that depend on earlier completions. A replay of fixed timestamps has no random input, so its reported values have no replication interval unless the trace is resampled.

8.6 The experimental frame

A run measures something only relative to its experimental frame. In BLIS the frame is one document, recorded in every Result:

  • the generator: the workload and its input models (§8.5), or a trace to replay, with its seeds;
  • the initial state: empty caches, or caches warmed by a stated rule;
  • the phases: warm-up, measured window and drain, each defined by a rule. The measured window is the stretch whose requests and tokens form every reported value. A request belongs to the window by its arrival time, and latency statistics are taken over those requests, including those that finish during the drain. Throughput counts tokens by their emission time within the window. The frame records both rules, and a source whose client uses another rule is simulated with its rule, which the point names;
  • the stop rule: a request count, a horizon (a simulated time at which the run stops), or both;
  • the acceptance conditions under which the run counts for this frame, such as achieved concurrency within a tolerance of the target, and few enough requests unfinished at the horizon;
  • the metric definitions (§8.7).

A run that fails its acceptance conditions produces no reported value. If any replication of a point fails, the point is not scored, and it is not scored on the replications that passed; the Result states how many failed.

8.7 What a metric means

Every metric that is reported, compared, ranked or used in a service-level check has one definition, with an identifier, in the metric registry in substrate/contracts/ (DEV-8): its formula, its statistic (a mean or a percentile), its population (requests, tokens or steps), its window and its unit, and whether it is a headline metric, one the dashboard publishes accuracy on. It covers latency, throughput, interactivity, goodput and service-level attainment. Time to first token, time per output token and inter-token latency follow the benchmark clients BLIS is compared with: time per output token excludes the first token and is averaged per request, and inter-token latency is pooled over tokens. A definition is never inferred from a field’s name.

A reported value is a metric at a scope: the whole cluster, one pool, or one instance. The scope selects the population; the formula, statistic, window and unit are unchanged. A reported value that aggregates over scopes, such as the largest p99 time to first token over instances, names the scope and the aggregate. Two reported values are compared only when their metric, scope and aggregate are all the same (DEV-8), and a report or ranking states all three for every reported value it shows.

A request’s fate is how it ended: completed; dropped, with a reason; timed out; in flight at the horizon; queued at the horizon; or not started. DEV-9 fixes where it is written and how it is counted. A request that emitted no token gives no token-latency sample.

A request in flight or queued at the horizon has an unknown latency that is at least what it has waited. A latency statistic states how it treats such requests: excluded, with their count beside it, or counted at their waiting time so far as a lower bound. A percentile is not reported when more requests are unfinished than the percentile leaves room for.

A quantile is reported only when the sample is large enough for it, and with an interval from the order statistics (minimum sample, §11.8).

8.8 Output analysis

A simulation’s outputs are estimates, and are analysed as estimates. A run is either terminating, measuring a fixed amount of work such as a benchmark of a set number of prompts at a set concurrency, or steady-state, measuring a system that has settled.

  • A terminating run discards nothing at its start, unless the measured run did. By default it is one run, reported as a point estimate that says it carries no interval. On request, its estimate is the mean over independent replications (runs with different scenario seeds), with a confidence interval from the spread between them (§8.8). InferenceX benchmarks are terminating runs. Their frame copies the measured run’s start state, stop rule and requests (COV-12), so seeds vary only what the requests do not fix.
  • A steady-state run discards a warm-up, the stretch at the start where the system is still filling. MSER-5 finds its length: it picks the cut that minimises the estimated standard error of the mean of the remaining series, with the cut limited to the first half of the run. It is applied to the series averaged over the replications, for each output series, including the prefix-cache hit rate, which often settles later than queue lengths. The warm-up is the largest cut over the series. The estimate comes from replications, or from batch means: one long run, after warm-up, split into 20 batches. The von Neumann ratio test of the batch means must not reject independence at the 10 percent level; otherwise the batch is doubled, and if no batch size passes the run is classed incomplete. A percentile gets its interval from replications, each holding enough samples for that percentile, never from batch means.
  • A run whose measured window shows a trend has not settled. If the backlog grows, the system is overloaded: its latency values describe a transient and are not reported. Its departure rate is reported as saturation throughput only if the departure rate itself shows no trend.

Independence assumptions. An interval is valid only as far as these hold. Replications are independent, because each has its own scenario seed (§8.4). Observations inside one run are not independent, because successive latencies are correlated through the queue, so no interval treats them as independent. Draws for different clients and entities are independent unless the workload models a dependence (§8.5). The cost model adds no random term to a step’s time. A run’s randomness comes from named substreams only: the workload’s draws, the router’s tie-breaks and draws, and any declared stochastic model of infrastructure, such as node-provisioning and instance-loading delays or KV-tier latency jitter. The Result’s frame lists each, and a reported interval states which of them it covers. Two runs with the same seed are identical, not independent.

Replications and confidence. A run is one replication unless an interval is requested. When it is, replications start at five and continue until the half-width of the interval is at most γ′ = γ / (1 + γ) times the absolute value of the estimate, or a stated limit is reached, in which case the width reached is reported. The adjustment is needed because a stopping rule on the interval width otherwise lets the interval under-cover; the stopping rule is part of the procedure that DEV-11 tests. For a comparison of two configurations the half-width target is the stated margin. A reported interval states its level, its method (replication means or batch means), the number of replications, and which uncertainty it covers. A comparison of two configurations uses the differences between paired replications that share common random numbers (§8.4). It has three outcomes: better, worse, or not distinguished. One configuration is better only when the whole interval of the difference lies beyond a stated margin. Not distinguished includes equivalence, where the whole interval lies within the margin. A search that compares many configurations controls the chance of a false winner across all its comparisons and re-estimates the winner on fresh seeds.

The interval covers the randomness of the workload. The model’s own uncertainty is separate: its coefficients have intervals (VAL-10) and its methods have measured errors (VAL-5). A recommendation is reported with a sensitivity run, in which the coefficients it depends on most are moved across their intervals, and states whether the ranking changes.

8.9 Verification and validation

BLIS checks two different things. Verification asks whether the code does what the simulation model says (the simulation model is BLIS’s description of the serving system; it is not a language model). Its checks are the oracle tiers (§7.4), the conservation of requests, determinism, the byte gate and the relations of DEV-14. Validation asks whether the model matches the real system for its intended use. Its checks are held-out accuracy against measured benchmarks, through the dashboard’s scoring harness (§11.7), and the validity of its rankings. Both rest on a record of assumptions: each engine module and each cost-model form lists in its manifest what it does not model and why that is believed not to matter. Maintainer practice: at each engine upgrade a reviewer reads the event trace of a standard scenario for plausibility and records the review in the upgrade report.

Validation has three levels, and a point reports every level its source records.

  • Aggregate. The metrics of §8.7, scored by error, accuracy and quantile error (§11.8).
  • Distribution. Where the source records per-request data, the simulated and measured distributions of each metric, scored by distribution distance (§11.8).
  • Event. Where the source records per-request data, requests are paired by request identity and compared by the event statistics of §11.8: latency, completion order, prefix-cache hit length, per-tier KV hits and, for a P/D point, each transfer.

A source that records aggregates only is validated at the first level and says so.

A change is a verification change when it must leave the model’s behaviour unchanged: a refactor, a speed-up, or a fix that makes the code match an oracle or a written rule. It is a validation change when it changes what is modelled: a pricing form, a coefficient, how links are shared, an input model, a timing rule such as the scrape delay, or the order of classes at one instant. A change that is both is split. A verification change that moves a reported value carries the evidence X13 asks of it.

The model’s validity domain is the range of models, chips, layouts, concurrencies, sequence lengths and replica counts its held-out data cover. It includes a (model, chip) pair only if some fit unit covers that pair, so a held point on a pair with no fit unit lies outside it. Held-out error measures generalisation across the configurations of a deployment family; generalisation across a chip or a model is measured by the leave-one-out runs of VAL-5. Every Result states whether its scenario lies inside the domain. Behaviour that appears only at cluster scale, such as router decisions across many replicas or contention on shared links, is verified against upstream code but not validated until measured cluster runs exist. When BLIS models a policy, such as an autoscaler or a saturation detector, its output states whether that policy has been validated, and against what.

Validity for decision use. BLIS ranks configurations, and a small error does not guarantee a correct ranking, because errors of opposite sign reverse an order. Ranking validity (§11.8) is reported as COV-11 states. A Result of blis-config-search states the tau of the nearest validated workload.

9Getting a value for every coefficient

9.1 The aim

The cost model needs a coefficient for every primitive on every chip: an attention rate, a GEMM efficiency curve, a collective’s latency. Fitted measurements will never exist for every combination, and a refusal would lower coverage where a sound estimate exists. So every primitive gets a value, and every value records how good it is.

9.2 Sources, in order of preference

For each lookup (primitive, kernel implementation, chip, and where relevant data type and group size) the cost model uses the entry with the smallest rank number. When the coefficient registry has no exact entry, the lookup falls back down the ranks to the most trusted entry the coefficient registry has for that chip, and the point names the method (VAL-3).

Seven methods rank a coefficient from fitted to assumed, and the cost model takes the most trusted one available.

A primitive family is the set of coefficients that price one kind of operation, such as dense GEMM, decode attention or all-reduce. What a coefficient is keyed by. A kernel coefficient is keyed by the kernel implementation that runs, so data from one engine fits another’s value wherever both run the same implementation. An engine-path cost (host time, scheduler time, launch cost, CUDA-graph replay) is keyed by the identity of the code that does the work, and by the host CPU of the node where it was measured. The code identity is the hash of the normalised bodies of the functions in the call closure that the engine’s code_paths.json lists. The oracle’s call trace at the modelled commit lists the qualified function and constant names in the closure (ported callees, and the module constants and field defaults read on the path); FID-4 makes the trace complete for ported functions. At any other commit the identity is the hash of those names’ normalised bodies and values there, produced from the source alone by the diff generator of FID-14; a name that no longer exists makes the identity differ. Normalisation removes comments, docstrings and logging only; an annotation that defines a field stays. The engine module supplies the identity in its plan (§6.2), and the substrate stores it as an opaque key, so no engine name appears in substrate (X2). Engines or commits with the same code identity share an entry. A commit whose code differs falls back as above (VAL-8); an upgrade writes a transferred entry from the previous identity (§12.4), so the coefficient survives at rank 3 until it is refitted. A lookup whose host CPU differs from the entry’s is transferred, with the rule of scaling by the ratio of the catalog’s single-thread scores of the two CPUs, or assumed.

When a transfer is valid. A transferred entry names its source chip and its rule. If the source and the destination chip differ in generation (in tensor-core instruction set or data-type support), the rule must be one that VAL-5 has validated for that pair of generations; otherwise the entry ranks as roofline, with the efficiency rule of rank 6.

9.3 How the quality of a less trusted value is tracked

VAL-1 and VAL-3 record each value’s method, VAL-5 publishes each method’s error, VAL-4 allows one entry per rank, and VAL-10 ranks a lookup outside its fit range with transferred. Every value below rank 1 appears in the blocker backlog (§11.6).

10The data ledger

10.1 Sources

The ledger (substrate/catalog/ledger/) lists every measured unit from every data source, with each unit’s role. It holds these sources:

  • SemiAnalysis InferenceX: end-to-end serving benchmarks for vLLM, SGLang and other engines, plus collective (CollectiveX) and operator (OperatorX) benchmarks, agent traces and speculative acceptance curves.
  • NVIDIA AISimulate: operator sweeps per chip, under vLLM, SGLang and TRT-LLM.
  • NVIDIA’s forward-pass dataset on Hugging Face (nvidia/aisimulate-fpm-dataset, Apache-2.0): whole forward-pass timings per model, chip and layout.
  • Red Hat’s configiq dataset on Hugging Face (redhat-performance/configiq-performance-upstream-data, CC-BY-4.0): aggregate end-to-end measurements of upstream vLLM releases, one row per model, accelerator, release, layout, workload and concurrency, with no per-request data, run identifiers, timestamps or engine command lines.

Any other source, such as an engine project’s published performance runs or the team’s own private runs, joins by the procedure of §12.2.

10.2 Units, identities and roles

A unit is the smallest piece of data the ledger assigns a role to:

  • one InferenceX benchmark run of one deployment and recipe fingerprint at one concurrency, with each attempt’s measurement;
  • one point of a CollectiveX or OperatorX run, such as one token count;
  • one point of an AISimulate sweep, such as one matrix shape;
  • a forward-pass cell;
  • one configiq row’s configuration at one concurrency, with each measurement of it.

A point is a unit as the dashboard scores it, and has its unit’s identifier. The identifier, unit_id, is the SHA-256 of a canonical JSON object (UTF-8, sorted keys, no spaces) holding only the source’s own identifying fields, so a BLIS change never changes a unit’s identity.

How roles are assigned

A unit’s role is computed, never stored. Near-copies of one unit must share its role, or one could be fitted while its near-copy judges the fit. So the role is drawn per role key, and every field of a role key is an identifying field:

  • InferenceX end-to-end: the source, model, hardware, precision, framework, benchmark type and configuration hash. The key leaves out the recipe fingerprint, concurrency, measured date and benchmark run, so one deployment’s sweep and its re-measurements share a role.
  • CollectiveX, OperatorX and AISimulate: the run or file, so a sweep shares a role.
  • Forward-pass dataset: the source, revision, model, chip and layout.
  • configiq: every identifying field except the concurrency.

The role is HMAC-SHA-256(partition secret, role_key) mod 100, compared with cut-points fixed per source in the ledger. The HMAC’s message is the canonical JSON of the role key, and its digest is read as a big-endian unsigned integer. Only the SHA-256 of the partition secret is committed (D7). The ledger records who generated the secret, when, and who owns its rotation.

The draw is random by role key and controls no dimension, so the sibling of a held unit may be a fit unit. Held-out accuracy therefore measures generalisation across configurations of deployment families that the fit units already cover. Generalisation to a chip or model with no fit unit is measured by leave-one-out runs in the error job (VAL-5) and is published as such. The ledger report lists, for each source, how many role keys hold each role, by chip and by model family, and names any chip or family with no held-out key, so that a new partition version can address it.

What the ledger commits, under substrate/catalog/ledger/:

  • the sources, each pinned to an exact revision, and the units, by unit_id, identifying fields and role key;
  • the ingest report: for each source revision, the records read, merged as duplicates, joined into one unit, and left out, each with its reason;
  • the cut-points, the partition version and the hash of the partition secret;
  • the legacy table and any alias tables (below).

The source supplies the units; a pull request does not. The ingest tool generates the unit list from the pinned source revision, in one canonical form, and CI regenerates it and requires a byte-for-byte match where the source can be fetched with no secret and no restore (D4). Each measurement belongs to exactly one unit, recognised by the SHA-256 of the canonical JSON of the record’s measured values. A record that reports an error, or whose measured values are empty, is left out and counted. The conclusion of the benchmark run, such as a failed matrix, is recorded on the unit and does not remove it, because a run that fails in one job still writes real measurements from the others.

A source can store one measurement as several records, as when each attempt of a run becomes its own row. The ingest tool applies these rules:

  • Records with the same identifying fields and measured values are one unit. The tool keeps the record with the smallest source row id (for a file source, the path and then the line) and lists the others as duplicates. The choice cannot change the unit’s identifier or role; it decides only which record’s other fields, such as the image digest and server log, the unit carries, and a field only a duplicate records comes from the duplicate with the smallest row id that records it.
  • Records with the same identifying fields and different measured values are one unit holding each measurement. Their spread is the measurement’s own noise (COV-10).
  • The same measured values under two identities are one unit when the role keys are equal, under the identity with the smallest row id; when the role keys differ they are left out, because one measurement could draw two roles.

The ingest report counts every record merged, joined or left out, so a known measurement cannot be re-added under a new unit_id to get a new role draw.

The ledger never commits the role of a select, validate or held unit. At each release of inference-sim, a secret-holding release job writes two published lists, substrate/catalog/ledger/published/fit.yaml and anchor.yaml. The dashboard reads them at the release commit it scores (COV-2).

Who may see which roles

InferenceX data are public, so written-down roles would let anyone tune a change against the held-out units. Each job therefore learns only the roles it needs:

  • fit and anchor members are published with each release, as lists of unit identifiers. Fitting scripts, people and agents read the fit list, and the dashboard shows the anchor points.
  • select members are visible only to the select job, which scores candidates and returns aggregates. validate members are visible only to the error job, which measures method error nightly (VAL-5). held members are visible only to the gate job (D7). The select and error jobs run in inference-sim for operator-level work and in accuracy-dashboard for whole-run work; the gate job runs in accuracy-dashboard, because held units are whole runs.

The published lists do not separate select, validate and held, so a change cannot be tuned against the held units without the gate job. Legacy sides (below) differ: the old FIT and HELD labels are public, so the fit-side units not on the fit list are exactly the select units, and the held-side units not on the anchor list are exactly the held units. The gate reports every held unit on a legacy side as a separate reported value, marked as not blind.

Pull-request code never sees the partition secret

A candidate is code a pull request controls. In a job that held the partition secret it could read the secret, or leak which units are held through its output. So every scoring run has two jobs (D7):

  • The candidate job has no secret. It fetches its modules and the pinned scoring harness, then runs the candidate with no network on every unit not on the published fit or anchor lists, and writes one prediction per unit.
  • The secret-holding job runs only scorer code from main. It computes roles and reduces the predictions to aggregates over at least min_points role keys (COV-13); a smaller lane is merged or unjudged as VAL-6 states.

A candidate could still learn which units are held by corrupting its predictions on chosen units and watching the aggregates move. So held-unit aggregates are returned only for a pre-registered change, or by the nightly and pre-release gate runs, and the gate job counts every evaluation made on each partition version. Each pre-registration commit gets one evaluation on held units. The ledger commits a budget of evaluations for each partition version; when the count reaches it, the following release uses a new partition version, which publishes the retired partition secret (below). Maintainer practice: the count of further evaluations of a change is shown on the pull request and in the release notes. A pull-request job without a pre-registration may read only the published fit units, through the scoring harness (§11.7), and its reported values are never landing evidence. Anchor reported values are public, so only the prospective accuracy of D9 is claimed as out-of-sample.

Three properties of the rule

  • Append-only. Roles for new units are drawn inside the secret-holding jobs, the first time a unit appears and before any job uses it. An existing unit keeps its role unless a new partition version says otherwise. Maintainer practice: a maintainer with write access approves a new partition version.
  • Legacy units keep their old side. A partition made before the ledger existed is carried over through ledger/legacy-map.yaml. Each legacy unit keeps its old label, fit side or held side, and the keyed rule chooses only within that side: fit or select, held or anchor. A unit whose legacy records carry both labels takes the fit side, because data that was fitted on cannot judge a fit; so does a new unit whose role key holds legacy units of both sides. A coefficient fitted from legacy records cites their units, and a release refuses it while any cited unit is in select; it is refitted from the fit list first (D1). The ingest tool generates the map and commits it with the legacy table.
  • Stable when identities are recomputed. If a source renames a field, or a change to the ingest tool changes how identifying fields or role keys are computed, the affected identifiers change and units would be redrawn: a held unit could become a fit unit. So such a change ships an alias table from old to new unit_id and role key, and an aliased unit keeps its role. CI generates the table by running the merge-base and candidate ingest tools on the same pinned source revision and pairing the identities each gives the same records. A change whose aliases would give one new unit or role key two roles needs a new partition version. The ingest code detects such a change from the source’s contract version (§12.2).

When a partition version is retired, its partition secret is published. The committed hash then lets anyone check that the split was drawn as claimed.

11Accuracy coverage

When inference-sim releases, the accuracy dashboard scores the new release at its next nightly run, with no change to its own code. It scores every anchor unit and grades how close each comparison is. InferenceX often runs older, nightly or custom engine builds, so an exact comparison is not always possible. BLIS maximises the share of points scored, their accuracy and their closeness to the run, and COV-9 makes this an obligation of every release.

11.1 Why settings must not be classified by the dashboard

The dashboard never classifies a setting. The engine module does, in its field list (VLM-3), and the dashboard reads that list (COV-3).

11.2 Four steps for scoring a point

  1. State. The dashboard copies the run’s recorded engine configuration and environment variables, unchanged, into the scenario’s engine block. A run records its configuration in several places. The launch configuration and the logged passed arguments hold the values passed; the logged resolved configuration, and the lines the engine prints about values it chose, hold the values resolved. A value any of them records is recorded by the run, so it is copied and not estimated (X19). The engine block holds the values passed.
    A field the run records only as resolved is copied as resolved when the engine models it or proves it inert; for any other field the resolved value is the engine’s own choice, and it is recorded on the point and not stated in the scenario. A resolved value that differs from a passed one is not a conflict, because the engine module must reproduce the engine’s resolution. Where the run logs a resolved value that differs from the module’s resolution of the passed value, the point is G2, names the field, and the difference is a fidelity defect for the backlog.
    Two sources that record the same stage with different values are a conflict, and the point is G5 with the reason value_conflict.
    The dashboard translates nothing, apart from the estimates of the next step. The scenario states no engine version (LIF-6); the run’s own commit is recorded on the point, and its distance from the modelled commit sets the grade (§11.3, §11.5). A recorded field that the modelled commit lacks is refused (X1), so the point is G5 with the reason field_not_in_release.
    A workload-dependent value the run records, such as the mean acceptance length its engine logs, is copied as stated; one it does not record is taken from the substrate’s profiles (D8), and with no profile either the point is G5 with the reason value_not_recorded.
  2. Estimate. When the run did not record a value the simulation needs, such as the maximum model length, or passed a setting BLIS does not model, such as an unsupported quantisation format, the dashboard applies the engine’s estimation rule for that field, which the module writes in its fields.json beside the field’s status. A rule is one of: leave the field unset, so the engine resolves the upstream’s default (X19); a stated setting that stands in for an unmodelled one, with the reason; or none. A rule may state when the stand-in is exact: preserves, a sentence naming what the upstream resolves identically, and valid_when, a list of clauses. The stand-in is exact for a recorded value when at least one clause holds, and a clause holds when every key in it holds. A value for which no clause holds is not stood in for, and the point is G5 with the reason field_not_modelled. Absent valid_when, the rule applies to every value. A rule never replaces the recorded value of a field the engine models or proves inert. For a setting the engine does not model, the stand-in, or leaving the field unset, takes the place of the recorded value, and the point names the field, the recorded value and what stood in for it. A not-modelled field that the engine reads and prices when stated is a status to correct (VLM-3). Every estimate is named on the point and makes it G2; a field with no rule makes it G5 (§11.4).
  3. Decide. For each field, the engine’s own fields.json says whether it is modelled, proven inert or not modelled.
  4. Price. The engine lowers the configuration to kernel implementations. For each implementation the cost model uses the most trusted entry the coefficient registry has for the chip (§9.2), and the point records which methods were used.

A gap at Estimate is a missing estimation rule, and a gap at Decide is porting work, both in the engine module. A gap at Price is a value below the most trusted method. All go to the backlog (§11.6).

Faults of the run and limits of the runner are not this reason (COV-8). The substrate’s per-point record (SUB-19) carries the same closed list of reasons.The simulator accepts the scenario.

Order of reasons. A point’s first reason, the one coverage and the backlog count it under, is the first that applies in the order of the table. The scope reasons come first, because a missing chip or model is a gap BLIS can close. The point keeps all its reasons.

11.5 One simulator release scores every point

One release scores every point (COV-6, COV-9), so a substrate improvement reaches every point without a backport. The previous release’s scores stay published.

11.6 Coverage and the blocker backlog

Coverage is reported as a funnel for each scored source, so every loss is a stated number. At each release the funnel counts:

  1. the rows the source holds;
  2. its units;
  3. the units in scope, which are those not chip_not_modelled;
  4. the units with recoverable inputs;
  5. the units scored;
  6. the units scored in each grade.

It also lists the top blockers, ranked by the points each one alone holds back and, for a coefficient below the most trusted method, by the share of predicted time it prices. A training-only source reports a training funnel: the rows held, the units, the units with recoverable inputs and the units used in a fit.

Inputs are recovered from the most durable record a source offers: a server log kept by the source’s API; a job log while its host keeps it, otherwise the recipe or script at the run’s commit; the archive for a measurement the live feed no longer serves. Inputs that a source deletes after a retention period are archived privately as they are pulled and never committed (D6). A point whose inputs are gone is G5 value_not_recorded.

Every night the dashboard publishes a ranked list, per engine, of everything that lowers coverage or grade: refused surface items, not-modelled fields, coefficients below the most trusted method, and unpriced execution modes. Each entry shows how many points it blocks or demotes. Engine and substrate work is chosen from the top of this list; each entry maps to one procedure (§12).

11.7 The scoring harness, and who may run it

The dashboard’s scoring harness is the one place where a simulation is compared with a measured end-to-end benchmark (§2.2). It takes a simulator build (an inference-sim release, or a commit of a branch or pull request), the catalog and coefficient registry to load, and a set of ledger units. It turns each unit’s recorded run into a scenario as §11.2 describes, runs the simulator, and compares, writing the same per-point records and aggregates whoever runs it.

The harness is named by its accuracy-dashboard commit; the dashboard cuts no release. A repository whose pull requests run it pins that commit in one pin file, and every reported value records the harness commit that produced it (X8). Anyone may run it, at any stage of a change; the stage decides which units it may read, because only secret-holding jobs may see select, validate and held units (D7):

11.8 Accuracy statistics

Every reported value and every gate uses these definitions. No other section defines them.

One definition of error, accuracy, distance and interval serves every reported value the dashboard publishes and every gate.
TermDefinition
ErrorThe error of a point on a metric is |simulated − measured| / measured, the absolute relative error. The signed relative error is published beside it as bias. Gates compare absolute errors only (VAL-6). A point whose measured value is zero is not scored on that metric.
AccuracyThe accuracy of a set of points on a metric is the median of their errors, with the mean and the 90th percentile beside it. Each role key counts once: the dashboard first averages the errors of a key’s points, and weighs the keys equally.
Quantile errorThe error of a stated quantile (p50, p90 or p99) of a latency metric, simulated against measured.
Minimum sampleA quantile q of n measured requests is scored only when n ≥ 10 / (1 − q): 20 for p50, 100 for p90, 1,000 for p99. A smaller sample marks that quantile not scored, and every statistic skips it. A scored quantile is published with a distribution-free interval from the order statistics.
Distribution distanceWhere per-request data exist, the Wasserstein-1 distance between the simulated and the measured per-request samples of a metric, divided by the measured mean. It is scored only when the measured sample holds at least 100 requests. The simulated sample pools the requests of all replications. Beside it the dashboard publishes its noise floor: the mean distance between two resamples, with replacement, of the measured sample. Where a source records aggregates only, the mean of the quantile errors at p50, p90 and p99, labelled quantile error and not distance.
Event statisticsRequests are paired by identity. Latency error: the error above on each pair, as the median and 90th percentile. Completion order: Kendall’s tau-b (ties allowed) of simulated against measured completion times, within each concurrency level. Prefix-cache hit and KV tiers: the median absolute difference in hit length (tokens) and in hits per tier. Transfer (a P/D point): the median absolute difference of the start and end time, each from the request’s arrival. Each has its cluster interval. A source without per-request data says so.
IntervalEvery aggregate accuracy shows a 95% interval from a cluster bootstrap: each resample draws role keys with replacement and takes all of a key’s points. The bootstrap is the BCa bootstrap of VAL-6, with the jackknife taken over role keys. An interval over fewer than 30 role keys is marked approximate. A comparison of two releases shows the interval of the paired difference on the points both score. A gate resamples the same way (VAL-6).
SlicesA slice view does not correct its intervals for the number of slices viewed. It ranks slices only by a Holm-corrected comparison with the headline.
Ranking validityFor at least 5 measured configurations of one workload and model: Kendall’s tau between the simulated and the measured rank of the configurations on each metric, and the regret, which is the measured loss of the simulated best against the measured best.

12Triggers

A trigger is an event that requires work, and each recurring trigger has one procedure. A procedure gives its trigger, the components it touches (named as in Table 1, §2.2), its steps, and what done means. Statements marked Maintainer practice describe what people decide (§4.2). The checks a procedure names protect correctness and accuracy.

12.1 Onboarding a model

Trigger
A team asks for a model; a model in the data has no catalog entry (the reason not_in_catalog, §11.4); or a catalog model’s deployments run a drafter the catalog lacks.
Components
substrate/catalog always. engines/<engine> when the model needs model support (§12.5) or a new kind of layer. substrate/registry only for a new primitive family. The simulator is untouched.
Steps
  1. Catalog entry. Add the vendor config.json at a full revision hash and model.yaml, and generate graph.yaml. If the architecture is new, add a graph handler. A new kind of layer also needs new graph vocabulary, and each engine module then learns to lower it (§12.7).
  2. Drafters. List the model’s drafters in model.yaml: its graph’s own speculator, and each separate drafter entry, which names its target. Onboard each separate drafter as a model. A drafter method an engine does not run is a new capability (§12.7).
  3. Find what is missing. Simulate the requested scenario for each engine, layout and cluster. A missing catalog entry is refused by name, an engine refuses what it cannot lower, and the Result records each coefficient’s method. The upgrade report (§12.4) answers the same questions in advance, for every model at once.
  4. Model support, when the scenario shows the model brings engine-facing code (§12.5).
  5. Coefficients, only for a new primitive family. Every catalog chip needs an assumed entry in each family without a roofline formula, and in each new family (VAL-2), so the model can run. For any other model the cost model uses the most trusted entry it has (D11). A fitted entry (SUB-4) is optional and raises accuracy when fit data exists.
Done when
  • T-M1 A model that needs no model support and no new primitive family is onboarded by one pull request of catalog data, with no engine code.
  • T-M2 Every requested layout runs, or the simulator refuses it by name.
  • T-M3 Every coefficient the model uses has a method, and the method mix is reported.

12.2 A new data source, or a new revision of one

Trigger
The team adds a source; a scheduled job finds new records, a new revision or a new acceptance curve in a source the ledger holds; or a source changes its format, which the ingest code sees as a new contract version.
Components
substrate/catalog/ledger and substrate/load. substrate/registry when a refit follows. accuracy-dashboard picks the units up at its next nightly run.
Steps
  1. Define the unit. Define its identifying fields, its role key so that near-copies share a role (§10.2), and the cut-points, which allot training roles only. Define how a record maps to an engine commit and to the kernel and code identities of §9.2.
  2. Identify each run’s settings from its own records: workload, cluster, GPU, model, engine settings and engine commit, and the metric’s definition. Name the record that settles each. Write the scenario writer with a test of every field against its record (D10). A value no record holds becomes a named substitution.
  3. Pin and ingest. Pin the revision or each row by id and content hash (D3). A source with a live feed joins continuously, by a scheduled job. A new source gets cut-points for training roles only (D9). Commit only redistributable data (D6).
  4. Roles. The secret-holding jobs draw each new unit’s role the first time they see it, before any use (D4). If the source changed its format, ship the alias table first, so every unit keeps its role.
  5. Refit only the families whose fit data changed. A refit that uses new units waits for the release whose release job publishes their fit list. Each refit follows §12.3.
  6. Acceptance profiles. Regenerate them. A new curve is carried, with its drafter, when its model and drafter resolve in the catalog; one that does not is skipped with a stated reason (D8).
  7. Report the source’s funnel (§11.6) and the coverage and grade changes per lane.
Done when
  • T-D1 No existing unit changed role.
  • T-D2 Every new unit has exactly one role, a new source has no held-out role, and the role key puts every pair of near-copies in the source’s data in one role.
  • T-D3 Every revision and row is pinned by id or hash.
  • T-D4 Coverage and grade changes per lane are reported.
  • T-D5 The scenario writer’s test covers every field against its record.
  • T-S1 After a format change, every old unit maps to a new identity with the same role.

12.3 An idea to improve accuracy

Trigger
A person or an agent proposes it, usually from the top of the backlog (§11.6).
Components
The component that owns the layer the idea changes: a coefficient or method (substrate/registry), a pricing form (substrate/kernel, and the engines that lower to it), or engine behaviour (engines/<engine>).
Steps
  1. Pre-register. Commit a file before any held-out data is read. It states the hypothesis, the layer it changes, the target lanes, the sources and lanes whose select and held units will be used (the jobs choose the units), the success criteria with the non-inferiority margin of VAL-6 for each criterion, and the predicted dashboard change.
  2. Make one change per pull request.
  3. Evaluate candidates by path. A writer script puts each candidate coefficient registry in its own directory, and the select job scores each with --registry <dir> (§13.5). A data-only candidate needs no rebuild.
  4. Choose among candidates on select units only.
  5. Evaluate once on held units, in the gate job (§13.5). It counts against the partition version’s budget (D7).
  6. Land the change if the criteria pass. Otherwise commit the negative result as a note.
Done when
  • T-A1 Results on held units exist only as outputs of the gate job, run after the pre-registration commit (D7).
  • T-A2 The change passed the landing gate of VAL-6.
  • T-A3 After release, the change in the dashboard’s prospective accuracy (D9) is within the predicted range, or the miss is recorded.
  • T-A4 A failed idea leaves a committed note with its evidence.

12.4 An engine upgrade

Trigger
A new final upstream release of vLLM or SGLang (release candidates are ignored), or a later upstream commit that a team scenario needs, on which the upstream’s required checks passed and from which the oracle environment builds. Maintainer practice: a maintainer with write access decides an on-demand upgrade and records it in an issue. A patch release is one more commit and follows this procedure.
Components
engines/<engine> (port, generated lists, oracle, recorded traces). The simulator, for the stack.json commit. substrate/registry only for a kernel implementation that has no coefficient yet.
Steps
  1. Generate the upgrade report. It holds:
    • the surface diff: new, removed and changed connectors, tiers, KV-cache managers, speculative methods, policies, configuration fields, defaults, metrics and event types (§7.5);
    • the field demand: for each new or changed field, how many dashboard points set it and to which values, so that the fields the data use most are modelled first;
    • the source diff: each ported function, by its Derived from header, as unchanged, changed (with the upstream diff) or removed, and the kernel implementations whose selection or kernel hash changed (including the hash of a selected tuned configuration) and the engine-path code identities that changed (§9.2). The dashboard uses the same generator to grade a run (§11.3);
    • for each model architecture the new commit registers: whether the catalog has it; whether it needs model support and for what; and, for each catalog chip, the coefficients it lacks, meaning any new primitive family that needs entries before the model can run and the kernels it would price below measured or calibrated.
  2. Move the port. Update the Upstream record to the new commit and the release it descends from. Regenerate fields.json, surface.json and kernel_impls.json at the new commit, and lock the oracle environment to it. Run all tiers.
  3. Re-port only the changed functions. Delete code for anything the new commit removed, including a model backport (§12.5) it now contains.
  4. Classify every new surface item (X9) and every new configuration field (VLM-3).
  5. Regenerate the recorded traces that changed. Each gets a trace-reviewed: line with its reason.
  6. Price. Each kernel implementation whose selection or kernel hash changed gets a coefficient by the methods of §9. Each engine-path identity that changed gets a transferred entry from the previous identity, whose rule is the per-function diff, so that a coefficient survives the upgrade until a refit. A transferred value states its rule (§9.2).
  7. Merge. The simulator’s stack.json then names the new commit, and every Result records it (LIF-6). A user who needs the old commit uses the release that ran it.
Done when
  • T-E1 Changes are confined to the engine’s directory, the simulator’s commit bump, and the coefficients the report named. Every kernel implementation and engine-path identity that changed has an entry with a stated method. The whole-run gate (§13.5) ran for the candidate against the previous release on held units, and no lane worsened beyond the margin of VAL-6, or each worsening lane is recorded as a defect in another term (VAL-11). The report states the change in each lane’s grade mix.
  • T-E2 Every ported file names the new commit, and no code for the old one remains except a listed backport. An upstream patch release is one more commit under this procedure.
  • T-E3 The surface list and field list are complete for the new commit.
  • T-E4 Every changed trace carries its review line.
  • T-E5 The replacement manifest is unchanged, or changed with a reason.
  • T-E6 The new release’s stack.json names the new commit and its Results record it (LIF-6). The previous release, which pins the old commit, reproduces its own recorded byte-gate output.

12.5 Model support

Trigger
The upgrade report or a requested scenario shows that a model brings engine-facing code the engine upgrade does not port. The cases are a KV-cache layout, its own kernels or a backend choice, a quantisation or weight-packing scheme, or a drafting method or scheduler hook that the engine module has not seen. A model that brings none of these needs no model support.
Components
engines/<engine> only, and substrate/registry when the model’s kernels need entries.
Steps
  1. Port the model’s engine-facing code from upstream at the modelled commit.
  2. If the model landed upstream after the modelled commit, apply the upstream commits that add it onto the modelled commit as a model backport, and list them in the Upstream record. The paths a backport may change are those of §7.1.
  3. Add an oracle scenario and a recorded trace for the new code, and classify its new surface items.
  4. Lower the model’s kernels, and price them by the methods of §9.
Done when
  • T-M4 The model’s engine-facing code is ported at the modelled commit, its oracle scenario passes, the weights check (T0) and the priced-equals-launched check (FID-11) pass on every catalog chip it is claimed for, and every coefficient it uses has a method, reported as for T-M3.
  • T-M5 A backport meets §7.1 and FID-14.

12.6 A new engine

Trigger
A team needs an engine BLIS does not model (the reason engine_unsupported, §11.4), such as TRT-LLM.
Components

  5. Implement engine.Engine and plan emission, and register the engine kind in the simulator.

Done when

13Automation: how the rules are kept

This section describes the automated checks and the agent work that runs against them. Review, approval, merge, release and signing are maintainer practice (§4.2). No automated check reads a pull request’s title or body. Agents do bounded work, such as porting a changed function, classifying a new field or fitting a coefficient, from the upgrade report or a requested scenario (§12), against the checks.

13.1 The invariant registry

Every invariant in this document is a record in substrate/contracts/invariants/:

- id: SUB-6
  statement: The cost model resolves nothing; every default, backend choice,
             padding and capture decision arrives in the plan or step shape.
  scope: [substrate/kernel]
  checks:
    - test: TestKernelResolvesNothing
      known_bad: a plan that leaves a default unresolved
      runs: pull_request
  status: ci                      # ci | partial | none

The status partial means some of a rule’s checks are written and others are not. A rule that is a maintainer practice (§4.2) has no checks. Each check runs on pull_request, nightly or release, and names a known-bad input that must make it fail (X18).

A generator renders these records into a section of each repository’s AGENTS.md, and a copy that does not match its record fails CI. A check on this document fails when a rule defined in the text is missing from Appendix A, or when the index lists a rule the text does not define.

13.2 Agent guidance

What a repository’s AGENTS.md holds. In this order it holds: what the repository is and owns, and what it must never hold (Table 1, §2.2); the rules that apply to a change here, rendered from the invariant registry; the commands that build, test and run every check, as CI runs them; what a change must also update (the README.md, a generated copy, the invariant registry record); and where to look next. It states no version, count or list of supported features, and states the rules a check cannot decide rather than those it enforces.

Review questions. A rule that depends on judgement may carry a review question with a trigger: the paths it concerns, or a description of the change, such as “a floating-point reduction is added”. Maintainer practice: the reviewer, a person or an agent a maintainer asks, applies each question whose trigger matches the change and records yes or no, with a reason and the files and lines that support it. A question is guidance for that review and never a check: no job runs, fails or waits on it.

13.3 On every pull request

CI runs per component directory, with path filters: a change runs the checks of the directories it touches, and the cross-directory checks (§3.4). Table 1 (§2.2) names each component’s checks.

  • A workflow starts on a pull request only when the code can have changed: opened, synchronize, reopened, and a change of base branch.
  • A pull request that can change prices also generates the price-change report: each benchmark scenario’s step prices before and after the change.
  • Heavy checks (oracles, mutation sweeps, the byte gate) run only for the directory whose code they test; accuracy gates run as §13.5 describes.

13.4 Every night

  • The nightly build builds and tests inference-sim at the head of its main branch and of each open release branch (§14.4), on three platforms, against the router fork commit each pins, and checks the import graph against Table 1.
  • Full-data gates rerun the coefficient registry writers, the landing gates and fixture-agreement checks on the full data, which a pull request’s CI cannot hold.
  • Detectors poll upstream commits and releases and the data sources, and list what is new in the nightly summary. A maintainer decides the work and records it in an issue.
  • The dashboard scores, publishes coverage and grades, and updates the backlog.

13.5 Where accuracy gates run

An accuracy gate compares a candidate with held units, which are whole runs from InferenceX (VAL-6). Where it runs depends on what it needs, and the partition secret stays in the jobs of D7:

  • Operator-level evidence needs only the cost model and the coefficient registry, for example whether an attention coefficient predicts sweep points kept apart for validation. The error job in inference-sim reports it nightly as method error on validate units (VAL-5). It informs review and never lands a change, because operator-level sources hold no held-out units (§10.3).
  • Whole-run gates need engines and the simulator, for example whether a change improves end-to-end latency on held-out deployments. They run the dashboard’s scoring harness (§11.7), the only end-to-end scorer, at the commit that inference-sim’s harness pin file names (X7). A candidate job in the pull request’s own repository builds the candidate and runs the harness with no secret, as §10.2 describes. accuracy-dashboard’s gate job refuses predictions made by a harness commit that is not on its main branch, reduces them to aggregates and reports the result on the pull request.

The gate compares two trees: the base, which is the pull request’s merge base, and the candidate, which is its head.

  • If the pull request changes only files under substrate/catalog/ and substrate/registry/, both trees load under the released simulator’s validators, and the code outside those directories at the merge base is identical to the code of the release, the gate runs the released simulator twice, once per tree. No rebuild is needed. If main carries unreleased code changes, the next case applies, so the data are judged with the code they will ship with.
  • Otherwise, as when the pull request changes the cost model or an engine module, or uses a data field the released simulator cannot read, the job builds one simulator from the base and one from the candidate, and each runs on its own tree.

Before a release is cut, the whole-run gate job runs once more, comparing the release candidate with the previous release, and with the best published release for each lane, on held units. A lane that fails the test of VAL-6 against either fails the check. A maintainer may still cut the release only after recording each such lane as one defect in another term (VAL-11).

The gate job runs on pull requests that carry a pre-registration, and again nightly on the full data.

13.6 Releases

inference-sim is the one tagged release (§14). Cutting it is maintainer practice (LIF-3). The generated inputs to a release are the list of pull requests merged since the previous release, the price-change report (§13.3) and stack.json (SIM-3).

accuracy-dashboard and blis-config-search cut no release (§14.1).

Standing authorization. A maintainer with write access may record, in a release plan, a standing authorization: a list of steps an agent may perform with the maintainer’s credentials, and the condition for each. The maintainer decides once, when the plan merges; the agent then performs each listed step when its condition holds, and records what it did on the pull request or issue. The conditions are at least these:

  • a merge needs every required check to pass on the head being merged, and a review by a different agent or a person that finds no blocker or major issue;
  • a release follows LIF-3 exactly, from a commit where every required check passed;
  • a job that holds the partition secret is dispatched, never read; a partition version is written only with the cut-points the release plan states, and keeps the secret;
  • a repository setting, transfer or archive is the one the release plan names.

An authorization never covers a change to this design, the retirement or publication of a partition secret, or a step the release plan does not name. A maintainer revokes it by editing the release plan.

CI or permissions enforce most of the prohibitions: trace and generated-file guards are CI checks, and without a standing authorization agent credentials have no permission to merge or tag. Maintainer practice: the reviewer rejects a change that skips a test, suppresses a lint or loosens a threshold without a stated reason, and a change that loads generated files into an agent’s context.

What a release guarantees about an engine module

A release of inference-sim, for each engine module:

  • models the upstream commit its Upstream record names, and no other;
  • passed that commit’s oracle tiers, its field list and surface list checks, and every invariant whose registry status is ci (§13.1);
  • differs from the previous release that models the same commit only by BLIS-side changes: bug fixes, newly modelled features, contract or substrate updates. They may change prices or decisions.   • holds only files ported from that commit or original to BLIS.

The pseudo-version Go derives for a router fork commit only orders commits and says nothing about the llm-d release modelled.

A detail of Go’s version ordering

To Go, -blis.N is a pre-release suffix. So vA.B.C-blis.1 sorts before vA.B.C, and go get …@latest prefers any plain release over every pre-release. Three rules follow for the router fork:

  • It never tags a plain v<upstream>; an optional tag always has a -blis.N suffix, with N from 1.
  • Pins name exact commits. A lint checks the version each build actually selects, not the text of go.mod (LIF-2).
  • A plain tag made earlier stays (LIF-1) and makes @latest wrong for that module. A retract line cannot fix this, because Go reads retractions only from the latest release version; an exclude line in inference-sim’s go.mod does (X11).

14.4 Release branches

inference-sim has a main branch, which models the newest upstream commit of each engine BLIS supports, and release branches release-vX.Y. When an engine module moves to a new upstream commit, inference-sim cuts release-vX.Y from its last release that ran the old commit.

A fix needed on the old commit is made first on the main branch if the main branch needs it too, then cherry-picked to the release branch; otherwise it is made on the release branch alone. A PATCH release from the release branch ships it. Only the release before the newest is supported this way, and its branch closes when inference-sim next moves an engine or llm-d to a new upstream commit.

The router fork keeps a branch release-<llm-d release> for the same purpose, cut from the last commit that modelled the old llm-d release, and the release branch of inference-sim pins it.

HMACA keyed hash. Without the key (here, the partition secret) the output cannot be predicted.
Holm correctionA way to test many lane, criterion and metric claims at once while keeping the chance of any false pass at the stated level (VAL-6).
Hosting contractThe interface between the simulator and the router fork’s embedded router: clock, runtime, sessions and KV events. The router fork owns it, with its conformance suite, so the fork depends on no BLIS module (RTR-3, §5.3).
In-flight depthThe most engine steps that run at once, PoolPlan.InFlight: 1 without asynchronous or overlap scheduling (SIM-7).
Inert, unprovenA field status that a release plan may allow for a stated period (§1): a field believed to have no effect, whose proof is still to come.
Invariant registryThe records of every invariant in this document: statement, checks and status, in substrate/contracts/invariants/ (§13.1). Each repository’s AGENTS.md section is generated from it.
ISL, OSLInput and output length of a request, in tokens.
KernelA GPU kernel. The directory substrate/kernel/ holds the cost model and is named for the Kernel interface it implements, not for a GPU kernel (§3.2).
Kernel hashCodeHash: the hash that identifies a kernel implementation, of its source and target GPU architecture, or of a binary library (§6.2).
Kernel implementationThe library, variant and kernel hash (CodeHash) that execute one primitive. The coefficient registry looks coefficients up by it.
Known-bad inputAn input that a check must reject. Each check in the invariant registry names one (X18).
KV cacheThe stored attention keys and values of each request. A KV connector moves it between machines; KV tiering moves it between GPU memory and host memory.
KV-cache manager, KV-cache specIn vLLM, the code that decides which blocks a request’s KV cache holds, which prefix blocks it shares and which blocks are evicted. The model’s layers are grouped, and each group has a KV-cache spec, such as full attention, sliding window or Mamba state. A registration table maps each spec type to a manager, and a coordinator runs one manager per group (§7.1).
Landing gateThe accuracy check a coefficient or pricing change must pass to merge (VAL-6).
LaneA group of held-out points judged together: the points that share an engine, modelled commit, chip, model and layout. The landing gate judges each lane (VAL-6).
LayoutHow a model is split across GPUs: the tensor, pipeline, data, expert and context parallel widths, and where each rank is placed.
LedgerThe committed list of every measured unit from every data source, with the rule that gives each unit a role (substrate/catalog/ledger/, §10).
Legacy table, legacy sideThe legacy table lists the units that were given a fit side or a held side before the ledger existed. Each keeps its side, and a held unit on a legacy side is reported as not blind (§10.2).
llm-d stackllm-d’s router in front of vLLM or SGLang engines, as llm-d’s published guides deploy it.
LoweringTurning a model’s architecture into the concrete operations one engine runs on one layout: which attention backend, which fused operations, which data types, which page size, how it shards and pads. It lives only in engine modules (SUB-15, §6.1).
Maintainer practiceA rule about process (review, approval, merge, issues, pull-request text, release notes, signing) that a maintainer with write access keeps with branch protection, required reviews and signed commits. It is written “Maintainer practice:” and has no check (§4.2).
ManifestThe list of everything the oracle replaces.
Memory poolIn SGLang, a store of KV cache or recurrent state in GPU memory, or, for HiCache, in host memory, with a separate allocator for its slots or pages. Each attention layout has its own pool type (§7.1).
Metric registryThe list in contracts/ of every metric’s definition: formula, statistic, population, window and unit (§8.7, DEV-8).
MLAMulti-head latent attention: attention that stores a compressed latent instead of full keys and values.
Model backportUpstream commits that add one model, applied onto the modelled commit and listed in the Upstream record. It carries model code only, never scheduler, KV-cache or connector changes, and is dropped when the modelled commit contains it (§12.5).
Model componentAn atomic or coupled model: a part of the simulated system with its own state, changed only by its own internal events and by messages from other model components. Atomic examples are an engine instance, the router, a link, or a client (one source in the workload generator); a pool and the cluster are coupled (§8.1). This is the DEVS sense, and differs from a component of Table 1.
Model supportWork in an engine module for one model, needed only when the model brings engine-facing code that an engine upgrade does not port, such as a new KV-cache layout, its own kernels or a new drafting method (§12.5).
Modelled commitThe upstream commit an engine module models. A build runs one modelled commit of each engine (LIF-5, LIF-6).
MoEMixture of experts.
Move, move form, legA move is one movement of KV between two places. Its form is one of the closed list of §6.1. Its price is the sum of its legs, each a copy over one path that the catalog states (§6.1).
MSER-5A warm-up rule: batch the output series in fives and cut where the variance of the remaining mean is smallest (§8.8).
MTPMulti-token prediction: a speculative-decoding method where extra model layers draft the next few tokens.
Named substitutionA value that no record of the run holds, stated on the point with the value used and its source. It lowers the grade. An estimated substitution is a named substitution whose value comes from a stated rule and not from a record (D10).
NIXLNVIDIA’s library for moving KV caches between machines. vLLM’s NixlConnector, the P/D connector llm-d’s guides use most, is built on it.
Not blindA held-side reported value from a unit whose label predates the ledger, so that the unit may have influenced earlier choices. The gate reports each such unit as a separate reported value for as long as such units are used (§10.2).
not_chargedA coefficient method for a cost that BLIS deliberately does not charge, with a written reason (VAL-1).
Offered loadRequests arriving per second, set by the workload rather than by the system’s response.
Onboarding a modelOne to three pieces of work, after any engine upgrade the model needs: a catalog entry, always; model support, when needed; and coefficients, only for a new primitive family (§12.1).
OracleThe harness that runs the upstream’s own code with its environment replaced, and records its decisions.
OverlayA directory given with --catalog-overlay or --registry-overlay. Each entry replaces the entry with the same identity in the data in use, or is added if none exists (§3.3).
P/DPrefill/decode disaggregation: one pool of engines processes prompts (prefill), another generates tokens (decode), and the KV cache moves between them.
Parallel DEVSThe form of DEVS in which all outputs at an instant are collected before any model component changes state (§8.2).
Partition secretThe 256-bit secret that, with a role key, decides a unit’s role. Only the secret-holding jobs read it (§10.2).
Partition versionA numbered version of the ledger’s role assignment. A new version is needed to change any existing unit’s role.
Perturbation testA test that changes one field and checks that some price, decision, or field of the emitted plan or step shape changes (SUB-11, VLM-3).
Pin fileA file that records the exact commit or release of another repository: the harness pin file in inference-sim, and the pin of an inference-sim release in each application (X11, X23).
Pin, re-pinTo require an exact commit or release of another module, in go.mod or a pin file; to update that requirement.
PointOne unit as the dashboard grades it, G1 to G5 (§11.3): for InferenceX, one benchmark run of one deployment and recipe fingerprint at one concurrency.
PoolA group of engine instances that share one configuration and layout, such as the prefill pool or the decode pool in P/D. Each pool has one PoolPlan.
PoolPlan, StepShape, engine.Transfer, plan.TransferThe objects an engine hands the cost model: a plan per engine pool, and the shape of each step. The engine reports each KV move as an engine.Transfer, which the cost model receives as a plan.Transfer (§6.1, §6.2). The unqualified word Transfer is not used.
Pre-registrationThe file of an accuracy change, committed before any held-out data is read, that states what the change will be judged on (§12.3).
Price-change reportA report, generated for every release and every pull request that can change prices, of each benchmark scenario’s step prices before and after the change (§13.3).
PrimitiveOne kind of work the cost model prices: an attention step, a matrix multiply, a collective, a memory transfer.
Primitive familyThe coefficients that price one kind of primitive, such as dense GEMM, decode attention or all-reduce (VAL-2).
Profile likelihoodA way to find a fitted coefficient’s interval by refitting the others at each candidate value (VAL-10).
Progress watchdogA check that fails a run when no request changes state for a set number of engine steps while work is waiting (SIM-7).
Provisional pointA point whose source records neither launch arguments nor frame, but whose row fits every preset of the launcher that published it. It is capped at G3 and kept out of the headline (COV-7).
Pseudo-versionThe Go version string that names one commit of a module that has no tag (X11).
Quarantine listThe list of tests that fail on the main branch, each with an owning issue and an expiry date; listed tests do not block merges until they expire (X25).
Radix cache, tree cache, tree coreSGLang’s prefix cache: a tree of token sequences whose nodes hold KV cache, so that requests sharing a prefix reuse it. A tree cache is any implementation of SGLang’s tree-cache interface. A tree core is the tree’s own data structure inside a radix cache (§7.1).
RatchetA count that CI allows to fall but never to rise.
Recorded traceThe oracle’s output for one scenario at one upstream commit, reviewed and committed (§7.4).
Release branchA branch release-vX.Y of inference-sim, cut when an engine module moves to a new upstream commit, and kept for fixes to the commit the last release ran (§14.4).
Reported valueA metric at a scope, with its aggregate: a number that a Result, a report or the dashboard shows. Two reported values are compared only when their metric, scope and aggregate are the same (§8.7, DEV-8).
ResultThe structured output of one run, written as JSON, including everything the run used (§3.3).
Review questionA yes/no question, attached to a rule, that a reviewer applies to a pull request and answers with the files and lines that support the answer (§13.2). It is guidance and never a check: it fails no CI job.
Role keyThe fields of a data unit that decide its role, so near-copies of one measurement share a role (§10.2).
RooflineAn estimate of a primitive’s time as the larger of its compute time at peak FLOPs and its memory time at peak bandwidth.
Router forkllm-d’s router code in a repository of its own. It owns the hosting contract and depends on no BLIS module (§2.1, §5.3).
Router tableThe substrate’s map from a router a run used to the nearest policy llm-d’s router offers (§11.4).
ScenarioThe YAML file a user gives BLIS: the engine and router configuration, the cluster, the workload and the seed.
Scoring harnessThe accuracy dashboard’s tool that turns measured benchmark runs into scenarios, runs a given simulator build, and compares. The only end-to-end scorer (§11.7).
Secret-holding jobOne of the four kinds of CI job that hold the partition secret: the release, select, error and gate jobs. They run only code from main. Only these can compute select, validate and held roles (§10.2).
Selected-version lintA check that reads the versions Go actually chose for a build (go list -m all), not the versions written in go.mod.
Simulated runtimeThe router fork’s runtime when BLIS hosts it: clock, timers, randomness and goroutines driven by simulated time (RTR-7, X4).
Simulation modelBLIS’s description of the serving system, as distinct from a language model and from the cost model (§8.9).
SliceThe points that share an attribute value, such as one chip. Below min_points no aggregate is shown (COV-13).
stack.jsonThe record, published with each inference-sim release, of its own commit, the router fork’s commit, the upstream commit each engine module models, its Go toolchain version and its llm-d guides commit (SIM-3).
Staging bufferA region of host memory through which a move passes between a storage device and the GPU (§6.1).
SubstrateThe engine-independent foundation: the substrate/ directory of inference-sim (§3).
Surface listThe generated list of every feature an upstream commit offers, each with a BLIS status.
Token recordThe per-request counts an engine emits: prompt tokens, tokens served from local and external caches, tokens computed and tokens emitted (SIM-12).
TP, DP, EPTensor, data and expert parallelism.
TranscriptionUpstream code that the oracle cannot run, such as a loop that blocks on network queues, rewritten for the oracle and listed in the manifest under its own kind (FID-8).
TriggerAn outside event that starts BLIS work, such as a new upstream release or a new model (§12).
TRT-LLMNVIDIA’s TensorRT-LLM serving engine. A new engine of this kind meets the same bar as vLLM and SGLang, with its C++ code checked through bindings (§7).
UCX, NCCLTransport libraries that choose how bytes move: UCX under NIXL, and NCCL for collectives and its own transfers (§6.1).
Unit, roleA unit is the smallest piece of data the ledger tracks. Its role says what it may be used for.
Upgrade reportThe report an engine upgrade generates: the surface diff, the field demand, the source diff and, for each model the new commit supports, whether the catalog has it, whether it needs model support and which coefficients it lacks (§12.4).
UpstreamThe project BLIS reproduces: vLLM, SGLang or llm-d.
Upstream recordThe Upstream value in an engine module’s provenance.go: the upstream commit the module models, the release that commit descends from, and any listed model backport (LIF-5).
Validity domainThe range of models, chips, layouts, concurrencies, sequence lengths and replica counts that held-out data cover (§8.9).
Value classA range of values of a modelled field that its evidence covers: the values the evidence sets, or a range split at every threshold the upstream compares the field with (VLM-3).
Verification, validationChecking that the simulator does what its model says (verification), and checking that the model matches the real system (validation) (§8.9).
Workload identityThe key under which a workload-dependent quantity, such as speculative acceptance or expert routing balance, is stored (D8).
