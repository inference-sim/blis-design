BLIS · M3.2 · summary

Data sources and calibration in M3.2

M3.2 calibrates BLIS on existing data only. It runs no new GPU or cluster experiments. Where no source measures a coefficient, the cost model uses the most trusted fallback entry (transferred, roofline or assumed, among others) and names its method on every point it prices. M3.2 keeps the sources M3.1 uses and adds three official ones from the vLLM and SGLang projects. Every run's settings are read from its own records. Accuracy is reported on InferenceX units held out for it and on configiq anchor units. configiq is not yet documented well enough to train on, so every configiq unit is an anchor unit. Everything else, the new sources included, is training data. The aim is to improve both engines: kernel coefficients are shared where vLLM and SGLang run the same kernel, and host and scheduler costs are fitted per engine.

The role shares do not change. For InferenceX, half of each new unit draw is held out (30% held, 20% anchor) and half is training (30% fit, 10% select, 10% validate). configiq is 100% anchor. What grows is the number of units those shares apply to. The 2026-11-18 nightly scored 238 InferenceX anchor units. With the M3.2 coverage work the ceiling is about 2,800 scored anchor units, or up to about 4,700 if older SGLang recipes still resolve. Held InferenceX units would be about 1.5 times the anchor units, and between about 187 and about 630 configiq units on H200 and B200 would be scored as anchor units. The ceiling is not higher mainly because vLLM runs from before February 2026 have no server log on the InferenceX API. These are upper bounds; M3.2 counts the recoverable units first.

How calibration works

  1. Pull and pin.Each source is fetched at a pinned revision. New rows join the ledger as they are published, and no age limit applies, so no unit is lost to a frozen snapshot or to its age. A unit can still be unscorable when its logs are gone, so logs that expire, such as GitHub job logs after about 90 days, are archived privately as they are pulled.
  2. Read each run's settings from its own records.The workload, cluster, GPU, model and engine settings come from the run's recipe, logs and launch commands, never from a BLIS default. A value no record holds is named on the point as a substitution, and it lowers the point's grade.
  3. Give each unit a fixed role.A seeded draw gives each InferenceX unit one role: fit, select, validate, held or anchor. Every configiq unit is an anchor unit. Units from the new sources get training roles only. Roles never change after the draw, so a fit is never chosen or judged on the held-out units.
  4. Fit coefficients on fit data only.Kernel constants come from kernel-level data: the operator sweeps and the traces' kernel timings. Step and host costs come from step-level data. Kernel coefficients are keyed by the kernel itself, so vLLM and SGLang share them when they run the same kernel. Host and scheduler costs are keyed by the engine code that does the work, so each engine gets its own. Every coefficient is written by its family's script; a measured one is reproduced from its data.
  5. Check end to end before accepting.A better per-kernel fit can make the whole prediction worse, because some errors offset each other. Each change is checked on the validation units first. A change that is to count as evidence is pre-registered and evaluated once on held units.
  6. Score, grade and report.Each held-out InferenceX unit and each configiq anchor unit is simulated as its run ran, and graded G1 to G5 by how closely BLIS reproduced its setup. Only these units make accuracy figures. Runs on older engine releases still count, at a lower grade. The dashboard shows a coverage funnel for InferenceX and configiq, and accuracy can be sliced by any recorded attribute, with the point count beside every figure.
