BLIS · M3.2 · executive summary

Data sources and calibration in M3.2

M3.2 calibrates BLIS on existing data, with one exception — a GB200 custom all-reduce micro-measurement on GB200 itself (blis-substrate#116); otherwise no new GPU or cluster runs. It keeps the sources M3.1 uses and adds three official ones from the vLLM and SGLang projects. Every source enters the same pipeline. Its runs are pinned and recorded, and each run's settings are read from its own records. Accuracy is reported only on InferenceX and configiq runs held out for it. Everything else, the new sources included, is used for training, fitting and validation, however serves accuracy best. Accuracy can be sliced by chip, engine, workload and more. Both engines improve. Kernel numbers are shared where vLLM and SGLang run the same kernel; host and scheduler costs are fitted per engine.

The role shares do not change. For InferenceX and configiq, half of every new unit's draw is held out (30% held, 20% anchor) and half is training (30% fit, 10% select, 10% validate). What grows is the number of points those shares apply to. Today 199 InferenceX anchors are scored. With the M3.2 coverage work the ceiling is about 2,700 anchors, and up to about 4,600, plus roughly 1.5 times as many held units, and about half of configiq's 1,702 units. It is not higher because vLLM runs from before February 2026 no longer have server logs to rebuild them from. These are upper bounds, and M3.2 measures the real count first.

How calibration works

  1. Pull and pin.Each source is fetched at a pinned revision. New rows join the ledger as they are published, so nothing is lost to a frozen snapshot or an age limit. Logs that expire, such as GitHub job logs after about 90 days, are archived privately as they are pulled.
  2. Read each run's settings from its own records.The workload, cluster, GPU, model and engine settings come from the run's recipe, logs and launch commands, never from a BLIS default. A value no record holds is named on the point as a substitution, and it lowers the point's grade.
  3. Give each run a fixed role.A seeded draw assigns each InferenceX and configiq run to fit, select, validate, held or anchor. Runs from the new sources get training roles only: fit, select or validate. Roles never change after the draw, so no fit can be tuned on the runs that judge it.
  4. Fit coefficients on fit data only.Kernel constants come from kernel-level data: operator sweeps and the traces' kernel timings. Whole-step and host costs come from step-level data. Kernel numbers are keyed by the kernel itself, so vLLM and SGLang share them when they run the same kernel. Host and scheduler costs are keyed by the engine code that does the work, so each engine gets its own. Every coefficient is written by a script, and that script reproduces it from the data.
  5. Check end to end before accepting.A better per-kernel fit can make the whole prediction worse, because some errors offset each other. Each change is checked on the validation runs first. A change that is to count as evidence is pre-registered and evaluated once on held runs.
  6. Score, grade and report.Each held-out InferenceX and configiq run is simulated as it ran, and graded G1 to G5 by how closely BLIS reproduced its setup. These are the only runs that make accuracy figures. Older engine releases still count, at a lower grade. The dashboard shows a coverage funnel for InferenceX and configiq and lets accuracy be sliced by any recorded attribute, with the point count beside every figure.

How the fits are done

BLIS does not train a black-box model. Each coefficient belongs to a small formula with a physical meaning, and only that formula's two or three constants are fitted:

  • Kernels as floor plus rate. An operator's time is a fixed floor plus its work divided by an achieved rate: a fraction of the chip's peak compute or memory bandwidth (a roofline). GEMM efficiency rises with batch size along a saturating ramp, eff(M) = eff_max · M / (M + M_half).
  • Collectives and transfers as latency plus bandwidth. A size-independent latency, then bytes divided by a link rate. Both are fitted per operation, rank count and fabric.
  • Memory terms are read off the engine's own start-up logs on fit runs: weights, activation peak, CUDA-graph capture.
  • Host and launch costs are fitted to step-level timings. Where only end-to-end runs exist, they are fitted to fit-run residuals and labelled as such.

The constants are found by grid search that minimises the mean absolute log ratio of predicted to measured time, so being 2× too slow and 2× too fast count the same. A few families use least squares. Each fit is seeded and deterministic. Where a fit reports a confidence interval, it comes from bootstrap resampling. Forms are tested on held-out shapes, with whole values of a dimension left out, so a form that only interpolates is caught. In M3.2, the same procedure fits per-engine host and scheduler costs from SGLang's traces.

What M3.2 changes

  • Three official vLLM and SGLang sources join the five existing ones, all used for training. Only held-out InferenceX and configiq runs report accuracy. The internal experiments stay private.
  • Settings are identified from each run's own records, for every source, as a fixed step in calibration.
  • Coverage is maximised. Today 199 of 20,364 InferenceX anchors are scored, mostly because the ledger stops at a September snapshot and scoring stops at 180 days. M3.2 removes both limits and scores SGLang runs.
  • configiq rows written by Red Hat's launcher get their missing settings from that launcher's own configuration, which raises how many score and how closely.
