Terms

Repositories. Design v3.0.0 has one simulator repository and the router fork. M3.2 builds that layout (DC3). Until the migration lands, the three repositories below still exist, and the issue numbers in this file name them.

  • inference-sim: the simulator. Its tagged release is the only one a milestone requires (v0.18.0 is M3.0, v0.18.1 is M3.1). Since M3.1 the other repositories are pinned by commit, and their tags are optional. After the migration it also holds the three below, as substrate/, engines/vllm and engines/sglang.
  • blis-substrate (substrate/): the shared contracts (contracts/), the cost model (kernel/), the model catalog (catalog/), the coefficient registry (registry/) and the ledger (catalog/ledger/).
  • blis-vllm and blis-sglang (engines/vllm, engines/sglang): Go models of the vLLM and SGLang engines, each ported from one upstream commit. Each is an engine module.
  • The router fork: inference-sim's fork of llm-d's router (llm-d-router, branch llm-d-r). It owns the hosting contract and depends on no BLIS module.
  • accuracy-dashboard: scores simulated runs against measured runs and publishes accuracy.
  • blis-config-search: searches deployment configurations with the simulator.
  • blis-design: the design (main) and these requirements (branch m32).

Data sources.

  • InferenceX: SemiAnalysis's public end-to-end serving benchmarks, with server logs and recipes.
  • configiq: Red Hat's public dataset of GuideLLM results for upstream vLLM releases. GuideLLM is a load generator for LLM servers.
  • AISimulate: NVIDIA's operator sweeps (one kernel at a time over many shapes) and forward-pass measurements.
  • forge: Red Hat's open-source benchmark launcher (openshift-psap/forge), which wrote most of configiq's recent rows (§3C).
  • AgentX: an agentic workload of recorded coding-agent sessions that InferenceX and the internal experiments replay.
  • The internal experiments: the team's own measured runs of its target scenarios. Their data is private; it is never published, and no public text says which runs it holds.
  • The dashboard nightly: accuracy-dashboard's nightly job, which scores the ledger's anchor units on the latest simulator release. (SGLang's own nightly CI is a different thing, and is always named as SGLang's.)
  • The dump is InferenceX's database dump db-dump/2026-09-28, which the ledger pins; its date is the cutoff between dump rows and supplements. Supplements are InferenceX rows published after the dump and added to the ledger one by one, each pinned by its row id and the SHA-256 of its content.

Design rules, sections and terms. IDs such as X7, SUB-15, LIF-5, COV-6, T-M1 or D6 name rules of design v3.0.0. The letters group them: X across components, SUB substrate, LIF versions and releases, COV accuracy coverage, VAL coefficients, D the ledger, T a trigger's test. A design section is written "design §n.m" and links to the design. A bare § number is this file's own section (§0 to §4, §3A to §3C); the design changes are DC1 to DC3 and the team request is DC4, without a §. The design's glossary, Appendix B, defines these terms, which keep its sense here: anchor, commit distance, drafter, engine module, engine upgrade, funnel, graph handler, graph vocabulary, headline, held-out unit, lowering, model backport (written "backport"), model support, named substitution (an estimated substitution is one whose value comes from a stated rule rather than a record), onboarding a model, oracle, primitive family, role key, router table, slice, training data and upgrade report. The design's term "lane" has a wider sense than this file needs, so the dashboard's per-engine groups are called groups here.

The ledger and roles.

  • Ledger: blis-substrate's list of every measured unit from every data source, with each unit's role (catalog/ledger/).
  • Run: one execution of a benchmark against a deployment, as a data source records it. One InferenceX run can measure several concurrencies; each becomes its own unit.
  • Row and records: a row is one line a source publishes (an InferenceX API row, a configiq CSV row); a run's records are everything its source keeps about it: rows, server log, recipe and launch command.
  • Scenario: the simulator's input describing one run to simulate: the deployment, the cluster and the workload.
  • Unit: one ledger entry. For InferenceX it is one configuration at one concurrency from one benchmark run, with every measurement of it. A point is a unit as the dashboard scores it.
  • Role: each unit has one of fit, select, validate, held or anchor, drawn once per role key by a seeded rule (design §10.2). Fit units fit coefficients, select units choose between fits, validate units check a fit. Held-out units are held (one evaluation per pre-registration) and anchor (the headline, the dashboard's accuracy figure). Training data is every fit, select or validate unit and all data from a source with no held or anchor role.
  • New InferenceX and configiq units draw 30% fit, 10% select, 10% validate, 30% held and 20% anchor. Older units were first split into a fit group and a held group; each stays in its group, and the ledger's rules split each group into roles (fit and select; held and anchor).

Grades. G1 (exact) to G5 (not scored), as design §11.3 defines them. G1 and G2 need the run's own engine commit; G3 and G4 are other commits, by commit distance.

Coefficients.

  • Coefficient methods are ranked in design §9.2: measured, calibrated, transferred, literature, vendor_spec, roofline, assumed. A lookup uses the most trusted entry the registry has, and records its method. A fallback entry is one whose method is transferred, literature, vendor_spec, roofline or assumed; it is used where no measured or calibrated entry exists, and every point it prices names its method.
  • TRT-LLM: NVIDIA's TensorRT-LLM serving engine, which BLIS does not model. vLLM-family, SGLang-family and TRT-LLM-family group InferenceX's frameworks by the engine underneath, as evidence/COVERAGE-FUNNEL.md Table F2 lists them (for example, the vLLM family includes Dynamo and llm-d deployments of vLLM).
  • P/D: prefill/decode disaggregation, where separate GPU pools run the prefill and decode phases.
  • Abbreviations: TP, DP and EP are tensor, data and expert parallelism. TTFT is time to first token and TPOT time per output token. ISL and OSL are input and output lengths in tokens.
  • Age limit: the dashboard's rule, today, that scores only runs measured in the last 180 days (§3A.2).
  • Speculative decoding uses a small drafter model to propose tokens. DSpark is one drafting method. Acceptance is the share of drafted tokens the target model keeps.

DC. Design changes (DC1 to DC3) and a team request (DC4)

Status. M3.2 implements design v3.0.0. The design states the rules. DC1 to DC3 are Decided: the design adopts them, and this section states each once. Table DC lists what M3.2 builds. Rule IDs and sections are those of v3.0.0. The lowering work of DC2, planned for M4, is part of M3.2.

Why. Changes crossed repositories in sequence: the per-pool offload fix took blis-substrate#402, blis-vllm#302 and inference-sim#2252, with full CI at each. And the new data (§1) is pinned to engine commits, not releases, which BLIS could not model.

The decisions

DC1. An engine module models one upstream commit, not only a release. A run on the modelled commit is the same build and can be graded G1 or G2. A run on any other commit names its commit distance and is graded G3 or G4. A model that lands upstream between upgrades is added as a model backport, which carries model code only. An engine upgrade produces an upgrade report of the models the new commit supports. In the design: design §7.1, §11.3, §12.4 and §12.5, and Table 1 in design §2.2; LIF-5, LIF-6, COV-6, T-E1 to T-E6, FID-14.

DC2. Lowering lives only in engine modules. The catalog's graph deriver writes checkpoint facts and nothing else. The onboard --plan command is removed: simulating the requested scenario and the upgrade report answer the same questions. The substrate has no rule layer, so contracts/rules/ is removed. A model that needs no model support and no new primitive family is onboarded by one catalog pull request. In the design: SUB-15, SUB-12, T-M1, T-M2 and design §12.1.

DC3. blis-substrate, blis-vllm and blis-sglang become directories of inference-sim. They are packages of inference-sim's one Go module (substrate/, engines/vllm, engines/sglang). The router fork, accuracy-dashboard, blis-config-search and blis-design stay separate. The router fork owns the hosting contract and its conformance suite, so it depends on no BLIS module and inference-sim imports it without a cycle. In the design: design §2.1, §2.2, §3.2, §3.4, §5.3 and §14.4 (Table 1, the layout, checks by directory, the router fork and release branches, in that order); X7, X11, SUB-1, SUB-13, RTR-3. X10 (bottom-up merge) is retired.

DC4 is a team request, not a design change; it follows the build list below.

Decided (2026-11-19). This is an M3.2 requirement, not a design change and not a patch release of M3.1.

Request. A GB200 configuration for both models on 16 GPUs, the capacity of Muse Spark (a model already in the catalog; its open checkpoint is Muse-Spark-Open), for the team to use and verify.
