D. Design changes M3.2 needs (proposal, for team review)

Status. Proposal, raised by the maintainer on 2026-11-18 for the team to review. Nothing in this section is decided or built until the review closes. Each change to the standing design lands first as a blis-design pull request to main, then in code. Whether D4 belongs in M3.2 or in a patch release of M3.1 is open.

Why. Three things recur.

  • Cross-repository friction. Most features touch contracts, an engine and the simulator together, and each repository boundary turns one change into a sequence. A change to blis-substrate is re-pinned in blis-vllm, blis-sglang and the router fork, then in inference-sim, with full CI at every hop. In M3.1, blis-substrate#373 was first held out because that cascade "cannot be green in the window". The per-pool offload fix took three sequential pull requests: blis-substrate#402, blis-vllm#302 and inference-sim#2252.
  • Teams ask for models that only an unreleased engine build supports (D4).
  • The new data is pinned to engine commits, not releases. Nearly every vLLM CI perf row names a vLLM commit (a few say nightly or a release tag), and every SGLang nightly names an SGLang commit (§1, §2.3). Today BLIS can model only a release, so it cannot fit against the exact engine code those runs used.

D0. Terms used in this section

  • Engine upgrade. Porting the diff of the code an engine module already models (scheduler, KV-cache manager, connectors, defaults, lowering) from one upstream commit to another. It changes behaviour for every model. "Port" and "move the modelled commit" mean the same thing here.
  • Model support. Work in an engine module for one model, needed only when that model brings engine-facing code of its own (D1 lists the cases). It is separate from the upgrade.
  • Onboarding a model. Up to three pieces of work, done after any engine upgrade the model needs:
    • Catalog entry (always): the model's config.json, its catalog entry, and a graph handler if the architecture is new. A new kind of layer also needs new graph vocabulary, and then the engine must learn to lower it, which makes the engine piece depend on this one.
    • Model support in the engine module, when needed.
    • Coefficients, required when a kernel the model runs on the target chip has neither a registry entry nor a coded fallback. The cost model refuses a missing coefficient rather than defaulting it (blis-substrate kernel/new.go: "A missing coefficient … is an error rather than a default"). A transferred or assumed entry, written by its family's writer script (SUB-4), makes the model run; a measured entry, fitted on fit units, makes it accurate.
  • Commit distance. How far a run's engine commit is from the modelled one: commits apart, and releases apart where the two sit in different releases. Under D1 it is named on a point beside its grade, as the release difference is today (§3A.5); the G3 and G4 rule for a different engine build (COV-6) is unchanged.

D1. Model any upstream commit, not only a release (vLLM and SGLang)

Today. An engine module models one upstream release (LIF-5). A build runs one release of each engine, and a scenario that names another is refused (LIF-6). A run on another release is scored as a named release difference (§3A.5, §11.5, COV-6).

Proposal.

  • An engine module models one upstream commit: a release tag, or a commit on the upstream's main or release branch. The Upstream record names the commit and the release it descends from. A build still runs one commit of each engine, so LIF-6's refusal stays, with a commit in place of a release.
  • An upgrade is ported as a diff, as v0.32.0 to v0.33.0 was. The generators (fields.json, surface.json, kernel_impls.json) already take the upstream reference as a parameter. The oracle environment is locked per commit.
  • A point whose run used the modelled commit has no release difference. Any other point names its commit distance (D0).
  • Model backport, the narrow case: the upstream commits that add one model are applied onto the modelled commit and listed in the Upstream record. A backport carries model code only, never scheduler, KV or connector changes, and folds away when the modelled commit contains it.
  • When to move. On each upstream release, and on demand when a team scenario needs a later commit. Each move re-runs the oracle and the goldens.
  • Model support is needed only when a model brings engine-facing code that an upgrade does not port, because it lives mostly in the model's folder (for example vllm/models/inkling2/):
    • a KV-cache layout the module has not seen, as DeepSeek-V4's sliding-window cache and compressor were (core/kv/layers.go);
    • its own kernels, or a backend choice the module does not lower, as Muse Spark's fused kernels were (blis-vllm#272);
    • a new drafting method or scheduler hook.
  • A model that brings none of these needs no model support. Onboarding it is the catalog entry, plus any coefficients its kernels lack (D0).
  • Upgrade report. Every engine upgrade generates a report of the models the new commit supports. For each model it gives:
    • whether the catalog has it;
    • whether it needs model support, and for what. This comes from the regenerated surface, field and kernel lists, which must give every new entry a status (X9), and from the model's own code paths;
    • for each catalog chip, the coefficients it lacks: those it cannot run without (no entry and no fallback), and those running on transferred or assumed values.
  • The report is the to-do list for model requests, in advance. A run of the requested scenario gives the same answer for one model: a missing catalog entry is refused by name (not_in_catalog), an engine refuses what it cannot lower, a missing coefficient is refused with its name, and the Result records each coefficient's method. No separate preflight command is needed (D2).

Effect. A new model on upstream main can be supported (D4). The vLLM CI perf and SGLang nightly runs can be fitted against the exact engine code that produced them (§1). A named release difference becomes a named commit distance, which is finer.

D2. Lowering out of blis-substrate, brought forward from M4

Today. The catalog's graph deriver still holds vLLM lowering. The plan moved its removal, and the contract-change review set that removes contracts/rules/ with model values moved into graph fields, from M3 to M4 (2026-11-17). The design already says a graph holds only what the checkpoint states, and that sharding, fusion, padding and the nodes emitted under a layout are lowering (SUB-15). It also says onboarding a model is one blis-substrate pull request with no engine code (§12.1, T-M1). Neither holds yet, and the second can hold only for a model that needs no model support or coefficients (D0).

Proposal. Bring both into M3.2.

  • Move all lowering into the engine modules.
  • Remove contracts/rules/, as the contract-change review set (§12.8).
  • Drop the onboarding preflight command that §12.1 describes (inference-sim onboard --plan, never built). A run of the requested scenario, and the upgrade report (D1), answer the same questions.

Effect. A new architecture built from existing kinds of layer is onboarded with a graph handler plus data; each engine lowers it with the lowering it already has. A new kind of layer still needs engine lowering (D0).

D3. Consolidate blis-substrate, blis-vllm, blis-sglang and blis-kvstore into inference-sim

Proposal. Move the four repositories into inference-sim as top-level directories, keeping their history (a subtree merge) and transferring their open issues.

  • contracts/ becomes its own small Go module inside the repository, versioned, because the router fork imports it. SUB-1 already limits it to the standard library and the YAML parser.
  • These stay separate:
    • the router fork, a fork of llm-d with upstream's import path;
    • accuracy-dashboard, because a scorer independent of the simulator is a deliberate audit property;
    • blis-config-search, which consumes simulator releases;
    • blis-design.

Separation of concerns is kept by checks, not by repository walls.

RuleKept by

What changes. One pull request can span the contracts, an engine and the simulator. The bottom-up merge order and the cascade of pins between BLIS repositories go away (X10, X11). Per-engine release branches (§14.4) become release branches of inference-sim, which already cuts release-v0.18. The rule that blis-substrate is one Go module (SUB-13) is restated for the new layout. A model's catalog entry, model support and coefficients (D0) become one pull request.

What is given up. The hard wall between repositories. A simulator change could edit catalog data in the same pull request, so the lints and CODEOWNERS must do what the walls did. Each repository's merge rules, checks and workflows have to be consolidated.

Timing. If adopted: at a release boundary, after the M3.1 cut, as the first M3.2 item, because D1 and D2 are easier in one repository. The migration is not sized yet; a sizing from the actual workflows, checks and open issues comes before the decision.

  • What stays held out. InferenceX and configiq keep their held and anchor shares, untouched. Accuracy figures come only from those. 1.5 Proposal. Calibration acceptance gates (precommit, X8). 3A.9 Proposal. Reconcile the frozen dump against the live API explicitly. Maintainer. As more sources come in, accuracy must be sliceable by all their data attributes. There is a version of this today.
