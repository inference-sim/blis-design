BLIS M3.2 plan

A focused companion to the full release plan: what is already delivered (M1–M3.1), in brief, and the M3.2 cut in full.

Status Working capture — not yet a frozen plan Scope M3.2, the next cut of M3 Sources m32/requirements.md, the release-plan gist, and PR #34 review Figures as of 2026-11-18

What this is. The full release plan schedules all four milestones (M1–M4). This companion keeps M1, M2, M3.0 and M3.1 to short delivered summaries (§1) and sets out M3.2 in full (§2): the carry-over from M3.1, new calibration data sources, settings identification, coverage maximisation, accuracy slicing, configiq, and the calibration acceptance gates. The review feedback on PR #34 is folded in, and the decisions still open before calibration begins are collected in §2.8.

Where M3.2 sits. M3 is released as a train of cuts — M3.0, M3.1, M3.2, … — not one release. M3.2 is a cut: an inference-sim PATCH from release-v0.18 (v0.18.x), with the lower repositories pinned by commit and needing no tag (blis-design #22). It changes no contract by itself; an incompatible change waits for v0.19.0 (M4). Its goal, as for every cut, is to maximise coverage, accuracy, closeness grade and correctness on the two scored sources — InferenceX and configiq — and to bring the new engine-project data in for calibration only.

2.1New data sources — for calibration only §1, §1.4

Maintainer. Bring three engine-project sources into BLIS: SGLang nightly profiler traces (sgl-project/ci-data — step/host overhead, kernels); the vLLM CI perf API (ci.vllm.ai/api/perf with the perf-eval recipes — current vLLM on H200/B200); and SGLang nightly job logs plus consolidated-metrics (scheduler behaviour, resolved server arguments). Licence is not a blocker — the data is queried, not redistributed — so none is committed to a public repo (D6); units are built from a pinned fetch at fit time, and a public figure cites the source URL and fetch date. Whether the rest of the inventory (Tritonbench, SGLang AMD P/D, llm-d Prism, blog step tables, MoE tuning configs, AgentX launch configs) is also in scope stays open (§1.3).

§1.4 (maintainer, 2026-11-18) — the key framing

The new data sets are used entirely for fitting and calibration. Accuracy on the dashboard is reported only on InferenceX and configiq points held out for it. Each new source's ledger rule draws only fit / select / validate roles — no held or anchor share; InferenceX and configiq keep their held and anchor shares untouched. No double use: a source that fits a coefficient never also grades it, and selection between candidate fits uses the select and validate shares, never the held-out points.

2.2Settings identification (apples to apples) §2

For every point used, the run's settings — workload, cluster, GPU, model, engine — must be recoverable; getting them right is what makes the comparison like-for-like, and it is part of the calibration process, not a one-off. Every value comes from the run's own records; a value no record holds is a named substitution with its source and lowers the grade; never a BLIS default. Each source's scenario writer has a test that checks every field against the record it came from (the per-source record that settles each setting is in SETTINGS-PROVENANCE.md). To confirm before any fit: the statistic aggregate_perf.py uses over repetitions, the vllm bench seed and range ratio at each commit, and how a recipe revision is matched to a row's date when the recipe changed that day.

2.3Which engine the data improves §3

Calibration improves both SGLang and vLLM; data that can only improve one engine is still used, not ignored. Kernel coefficients stay keyed by kernel implementation, so SGLang data fits vLLM's value wherever both run the same implementation. Engine-path costs (host, scheduler, launch, CUDA-graph replay) are keyed by the identity of the code that does the work, so each engine has its own value with no engine name in substrate (X2). Host overheads are scoped by hardware and model today; this is a design change that must land before the plan — it needs a blis-design issue and a blis-substrate PR, and neither exists yet (workstream 1 in §2.10).

2.4Maximise scorable coverage §3A

Today 199 of 20,364 InferenceX anchors are scored and ~0 of 1,702 configiq units; the losses are mostly policy and a frozen ledger, not missing data (COVERAGE-FUNNEL.md). The levers:

  • 3A.1 The ledger follows each source. Every row a source publishes becomes a unit — auto-pinned by record id and content SHA-256 on a schedule — not only the db-dump/2026-09-28 rows plus hand-pinned supplements.
  • 3A.2 No age limit on scoring. The 180-day window stops being a gate; every anchor whose inputs can be recovered is scored, at its grade. A date range becomes a slice (§2.5).
  • 3A.3 Recover inputs from durable records; keep the ones that expire. /server-log for single-turn; the job log or the recipe at the run's commit for SGLang and P/D; the dump for superseded measurements; a private archive (D6) for the ~90-day GitHub artifacts, pulled as they are published. Inputs truly gone → G5 with a reason.
  • 3A.4 Engine and table gaps, ranked by points held back. SGLang field list; the router table (Dynamo's router); the not-modelled settings tail (data_parallel_rpc_port, NCCL/FlashInfer envs, …), each modelled, proven inert, or given an estimation rule. TRT-LLM stays refused — BLIS has no TRT engine.
  • 3A.5 Older engine releases are scored, not refused — a named release difference at a lower grade, for both engines.
  • 3A.6 Coverage is a funnel per source, every release — held by the source → units → in scope → inputs recoverable → scored, by grade, with the top blockers by points they alone hold back.
  • 3A.7 configiq — waiting on the team's answers; see §2.6.

3A.9 Reconcile the frozen dump against the live API (added on PR #34)

InferenceX stopped publishing dumps after db-dump/2026-09-28 (weekly Apr–Sep 2026, none since), so the pinned dump is a dead, aging source on ever-older vLLM/SGLang releases while every fresh run comes only from the API. Therefore: the dump is a frozen genesis archive, not a base to advance — it is the only copy of pre-09-28 history, including measurements the API has superseded and no longer serves; all forward coverage is 3A.1's auto-pinned supplements. A run that straddles the cutoff keeps one measured_date (the earliest over its records) and one unit, because the ingest tool reads the dump and the API supplements together before building units; the binding constraint is that the automation never ingests new API rows apart from the dump, pinned by a test with a straddling run. Old-release runs carry the §3A.5 grade and feed calibration by §1.4's draw. The funnel and slices show the dump-vs-API share of the held-out set. A dump row is never re-pulled from the API (the two print numbers differently and the API lacks the superseded history) — the id-floor stays.

2.5Slice accuracy, and the small-slice guard §3B

Every scored point carries its attributes, and the dashboard filters and groups by any of them — source, role, model, precision, chip, node count, interconnect, engine, release distance, topology (TP/DP/EP/P-D pools), speculative method, offload and KV tiers, router, workload type, ISL/OSL, concurrency, arrival process, prefix sharing, measured date, grade, and each named substitution — with every aggregate recomputed from the surviving points. Each slice shows its point count and coverage beside its accuracy.

Small-slice guard — decided per review

Decision: raw point rows are always visible at every n; an aggregate accuracy figure is always withheld below min_points (10) at every level — headline and every drilled-in leaf alike — and a withheld aggregate is excluded from every verdict. (The earlier "stop applying it at a drilled-in leaf" alternative is dropped: it let a small slice look like strong evidence.) The threshold (10) stays, and a test pins the behaviour. The guard's UI legibility — show the count (n=3 · mean held) rather than a bare verdict, and have the points table state the rule — is tracked in accuracy-dashboard#160.

2.6configiq §3C

Classify each row by writer: Family A (forge, prefix-caching on) 779 units, Family C (manual imports) 128, Family D (Model Furnace and older imports) 803 — the family decides how a blank is read (a blank is value_not_recorded → G5 unless a launcher preset matches). Family A: fill every blank from forge's own records (the CPT matrix and presets at the run-date commit; vLLM defaults for flags forge never passes; the forge frame — concurrent profile, 275 s window, warm-up/ramp, GuideLLM release, seed 42). Family D: fill only what the public guide and furnace defaults support, as named estimated substitutions at a lower grade; TP=1 rows may have used data parallelism and stay unscored. Check each filled frame against the data (the Little's-law window from the concurrency-1 row). Model the multi-turn and prefix workloads as they ran.

Pin one dataset revision and hash, and regenerate every count from it — the three writer families (779 + 128 + 803 = 1,710) and the 1,702 headline differ by 8, which the pinned revision must reconcile. It is not append-only (444 rows were removed between revisions), so configiq is hand-adopted per revision, unlike InferenceX's auto-pin. Ask Red Hat (maintainer owns the conversation): publish an allow-listed runtime_args, the image tag, the GuideLLM version, the cluster tag, start/end times, DP and the turn index; fix the case mismatch that drops DP; publish more of the ~52 models the CSV holds. configiq's settings recovery stays provisional until these land.

2.7Calibration acceptance gates — precommit review

§1.4 separates fit/select/validate from held/anchor, but the requirements do not yet say what numerical result accepts a fit. Before any fitting reads these sources, precommit (X8):

  • the baseline each fit must beat (the current released coefficients);
  • the error metric and the mandatory slices it is evaluated on (engine, chip, workload at least);
  • the minimum sample count per slice for a verdict (at least the §2.5 min_points);
  • the allowable per-engine / per-chip regression a fit may cause elsewhere;
  • the held/anchor verdict (evaluated once, after selection) and the revise-or-revert rule.

Partition rule (replacing the loose "a source never both fits and grades"): InferenceX and configiq deliberately provide both training and held partitions. The split is assigned at the role-key (configuration) level — source, model, hardware, precision, framework, benchmark type and configuration hash — not per row, so every concurrency and repetition of one configuration shares a role and correlated repetitions never straddle the fit↔held boundary. A coefficient is never selected or graded on the role-group that fit it; selection uses the select/validate shares only. New sources (§1.4) draw fit/select/validate only. Without these, the selection procedure can be finalised after seeing its outcomes — exactly what X8 prevents.
