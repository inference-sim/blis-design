Terms

Repositories.

  • inference-sim: the simulator. Its tagged release is the only one a milestone requires (v0.18.0 is M3.0, v0.18.1 is M3.1). Since M3.1 the other repositories are pinned by commit, and their tags are optional.
  • blis-substrate: the shared contracts (contracts/), the cost model (kernel/), the model catalog (catalog/), the coefficient registry (registry/) and the ledger (catalog/ledger/).
  • blis-vllm and blis-sglang: Go models of the vLLM and SGLang engines, each ported from one upstream version. Each is an engine module.
  • blis-kvstore: reserved for models of KV-cache store packages such as Mooncake and LMCache. It is empty.
  • The router fork: inference-sim's fork of llm-d's router (llm-d-router, branch llm-d-r).
  • accuracy-dashboard: scores simulated runs against measured runs and publishes accuracy.
  • blis-config-search: searches deployment configurations with the simulator.
  • blis-design: the standing design (main) and these requirements (branch m32).

Data sources.

  • InferenceX: SemiAnalysis's public end-to-end serving benchmarks, with server logs and recipes.
  • configiq: Red Hat's public dataset of GuideLLM results for upstream vLLM releases. GuideLLM is a load generator for LLM servers.
  • AISimulate: NVIDIA's operator sweeps (one kernel at a time over many shapes) and forward-pass measurements.
  • The internal experiments: the team's own measured runs of its target scenarios. Their data is private; it is never published, and no public text says which runs it holds.
  • The dashboard nightly: accuracy-dashboard's nightly job, which scores the ledger's anchor units on the latest simulator release. (SGLang's own nightly CI is a different thing, and is always named as SGLang's.)
  • The dump is InferenceX's database dump db-dump/2026-09-28, which the ledger pins. Supplements are InferenceX rows published after the dump and added to the ledger one by one, each pinned by its row id and the SHA-256 of its content.

Standing-design rules and sections. IDs such as X7, SUB-15, LIF-5, COV-6, KVS-2, T-M1 or D6 name rules of the standing design (blis-design main). The letters group them: X across repositories, SUB substrate, LIF versions and releases, COV accuracy coverage, KVS KV stores, VAL coefficients, D the ledger, T a trigger's test. Each citation here says what the rule requires where that matters. A standing-design section is written "design §n". A bare § number is this file's own section (§0 to §5, §3A to §3C); the design changes are DC1 to DC5, without a §.

The ledger and roles.

  • Run: one execution of a benchmark against a deployment, as a data source records it. One InferenceX run can measure several concurrencies; each becomes its own unit.
  • Row and records: a row is one line a source publishes (an InferenceX API row, a configiq CSV row); a run's records are everything its source keeps about it: rows, server log, recipe and launch command.
  • Scenario: the simulator's input describing one run to simulate: the deployment, the cluster and the workload.
  • Unit: one ledger entry. For InferenceX it is one configuration at one concurrency from one benchmark run, with every measurement of it. A point is a unit as the dashboard scores it.
  • Role: each unit has one role, drawn once by a seeded rule: fit, select, validate, held, anchor or report. A report unit gives context only and never yields a number. The draw is per role key, so units that are near-copies share a role. For InferenceX the role key is the source, model, hardware, precision, framework, benchmark type and configuration hash; it leaves out the recipe fingerprint, the concurrency, the measured date and the benchmark run. For configiq it is every identifying field except the concurrency.
  • For new InferenceX and configiq units the draw is 30% fit, 10% select, 10% validate, 30% held and 20% anchor. Units from older ledger revisions were first split into a fit group and a held group. They stay in that group, and the ledger's rules split each group into roles (fit and select; held and anchor).
  • Training data: every unit whose role is fit, select or validate, and every source with no held-out roles. Its shares are fit (used to fit coefficients), select (used to choose between fits) and validate (used to check a fit).
  • Held-out shares: held and anchor. Anchor units make the published headline, the dashboard's accuracy figure. Held units judge a pre-registered change, with one evaluation per pre-registration (design §10.2). Pre-registering a change means committing its hypothesis and gates before any held-out data is read (design §12.3).

Grades. How closely a point's simulated setup matches its run. Table T1 gives the five grades.

Table T1. G1 to G4 are scored grades; G1 needs the run's own engine release, every setting it sets modelled or proven inert, and every coefficient measured or calibrated.

  • Named substitution: a value no record of the run holds, stated on the point with the value used and its source. It lowers the grade. An estimated substitution is a named substitution whose value comes from a stated rule rather than a record.
  • Release difference: what a point names when its run used an engine release other than the one BLIS models (§3A.5).

Coefficients and engines.

  • Coefficient methods (design §9.2), from most to least trusted: measured (fitted to microbenchmarks of that exact kernel implementation on that chip), calibrated (a physical formula with one or two factors fitted to end-to-end or forward-pass data), transferred (measured on a related implementation or chip, moved by a stated rule), literature (a cited published figure), vendor_spec (a datasheet figure), roofline (computed from catalog facts with a default efficiency from the same family) and assumed (a stated assumption with its reason). For each lookup the cost model uses the most trusted entry the registry has for that chip, and records its method.
  • Lane: the kernel implementation a coefficient is fitted on, such as NCCL's all-reduce or a custom all-reduce. The dashboard's per-engine groups are called groups here, not lanes.
  • Lowering: turning a model's graph (what its checkpoint states) into the operations one engine runs on one layout: sharding, fusion, padding, and the nodes it emits. A graph handler is catalog code that builds one model family's graph from its config.json. The graph vocabulary is the set of node kinds a graph may use.
  • Oracle: an engine module's harness that runs the real upstream code with only the transport and the clock replaced, to check the Go model against it. Goldens are the oracle's recorded outputs. The byte gate checks that a refactor leaves simulator output unchanged, byte for byte.
  • P/D: prefill/decode disaggregation, where separate GPU pools run the prefill and decode phases.
  • Abbreviations: TP, DP and EP are tensor, data and expert parallelism. TTFT is time to first token, TPOT time per output token, ITL inter-token latency. ISL and OSL are input and output lengths in tokens. MTP is multi-token prediction, a form of drafting.
  • Router table: the substrate's map from a router a run used, such as Dynamo's, to the nearest policy llm-d's router offers.
  • Age limit: the dashboard's rule, today, that scores only runs measured in the last 180 days (§3A.2).
  • Funnel: the count of units at each stage from the source to scored (§3A.6). Slice: the subset of points that share an attribute value, such as one chip (§3B).
  • Speculative decoding uses a small drafter model to propose tokens. DSpark is one drafting method. Acceptance is the share of drafted tokens the target model keeps.
  • Muse Spark: a model in the catalog (its open checkpoint is Muse-Spark-Open). TEP8 and DEP8 are two of the 8-GPU layouts its scenario files use: TEP8 shards attention with 8-way tensor parallelism and the experts with expert parallelism; DEP8 runs 8 data-parallel ranks, with expert parallelism for the experts.

Terms section DC adds.

  • Engine upgrade: porting the diff of the code an engine module already models (scheduler, KV-cache manager, connectors, defaults, lowering) from one upstream commit to another. It changes behaviour for every model.
  • Model support: work in an engine module for one model, needed only when that model brings engine-facing code of its own. DC1 lists the cases.
  • Onboarding a model: one to three pieces of work, done after any engine upgrade the model needs:
    • Catalog entry, always: the model's config.json, its catalog entry, and a graph handler if the architecture is new. A new kind of layer also needs new graph vocabulary. The engine must then learn to lower the new kind, and that lowering depends on the catalog entry.
    • Model support, when needed.
    • Coefficients. By design every kernel can be priced: when the registry has no exact entry, the cost model uses the most trusted one it has for that chip, at worst a roofline or an assumed entry, and the substrate must carry an assumed entry for every catalog chip in each family that has no roofline (design §9.2, VAL-2). So new entries are required only for a brand-new primitive family, and the cost model fails without them (blis-substrate kernel/new.go: "A missing coefficient … is an error rather than a default"). Elsewhere a fitted entry, written by its family's writer script (SUB-4), raises accuracy above the fallback.
  • Commit distance: how far a run's engine commit is from the modelled one, counted from their merge base: commits apart, and releases apart where the two commits are in different releases.

DC. Design changes M3.2 needs (proposal, for team review)

Status. The maintainer raised these on 2026-11-18 for the team to review. Nothing in this section is decided or built until the review closes. Each change to the standing design lands first as a blis-design pull request to main, then in code. Whether DC4 belongs in M3.2 or in a patch release of M3.1 is open.

Why. Three problems keep recurring.

  • Changes cross repositories in sequence. Most features touch the contracts, an engine and the simulator together. A change to blis-substrate is re-pinned in blis-vllm, blis-sglang and the router fork, then in inference-sim, with full CI at each step. In M3.1, blis-substrate#373 was first deferred because that sequence could not pass CI in every repository before the release. The per-pool offload fix took three sequential pull requests: blis-substrate#402, blis-vllm#302 and inference-sim#2252.
  • Teams ask for models that only an unreleased engine build supports (DC4).
  • The new data is pinned to engine commits, not releases. Nearly every vLLM CI perf row names a vLLM commit (a few say nightly or a release tag), and every SGLang nightly names an SGLang commit (§1, §2.3). BLIS models only releases, so it cannot fit against the exact engine code those runs used.

DC1. Model any upstream commit, not only a release (vLLM and SGLang)

Today. An engine module models one upstream release (LIF-5). A build runs one release of each engine, and a scenario that names another is refused (LIF-6). A run on another release is scored with a release difference, and graded G3 or G4 (COV-6, design §11.3 and §11.5).

Proposal.

  • An engine module models one upstream commit: a release tag, or a commit on the upstream's main or release branch. The Upstream record (the engine module's statement of what it ports) names the commit and the release it descends from. A build still runs one commit of each engine, so LIF-6's refusal stays, with a commit in place of a release.
  • An engine upgrade is ported as a diff, as the move from vLLM v0.32.0 to v0.33.0 was. Each engine module's generated lists (fields.json, surface.json, kernel_impls.json) are regenerated at the new commit, and the oracle environment is locked to it. Today the generators work at the tag level: gen_surface.py refuses a checkout at another commit, gen_kernel_impls.py needs one kernels/<tag>/attention.json per release, and gen_fields.py holds release-specific paths. They need work to take any commit.
  • Grading. A run on the modelled commit counts as the same build: it can reach G1 or G2. Any other run names its commit distance and is graded G3 or G4 as today. This changes the G1 condition (design §11.3: "the run's engine release is the one run by the inference-sim release doing the scoring"), design §11.5 and COV-6.
  • Model backport. For a model that lands upstream between upgrades, the upstream commits that add it are applied onto the modelled commit and listed in the Upstream record. A backport carries model code only, never scheduler, KV-cache or connector changes. It is dropped when the modelled commit contains it.
  • When to upgrade. On each upstream release, and on demand when a team scenario needs a later commit. Each upgrade re-runs the oracle and the goldens.
  • When a model needs model support. Only when it brings engine-facing code that an upgrade does not port. That code lives mostly in the model's folder upstream (for example vllm/models/inkling2/):
    • a KV-cache layout the engine module has not seen, as DeepSeek-V4's sliding-window cache and compressor were (blis-vllm core/kv/layers.go);
    • its own kernels, or a backend choice the engine module does not lower, as Muse Spark's fused kernels were (blis-vllm#272);
    • a new drafting method or scheduler hook. A model that brings none of these needs no model support. Onboarding it is the catalog entry, plus any coefficients its kernels lack.
  • Upgrade report. Each engine upgrade generates a report of the models the new commit supports. For each model it gives:
    • whether the catalog has it;
    • whether it needs model support, and for what. This comes from the regenerated lists, which must give every new entry a status (X9: every upstream feature is modelled, refused by name, or out of scope), and from the model's own code;
    • for each catalog chip, the coefficients it lacks: any brand-new primitive family it needs entries for, and the kernels it would price below measured or calibrated (transferred, roofline or assumed).
  • Answering a model request. The upgrade report answers in advance. For one model, simulating the requested scenario answers too: a missing catalog entry is refused by name (not_in_catalog), an engine refuses what it cannot lower, a brand-new primitive family with no entries is refused, and the Result (the simulator's output document) records each coefficient's method. No separate preflight command is needed (DC2).

Effect. A new model on upstream main can be supported (DC4). The vLLM CI perf and SGLang nightly runs can be fitted against the exact engine code that produced them (§1). A release difference becomes a commit distance, which is more precise.

DC2. Lowering out of blis-substrate, brought forward from M4

Today. The catalog's graph deriver, which writes each model's graph from its config.json, still holds vLLM lowering. On 2026-11-17 the plan moved two things from M3 to M4: removing that lowering, and the review set that removes contracts/rules/ and moves model values into graph fields. The design says a graph holds only what the checkpoint states (SUB-15). It also says onboarding a model is one blis-substrate pull request with no engine code (design §12.1, T-M1). Neither holds yet. The second can hold only for a model that needs no model support and no new coefficients.

Proposal. Three changes:

  • move all lowering into the engine modules;
  • drop the onboarding preflight command that design §12.1 describes (inference-sim onboard --plan, never built), because simulating the requested scenario, and the upgrade report (DC1), answer the same questions;
  • remove contracts/rules/, as a contract-change review set (design §12.8), if Q3 brings it into M3.2.

Effect. A new architecture built from existing kinds of layer is onboarded with a graph handler and data, and each engine lowers it with the lowering it already has. A new kind of layer still needs new engine lowering.

DC3. Consolidate blis-substrate, blis-vllm, blis-sglang and blis-kvstore into inference-sim

Proposal. Move the four repositories into inference-sim as top-level directories. Keep their history with a subtree merge, and transfer their open issues.

  • Every moved directory becomes a package of inference-sim's one Go module, the engines and blis-kvstore included. An engine module is then a directory, not a repository.
  • One part of contracts/ moves to the router fork instead: the hosting contract, below.
  • These stay separate repositories:
    • the router fork, a fork of llm-d that keeps upstream's import path;
    • accuracy-dashboard, because a scorer independent of the simulator is a deliberate audit property;
    • blis-config-search, which consumes simulator releases;
    • blis-design.

The hosting contract moves to the router fork, so the fork depends on no BLIS module. inference-sim imports the router fork. Today the fork, in turn, imports two BLIS packages, and only these two:

  • contracts/embed, the hosting contract: the interface between the simulator's sim/llmd/ (its clock, runtime, sessions and KV events) and the fork's pkg/embed;
  • contracts/conformance/embedtest, its conformance suite.

The fork's test TestImportsOnlySubstrateContracts (pkg/embed/imports_test.go) enforces that limit over every dependency, tests included (X7: dependencies point one way; the router card). The two packages import no other BLIS package. Together they are about 2,300 lines of Go (682 in embed, 1,661 in embedtest, tests excluded). In blis-substrate's history, 12 commits touched them, against 346 for the rest of contracts/. Those 12 changes, such as session headers and the engine that published a KV-event batch, came with changes to the fork.

So under DC3:

  • The hosting contract and its conformance suite move into the router fork as new files, in a directory of their own (for example blisembed/). The fork's patch budget counts only lines changed in files it shares with upstream llm-d, and new files are free (hack/hosting-lint/budget.txt), so the move costs none of it.
  • The fork then imports no BLIS module, and inference-sim imports the hosting contract from the fork, through the one replace it already has (X11). Every dependency points from inference-sim to the fork, so there is no cycle.
  • The fork's import test changes to forbid every github.com/inference-sim/ package.
  • The contract keeps its rules: it changes only compatibly (SUB-1), and its conformance suite runs in the fork's CI, as it runs against the fork today.
  • A change to the hosting contract lands in the fork first, and inference-sim then moves its pin. That is how a change to the router lands today.
  • The rest of contracts/ stays in inference-sim, as plain packages of its one module. No second module, no second replace and no new pin check is needed.

The cost is one oddity: the contract is BLIS's, but inference-sim imports it under llm-d's module path (github.com/llm-d/llm-d-router/blisembed), because the fork keeps upstream's path.

Two other placements were considered. Making all of contracts/ a nested module in inference-sim also avoids a cycle, but it needs a second, local-path replace, an exception to X11, and a check that the fork's pinned commit is an ancestor of the simulator's. Moving all of contracts/ into the fork would send every engine, cost-model and scenario contract change through the fork, which rebuilds the sequence DC3 removes, and would put BLIS's core interfaces in a repository whose job is to track upstream llm-d. A third way, keeping every repository and removing the sequence with tooling, is open question Q4.

What changes. One pull request can span the contracts, an engine and the simulator. The bottom-up merge order (X10) and the sequence of pins between BLIS repositories (X11) go away; the one remaining pin is inference-sim's pin of the router fork. Per-engine release branches (design §14.4) become release branches of inference-sim, which already cuts release-v0.18. The rule that blis-substrate is one Go module (SUB-13) becomes the same rule for inference-sim. A model's catalog entry, model support and coefficients become one pull request.

What is lost. The boundary between repositories. A simulator change could edit catalog data in the same pull request, so the lints and CODEOWNERS must do what the boundary did. Each repository's merge rules, checks and workflows have to be consolidated.

Timing. If adopted: at a release boundary, as the first M3.2 item, because DC1 and DC2 are easier in one repository. The migration is not sized yet. A sizing from the actual workflows, checks and open issues comes before the decision.

3A.9 Proposal. Treat the dump as frozen, and reconcile it with the live API. InferenceX published a dump weekly from April to September 2026, and none after db-dump/2026-09-28. The pinned dump is now a fixed source whose runs are on ever older vLLM and SGLang releases, while every new run comes only from the API. The rule that splits record ids between them (the dump owns ids up to the cutoff, supplements own the ids above it) does not state that the dump is final. To apply:

  • Treat the dump as a frozen archive. It is the only copy of history before 2026-09-28, including measurements the API has superseded and no longer serves, and it will not grow. All new coverage comes from §3A.1's automatic API supplements.
  • Give each benchmark run one measured_date, across the cutoff. A benchmark run's date is the earliest date over all its records. Ingest already reads the dump and the API supplements together, so a run with early records in the dump and later ones on the API keeps one date, and its units keep one identity (blis-substrate ledger/cmd/ledger/main.go appends supplement rows before inferencex.Ingest; the dashboard's pull takes the date from the ledger). §3A.1's automation must keep that: it must never ingest new API rows apart from the dump. A test should pin it, with a run whose records straddle the cutoff and whose units keep one date.
  • Grade old runs by their release difference. Dump runs on old releases carry §3A.5's release difference. Under §1.4, their training shares feed calibration. Their anchor share counts in the headline at its grade (§3A, the maintainer's decision), and their held share in pre-registered evaluations. The same-release figure is a slice (§3B).
  • Show the split. Keep each point's source (dump or api) and its release difference, and have §3A.6's funnel and §3B's slices report what share of the held-out units comes from the dump and what share from the API. A headline dominated by old dump runs is then a stated number.
  • Never re-pull a dump row from the API. The API and the dump can report the same row's numbers differently: the dashboard nightly already marks 5 units row_differs_from_ledger. The API also lacks the dump's superseded history. Keep the id split.

3B. Slice accuracy by any recorded attribute

Maintainer. As more sources come in, accuracy must be sliceable by all their data attributes. A version of this exists today.

Today the dashboard nightly's summary breaks counts down by engine, engine release, chip and grade, and the dashboard filters only on multi-node runs and on the estimate tier (whether a point's values were estimated), over a fixed grouping by model, hardware and framework.

Proposal. Every scored point carries its attributes, and the dashboard filters and groups by any of them, with every aggregate recomputed from the points that remain (as filter.ts already does):

  • source and role;
  • model, precision, chip, node count, interconnect;
  • engine, engine release or commit, and its release difference (a commit distance under DC1);
  • topology (TP, DP, EP, P/D pools), speculative method, offload and KV tiers, router;
  • workload type, ISL and OSL, concurrency, arrival process, prefix sharing;
  • measured date;
  • grade, and each substitution named on the point.

Each slice shows its point count and coverage beside its accuracy, so a small slice cannot pass for a strong result.

Proposal (accepted; raised in team review). The rule for small slices. min_points is 10. Today the dashboard shows a bare "too few points" for any figure over fewer than 10 points, while the per-point table below it still lists every measurement, so the two appear to disagree, and the label covers most fine slices. The rule:

  • the point rows stay visible at every count;
  • an aggregate accuracy figure is never shown below min_points, at any level, from the headline to a drilled-in slice, and an aggregate not shown is excluded from every verdict;
  • in its place the dashboard shows the count (n=3 · mean withheld), and the per-point table states the rule;
  • the threshold stays at 10, and a test pins the behaviour.

An earlier idea, to stop applying the rule in a drilled-in slice, is dropped: it let a small slice look like strong evidence. Tracked in accuracy-dashboard#160.

3C. configiq: settings and closeness

Evidence: evidence/CONFIGIQ-FINDINGS.md (Red Hat's repositories, read on 2026-11-18; the parser's regular expression and forge's cpt.yaml checked by hand). The configiq team's answers are still pending, and they override anything inferred here.

Three things write configiq's rows: forge (openshift-psap/forge, Red Hat's open-source benchmark launcher), manual imports, and Model Furnace (an earlier, private Red Hat launcher). The publisher keeps a filtered copy of Red Hat's private results CSV.

Correction to how BLIS reads blanks. BLIS treated a blank engine column as "not recorded" unless the row matched a forge preset. A blank means the flag was not passed only for rows forge wrote. The publisher extracts settings from a free-text runtime_args field with a regular expression, which misses space-separated values and bare flags. So a blank in a manually imported or Model Furnace row can hide a value the run set. A blank prefix_caching never means "on".

All of §3C is proposal, pending the team's answers.

3C.1 Classify each row by its writer. The counts are on the current dataset revision, which has 1,710 whole-run units; the ledger's pinned revision has 1,702. Family A is forge's, recognised by a /v1/... request type and prefix caching on: 779 units, 373 of them on H200 or B200. Family C is manual imports: 128 units. Family D is Model Furnace and older manual imports: 803 units. No family B was found. The family decides how blanks are read.

3C.2 Family A: fill every blank from forge's own records, each named as the substitution it is:

  • the CPT matrix (forge's per-model test matrix, cpt.d/cpt.yaml) and the presets at the commit in force on the run's date, matched on model, TP, KV dtype and request type;
  • vLLM's defaults at that release and device, for flags forge never passes (max_num_seqs, chunked prefill, max_num_batched_tokens, precision);
  • the run's frame from forge's history: a concurrent load profile, a measurement duration of 275 s from 2026-09-22, the warm-up and ramp-up then in force, the GuideLLM release, seed 42, ignore_eos, and streaming.

This replaces today's preset match, which misses cpt.yaml.

3C.3 Family D: fill only what the public benchmark guide and Model Furnace's defaults support. That is prefix caching off, and a measurement duration of 450 s or 600 s, when max_seq_len is 8192 or 10000 and memory utilisation is 0.92. These are estimated substitutions and lower the grade. Rows whose TP is 1 may have used data parallelism, and stay unscored.

3C.4 Check each filled frame against the data. The measurement duration derived by Little's law from the concurrency-1 row must agree with the frame used. Only successful requests are compared.

3C.5 Model each configiq workload as it ran: the multi-turn shapes (benchconf's interactive-chat, with a first prompt of about 4,000 tokens and 45 s between turns) and the prefix workloads.

3C.6 Pin the dataset revision. The dataset is not append-only: 444 rows were removed between two revisions.

3C.7 Ask Red Hat, beyond the questions the maintainer already sent (§3A.7), to:

  • publish an allow-listed runtime_args, the image tag, the GuideLLM version, the cluster tag, the start and end times, DP and the turn index;
  • fix the case mismatch that drops DP;
  • publish more of the roughly 52 models their internal CSV holds.
