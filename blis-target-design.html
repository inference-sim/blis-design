BLIS Target Design

How the BLIS repositories are divided, what each one owns, the rules that keep them correct, and how we upgrade them when vLLM, SGLang, llm-d or our data change.

Status Standing design: true for every release Scope the llm-d stack, with vLLM or SGLang as the engine Companion each release has its own release plan, which schedules the work this design requires

What BLIS is. BLIS simulates an LLM serving cluster. It runs two kinds of code: the router of llm-d, a Kubernetes-based stack that routes requests to vLLM or SGLang engines, unchanged; and Go ports of the vLLM and SGLang engines. Each port covers the engine's scheduling, its KV-cache management, its KV transfer and tiering, and how it resolves its settings and chooses its kernels (§7.1). Each is tested step by step against the engine's own code. A cost model, built from published hardware facts and fitted coefficients, prices every step. This document describes the shape BLIS has, the rules that keep it correct, and how those rules are checked. It holds for every release. What a particular release does to reach it, and when, is in that release's plan; §1 explains how the two documents relate.

The main ideas.

  1. One repository, blis-substrate, holds everything that is true whatever engine runs: the shared contracts, the published facts, the fitted coefficients and the cost model. Each other repository tracks one upstream or serves one purpose, and every kind of work has exactly one owner (§2.2).
  2. Engines hand the cost model a fully resolved description of what runs, so the cost model does not depend on which engine produced it.
  3. Every upstream release gets a list of its features, generated from the upstream's own source. Each feature is modelled, refused by name, or declared out of scope, and CI fails while any feature has no status. Missing features are then counted and ranked, instead of being discovered only when someone needs one.
  4. Every coefficient the cost model needs has a value, labelled by how it was obtained: measured, derived from a roofline, taken from published work, or borrowed. Coverage can then grow without hiding how good each estimate is.
  5. The simulator follows explicit rules for a discrete-event simulation and for analysing its output, so its figures are reproducible and carry their uncertainty (§8).
  6. Every rule in this document has an identifier and a repository that runs its check. Automated checks enforce every rule that can be checked mechanically. Agents do scoped tasks that must pass those checks. People answer the yes/no questions that need judgement (§13).

1How to read this document

Words. MUST, MUST NOT and SHOULD mean what they mean in RFC 2119. An invariant is a statement about the repositories that every merged pull request and every release keeps true.

Registries. Three things in this design are called registries, and the word is never used alone. The coefficient registry is the substrate’s fitted and assumed coefficients, with their provenance (blis-substrate/registry/, the --registry flag); it is what --catalog is paired with. The invariant registry is the project’s rules, each with its statement, checks and status (blis-substrate/contracts/invariants/, §13.1). The metric registry is the definition of every metric a Result may report (contracts/metrics, §8.7). An upstream’s own tables are called registration tables, and engines are said to register a factory, not to be in a registry.

Identifiers. Every invariant has a short identifier, such as X3 or SUB-4. Pull requests cite these identifiers, and CI checks that every cited identifier exists (§13). The prefixes are:

How a rule is enforced. A rule is one of three kinds, and the design says which (§4.2). An automated rule names a deterministic check, and the repository that runs it, which fails the pull request, the nightly run or the release when the rule is broken. A maintainer practice is a rule a person with write access keeps for a repository as a whole, such as its branch protection, who may cut a release, and signing; it is stated once, with a checklist, and no program in another repository audits it. Agent guidance is a rule an agent follows on every change it writes or reviews, and is rendered into each repository’s AGENTS.md. Where a rule depends on judgement, a review question is written for it. A review question is guidance for the review agent, which applies it to every pull request it reviews and answers it in a review comment with a reason and the lines that support it (§4, §13.2). It is never a check: it fails no CI job and waits for no person. The one reviewer with write access reads the agent’s answers as part of reading the change.

This design and the release plans. This document is the standing design: every statement in it holds for every release, and it says what must be true, not what is true at the moment. It contains no dates, milestones or status. Each release has a separate release plan, which records where the repositories stand, schedules the work that brings them in line with this design, and lists the release's open questions. A plan may schedule invariants and may relax one temporarily, naming it and the milestone at which the relaxation ends, but it may not create a rule. A new rule enters this document first, with an identifier. Each plan's status table is generated from the invariant registry (§13.1), so a plan and this design cannot disagree about which invariants exist.

Two short companions. The design is a reference, about ninety printed pages. Two summaries sit beside it for a reader who knows llm-d and vLLM and wants the shape of the simulator first: a three-page summary of the architecture and the seven-page summary of it with the detail a contributor needs before changing code. A page is a standard print page (US Letter, 0.9 inch margins, 10.5 point text). The page limits are part of the design: a summary does not grow when the design does. A design change that belongs in a summary takes the room of something that matters less to its reader, and a change that fits neither is left to the design alone. Each summary states no version, count, date or milestone, links every claim to the section that states it, and defers to the design where they differ. A section a summary cites keeps its number.

Citations. Claims about upstream code cite a file and line range at a pinned release. The releases and commits are the ones stack.json records for each engine and for the llm-d router. When an engine repository moves to a new upstream release, the citations that describe its behaviour move with it. A claim drawn from reading code that a recorded run has not confirmed is marked inferred.

2.2 Where a fact belongs

Every fact, rule and value has exactly one owner. To decide which, ask what the fact depends on:

  • If its value changes when an engine releases a new version, it belongs in that engine's repository, on the branch that models that release (§14.4).
  • If it changes when llm-d releases a new version, it belongs in the router fork.
  • If it changes with the simulator's own design, it belongs in inference-sim.
  • Otherwise it belongs in blis-substrate: it is true of the hardware, the model, the physics or the data, whatever engine runs.

To check a change to the substrate, ask whether a second engine would need the same edit. If not, the change belongs in an engine repository.

The same rule applies to work, not only to facts. Each kind of work has one owning repository, and no other repository holds a second copy of it. Another repository that needs the work calls the owner's command or imports the owner's package.

3blis-substrate

3.1 Why one repository

The substrate has four parts: the contracts and data types, the catalog of facts, the coefficient registry, and the cost model. They change together:

  • A model whose architecture is already supported needs only a catalog entry. A model with something new in its architecture usually needs a new data field, a catalog entry, new coefficients and a change to the cost model, all at once.
  • The data are validated by the contracts' validators, and the cost model is tested against the data. If the parts lived in separate repositories, each change would be released in order, each release would force the next repository to update its pin, and consistency would rest on vendored copies and lock files. The release plan's background describes what that cost when the parts were separate.

In one repository, such a change is one pull request, one review and one release. Each release also embeds its own data, which is small enough to compile into the program. Paths still override the embedded copy, so a data-only recalibration that the released validators accept needs no rebuild (§3.3).

The substrate is one Go module, tagged vX.Y.Z. One commit gets one tag. Every repository that uses the substrate pins a version of it.

The module has two kinds of package:

  • Packages under contracts/ hold interfaces, data types, validators of those types, conformance suites, the engine harness and the invariant registry. They import only the Go standard library, the YAML parser and each other. The engine repositories and the router fork import only these packages, and an import test in each of those repositories enforces it.
  • All other packages hold the cost model, the catalog and coefficient registry validators, the data loader, and the embedded data. Only inference-sim imports them.

Why a refit needs no engine or router release. Suppose blis-vllm pins substrate v1.2.0 and inference-sim pins v1.5.0, which carries new coefficients. Go builds every module in a program with the newest version any of them requires, so inference-sim's build uses v1.5.0 for blis-vllm too. The packages under contracts/ change only compatibly, except through a contract-change review set (a group of pull requests across repositories, reviewed and released as one change), which releases every implementer together (SUB-1, §12.8). So blis-vllm compiles against v1.5.0 unchanged, and no new blis-vllm release is needed. The nightly compatibility build (§13.4) confirms that every repository, at the tag the newest inference-sim release pins, still compiles and passes its tests against the newest substrate.

Engines must not move the simulator's data. The same rule works in reverse: if an engine required a newer substrate than inference-sim does, the simulator would be built with that newer substrate, and its embedded coefficients would change because of an engine release. To prevent that:

  • An engine or the router fork requires the oldest substrate version whose contracts/ packages it uses. It never requires a version newer than inference-sim's current requirement; the release bot refuses such a release. When an engine needs a newer contract, the release bot moves inference-sim first, in the same review set. On a release branch (§14.4) the bound is the substrate requirement of the inference-sim release branch the fix ships in. A fix that needs a newer contract moves that branch to the newer substrate first, in a PATCH release whose notes carry its price-change report. A fix that would need a substrate past an incompatible contract change is not backported.
  • Before every inference-sim release, go test runs every engine and router package in a scratch copy of inference-sim's module, with test dependencies added, so each is tested against the substrate the simulator actually selects (LIF-2).
  • inference-sim's own requirement on the substrate must equal the version its build selects. If a dependency raises it, the build fails until the release bot re-pins inference-sim, which produces the usual price-change report (LIF-2).

What one module costs. A repository that pins the substrate downloads all of it, mostly vendor config.json files (the release plan's evidence gives the size at the time of that plan; Go's limit for a module is 500 MB). Go compiles only the packages a program imports, so an engine build never compiles the cost model or the embedded data. A CI check fails if the module exceeds 100 MB uncompressed, well before Go's 500 MB limit (SUB-13).

3.3 Data: a path first, the embedded copy as the default

The catalog and the coefficient registry reach a running program in one of two ways. Both are always available, and every run records which one it used.

  • A path. --catalog <dir> and --registry <dir> (or BLIS_CATALOG and BLIS_REGISTRY) name directories with the same layout as blis-substrate/catalog/ and blis-substrate/registry/, such as a checkout, a working tree or an exported revision. When a path is given, the run uses that directory instead of the embedded copy. Recalibration uses this. A fitting script writes candidate coefficients to a directory, and the released simulator scores them with no rebuild. Comparing two coefficient registries means running one binary twice with two paths.
  • The embedded copy. When no path is given, the run uses the data compiled into the substrate with go:embed. A release therefore carries the exact data it was tested with, and a user of a released binary needs no checkout. inference-sim cannot be installed with go install …@version, because Go refuses that for a module whose go.mod has a replace directive, and inference-sim carries one (X11). So each release ships signed binaries for the three supported platforms, with the provenance and bill of materials of X21. A source build needs a checkout at the tag.
  • What stays fixed. A model runs only if it is in the catalog in use, and it is resolved from its graph.yaml. A missing model is refused with the catalog's source (the embedded release, or a path) and the relative path its entry belongs at. No run creates or changes catalog or coefficient registry files, no run fetches anything from the network, and the deployment always comes from a required scenario.

The two flags are independent. A run may, for example, use the embedded catalog with a candidate coefficient registry.

Private additions. To run a private model against released data, --catalog-overlay <dir> and --registry-overlay <dir> add entries to the data in use. An entry is identified as follows:

  • In the catalog, a whole model directory (models/<name>/), or a whole hardware, device, network or workload file.
  • In the coefficient registry, one coefficient, identified by its set, its name, its scope and its method.

An overlay entry with the same identity as an existing entry replaces it; any other entry is added. The combined data are then validated in full, including the rules that each lookup has at least one entry (VAL-2) and at most one per rank (VAL-4). An overlay may not contain ledger files.

Overlays have their own flags because a recalibration candidate replaces the whole coefficient registry. If one flag could either replace or add to the data, an A/B comparison would be ambiguous.

Which files count as data

The file patterns are defined once, in the substrate's top-level package (data.go). That package must sit at the top of the repository, because Go's go:embed can only embed files at or below the package's own directory. The patterns are: hardware, devices, networks, workloads, measurement sources, each model's model.yaml and graph.yaml, every coefficient set, and acceptance and routing profiles. Most of the ledger is not runtime data: pricing never reads it, and it can be large, because it lists every unit. Seed-holding jobs (the CI jobs that hold the secret used to assign data roles, §10.2) read it from a checkout of the repository at the substrate tag they use, including those in accuracy-dashboard. The exception is the three published role lists (catalog/ledger/published/), which are embedded so that inference-sim ledger can print them offline.

The go:embed directive must list literal patterns, so a test checks that they equal the loader's. A path is read with the same patterns, and the loader refuses anything that would make the data ambiguous:

  • a file under a data directory that matches no pattern, such as coefficients/x.yml where .yaml is expected. Ignoring it would silently drop a candidate's change.
  • a symbolic link;
  • a data file containing a carriage return;
  • two paths that differ only in letter case.

The data directories are exactly those the patterns in data.go name. Files outside them, such as scripts and documents, are ignored. Two things inside them are ignored by name: a model directory's config.json, and everything under catalog/ledger/ except published/. The check that graph.yaml's recorded derived_from hash matches config.json runs in the validators, in CI, not in the loader. So a path load and an embedded load validate the same files in the same way (SUB-9).

Vendor config.json files are not data in this sense. They stay in the repository for provenance and for the graph deriver, but the runtime never reads them. Every model value the runtime needs is a field of the graph, written by the deriver from config.json and the safetensors headers. No runtime code reads config.json, no model value is hard-coded in the cost model or an engine, and no user is asked to copy a value from a checkpoint into a setting (SUB-3).

Recording what was used

Every run computes a content hash for each of the catalog and the coefficient registry. It lists every data file as <sha256 of the file's bytes> <path relative to the catalog or registry directory, with forward slashes>, sorts the lines by path in byte order, ends every line, including the last, with a line feed, and takes the SHA-256 of the result. The loader refuses carriage returns, so the hash is the same on every machine. The Result document records, for each of the catalog and the coefficient registry:

  • its source: embedded or path;
  • its content hash;
  • the hash of each overlay, and the hash of the combined data. With no overlay the combined hash is the base hash. Otherwise it is the SHA-256 of the line <base hash> base followed by one line <overlay hash> overlay for each overlay in the order applied, each line ending in a line feed, so it names the base and every overlay and their order.

It also records the build the simulator came from: a tagged release, or unreleased.

A run uses released data when all of these hold:

  • the simulator is a tagged inference-sim release, whose stack.json names a tagged substrate release;
  • the catalog and coefficient registry hashes equal that substrate release's embedded hashes;
  • no overlay is used.

Every other run is experimental, including every run from stack CI, a local build or go run. Only released-data results are published (X8).

Checking data at load

Whatever its source, the data is validated when it is loaded, by the same validators CI runs. That includes the checks between the catalog and the coefficient registry, for example that every chip a coefficient names exists in the catalog in use. A candidate coefficient registry that does not fit the catalog it runs with is refused.

Each run also reports which coefficient registry entries were selected (a lookup returned them), and which coefficient files were never loaded. The report covers every reader behind the Environment, including acceptance and routing profiles. Without it, a candidate that adds a coefficient family no released code reads would be silently ignored and would look like a no-op. The landing gate uses this report (VAL-6).

The ledger in a candidate

A candidate may add data units, for example after a data drop. The gate and select jobs read units from the candidate's tree and compare them, by unit_id, with the ledger at the pull request's merge base:

  • a new unit has its role drawn by the job;
  • a unit_id present at the merge base but absent from the candidate is refused, unless an alias table or a new partition version covers it and a person has approved it. A unit whose identifying fields changed shows up exactly this way, because its unit_id is a hash of those fields.

Roles are never read from a file (D4), so a candidate cannot change which units are held out.

4Rules that span repositories

These rules hold across the whole system. A pull request that breaks one must not merge, whatever its tests show. Each rule lists its target checks, the repository that runs each check, and the review guidance that remains.

Review guidance is reserved for questions that need judgement. A question is guidance for the review agent, never a check. When a pull request changes something a question covers, the review agent answers it in a review comment, yes or no, with a reason and the files and lines that support it. No CI job fails or waits on a question, and no person has to answer one. The question’s Expertise line names the knowledge the agent brings, not a group of people. An answer in the unwanted direction is a finding, which the one reviewer with write access reads with the rest of the review (§13.2).

The test. A rule is automated when a program can decide it from the repository’s own contents and the repositories below it, the same way release after release, and when running it needs no knowledge of a repository above it. A rule about the repository as a whole, about who holds a permission, or about an act only a person can perform is a maintainer practice. A rule that shapes how a change is written or judged, and that a program cannot decide, is agent guidance. A rule can be both: a program checks the form of a commit message while an agent follows the convention that produces it, and a person signs the commit.

Dependency direction holds for all three. An automated check reads only its own repository and the repositories it depends on (X7). A check in one repository never reads the settings, branches, issues or workflows of another, and no job exists to audit a practice from a different repository. A practice is kept in the repository it concerns, in that repository’s own settings and documentation. Agent guidance names only what the repository it is rendered into may know. A program is added for a rule only when the rule is deterministic and local; complexity, or a link between layers that the dependency direction forbids, is a reason to keep a rule a practice.

6The boundary between engines and the cost model

6.1 The rule

Only an engine repository knows its upstream, so only it works out the engine's behaviour: defaults, backend choices, padding and graph-capture sizes. It hands the cost model three plain objects, described in physical units (bytes, tokens, ranks), never in an engine's vocabulary: a PoolPlan, a StepShape, and an engine.Transfer for each KV move. The cost model never sees an engine's settings and never applies an engine's rules (SUB-6).

6.2 The plan and the step shape

Both are defined in contracts/engine. Every field added later must keep its zero value meaningful, so the contract only grows (SUB-1).

// PoolPlan is fixed for the life of one engine pool.
type PoolPlan struct {
    Hardware string         // catalog chip name
    Fabric   string         // catalog network name; "" on one node
    Layout   Layout         // tensor, pipeline, data, expert and context parallel widths, and rank placement
    Layers   []LoweredLayer // one entry per (layer, primitive)
    KV       []KVGroup      // per cache group: bytes per page, tokens per page, full or sliding window
    KVBudget []int64        // bytes per rank available for KV, one value per pipeline stage
    Tiers    []KVTier       // the KV tiers below GPU memory, as the engine resolved them
    Graphs   GraphPolicy    // CUDA-graph buckets, keyed by token count or by batch size
    Drafts   DraftPolicy    // speculative decoding: chain length, or tree (top-k × steps)
    DraftLayers []LoweredLayer // the draft model's own layers, lowered like the target's
    Host     HostPlan       // per-request and per-token host work (admission, sampling, detokenizing)
    Weights  []ResidentTensor // per rank: shape, stored data type and sharding, after weight post-processing
    Buffers  []Buffer       // engine-chosen buffers and workspaces, sized as the upstream sizes them
    InFlight int            // most steps in flight at once; 1 without asynchronous or overlap scheduling
}

type LoweredLayer struct {
    Layer      int          // index in the model graph
    Stage      int          // pipeline stage that runs it
    Primitive  string       // from a fixed list: "attention.decode", "gemm", "moe.grouped_gemm", "all2all", …
    KernelImpl KernelImpl   // what executes it; the registry looks coefficients up by this
    Shape      PrimitiveShape
    Collective *Collective  // group, bytes, and whether it crosses nodes
}

type KernelImpl struct {
    Library  string         // from a fixed list in contracts, e.g. a named attention library
    Variant  string         // the library's own exported kernel name; an engine's backend names map to it in the engine's lowering
    CodeHash string         // hash of source and target GPU architecture, or of a binary library (below)
}

type KVTier struct {
    Device   string         // catalog device name, e.g. host DRAM, local NVMe
    Bytes    int64          // capacity per rank, as the engine sized it
    Shared   bool           // one copy per node rather than one per rank
}

// StepShape is one engine step on the data-parallel ranks that run in lockstep, already padded by the engine.
type StepShape struct {
    Mode      StepMode      // Mixed, ExtendOnly, DecodeOnly, Verify, Prebuilt or Idle
    Ranks     []RankStep    // per data-parallel rank in the lockstep group: each request's scheduled and cached tokens
    Padded    []PaddedShape // per rank: the shape actually launched (graph bucket, padding)
    Drafts    DraftShape    // tokens drafted and verified this step
    Stage     int           // pipeline stage; 0 without pipeline parallelism
}

Prebuilt is SGLang's P/D decode merge: KV arrived from the prefill pool, so the step runs no forward pass. It still has scheduler and host cost, which the cost model prices.

PaddedShape also records how the step launches: a full CUDA-graph replay, a piecewise replay with some layers run eagerly, or a fully eager run. These have different costs, so the engine states which one applies.

These definitions imply five rules:

  • The engine pads the batch, and the cost model prices the padded shape. vLLM pads in its model runner, to token-sized graph buckets and data-parallel padding rules. SGLang captures decode graphs by batch size. Each engine reports the shape it launches in Padded. When data-parallel ranks run in lockstep, padding depends on every rank's tokens in the same step, so a StepShape describes all the ranks that run in lockstep. The engine decides which ranks those are. In vLLM v0.32.0, data-parallel ranks run in lockstep only for mixture-of-experts models; for a dense model each rank is an independent engine (v1/engine/core.py:1473-1481), so its StepShape has one rank.

  • The engine names the exact kernel implementation. SGLang, for example, picks an attention backend per chip and model, and forces a page size of 64 for FlashMLA (arg_groups/overrides.py:1146-1154). The engine's lowering records that choice in KernelImpl, and the coefficient registry prices that exact implementation.

    The coefficient registry's lookup key uses a hash of the kernel's source (the kernel hash, CodeHash), not a package version. Engines pin library versions in their lock files (vLLM v0.32.0 pins flashinfer-python==0.7.0.post1), and those versions move often without changing a given kernel. A coefficient lists the kernel hashes it is valid for. A version bump that leaves a kernel unchanged therefore needs no substrate change. A kernel whose source changed gets a new key, and the substrate must supply a value for it (§9). Libraries shipped only as binaries, such as cuBLAS, cuDNN and FlashInfer's precompiled kernels, are keyed by the SHA-256 of the shipped library file together with the target GPU architecture. For a kernel built from source, the hash covers the source and the target GPU architecture. A compiler or CUDA toolkit change can change a kernel's speed without changing its source; the engine records the toolkit version with each kernel implementation, and the coefficient registry treats a toolkit change like a library change that leaves the source alone: the entry stays, and the landing gate (VAL-6) shows whether the old value still holds. Each engine release ships a generated table, kernel_impls.json, of every kernel implementation it can emit, for its pinned library versions and for every library version seen in InferenceX runs. Runtime tuning (autotuned launch configurations, library heuristics, and tuned-configuration files such as vLLM's per-GPU fused-MoE configurations) is part of the implementation's measured behaviour, not a separate key. If a lookup has no entry for an exact implementation, the cost model takes the most trusted entry §9.2 offers for that chip, at worst the primitive family's roofline or assumed entry, and the price records that method (VAL-3). Kernels that ship inside an engine, such as vLLM's custom all-reduce, use the library names vllm-csrc and sglang-kernel. These are library names, and the engine-name check (X2) allows them as such.

  • The engine decides which KV blocks move between tiers, and the substrate prices each move. Which blocks move between GPU memory, host memory and storage, when, and under which policy, is engine behaviour: vLLM's offloading connector and tiering factory, SGLang's HiCache. The engine reports each move as an engine.Transfer. The cost model turns each transfer into a demand: bytes per link, from catalog device facts and coefficient registry tier coefficients. The engine returns its transfers to the simulator with each step. The simulator asks env.TransferDemand for each one, which returns the bytes each link must carry.
  • Sharing a link over time is the simulator's job. A transfer can span many steps, and several transfers can share one link. Dividing a link's bandwidth among concurrent transfers depends on when they happen, so it belongs to the simulator's event loop. This is the one place the simulator does resource arithmetic, and X3 states it as the only exception. Everything else about tiers comes from the engine or the cost model: capacity, bytes per block, and which blocks move.
  • The engine combines pipeline stages. With pipeline parallelism the engine emits one StepShape per stage. The cost model prices each stage alone. How stages overlap, and where bubbles occur, is the engine's batch-queue behaviour, so the engine combines the stage times and reports them to the simulator.

6.3 How an engine is built: two phases

An engine cannot size its KV cache without knowing how much memory the model's weights, activations and buffers take. That is the cost model's arithmetic. The cost model, in turn, cannot price a step without the engine's plan. inference-sim breaks the loop by giving the engine an environment when it builds it:

// contracts/engine: what an engine may ask of the substrate while it is built and run.
type Environment interface {
    Graph(model string) (*model.Graph, error)          // the catalog's model graph
    Chip(name string) (*hardware.Chip, error)          // catalog hardware facts
    Memory(partial PoolPlan) (kernel.MemoryBreakdown, error) // weights, activations, buffers; per stage
    Price(plan PoolPlan, step StepShape) (kernel.StepEstimate, error)
    TransferDemand(plan PoolPlan, t Transfer) (kernel.TransferDemand, error)
    Acceptance(model, drafter, workload string) (acceptance.Profile, error)
}

// engine.New builds an engine for one pool.
func New(spec Spec, env Environment) (Engine, error)

Construction then runs in two phases:

  1. Plan. The engine resolves its configuration and lowers the model into a partial PoolPlan, one whose KV budget is still empty. The partial plan carries the engine's own profiling step shape (in vLLM, the shape its memory profiling run uses; in SGLang, the shape behind its reserve formula) and the set of graphs it will capture. The engine states the resident weights and the buffers it chooses in the partial plan. env.Memory sums their bytes, and sizes the activations of the profiling shape and the graph pools. Choosing the profiling shape is engine policy; the cost model only sizes the shape it is given. The engine then applies its upstream's budget rule, such as vLLM's gpu_memory_utilization or SGLang's mem_fraction_static, and fills in KVBudget.
  2. Run. Each step, the engine forms a StepShape and asks env.Price for its time.

inference-sim implements Environment using the substrate's cost model and data loader. Engines therefore import only packages under contracts/, yet run against the released catalog, coefficient registry and cost model. Engine tests use a small reference implementation in contracts/conformance, which prices from fixed test values.

7.6 Port a shared framework before the features built on it

Connectors, tiers and KV-cache managers are built on shared frameworks. In vLLM these are the connector base class; the offload spec, manager and tiering layers; and the KV-cache coordinator with the manager base class, which every spec type's manager extends. In SGLang they are the HiCache controller and storage interface, and the tree-cache interface with the allocator and memory-pool base classes. Porting one framework completely, with recorded traces of its contract, makes each further connector, tier or manager a smaller change. Without it, each one is a large port of its own. Engine repositories therefore port a framework as a unit before porting the features built on it.

8Simulation method

BLIS is a discrete-event simulator: it moves simulated time from one event, such as a request arriving or a step ending, to the next. Between events, state either stays fixed or changes at a known constant rate. This section states the rules such a simulation must follow, whatever engine it runs. It takes its terms from DEVS, the Discrete Event System Specification introduced by Bernard Zeigler. The rules cover which part of the system may change state and when, what happens when two events fall at the same instant, how random numbers are drawn, and what a run measures. The table gives each term with its meaning in BLIS.

8.1 Components and how they couple

Each component changes its state only through its three transitions, and sends messages only through its output function. The output function runs on the component's state just before an internal or confluent transition, and every message it sends carries that instant's time. An external transition sends nothing. A component that must answer a message at once, as the router answers a request, schedules an internal event with a time advance of zero and sends its answer then.

Between events a component's state is constant, or changes at a constant rate. A link is the one component of the second kind: its state is the set of transfers in progress and the bytes each has left, and its time advance is the earliest time a transfer finishes under the current sharing of the link. Every start or end of a transfer, and every step that starts or ends a cross-domain collective, is an event that recomputes the rate of every other transfer on the link.

Components interact only through messages. No component reads another's state directly. The router learns about an engine only through the metrics and KV events the engine sends, at the times it sends them, after the delay the deployment's scrape and event-delivery settings impose. This rule lets each component be tested alone and then together.

Within a component, nothing depends on goroutine scheduling, the system clock or the order of iteration over a map. Concurrency inside a component, such as the router's background work, runs on the simulated runtime, which serialises it (RTR-7).

8.2 One instant

Many events fall at the same simulated instant, for example a step ending as a metrics scrape is due. BLIS processes an instant in the way Parallel DEVS defines, in three phases:

  1. Every component whose internal event falls at this instant runs its output function.
  2. Each component receives the bag of every message addressed to it at this instant. BLIS sorts the bag by the key below, so a transition that reads it in order is deterministic.
  3. Each component then makes exactly one transition: confluent if it had both an internal event and messages, internal if only the first, external if only the second.

So no component sees another component's state change from the same instant before making its own. The messages a component receives at one instant are ordered by a key: (time, class, sender, the sender's own count of messages sent). The class is a fixed order of message kinds, such as "transfer complete" before "new request". Each class's position is stated with its reason, and a change to the order is a change to the model (§8.9). The key contains no global counter, so it depends only on what each sender has done, not on the order in which the simulator happened to schedule things. Two messages with the same key are a defect.

A component's confluent transition says what it does when its own event and a message coincide. For an engine, this follows from where the upstream's loop reads its input queue, not from a choice BLIS makes, except where the upstream's order is a race (below). A request that arrives while a step runs is an ordinary message: an external transition holds it until the engine next reads its input. When that is depends on the engine and its settings. Under vLLM's asynchronous scheduling, on by default, the next batch is scheduled while the current one runs, so a request arriving during step N usually first joins step N+2, because step N+1 was scheduled when step N started. Without it, the request can join step N+1. Each engine declares, for each kind of external input, the step boundary at which it takes effect, whether it arrives during a step or at the instant one ends. Where the upstream's order is a race between threads, the declaration says so and names the order BLIS uses.

A value one component publishes for others, such as an engine's metrics, carries its time and a publication sequence number, and a reader that caches it keys the cache on both.

8.3 Time and progress

Simulated time is an integer number of microseconds. A step time the cost model prices is converted to microseconds once, by one rounding rule. Two events that rounding makes simultaneous are ordered by the key (§8.2). Arithmetic whose result reaches the order of events or the Result is written so that it gives the same bits on every supported platform (X6).

Simulated time must advance: only finitely many events may happen in any finite stretch of simulated time. Every cycle of components that can pass messages around in zero time contains a component with a positive time advance, or a declared bound on how many times the cycle can repeat at one instant. An engine step that changes no state is an error unless the engine scheduled it as a wake-up, or it is an idle or dummy step the upstream itself runs, such as vLLM's dummy batches on idle data-parallel ranks of a mixture-of-experts model, which the engine declares.

A component changes its own next event only by recomputing its time advance after a transition. The event it no longer wants is marked stale, by a generation number, and dropped when it reaches the front of the queue. It cannot affect the result, wherever it sits in the queue.

8.4 Random numbers

Every random draw comes from a substream named by component, purpose and entity: for example, client 3, prompt length, request 17. The substream's seed is the SHA-256 of the scenario seed and that name, and the generator gives streams for different seeds that can be treated as independent. Its name and version are part of the experimental frame, because a new generator changes every draw. So request 17 of client 3 gets the same prompt length whatever happened to requests 1 to 16, in every configuration.

This is the basis of common random numbers: two runs that differ only in configuration give the same requests the same random inputs. Their outputs are then usually positively correlated, so the difference between them varies less from seed to seed and can be estimated with fewer runs. It does not make the difference free of noise. Some draws depend on how the system responds, for example a retry after a timeout, or a router's tie-break. They use their own substreams, and do not line up between configurations. Comparisons therefore still need replications and intervals (§8.8).

8.5 Input models

Every distribution the workload generator draws from names its family, its parameters, how they were estimated, and the trace they were estimated from, and passes a stated goodness-of-fit test against held trace data. Where a dependence matters, it is modelled, not assumed away: output length against prompt length, the burstiness of arrivals, and the structure of sessions.

A trace records the causes of each arrival, not only its time: which session a request belongs to, and how long the client waited after the previous response. Replaying a trace under a different configuration recomputes the arrivals that depend on earlier completions. A replay of fixed timestamps has no random input, so its figures have no replication interval unless the trace is resampled.

8.6 The experimental frame

A run measures something only relative to its experimental frame. In BLIS the frame is one document, recorded in every Result:

  • the generator: the workload and its input models (§8.5), or a trace to replay, with its seeds;
  • the initial state: empty caches, or caches warmed by a stated rule;
  • the phases: warm-up, measured window and drain, each defined by a rule;
  • the stop rule: a request count, a horizon (a simulated time at which the run stops), or both;
  • the acceptance conditions under which the run counts for this frame, such as achieved concurrency within a tolerance of the target, and few enough requests unfinished at the horizon;
  • the metric definitions (§8.7).

A run that fails its acceptance conditions produces no figure. Running a scenario, exporting its trace and replaying the trace under the same configuration gives an identical Result. Converting another tool's workload into BLIS's preserves, phase by phase, the offered load (requests arriving per second), how variable the gaps between arrivals are, the joint distribution of prompt and output lengths, and the session structure; each converter is checked against its source with two-sample tests.

8.7 What a metric means

Every metric that is reported, compared, ranked or used in a service-level check has one definition, with an identifier, in the metric registry in contracts/ (DEV-8): its formula, its statistic (a mean or a percentile), its population (requests, tokens or steps), its window and its unit. The metric registry includes latency (time to first token, time per output token, inter-token latency, end-to-end latency, scheduling delay and queueing delay), each with its mean and the percentiles a report needs. It also includes throughput (requests, output tokens and total tokens per second; the token rates also per accelerator), interactivity (output tokens per second per request), goodput, and service-level attainment. Time to first token, time per output token and inter-token latency follow the definitions of the benchmark clients BLIS is compared with: time per output token excludes the first token and is averaged per request; inter-token latency is pooled over tokens. Two figures are compared only when their definitions, scopes and aggregates are all the same, and a definition is never inferred from a field's name.

A figure is a metric at a scope: the whole cluster, one pool, or one instance. The scope selects which requests, tokens or steps form the population; the formula, statistic, window and unit are unchanged. A figure that aggregates over several scopes, such as the largest p99 time to first token over instances, names the scope it ranges over and the aggregate. Two figures are compared only when their metric, scope and aggregate are all the same (DEV-8). A report or ranking states the metric, scope and any aggregate of every figure it shows.

A request's fate is how it ended: completed; dropped, with a reason; timed out; in flight at the horizon; queued at the horizon; or not started. It is written once, at one place in the code, and every latency sample is derived from it. A request that emitted no token gives no token-latency sample. The generator keeps its own count of arrivals, and conservation compares that count with the sum of fates, so that a counting error in the fates cannot be hidden by the same error elsewhere.

Requests in flight or queued at the horizon have not finished, so their latency is unknown but at least what they have waited. A latency statistic states how it treats them: excluded, with their count reported beside it, or counted at their waiting time so far as a lower bound. A percentile is not reported when more requests are unfinished than the percentile leaves room for.

8.8 Output analysis

A simulation's outputs are estimates, and are analysed as estimates. A run is either terminating, measuring a fixed amount of work such as a benchmark of a set number of prompts at a set concurrency, or steady-state, measuring a system that has settled.

  • A terminating run discards nothing at its start, unless the measured run did. Where the run has random input, its estimate is the mean over several independent replications (runs with different scenario seeds), with a confidence interval from the spread between them. InferenceX benchmarks are terminating runs. Their frame copies the measured run's start state, stop rule and requests (COV-12), so seeds vary only what the requests do not fix.
  • A steady-state run discards a warm-up, the stretch at the start where the system is still filling. The warm-up length is found by a stated method, such as MSER-5 (which picks the cut that minimises the variance of the remaining mean), applied to each output series, including the prefix-cache hit rate, which often settles later than queue lengths. Its estimate comes from replications, or from batch means: one long run, after warm-up, split into 10 to 30 equal batches, long enough that neighbouring batch means are not correlated. A percentile gets its interval from replications, each holding enough samples for that percentile, never from batch means.
  • A run whose measured window shows a trend has not settled. If the backlog grows, the system is overloaded: its latency figures describe a transient and are not reported, and its departure rate is reported as saturation throughput only if the departure rate itself shows no trend.

Replications start at five and continue until the interval is narrower than a stated fraction of the estimate, or a stated limit is reached, in which case the width reached is reported. A comparison of two configurations is made on the differences between paired replications that share common random numbers (§8.4), and has three outcomes: better, worse, or not distinguished. One configuration is better only when the whole interval of the difference lies beyond a stated margin. Not distinguished includes the case called equivalent, where the whole interval lies within the margin. A search that compares many configurations controls the chance of a false winner across all its comparisons, and re-estimates the winner on fresh seeds, because the best of many noisy estimates is biased upward.

This interval covers the randomness of the workload. The model's own uncertainty is separate: its coefficients have intervals (VAL-10) and its methods have measured errors (VAL-5). A figure states which uncertainty its interval covers. A recommendation is reported with a sensitivity run, in which the coefficients it depends on most are moved across their intervals, and states whether the ranking changes.

A deterministic run is reproducible, not accurate. Where a run has random input, one run gives an estimate but no interval for it. Byte identity shows that a refactor changed nothing; it does not show that a figure is right.

8.9 Verification and validation

BLIS checks two different things. Verification asks whether the code does what the simulation model says (here "model" means BLIS's description of the serving system, not an LLM): the oracle tiers (§7.4), the conservation of requests, determinism and the byte gate. Validation asks whether the model matches the real system: held-out accuracy against measured benchmarks, through the dashboard's scoring harness (§11.7).

A change is a verification change when it must leave the model's behaviour unchanged: a refactor, a speed-up, or a fix that makes the code match an oracle or a written rule. It is a validation change when it changes what is modelled: a pricing form, a coefficient, how links are shared, an input model, a timing rule such as the scrape delay, or the order of classes at one instant. The class follows from what the change does, not from the repository it is in. A change that is both is split. A verification change that moves a published figure, such as a fix that makes the port match its oracle, carries the evidence X13 asks of it.

The model's validity domain is the range of models, chips, layouts, concurrencies, sequence lengths and replica counts its held-out data cover. Every Result states whether its scenario lies inside it. Behaviour that appears only at cluster scale, such as router decisions across many replicas or contention on shared links, is verified against upstream code but not validated until measured cluster runs exist. Where measurements at several sizes exist, the simulated curve across sizes is compared with the measured curve, not only single points. When BLIS models a policy, such as an autoscaler or a saturation detector, its output states whether that policy has been validated, and against what.

9Getting a value for every coefficient

9.1 The aim

The cost model needs a coefficient for every primitive on every chip: an attention rate, a GEMM efficiency curve, a collective's latency. Fitted measurements will never exist for every combination. If a missing coefficient caused a refusal, coverage would fall even where a sound estimate exists.

The aim is that every primitive gets a value, and every value records how good it is.

How to tell measured from calibrated. A value is measured when its data units are microbenchmarks of exactly this kernel implementation on this chip. It is calibrated when its data units are composite, such as end-to-end runs or whole forward passes, from which a factor of a structured formula is inferred.

Every value is stored. Every value of every rank, roofline values included, is a coefficient registry entry written by a writer script. The cost model only looks values up. That keeps every price traceable to a committed entry.

9.3 How the quality of a less trusted value is tracked

  • Labelling. Every coefficient records its method, and every price records the methods of the coefficients it used.
  • Error measurement. Each method's typical error is measured by leaving one chip out: for chips that have a measured value, compute each less trusted method's estimate as if the measurement did not exist, and compare. That error is published per method and per primitive family.
  • Replacement. For each lookup there is at most one entry per rank, and the cost model uses the most trusted one, the entry with the smallest rank number. Removing a more trusted entry (one with a smaller rank number) needs a supersedes: record that cites a defect issue, such as a measurement found to be wrong. That record triggers a review question. Replacing a measured value with a newly measured one is a normal accuracy change, with held-out evidence.
  • Backlog. Every value below rank 1 appears in the blocker backlog (§11.6), weighted by how many points it prices.

Extrapolation. A fitted entry records the range of inputs its data covered (VAL-10). A lookup outside that range is extrapolated: it keeps the entry's value, but for VAL-3 it ranks with transferred, so the price and the point's grade show that the value is used where it was never measured.

10.1 Sources

Three external sources feed BLIS:

  • SemiAnalysis InferenceX: end-to-end serving benchmarks for vLLM, SGLang and other engines, plus collective benchmarks (CollectiveX), operator benchmarks (OperatorX), agent traces and speculative acceptance curves.
  • NVIDIA AISimulate: operator sweeps per chip, collected under vLLM, SGLang and TRT-LLM.
  • NVIDIA's forward-pass dataset on Hugging Face (nvidia/aisimulate-fpm-dataset, Apache-2.0): whole forward-pass timings per model, chip and layout.

Each source is useful for several purposes. The ledger lets each source be used for all of them, while making sure no single data point is used for two purposes that must stay apart.

10.2 Units, identities and roles

A unit is the smallest piece of data the ledger assigns a role to:

  • one InferenceX benchmark run of one deployment and recipe fingerprint at one concurrency, with the measurement of each attempt that produced one;
  • one point of a CollectiveX or OperatorX run, such as one token count;
  • one point of an AISimulate sweep, such as one matrix shape;
  • a forward-pass cell.

Its identifier, unit_id, is the SHA-256 of a canonical JSON object holding only the source's own identifying fields. The JSON is UTF-8, with sorted keys and no spaces. Because nothing from BLIS enters the identifier, a BLIS change can never change a unit's identity.

How roles are assigned

A unit's role is computed, not stored. Units that are near-copies of each other must share a role, or one could be fitted while its near-copy judges the fit. So the role is drawn per role key, not per unit. For InferenceX the role key is the source plus model, hardware, precision, framework, benchmark type and configuration hash. It leaves out the recipe fingerprint, concurrency, measured date and benchmark run, so one deployment's whole sweep and its re-measurements share one role, whether or not each record carries a fingerprint. Every field of the role key is an identifying field, so a unit's identity fixes its role key. For CollectiveX, OperatorX and AISimulate it is the run or file, so a whole sweep shares one role. For the forward-pass dataset it is the source, revision, model, chip and layout. Legacy units are the exception: they keep their legacy side (below). The rule is HMAC-SHA-256(seed, role_key) mod 100, compared with cut-points fixed per source in the ledger. For example, one source might send 0–29 to fit, 30–39 to select, 40–49 to validate, 50–79 to held and 80–99 to anchor. For a unit on a legacy side, the same value is compared with two more cut-points fixed per source, one dividing fit from select and one dividing held from anchor. The HMAC's message is the canonical JSON of the role key, and its digest is read as a big-endian unsigned integer. The seed is 32 random bytes from a cryptographic generator. It is a CI secret, and only its SHA-256 is committed; with 256 bits of entropy, the seed cannot be recovered from its hash. Who generated it, when, and who owns its rotation are recorded in the ledger.

What the ledger commits, under catalog/ledger/:

  • the sources, each pinned to an exact revision;
  • the units, by unit_id, identifying fields and role key;
  • the ingest report: for each source revision, the records read, those merged as duplicates, those joined into one unit, and those left out, each with its reason;
  • the cut-points and the partition version;
  • the legacy table and any alias tables (below);
  • the hash of the seed.

Units come from the source, not from the pull request. The unit list is generated by the ingest tool from the pinned source revision, which puts every identifying field in one canonical form. CI regenerates the list and requires it to match byte for byte. Each measurement belongs to exactly one unit. The ingest tool recognises a measurement by the SHA-256 of the canonical JSON of the record's measured values (for InferenceX, its metrics object). A record that reports an error, or whose measured values are empty, is not a measurement; it is left out and counted. The conclusion of the benchmark run, such as a failed or cancelled matrix, is recorded on the unit and does not remove it, because a run that fails in one job still writes real measurements from the others. A source sometimes stores one measurement as several records, as when each attempt of a benchmark run becomes its own row. Records with the same identifying fields and the same measured values are one unit: the ingest tool keeps the record with the smallest source row id (for InferenceX, benchmark_results.id; for a file source, the path and then the line) and lists the others as its duplicates. Because the records agree on every identifying field and every measured value, the choice cannot change the unit's identifier or role. It decides only which record's other fields, such as the image digest and the server log, the unit carries; a field only a duplicate records is taken from the duplicate with the smallest row id that records it. Records with the same identifying fields and different measured values are one unit holding each measurement, and their spread counts as the measurement's own noise (COV-10). The same measured values under two identities with one role key are one unit, under the identity of the record with the smallest row id. Under two identities whose role keys differ, they are left out, because they could let one measurement draw two roles. The ingest report counts every record merged, joined or left out. So a pull request cannot re-add a known measurement under a new unit_id to get a new role draw.

The ledger never commits the role of a select, validate or held unit. At each substrate release, a seed-holding release job writes the three published lists, catalog/ledger/published/fit.yaml, anchor.yaml and report.yaml. These three files are runtime data and are embedded with the rest of the catalog. The rest of the ledger is not.

Pull-request code never sees the seed

A candidate is code the pull request controls. If it ran in a job that holds the seed, it could read the secret, or leak which units are held through its output. So every scoring run has two jobs. A candidate job, with no secret, fetches its modules and the pinned scoring harness, then runs the candidate with no network on every unit not on the published fit, anchor or report lists, and writes one prediction per unit. The seed-holding job runs only scorer code from main, computes roles, and reduces the predictions to aggregates. Each aggregate covers at least 10 units; a smaller lane is merged with its neighbours or not reported. A candidate could still try to learn which units are held, by corrupting its predictions on chosen units and watching the aggregates move. So held-unit aggregates are returned only for a pre-registered change, or by the nightly and pre-release gate runs, which are counted and reported as such; every evaluation is counted (below). Pull-request jobs without a pre-registration may read only the published fit units, through the dashboard's scoring harness (§11.7). Their figures inform review and are never landing evidence. Anchor units are scored only for the published dashboard, so no change can be tuned against the figures it reports.

Each pre-registration commit gets one evaluation on held units. Any further evaluation of the same change is counted, and the count is shown on the pull request and in the release notes, so repeated tuning against held units is visible.

Three properties of the rule

  • Append-only. Roles for new units are drawn inside the jobs that hold the seed, the first time a unit appears, and before any job uses it. An existing unit keeps its role unless a new partition version, approved in a pull request by the reviewer with write access, says otherwise.
  • Legacy units keep their old side. A partition made before the ledger existed is carried over through ledger/legacy-map.yaml. Each legacy unit keeps its old label, fit side or held side, and the keyed rule chooses only within that side: fit or select, held or anchor. A unit whose legacy records carry both labels takes the fit side, because some of its records may already have been fitted on, and data that was fitted on cannot judge a fit. This happens when the new identity joins records the old partition split, for example by removing the image digest. A new unit whose role key holds legacy units takes their side, and the fit side if they hold both. Legacy units of one deployment can still be on both sides, because the old partition split deployments by concurrency; this is one more reason legacy held units are not blind. A coefficient fitted from legacy records before the ledger existed cites their units. A substrate release refuses such a coefficient while any unit it cites is in select; it is refitted from the fit list first (D1). The ingest tool generates the map from legacy point identifiers to units and commits it with the legacy table, listing each unit that takes a side by these rules. Because the old split is public, legacy held units are not blind (above).
  • Stable when identities are recomputed. If InferenceX renames a field, or a change to the ingest tool changes how identifying fields or role keys are computed, the affected unit_ids or role keys change, and units would be redrawn: a held unit could become a fit unit. So such a change must ship an alias table from old to new unit_id and role key, and an aliased unit keeps its role. The alias table is generated, not written: CI runs the merge-base and candidate ingest tools on the same pinned source revision and pairs the identities each gives the same records. A change whose aliases would give one new unit or role key two different roles needs a new partition version, which a person approves. The ingest code detects such a change from the source's contract version (§12.8).

When a partition version is retired, its seed is published. The committed hash then lets anyone check that the split was drawn as claimed.

11Accuracy coverage

When inference-sim releases, the accuracy dashboard scores the new release at its next nightly run, with no change to its own code. The dashboard scores every anchor unit, and grades how close each comparison is. InferenceX often runs older, nightly or custom engine builds, so a perfect comparison is not always possible.

11.1 Why settings must not be classified by the dashboard

A dashboard that keeps its own table of which engine settings are modelled will disagree with the engine. The engine changes, and the table does not. The release plan's background shows what that cost. So the dashboard never classifies a setting. The engine repository does, in its field list (VLM-3), and the dashboard reads that list.

11.2 Four steps for scoring a point

  1. State. The dashboard copies the run's recorded engine configuration and environment variables, unchanged, into the scenario's engine block. A run records its configuration in several places: the launch configuration, the arguments the engine logs as passed, the configuration it logs as resolved, and lines it prints about values it chose. The first two record the values passed; the last two record the values resolved. The dashboard reads every one, and a value any of them records is recorded by the run, so it is copied rather than estimated (X19). The engine block holds the values the run passed; a field the run records only as resolved is copied as resolved. This applies to a field the engine models or proves inert; for any other field the resolved value is the engine's own choice, not a setting the run made, so it is recorded on the point and not stated in the scenario, and the field's estimation rule applies only to a value the run passed. A resolved value that differs from a passed one is not a conflict, because the engine resolves its settings: the engine repository must reproduce that resolution. Where the run logs a resolved value that differs from the engine repository's resolution of the passed value, the point is G2, names the field, and the difference goes to the backlog as a fidelity defect. Two sources that record the same stage, such as the launch configuration and the logged passed arguments, with different values are a conflict, and the point is G5 with the reason value_conflict. The dashboard translates nothing, apart from the estimates of the next step. The one exception is engine.version: it is set to the engine release that the scoring inference-sim release runs, and the run's own release is recorded on the point (§11.5). A recorded field that the modelled release does not have would be refused (X1), so the point is G5 with the reason field_not_in_release, naming the field. A workload-dependent value the run records, such as the mean acceptance length its engine logs, is copied into the scenario as stated (D8). One it does not record is taken from the substrate's profiles, and is not an estimate under the next step. With no profile either, the point is G5 with the reason value_not_recorded.
  2. Estimate. When the run did not record a value the simulation needs, such as the maximum model length, or used a setting BLIS does not model, such as an unsupported quantisation format, the dashboard applies the engine's estimation rule for that field. Each engine repository writes these rules in its fields.json, beside each field's status: one of: leave the field unset, so the engine resolves the upstream's default (X19); a stated setting that stands in for an unmodelled one, with the reason; or none. The dashboard holds no rules of its own. A rule applies in two cases: the run did not record the value, or the run passed a setting the engine does not model. A rule never replaces the recorded value of a field the engine models or proves inert: that value is carried into the scenario as stated. For a setting the engine does not model, the rule's stand-in, or leaving the field unset, takes the place of the recorded value in the scenario, and the point names the field, the recorded value and what stood in for it. A not-modelled field that the engine reads and prices when it is stated is a status to correct, either to modelled with its evidence or to refused when stated (VLM-3); the rule does not stand in for that. Every estimate is named on the point and makes it G2; a field with no estimation rule makes the point G5, with the reason value_not_recorded for a missing value or field_not_modelled for an unmodelled setting.
  3. Decide. For each field, the engine's own fields.json says whether it is modelled, proven inert or not modelled. The dashboard keeps no table of its own.
  4. Price. The engine lowers the configuration to kernel implementations. For each implementation the cost model uses the most trusted available entry, the one with the smallest rank number (§9.2), and the point records which methods were used.

A gap at Estimate is a missing estimation rule, and a gap at Decide is porting work, both in the engine repository. A gap at Price is a value below rank 1. All three go to the backlog.

11.4 Reasons a point is not scored (G5)

  • code_not_visible: the run loaded code BLIS does not have. That is a class, module or plugin that a configuration field or plugin entry point names and the pinned upstream release does not ship, such as an out-of-tree connector, scheduler, worker or logits processor, or a patched private build. This reason takes precedence over field_not_modelled.
  • router_unsupported: the run was measured behind a router BLIS does not host, and the router table has no entry for it or says that no llm-d policy is close enough. BLIS hosts only llm-d's router (X4) and never simulates another, so such a point stays in the coverage counts as not scored. The router table (catalog/routers in blis-substrate) lists each router BLIS does not host, by the mode and session-affinity setting a run used, with the llm-d policy it maps to, or an explicit statement that no llm-d policy is close enough, and the evidence for the match or the mismatch: a citation of both routers' code or documentation at the revisions the runs used. An entry maps a router to an llm-d policy only with that evidence; a router and mode with no such entry stays router_unsupported. A point behind a router the table maps is G2 (§11.3), never G1, and it is never presented as if llm-d had routed the run. Hosting another router would add an upstream to this design.
  • value_not_recorded: the result depends on a value the run did not record. It becomes G2 when an estimation rule in the engine's fields.json covers the value (§11.2).
  • field_not_modelled: the run sets a field the engine classifies as not modelled, and the field has no estimation rule. It clears when the field is modelled or gains a rule.
  • field_unclassified: the engine has not classified a field the run sets, or its repository publishes no field list yet. It is a blocker-backlog entry, cleared when an engine release classifies the field or publishes the list.
  • engine_unsupported: no BLIS engine repository exists for the run's engine, as with TRT-LLM.
  • topology_unsupported: the run was measured on a deployment the scoring harness cannot write as a scenario: several engines, as in a prefill and decode split or a run across nodes, where it builds one colocated pool. It is a blocker-backlog entry, cleared when the harness can write that topology.
  • not_in_catalog: the run's model or chip has no catalog entry yet. This is a model-onboarding trigger (§12.1), and the backlog counts it.
  • field_not_in_release: the run sets a configuration field that the engine release inference-sim runs does not have. It clears when inference-sim moves to a release that has the field.
  • value_conflict: two sources that record the same stage of one field, such as the launch configuration and the logged passed arguments, give different values (§11.2). This is a data issue, reported to the source.
  • build_unparseable: the run's recorded engine build cannot be read. This is a data issue, reported to the source.

11.5 One simulator release scores every point

Each inference-sim release runs one upstream release of each engine (LIF-6). The dashboard scores all points with one inference-sim release at a time (COV-9). A point measured on that engine release can be G1 or G2. A point measured on another release is scored on the release inference-sim runs, and graded G3 or G4 by how much of the ported code differs (§11.3). So every point is priced by the same substrate and engine code, and a substrate improvement reaches every point without a backport.

The previous inference-sim release's scores stay published with it, so a reader can compare a point on its own engine release across BLIS releases.

11.6 The blocker backlog

Every night the dashboard publishes a ranked list, per engine, of everything that lowers coverage or grade:

  • refused surface items;
  • not-modelled fields;
  • coefficients below rank 1;
  • unpriced execution modes.

Each entry shows how many points it blocks or demotes. Engine and substrate work is chosen from the top of this list, and each entry maps to one playbook (§12).

11.7 The scoring harness, and who may run it

The dashboard's scoring harness is the one place where a simulation is compared with a measured end-to-end benchmark (§2.2). It takes three inputs: a simulator build (a released tag, or a commit of a branch or pull request), the catalog and coefficient registry it should load (embedded, or paths), and a set of ledger units. It turns each unit's recorded run into a scenario as §11.2 describes, runs the simulator, and compares. It writes the same per-point records and aggregates, whoever runs it.

The harness is released from accuracy-dashboard tags and named by its release and commit. It is run as a script on a runner that builds the simulator, not as a container image. A repository whose pull requests run it pins that release or commit in one pin file, as it pins any dependency, and the release bot moves the pin. Every figure records the harness commit that produced it (X8).

Anyone may run it, at any stage of a change: on a feature branch, on a draft pull request, or on a pull request under review. What changes with the stage is which units it may read, because only seed-holding jobs may see select, validate and held units (D7):

12.3 An idea to improve accuracy

Detected
A person or an agent proposes it, usually from the top of the backlog.
Preflight

A pre-registration file, committed before any held-out data is read. It states:

  • the hypothesis;
  • the layer it changes: a coefficient, a method, a pricing form, or engine behaviour;
  • the target lanes;
  • the sources and lanes whose select and held units will be used (the jobs choose the units themselves);
  • the success criteria;
  • the predicted dashboard change.
Steps
  1. Make one change per pull request.

One change in the repository that owns the layer. A bundle of several ideas is refused.

Detected
The engine repository's release watcher, a scheduled job, watches the upstream's final release tags (release candidates are ignored, §14.1) and opens an upgrade pull request with the preflight attached.
Preflight

Three generated reports:

  • The surface diff: new, removed and changed connectors, tiers, KV-cache managers, speculative methods, policies, configuration fields, defaults, metrics and event types (§7.5).

  1. Cut the release branch release-<old> from main, so fixes to the old release can still ship (§14.4).

Proportional to the number of changed ported functions and new surface items, not to the size of the engine.

13Automation: how the rules are kept

Rules are kept by three kinds of worker, used in this order of preference:

  1. Deterministic checks decide everything that can be decided mechanically. Given the same commit, they give the same answer.
  2. Agents do bounded work: porting a changed function, classifying a new field, fitting a coefficient. They work from a preflight, against the checks, inside a budget.
  3. People answer the yes/no questions in §4 and §5, approve releases, and set direction.

13.1 The invariant registry

Every invariant in this document is a record in blis-substrate/contracts/invariants/:

- id: SUB-6
  statement: The cost model resolves nothing; every default, backend choice,
             padding and capture decision arrives in the plan or step shape.
  scope: [blis-substrate/kernel]
  checks:
    - repo: blis-substrate
      test: TestKernelResolvesNothing
      runs: pull_request
  review: null                    # or {question, reviewer, trigger}
  status: new                     # ci | partial | new | review
  target: {status: ci, milestone: 4}   # a milestone of a release plan

The status partial means some of an invariant's checks run in CI and others are still new. The status review means the invariant is enforced only by its review question, with no mechanical check; X1 to X9 keep a review question beside their checks, and no invariant in this document is review alone. Each check has its own status, so the invariant registry shows which parts are enforced.

An invariant registry check's runs value is pull_request, nightly or release for an automated check, or practice for a maintainer practice (§4.2). A practice record names the repository it concerns and its checklist item, and has no test: no program in another repository reads it. A practice is confirmed by a person ticking its item on the repository’s maintainer checklist; it has no check run to pass, so the release bot does not wait on it.

A generator turns these records into this document's appendix, into a section of every repository's AGENTS.md that carries the agent guidance, into the checklist of every pull-request template, and into a maintainer checklist for each repository that lists its practices. A rendered copy that does not match its record fails CI.

What a repository’s AGENTS.md holds. It is the first file an agent reads, so it is short and complete. It holds, in this order: what the repository is and owns, and what it must never hold (§5); the rules that apply to a change here, rendered from the invariant registry; the commands to build, test and run every check, exactly as CI runs them; what a change in this repository must also update (the documentation, the generated copy, the invariant registry record, the plan’s issue); and where to look next. It states no version, count or list of supported features, and leaves the concepts to the design, which a person reads. It does not restate a rule that CI enforces and an agent cannot get wrong; it states the rules a check cannot decide. A repository adds to it only through the invariant registry or a pull request that the reviewer with write access approves.

13.2 On every pull request

  1. The template lists the invariant identifiers the change claims to keep or introduce. CI fails if any identifier does not exist. The invariant registry lives at contracts/invariants/, and every Go repository pins the substrate, so each reads the invariant registry version it pins; blis-config-search and accuracy-dashboard, which depend only on inference-sim, read it through inference-sim invariants at the release they pin. The shared workflow lives in blis-substrate/.github/workflows, and each repository calls it by commit (X21).
  2. For each cited identifier whose status is ci, CI confirms its checks passed. A check in this repository must pass on this pull request. A check in another repository must have passed at the version this pull request pins.
  3. The review agent reads the changed paths and the diff against every review question’s trigger. A few triggers depend on what changed, not where, such as “a floating-point reduction is added”; the agent applies those by reading the diff.
  4. For each question that applies, the review agent answers it in a review comment with yes or no, a reason, and the files and lines that support the answer. A question is guidance for that review and never a check: no CI job fails because a question is unanswered or answered in the unwanted direction, and no person has to answer or tick one. An answer in the unwanted direction is a finding like any other (§13.7): the reviewer with write access reads it with the rest of the review, and branch protection blocks the merge until that reviewer approves and every conversation is resolved.

13.3 On every release

  1. The release bot refuses to tag unless every ci invariant the repository owns passed at the commit being tagged.
  2. The release notes are generated, never typed. They list the price-change report (each benchmark scenario's step prices before and after the change), changed coefficient values, changed traces, contract differences, invariants added or changed, review answers, and the exact upstream versions.
  3. Once the milestone named in an invariant's target is reached, the release bot refuses to tag until that invariant has its target status.

13.4 Every night

  • The nightly compatibility build builds every repository at the tag the newest inference-sim release pins, and at the newest tag on each open release branch, with the substrate raised to its newest tag (skipping a release branch whose contracts the newest substrate no longer fits), on three platforms. It runs each repository's tests and checks the module graph against Figure 1.
  • Full-data gates rerun coefficient registry writers, the landing gates and fixture-agreement checks on the full data, which CI cannot hold.
  • Detectors poll upstream releases and data sources, and open trigger pull requests.
  • The dashboard scores, publishes coverage and grades, and updates the backlog.
  • A status page shows every invariant by repository with its latest result.

13.5 Where accuracy gates run

An accuracy gate compares a candidate with held-out data (VAL-6). Where it runs depends on what it needs:

  • Operator-level gates need only the cost model and the coefficient registry, for example "does this attention coefficient predict the held-out sweep points?" They run in blis-substrate's gate job, which holds the role seed in that repository's protected environment (D7).
  • Whole-run gates need engines and the simulator, for example "does this change improve end-to-end latency on held-out InferenceX deployments?" They run the dashboard's scoring harness (§11.7), the only end-to-end scorer, at the release or commit the repository pins. A candidate job in the pull request's own repository builds the candidate and runs the harness with no secret and a read-only token, on every unit not on the published fit, anchor or report lists, and writes one prediction per unit. accuracy-dashboard's gate job holds the role seed (D7), runs only its own main, refuses predictions made by a harness commit other than one released from its main, reads them as untrusted input, reduces them to aggregates and reports the result on the pull request.

The gate compares two trees: the base, which is the pull request's merge base, and the candidate, which is its head. Comparing against the merge base, rather than against the last release, keeps unrelated changes already on main out of the comparison. Each tree's catalog and coefficient registry are passed with --catalog and --registry.

  • If the pull request changes only files under catalog/ and registry/, and both trees load under the released simulator's validators, and the code outside those directories at the merge base is identical to the substrate release that simulator embeds, the gate runs the released simulator twice, once per tree. No rebuild is needed. If main carries unreleased code changes, the next case applies, so the data are judged with the code they will ship with.
  • Otherwise, for example when the pull request changes the cost model or an engine, or uses a data field an older simulator cannot read, stack CI (§13.6) builds one simulator from the base and one from the candidate, and each runs on its own tree.

Before a substrate release is tagged, the release bot triggers the whole-run gate job once more, comparing the candidate (its code and its data) with the previous release (its code and its data) on held units. A lane that gets worse by the test of VAL-6 blocks the tag, unless it is recorded as a defect in another term and approved (VAL-11). That final check covers changes that were each fine alone but interact. In every case the substrate's CI imports no repository above it (X7). A substrate pull request's candidate job builds inference-sim through stack CI and runs the pinned harness. Those are the two uses of higher repositories X7 allows, and the candidate job imports neither.

The gate job runs on pull requests that carry a pre-registration, and again nightly on the full data. Any pull request, draft or not, may also run the harness on published units for review (§11.7); that run holds no seed and decides nothing.

13.6 The release bot

A review set spanning repositories is described by one file, stack.lock, which lists each repository's branch head. During review, a "stack CI" job builds and tests the heads together, through a go.work file it generates and never commits (X11). Each repository keeps its released pins until the set is approved. Then the bot:

  1. merges and tags each repository bottom-up;
  2. writes each pin once;
  3. runs the next layer's checks against the new tags.

No person or agent re-pins by hand, and no agent waits on CI.

The bot's code lives in blis-substrate/tools/release, and its tags are signed. If the bot is unavailable, a documented manual procedure, run by a person with write access, produces the same tags in the same order.

13.8 Keeping agent work cheap

  • The preflight sets the scope. An agent works only on the preflight's list, within its budget. Work outside the list is a new trigger.
  • Tools do mechanical work. Re-pinning, re-vendoring, regenerating traces, diffing releases and updating descriptions are commands.
  • Agents do not wait. When CI or review is pending, the session ends and resumes on an event.
  • Reviews by agents are narrow. An audit agent receives one diff and one trigger's done-when list.

What an engine tag guarantees

An engine release, like any software, can ship with a bug or a gap that is found later. That is expected, and it is why N exists: the fix is a new -blis.N on the same upstream release, released and pinned the same way as any other.

A tag vX.Y.Z-blis.N of blis-vllm or blis-sglang means:

  • It models upstream release vX.Y.Z, at the commit its Upstream record names, and no other release.
  • It passed that release's oracle tiers, its field list and surface list checks, and every ci invariant (LIF-3).
  • A higher N on the same upstream release is a BLIS-side change only: a bug fix, a newly modelled feature or plugin, a contract or substrate update. It may change prices or decisions. Its release notes say what kind of change it is and whether prices or decisions changed, and include the price-change report (§13.3).
  • Every file is either ported from vX.Y.Z or original to BLIS. Nothing is kept for an older release.

The module's version number is the upstream's version number, so the module cannot use it to signal a breaking change to its Go API. That costs nothing here, because only inference-sim imports an engine module, and it pins the exact tag (LIF-2). If an upstream reaches v2, the module path gains /v2, as Go requires.

Upstream versions that are not Go versions

  • Release candidates (vLLM's v0.33.0rc0, SGLang's v0.5.3rc0) are not modelled. An engine module models final releases only.
  • Post releases, of vLLM or SGLang (for example SGLang's v0.5.6.post1 or vLLM's v0.6.1.post1), are written v0.5.6-post.1.blis.N. The dot after post makes Go compare the number numerically, so post.2 sorts before post.10. Every -post.K.blis.N sorts after every v0.5.6-blis.N and before v0.5.7-blis.1, which is the upstream order. These orderings are Go's own (golang.org/x/mod/semver).
  • Four-part versions, such as vLLM's v0.10.1.1, are written v0.10.1-rev.1.blis.N. Go compares these words as text, and both post and rev sort after blis, so a post release or a four-part release sorts after every -blis.N tag of its three-part base and before the next three-part version. If an upstream ever publishes both on one base, the rev form is used for the four-part release.

A detail of Go's version ordering

To Go, -blis.N is a pre-release suffix. So v0.32.0-blis.1 sorts before v0.32.0. Among suffixed tags, v0.32.0-blis.2 sorts before v0.32.0-blis.10, and both sort before v0.32.1-blis.1. go get …@latest also prefers any plain release over every pre-release. This is Go's own ordering (golang.org/x/mod/semver) and the behaviour of go get.

Three rules follow:

  • Engine modules and the router fork never tag a plain v<upstream>. Every tag has a -blis.N suffix, with N from 1.
  • Pins name exact tags. The release bot never resolves @latest, and a lint checks the version each build actually selects, not the text of go.mod (LIF-2).
  • A plain tag made before this rule stays, because tags are never moved or deleted (LIF-1). It makes @latest wrong for that module, and a module that requires it outranks every -blis.N tag in version selection. A retract line does not fix this: retractions never change version selection, and Go reads them only from the latest release version, which is the plain tag itself. An exclude line in inference-sim's go.mod does, because Go applies the main module's excludes to the whole build (X11).

14.4 Release branches

Each upstream-tracking repository has a main branch (llm-d-r in the router fork) that models the newest upstream release BLIS supports. When BLIS moves to a new upstream release, two branches are cut:

  • in the upstream-tracking repository, release-<upstream>, for example release-0.32.0, from the last commit that modelled the old release;
  • in inference-sim, release-vX.Y, from its last release that ran the old upstream release.

A fix needed on the old release is made first on the main branch if the main branch needs it too, then cherry-picked to the release branch; otherwise it is made on the release branch alone. The release branch then gets the next tag for its upstream release, for example v0.32.0-blis.3 after v0.32.0-blis.2, and the fix is shipped by a PATCH release from inference-sim's release branch. A tag on a release branch alone reaches no user, because every inference-sim release pins exact tags.

Only the inference-sim release before the newest one is supported this way. Both release branches close when inference-sim next moves an engine or llm-d to a new upstream release.

At start-up the model's layers are grouped, and each group has a KV-cache spec, such as full attention, sliding window or Mamba state. KVCacheSpecRegistry maps each spec type, or a group's role, to a manager; one manager may serve several spec types. A coordinator runs one manager per group (§7.1).
Landing gateThe accuracy check a coefficient or pricing change must pass to merge (VAL-6).
LaneOne engine, engine release, chip, model and layout, as the dashboard groups points.
LayoutHow a model is split across GPUs: the tensor, pipeline, data, expert and context parallel widths, and where each rank is placed.
Ledger ownerA person the project team names to own the role seed and its rotation (§10.2).
llm-d stackllm-d's router in front of vLLM or SGLang engines, as llm-d's published guides deploy it.
LoweringTurning a model's architecture into the concrete kernels an engine release runs: which attention backend, which fused operations, which data types, which page size.
Maintainer practiceA rule a person with write access keeps for a repository as a whole, such as its branch protection, its tag settings, its merge methods and, encouraged but not required, the signing of its commits (§4.2). It is stated once with a checklist item, enforced by the hosting service where a setting exists, and audited by no program in another repository.
ManifestThe list of everything the oracle replaces.
Memory poolIn SGLang, a store of KV cache or recurrent state in GPU memory, or, for HiCache, in host memory. A separate allocator hands out its slots or pages. Each attention layout (full attention in its MHA and MLA forms, sliding window, Mamba, hybrid, sparse) has its own pool type (§7.1).
Message classOne of a fixed order of message kinds, used with time, sender and the sender's send count to order messages at one instant (§8.2)
Metric registryThe list in contracts/ of every metric's definition: formula, statistic, population, window and unit (§8.7, DEV-8).
MilestoneOne of the numbered steps in which a release plan delivers its work.
MLAMulti-head latent attention: attention that stores a compressed latent instead of full keys and values.
MoEMixture of experts.
MooncakeA KV transfer and storage system, used by vLLM connectors and as SGLang's default P/D transfer backend.
MSER-5A warm-up rule: batch the output series in fives and cut where the variance of the remaining mean is smallest (§8.8).
MTPMulti-token prediction: a speculative-decoding method where extra model layers draft the next few tokens.
NIXLNVIDIA's library for moving KV caches between machines. vLLM's NixlConnector, the P/D connector llm-d's guides use most, is built on it.
Not blindA held-side figure from a unit whose label predates the ledger, so that the unit may have influenced earlier choices. The gate reports each such unit as a separate figure for as long as such units are used (§10.2).
Offered loadRequests arriving per second, set by the workload rather than by the system's response.
OracleThe harness that runs the upstream's own code with its environment replaced, and records its decisions.
Output functionWhat a component sends, evaluated just before an internal or confluent transition (§8.1).
OverlayA directory given with --catalog-overlay or --registry-overlay. Each entry replaces the entry with the same identity in the data in use, or is added if none exists (§3.3).
P/DPrefill/decode disaggregation: one pool of engines processes prompts (prefill), another generates tokens (decode), and the KV cache moves between them.
Paired bootstrapA way to put an interval on the difference between a candidate's error and the base's error on the same units, by resampling the units and recomputing the difference. The landing gate fails a lane only when the whole interval lies above zero (VAL-6).
Parallel DEVSThe form of DEVS in which all outputs at an instant are collected before any component changes state (§8.2).
Partition versionA numbered version of the ledger's role assignment. A new version is needed to change any existing unit's role.
Perturbation testA test that changes one field and checks that some price, decision, or field of the emitted plan or step shape changes (SUB-11, VLM-3).
Pin, re-pinTo require an exact version of another module in go.mod; to update that requirement.
PlaybookThe fixed steps for one kind of trigger, run by CI and, where needed, by an agent (§12).
PointOne InferenceX unit as the dashboard grades it, G1 to G5 (§11.3): one benchmark run of one deployment and recipe fingerprint at one concurrency.
PoolA group of engine instances that share one configuration and layout, such as the prefill pool or the decode pool in P/D. Each pool has one PoolPlan.
PoolPlan, StepShape, TransferThe three objects an engine hands the cost model: a plan per engine pool, the shape of each step, and one transfer per KV move (§6.1, §6.2).
Pre-registrationThe preflight file of an accuracy change, committed before any held-out data is read, that states what the change will be judged on (§12.3).
PreflightThe generated report that fixes a trigger's scope before work starts.
Price-change reportA report, generated for every release and every pull request that can change prices, of each benchmark scenario's step prices before and after the change (§13.3).
PrimitiveOne kind of work the cost model prices: an attention step, a matrix multiply, a collective, a memory transfer.
Profile likelihoodA way to find a fitted coefficient's interval by refitting the others at each candidate value (VAL-10).
Progress watchdogA check that fails a run when no request changes state for a set number of engine steps while work is waiting (SIM-7).
Quarantine listThe list of tests that fail on the main branch, each with an owning issue and an expiry date; listed tests do not block merges until they expire (X25).
Radix cache, tree cache, tree coreSGLang's prefix cache: a tree of token sequences whose nodes hold KV cache, so that requests sharing a prefix reuse it. A tree cache is any implementation of SGLang's tree-cache interface; the default is the unified radix cache, and others can be registered. A tree core is the tree's own data structure inside the unified radix cache, implemented in Python and in Rust (§7.1).
RatchetA count that CI allows to fall but never to rise.
Recorded traceThe oracle's output for one scenario at one upstream commit, reviewed and committed. The commit marker golden-reviewed: keeps an older name for the same thing.
Release branchA branch release-<upstream> in an upstream-tracking repository, or release-vX.Y in inference-sim, kept for fixes to an upstream release after main moves to the next one (§14.4).
Release ownerA person with write access to a repository who cuts a release by the manual procedure when the release bot is unavailable (§13.6), with standard git or the hosting service's interface.
Release watcherThe scheduled job in each upstream-tracking repository that detects new upstream releases and opens the upgrade pull request (§12.4).
Released data, experimental dataA run uses released data when the simulator is a tagged inference-sim release, its catalog and coefficient registry hashes equal the embedded hashes of that release's substrate, and it uses no overlay. Any other run is experimental. Only released-data results are published.
ReplicationOne run of a scenario with its own scenario seed. Several replications give a confidence interval (§8.8).
ResultThe structured output of one run, written as JSON, including everything the run used (§3.3).
Review questionA yes/no question, attached to an invariant, that the review agent applies to a pull request and answers in a review comment with the files and lines that support the answer (§13.2). It is guidance and never a check: it fails no CI job and waits for no person. Its expertise line names the knowledge the agent brings, and its applies-when line says which changes it covers.
Review setThe pull requests, across repositories, that make up one change.
Role keyThe fields of a data unit that decide its role, so near-copies of one measurement share a role (§10.2).
RooflineAn estimate of a primitive's time as the larger of its compute time at peak FLOPs and its memory time at peak bandwidth.
Runtime interface (seams)The points where the router fork reads time, starts work, draws random numbers or makes calls, so BLIS can supply simulated versions.
ScenarioThe YAML file a user gives BLIS: the engine and router configuration, the cluster, the workload and the seed.
Scoring harnessThe accuracy dashboard's tool that turns measured benchmark runs into scenarios, runs a given simulator build, and compares. The only end-to-end scorer (§11.7).
Seed-holding jobOne of the four kinds of CI job that hold the role seed: the release job, the select job, the error job and the gate job. They run only code from main, never a pull request's code. Only these can compute select, validate and held roles (§10.2).
Selected-version lintA check that reads the versions Go actually chose for a build (go list -m all), not the versions written in go.mod.
Simulated runtimeThe router fork's runtime when BLIS hosts it: clock, timers, randomness and goroutines driven by simulated time (§7.3).
Stack CIThe CI job that builds and tests a review set's branch heads together, before anything is tagged (§13.6). Its file, stack.lock, lists those heads.
stack.jsonThe record, published with each inference-sim release, of the exact version of every BLIS module and upstream release it was built and tested with, its Go toolchain version and its llm-d guides commit (SIM-3).
SubstrateThe engine-independent foundation: blis-substrate.
Surface listThe generated list of every feature an upstream release offers, each with a BLIS status.
Terminating run, steady-state runA run that ends by its stop rule (terminating), or one that measures a system after it has settled (steady-state) (§8.8).
Time advanceHow long until a component's next internal event, given its state (§8.1).
Token recordThe per-request counts an engine emits: prompt tokens, tokens served from local and external caches, tokens computed and tokens emitted (SIM-12).
TriggerAn outside event that starts BLIS work, such as a new upstream release or a new model (§12).
Unit, roleA unit is the smallest piece of data the ledger tracks. Its role says what it may be used for.
UpstreamThe project BLIS reproduces: vLLM, SGLang or llm-d.
Upstream recordThe Upstream value in an engine repository's provenance.go: the one upstream release, and its commit, that the repository models (LIF-5).
Upstream-tracking repositoryblis-vllm, blis-sglang or the router fork. The first two are also called engine repositories.
Validity domainThe range of models, chips, layouts, concurrencies, sequence lengths and replica counts that held-out data cover (§8.9).
VerdictA CI result or the review agent’s review, including its answers to review questions. Each names the tree it judged (X22).
Verification, validationChecking that the simulator does what its model says (verification), and checking that the model matches the real system (validation) (§8.9).
Warm-upThe stretch at the start of a steady-state run that is discarded because the system has not settled (§8.8).
Workload identityThe key under which a workload-dependent quantity, such as speculative acceptance or expert routing balance, is stored (D8).
