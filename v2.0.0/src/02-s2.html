2.1 Eight repositories

The target system has eight repositories. Four track upstream code: the two engines, the llm-d router, and the KV stores that engines call. One is the shared foundation, one is the simulator, and two are applications that use the simulator.

2.2 Where a fact belongs

Every fact, rule and value has exactly one owner. To decide which, ask what the fact depends on:

  • If its value changes when an engine releases a new version, it belongs in that engine's repository, on the branch that models that release (§14.4).
  • If it changes when llm-d releases a new version, it belongs in the router fork.
  • If it changes when a KV store package releases a new version, it belongs in blis-kvstore. A KV store package is a package outside the engine's tree that an in-tree connector or storage backend calls, that holds KV, and that decides what it holds, where each object lives or what it evicts. It does not matter whether one engine calls it or both. A store that decides nothing, such as a file system or an object store that only holds bytes, is a catalog storage device, priced as §6.1 states.
  • If it changes with the simulator's own design, it belongs in inference-sim.
  • Otherwise it belongs in blis-substrate: it is true of the hardware, the model, the physics or the data, whatever engine runs.

To check a change to the substrate, ask whether a second engine would need the same edit. If not, the change belongs in an engine repository.

The same rule applies to work, not only to facts. Each kind of work has one owning repository, and no other repository holds a second copy of it. Another repository that needs the work calls the owner's command or imports the owner's package.

So inference-sim runs simulations and holds no scorer, and a fitting script that wants an end-to-end figure runs the dashboard's scoring harness rather than writing its own. Two repositories that each compute an accuracy figure would sooner or later disagree about what the figure means.

Why KV store packages have their own repository. The engine repository of the first engine that calls a store cannot hold it. The store's behaviour changes when the store releases, not when that engine does, and an engine repository holds only code ported from its own upstream (VLM-2), so the second engine would depend on the first engine's release branch for code neither engine wrote. The substrate and inference-sim hold no behaviour (X2, X3). Each store is an upstream with its own releases. Its decisions are ported once, in one package of blis-kvstore, which records each store's release separately (§14.1). Each engine reaches it through kvstore.Store (§6.5), as the simulator reaches the router through contracts/embed. The connector and its adapter to the store stay in the engine repository, because they are the engine's code.
