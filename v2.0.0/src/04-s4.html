4Rules that span components

These rules hold across the components of Table 1 (§2.2): inference-sim, which is one repository, and its neighbours, the router fork, accuracy-dashboard and blis-config-search. A pull request that breaks one does not merge, whatever its tests show. Rules X1 to X9 list their checks, where each runs, and the review question that remains; X11 to X29 follow in §4.1. A path that begins contracts/, catalog/, registry/, kernel/, validate/ or load/ is under substrate/. An engine module is a directory under engines/.

A review question needs judgement, so no CI job runs or waits on it. The maintainer who reviews a pull request asks the questions that cover what the pull request changes. An answer in the unwanted direction is a finding, which the reviewer weighs with the rest of the review.

BLIS adds only what the real system learns from its environment: hardware, cluster topology and workload. Engine modules resolve defaults exactly as the upstream does. The router needs no port of its defaults: the fork runs llm-d’s own flag parsing, configuration loader and Kubernetes decoding unchanged, so a value the real router rejects is rejected with the router’s own message. An unknown or unsupported field is refused by its upstream name, never ignored. The one exception is the router’s flags that only change how a deployed router is served or observed (transport, TLS, leader election, ports, telemetry). Those are accepted, have no effect, and are named in a warning.

4.1 Other cross-component rules

X10 is not used (Appendix C). These rules cover pins, data, tests, documentation and process. A rule marked Maintainer practice is kept by people; every other rule has a named check. Maintainers with write access decide on each pull request, with the hosting service’s own branch protection, required reviews and signed commits. No custom program polices a pull request’s text, a review or an issue. There is no CODEOWNERS file. Rules that need a program protect the product’s correctness or accuracy.

  • X11 Pins are exact commits. The pins among the repositories are: inference-sim’s pin of the router fork, by one commit as a Go pseudo-version; inference-sim’s pin of the accuracy-dashboard scoring harness, by commit, in one harness pin file (X7); and the pins of blis-config-search and accuracy-dashboard, each of which pins an inference-sim release by its tag and commit and moves to a new release by a pull request. A pin never names a branch, a local path or @latest, and no repository commits a go.work file. The only committed replace directive is the one in inference-sim’s go.mod that substitutes the router fork for upstream llm-d. It exists because the fork keeps upstream’s module path (github.com/llm-d/llm-d-router), so Go cannot fetch the fork by its own path. It names the pseudo-version of one fork commit, so it pins as exactly as a require does, and go.sum records its hash. It may appear only in inference-sim, because Go ignores replace directives in every module but the one being built. No other module requires the fork.Checked by: a module lint in each Go repository: in inference-sim, exactly one replace, from github.com/llm-d/llm-d-router to github.com/inference-sim/llm-d-router, at a pseudo-version; no replace elsewhere; no other module requiring github.com/llm-d/llm-d-router; no committed go.work. The harness pin file names a commit. In each application, its pin file names a release by tag and commit.
  • X12 Only derived values are committed, never third-party data, with one exception: vendor config.json files whose licence is on the allow-list. Each such model records the licence identifier in its model.yaml. A model whose licence is not on the allow-list commits only the file’s hash and revision, and the deriver fetches it in a nightly job that holds the access token; pull-request jobs check only the committed hash and revision and the graph’s derived_from hash, so no pull-request job needs a secret. Each derived value cites its source by URL and commit or hash. No private name appears in a file, commit, pull request or issue, and reports and documents name internal data neutrally, as internal experiments.Checked by: provenance schema rules; a check that every committed config.json has an allow-listed licence in its model.yaml; a scan of committed files for private names. These run in CI on the project’s own repositories. No simulation path reads, requires or enforces a licence: the loader checks that data is well formed, and a catalog or coefficient registry a user supplies is not refused for lacking a licence record. Maintainer practice (§4.2): reviewers keep private names out of commit messages, pull requests and issues.
  • X13 Every behaviour change has a test that fails without it. A test asserts observable behaviour. It does not assert source text, declaration order, hashes, or recorded outputs as a shortcut for behaviour, and such a test counts towards no tier of §7.4. A validation change (§8.9) to a published number carries success criteria fixed in advance, plus held-out evidence. A verification change that moves published numbers, such as a fidelity fix, carries the price-change report and the scoring harness’s reported values on published units, and is never rejected for exposing an error elsewhere (VAL-11). A refactor shows identical output on the byte gate and on the dashboard’s corpus: the recorded configuration of every ledger unit the dashboard can simulate, re-run through the scoring harness, with no measured value read. 4.2 Three kinds of rule

Every invariant is kept in one of three ways. The design says which, so that a rule with no program behind it is a stated decision.

The three kinds of rule differ in who keeps them: a program, a person with write access, or an agent.

The test. A rule is automated when a program can decide it from the repository’s own contents and what it imports, the same way each time. A rule about who holds a permission, about a repository’s settings, or about an act only a person can perform is a maintainer practice. A rule that shapes how a change is written or judged, and that a program cannot decide, is agent guidance. A rule can be more than one kind: a person signs a commit, and an agent follows the convention that words its message.

Lints. A lint reads source text, headers or the import graph. It checks where code lives and how it is written, so it is automated for architecture: the import graph, licence and provenance headers, generated-file freshness. A lint never stands as the only check of a correctness invariant. Determinism, independence from the clock and neutrality of the cost model each have a behavioural test (X6, SUB-11), and a lint is called a lint, never a test.

Dependency direction holds for all three. An automated check reads only its own repository and what it imports (X7). A check in one repository never reads the settings, branches, issues or workflows of another. A practice is kept in the repository it concerns. A program is added for a rule only when the rule is deterministic and local, and protects the correctness or accuracy of the product.
