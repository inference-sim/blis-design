4Rules that span repositories

These rules hold across the whole system. A pull request that breaks one must not merge, whatever its tests show. Each rule lists its target checks, the repository that runs each check, and the review guidance that remains.

Review guidance is reserved for questions that need judgement. A question is guidance for the review agent, never a check. When a pull request changes something a question covers, the review agent answers it in a review comment, yes or no, with a reason and the files and lines that support it. No CI job fails or waits on a question, and no person has to answer one. The question’s Expertise line names the knowledge the agent brings, not a group of people. An answer in the unwanted direction is a finding, which the one reviewer with write access reads with the rest of the review (§13.2).

  • X1 Users configure BLIS with the upstream's own configuration. What a user would hand llm-d, vLLM or SGLang is what they hand BLIS, in the upstream's own field names, types, defaults and errors. BLIS adds only what the real system learns from its environment: hardware, cluster topology and workload. Engine repositories resolve defaults exactly as the upstream does. The router needs no port of its defaults: the fork runs llm-d's own flag parsing, configuration loader and Kubernetes decoding unchanged, so a value the real router rejects is rejected with the router's own message. An unknown or unsupported field is refused by its upstream name, never ignored. The one exception is the router's flags that only change how a deployed router is served or observed (transport, TLS, leader election, ports, telemetry). Those are accepted, have no effect, and are named in a warning.

4.1 Process rules

  • X10 Repositories are merged bottom-up, and inference-sim is the only repository whose release is required. A tag in any other repository is optional: no pin names one and nothing waits for one. A change spanning repositories is one review set. Each repository's part is on its main branch, or on a release branch (§14.4), before an inference-sim release pins it. A repository that inference-sim pins merges pull requests with a merge commit or a fast-forward, never a squash or a rebase, so a pull request's head commit, once merged, stays on the branch.Checked by: release bot (§13.6). Maintainer practice (§4.2): those repositories allow no other merge method.
  • X11 Pins are exact commits. A repository pins another BLIS repository by one commit: a Go module by that commit's pseudo-version, anything else by its full hash. blis-config-search and accuracy-dashboard pin an inference-sim release by its tag and commit, and move to each new release automatically (§13.6). A pin never names a branch, a local path or @latest. The commit an inference-sim release pins is on the pinned repository's main branch or on one of its release branches. While a review set is open, a pull request may pin the head of a pull request below it in the same set (§13.6). The only committed replace directive is the one in inference-sim's go.mod that substitutes the router fork for upstream llm-d. It exists because the fork keeps upstream's module path (github.com/llm-d/llm-d-router), so Go cannot fetch the fork by its own path; a replace is Go's only way to substitute it. It names the pseudo-version of one commit of the fork, never a branch or a local path, so it pins as exactly as a require does, and go.sum records its hash. It may appear only in inference-sim, because Go ignores replace directives in every module but the one being built. No other module requires the fork; engines and other repositories use only the router contract in contracts/embed. The only committed exclude directives are those in inference-sim that skip a plain tag made before the rule of §14.1, and no repository commits a go.work file.Checked by: selected-version lint (LIF-2), in every repository: each BLIS module resolves to a pseudo-version, or to a tag made before the rule of §14.1; no replace outside inference-sim; in inference-sim, exactly one, from github.com/llm-d/llm-d-router to github.com/inference-sim/llm-d-router; no other module requiring github.com/llm-d/llm-d-router; exclude directives only in inference-sim, each naming a plain tag of an engine module; no committed go.work. The release bot checks that each pinned commit is on its repository's main branch or a release branch.
  • X12 Only derived values are committed, never third-party data, with one exception: vendor config.json files whose licence is on the allow-list. Each such model records the licence identifier in its model.yaml; a model whose licence is not on the allow-list commits only the file's hash and revision, and the deriver fetches it in a nightly job that holds the access token; pull-request jobs check only the committed hash and revision and the graph's derived_from hash, so no pull-request job needs a secret. Each derived value cites its source by URL and commit or hash. No private names appear in files, commits, pull-request text or issue text, and reports and documents name internal data neutrally, as internal experiments.Checked by: name scan in every repository, which also reads the text of every open issue each night; provenance schema rules; a check that every committed config.json has an allow-listed licence in its model.yaml. These are checks on the project’s own repositories, run in CI. No simulation path reads, requires or enforces a licence: the loader checks that data is well formed, and a catalog or coefficient registry a user supplies is not refused for lacking a licence record.
  • X13 Every behaviour change has a test that fails without it. A validation change (§8.9) to a published number carries success criteria fixed in advance, plus held-out evidence. A verification change that moves published numbers, such as a fidelity fix, carries the price-change report and the scoring harness's figures on published units, and is never rejected for exposing an error elsewhere (VAL-11). A refactor shows identical output on the byte gate and on the dashboard's corpus: the recorded configuration of every ledger unit the dashboard can simulate, re-run through the scoring harness, with no measured value read. That corpus covers shapes the byte gate does not. Each nightly run of the whole corpus records which functions each point reaches. A pull request then runs every point that reaches a function it changes, in parallel; with no such record for its base, it runs the whole corpus. The whole corpus also runs before every release. A pull request that is both a refactor and a behaviour change is split.Checked by: byte gate in inference-sim; the corpus comparison, run by the scoring harness at the pinned commit from each repository's CI, for pull requests declared as refactors; landing gate (VAL-6); mutation checks: on a pull request, the functions it changes and the functions covered by any test it changes are mutated, and only the tests that cover them run; and the full sweep runs nightly and on release tags.
  • X14 A pull request's description is accurate: the commit hashes it lists are the branch heads, it merges cleanly, and every invariant it cites exists.Checked by: the description check, a shared workflow run in every repository.
  • X15 Each validation rule exists once, in Go, in blis-substrate. Python tools validate data by calling the substrate's validate command. A Python check that restates a Go rule must pass a test that runs both on the same set of failing examples.Checked by: the parity test in blis-substrate; a lint that flags schema-like rule code in Python scripts.
  • X16 A skipped test in a required or gate job is a failure, not a pass, unless it is on the quarantine list of X25. A gate's workflow triggers are among the paths it declares, so removing a trigger needs review. A gate whose last real run is more than seven days old is shown as failing.Checked by: each repository's CI configuration; the nightly status page (§13.4).
  • X17 Every repository's protected branch requires its named checks, including formatting and lint. No change merges without a successful run of them, on the tree being merged (X22).Maintainer practice (§4.2): the repository’s own branch protection, set by a person with write access and enforced by the hosting service on every merge; its required checks are the repository’s own jobs. No other repository audits it. The settings are on the maintainer checklist (§13.1).
  • X18 Every check in the invariant registry names a known-bad input that must make it fail. A check that cannot fail is not a check.Checked by: a nightly job in blis-substrate that runs each check on its known-bad input and fails if the check passes; the nightly mutation sweep (T7), which covers substrate validators and the simulator's own checks as well as engine code.
  • X19 Scripts and generators, in every language, never write an engine default. They leave an unstated setting unstated, or read the default with inference-sim fields. A rendered scenario or report shows each resolved value with its source: stated by the user, recorded by the measured run (including a value it logs as resolved), the engine's default, or, for a workload-dependent value, a cited measurement (D8).Checked by: the engine-name lint (X2), run on *.py and *.sh in every repository that has scripts; in every scenario generator, a test that a generated scenario contains only stated or recorded values, and workload-dependent values with their citation.   • X20 A commit written with an agent's help says so in one Assisted-by: <tool> line, and carries no Co-authored-by line naming the tool. An agent never signs off in its own name, since only a person can certify the DCO. Signing a commit and adding a DCO Signed-off-by line are encouraged for the person who takes responsibility for it, and an agent that pushes commits for a person, on that person’s instruction and with that person’s key, may sign and sign off in that person’s name; no check requires either. Release-bot commits are signed with the bot's identity and carry no sign-off. In the router fork, this applies to every commit not reachable from the upstream tag being merged; upstream history is kept as upstream wrote it.Checked by: a commit-policy check, required on every pull request in every repository, over the commits the pull request adds. It checks the form an agent can get wrong: one Assisted-by line, no Co-authored-by naming a tool, no Signed-off-by naming a tool. It does not check for a signature or a sign-off. Maintainer practice (§4.2): the person who takes responsibility signs the commits and signs them off, or instructs an agent to push them in that person’s name. It is encouraged and never fails a pull request. Agent guidance (§4.2): how a commit message names agent help.
  • X21 Everything a build or a release runs is pinned and traceable. GitHub Actions are pinned by commit, not by tag. Python environments used by oracles and fitting scripts are locked with hashes. Each inference-sim release publishes build provenance and a software bill of materials. Each repository keeps the licence and notice files its code requires, including blis-vllm's NOTICE for code derived from vLLM; by policy blis-sglang keeps one too for code derived from SGLang. Each derived file keeps upstream's licence header (vLLM's SPDX line, SGLang's Apache notice) and states that it was changed, as Apache-2.0 section 4(b) requires.Checked by: a workflow lint that refuses an action not pinned by commit; pip install --require-hashes in every Python CI job; the release job, which fails without provenance and a bill of materials; a check that LICENSE and any required NOTICE exist; the provenance test checks each derived file's licence header.
  • X22 Every verdict (a CI result or the review agent's review, including its answers to review questions) names the git tree hash of the exact tree it judged. A CI verdict is on the head tree of the pull request. The review agent’s verdict is on the head tree, and is given again after a push. BLIS repositories do not use a merge queue. Every job that scores, fits or checks data states the minimum number of items it must process, and fails below it. No step in a required job ignores an exit code.Checked by: the shared pull-request check in blis-substrate/.github/workflows, called by every repository, which records each review-agent answer with the head tree; branch protection, which dismisses an approval when a push changes the tree; a workflow lint that refuses ignored exit codes; each job's item count.
  • X23 A version is written in one place. stack.json, each repository's go.mod, contracts/toolchain, and each application's or harness pin file are the only files that state a version; every other file that mentions one (Dockerfiles, workflow files, documentation) is generated from them. Documentation does not repeat a version those files state: it says “the pinned release” and links to the file that states it. A page names an upstream release only when the page is about that release, or where a citation needs it (vllm/<path>:<lines>@<commit8>), because a line number means nothing without its release. A workflow reads the Go version from go.mod. A draft specification under specs/ is a record of what was planned and is exempt.Checked by: a lint in every repository, over every file type except records under specs/, for version literals of BLIS modules or Go that are not generated.   • X24 Every review finding ends in one of three outcomes before merge: fixed, filed as a linked issue, or rejected with a reason. An issue closes only through a commit or pull request that names it, or as not planned, by a reviewer with write access, with a reason.Checked by: branch protection, which refuses a merge while a review conversation is unresolved; a pull-request check that refuses a thread with no outcome; a nightly job in each repository that reopens an issue closed any other way.   • X25 Tests read only their declared inputs, never sibling checkouts, ignored directories or the user's environment.   • X26 In documentation, every source path, symbol, issue or pull-request reference, and every statement that a feature is supported, is either generated (from surface.json, stack.json or the code) or checked against the pinned tree. A pull request carries the documentation change that its own change needs: a path it removes or renames, a behaviour it changes, a setting it adds or drops. A repository that adopts the check clears the findings it already has in the pull request that first requires the check, so the check is green from then on and every later finding is a pull request’s own. No finding is hidden from the check by a list of known ones. Documentation has two kinds of reader and is written for each. A person needs the concept: the design, the invariants, the process and why they are so, with no version, count or other detail that changes without the idea changing. An agent needs pointers: where a rule, a file or a command lives, so it can change the code correctly. Each page is for one of them, says which, and is no longer than that reader needs. A page for people holds no path, symbol, version or count, so there is nothing in it for a check to fail on; the reference check reads the pages for agents, and skips records such as specs/ and RFCs, which say what was true when written. A check that fails a pull request for something it did not touch, or for a detail that was never needed, is a defect in the check, and the fix is to narrow the check or delete the detail, never to add a list of known findings. Documentation is short, it says where a rule, a file or a command lives and links to it, and it leaves out anything that can drift without a check noticing, such as a version, a count, a line number or a list of what is supported at the moment of writing.Checked by: a documentation reference check in every repository, which fails on any reference that does not resolve in the tree the pull request produces. In the router fork the check covers the documents the fork wrote; upstream’s documents are kept as upstream wrote them (X4). Review guidance (§4.2): the review agent asks whether the change leaves a document describing something it removed or changed, and raises a finding when it does.
  • X27 An open bug labelled as breaking an invariant blocks a release of the repository where the bug lives, and of each repository that ships that code, unless the release fixes only that bug or a security issue, or a release owner records a waiver in the release notes.Checked by: the release bot.
  • X28 An issue in a BLIS repository that is cited as the reason for a refusal, for a refused or not-modelled item in a field or surface list, or in a code comment that marks a gap or a divergence, stays open.   • X29 Each engine module, the substrate, the router fork and inference-sim document themselves in one README.md. 4.2 Three kinds of rule

Every invariant is kept in one of three ways. The design says which, so that a rule with no program behind it is a decision and not a gap.

The test. A rule is automated when a program can decide it from the repository’s own contents and the repositories below it, the same way release after release, and when running it needs no knowledge of a repository above it. A rule about the repository as a whole, about who holds a permission, or about an act only a person can perform is a maintainer practice. A rule that shapes how a change is written or judged, and that a program cannot decide, is agent guidance. A rule can be both: a program checks the form of a commit message while an agent follows the convention that produces it, and a person signs the commit.

Dependency direction holds for all three. An automated check reads only its own repository and the repositories it depends on (X7). A check in one repository never reads the settings, branches, issues or workflows of another, and no job exists to audit a practice from a different repository. A practice is kept in the repository it concerns, in that repository’s own settings and documentation. Agent guidance names only what the repository it is rendered into may know. A program is added for a rule only when the rule is deterministic and local; complexity, or a link between layers that the dependency direction forbids, is a reason to keep a rule a practice.
