10The data ledger

10.1 Sources

Four external sources feed BLIS:

  • SemiAnalysis InferenceX: end-to-end serving benchmarks for vLLM, SGLang and other engines, plus collective benchmarks (CollectiveX), operator benchmarks (OperatorX), agent traces and speculative acceptance curves.
  • NVIDIA AISimulate: operator sweeps per chip, collected under vLLM, SGLang and TRT-LLM.
  • NVIDIA's forward-pass dataset on Hugging Face (nvidia/aisimulate-fpm-dataset, Apache-2.0): whole forward-pass timings per model, chip and layout.
  • Red Hat's configiq dataset on Hugging Face (redhat-performance/configiq-performance-upstream-data, CC-BY-4.0): aggregate end-to-end GuideLLM measurements of upstream vLLM releases, one row per model, accelerator, release, layout, workload and concurrency. It holds no per-request data, no run identifiers, no timestamps and no engine command lines, so it supplies aggregates only.

Each source is useful for several purposes. The ledger lets each source be used for all of them, while making sure no single data point is used for two purposes that must stay apart.

10.2 Units, identities and roles

A unit is the smallest piece of data the ledger assigns a role to:

  • one InferenceX benchmark run of one deployment and recipe fingerprint at one concurrency, with the measurement of each attempt that produced one;
  • one point of a CollectiveX or OperatorX run, such as one token count;
  • one point of an AISimulate sweep, such as one matrix shape;
  • a forward-pass cell;
  • one configiq row's configuration at one concurrency, with each measurement of it.

Its identifier, unit_id, is the SHA-256 of a canonical JSON object holding only the source's own identifying fields. The JSON is UTF-8, with sorted keys and no spaces. Because nothing from BLIS enters the identifier, a BLIS change can never change a unit's identity.

How roles are assigned

A unit's role is computed, not stored. Units that are near-copies of each other must share a role, or one could be fitted while its near-copy judges the fit. So the role is drawn per role key, not per unit. For InferenceX the role key is the source plus model, hardware, precision, framework, benchmark type and configuration hash. It leaves out the recipe fingerprint, concurrency, measured date and benchmark run, so one deployment's whole sweep and its re-measurements share one role, whether or not each record carries a fingerprint. Every field of the role key is an identifying field, so a unit's identity fixes its role key. For CollectiveX, OperatorX and AISimulate it is the run or file, so a whole sweep shares one role. For the forward-pass dataset it is the source, revision, model, chip and layout. For configiq it is every identifying field except the concurrency, so one sweep and its re-measurements share one role. Legacy units are the exception: they keep their legacy side (below). The rule is HMAC-SHA-256(seed, role_key) mod 100, compared with cut-points fixed per source in the ledger. For example, one source might send 0–29 to fit, 30–39 to select, 40–49 to validate, 50–79 to held and 80–99 to anchor. For a unit on a legacy side, the same value is compared with two more cut-points fixed per source, one dividing fit from select and one dividing held from anchor. The HMAC's message is the canonical JSON of the role key, and its digest is read as a big-endian unsigned integer. The seed is 32 random bytes from a cryptographic generator. It is a CI secret, and only its SHA-256 is committed; with 256 bits of entropy, the seed cannot be recovered from its hash. Who generated it, when, and who owns its rotation are recorded in the ledger.

What the ledger commits, under catalog/ledger/:

  • the sources, each pinned to an exact revision;
  • the units, by unit_id, identifying fields and role key;
  • the ingest report: for each source revision, the records read, those merged as duplicates, those joined into one unit, and those left out, each with its reason;
  • the cut-points and the partition version;
  • the legacy table and any alias tables (below);
  • the hash of the seed.

Units come from the source, not from the pull request. The unit list is generated by the ingest tool from the pinned source revision, which puts every identifying field in one canonical form. CI regenerates the list and requires it to match byte for byte. Each measurement belongs to exactly one unit. The ingest tool recognises a measurement by the SHA-256 of the canonical JSON of the record's measured values (for InferenceX, its metrics object). A record that reports an error, or whose measured values are empty, is not a measurement; it is left out and counted. The conclusion of the benchmark run, such as a failed or cancelled matrix, is recorded on the unit and does not remove it, because a run that fails in one job still writes real measurements from the others. A source sometimes stores one measurement as several records, as when each attempt of a benchmark run becomes its own row. Records with the same identifying fields and the same measured values are one unit: the ingest tool keeps the record with the smallest source row id (for InferenceX, benchmark_results.id; for a file source, the path and then the line) and lists the others as its duplicates. Because the records agree on every identifying field and every measured value, the choice cannot change the unit's identifier or role. It decides only which record's other fields, such as the image digest and the server log, the unit carries; a field only a duplicate records is taken from the duplicate with the smallest row id that records it. Records with the same identifying fields and different measured values are one unit holding each measurement, and their spread counts as the measurement's own noise (COV-10). The same measured values under two identities with one role key are one unit, under the identity of the record with the smallest row id. Under two identities whose role keys differ, they are left out, because they could let one measurement draw two roles. The ingest report counts every record merged, joined or left out. So a pull request cannot re-add a known measurement under a new unit_id to get a new role draw.

The ledger never commits the role of a select, validate or held unit. At each substrate release, a seed-holding release job writes the three published lists, catalog/ledger/published/fit.yaml, anchor.yaml and report.yaml. These three files are runtime data and are embedded with the rest of the catalog. The rest of the ledger is not.

Who may see which roles

InferenceX data are public. If every role were written down, anyone could work out which units are held out and tune a change against them. So the roles are revealed only as far as each job needs:

RoleWho learns the members
fitPublished with each substrate release, as a list of unit identifiers. Fitting scripts, people and agents read it.
anchorPublished, because the dashboard shows these points.
selectOnly the select job, which scores candidates on these units and returns aggregate results. It runs in blis-substrate for operator-level candidates and in accuracy-dashboard for whole-run candidates.
validateOnly the error job, the nightly job that measures method error (VAL-5), which returns aggregates. It runs in blis-substrate for operator-level methods and in accuracy-dashboard for whole-run comparisons.
heldOnly the gate job, which returns aggregates (D7). It too runs in blis-substrate for operator-level gates and in accuracy-dashboard for whole-run gates.
reportPublished; these units never produce a number.

For a unit whose role key holds no legacy unit, the published lists do not separate select, validate and held, so a change cannot be tuned against the held units without access to the gate job. Units on a legacy side, legacy or new (below), are different. The old FIT and HELD labels and the rules that assign a side are public, so the fit-side units not on the published fit list are exactly the select units, and the held-side units not on the anchor list are exactly the held units. The gate therefore reports every held unit on a legacy side as a separate figure, marked as not blind, for as long as such units are used.

Pull-request code never sees the seed

A candidate is code the pull request controls. If it ran in a job that holds the seed, it could read the secret, or leak which units are held through its output. So every scoring run has two jobs. A candidate job, with no secret, fetches its modules and the pinned scoring harness, then runs the candidate with no network on every unit not on the published fit, anchor or report lists, and writes one prediction per unit. The seed-holding job runs only scorer code from main, computes roles, and reduces the predictions to aggregates. Each aggregate covers at least 10 units; a smaller lane is merged with its neighbours or not reported. A candidate could still try to learn which units are held, by corrupting its predictions on chosen units and watching the aggregates move. So held-unit aggregates are returned only for a pre-registered change, or by the nightly and pre-release gate runs, which are counted and reported as such; every evaluation is counted (below). Pull-request jobs without a pre-registration may read only the published fit units, through the dashboard's scoring harness (§11.7). Their figures inform review and are never landing evidence. Anchor units are scored only for the published dashboard, so no change can be tuned against the figures it reports.

Each pre-registration commit gets one evaluation on held units. Any further evaluation of the same change is counted, and the count is shown on the pull request and in the release notes, so repeated tuning against held units is visible.

Three properties of the rule

  • Append-only. Roles for new units are drawn inside the jobs that hold the seed, the first time a unit appears, and before any job uses it. An existing unit keeps its role unless a new partition version, approved in a pull request by the reviewer with write access, says otherwise.
  • Legacy units keep their old side. A partition made before the ledger existed is carried over through ledger/legacy-map.yaml. Each legacy unit keeps its old label, fit side or held side, and the keyed rule chooses only within that side: fit or select, held or anchor. A unit whose legacy records carry both labels takes the fit side, because some of its records may already have been fitted on, and data that was fitted on cannot judge a fit. This happens when the new identity joins records the old partition split, for example by removing the image digest. A new unit whose role key holds legacy units takes their side, and the fit side if they hold both. Legacy units of one deployment can still be on both sides, because the old partition split deployments by concurrency; this is one more reason legacy held units are not blind. A coefficient fitted from legacy records before the ledger existed cites their units. A substrate release refuses such a coefficient while any unit it cites is in select; it is refitted from the fit list first (D1). The ingest tool generates the map from legacy point identifiers to units and commits it with the legacy table, listing each unit that takes a side by these rules. Because the old split is public, legacy held units are not blind (above).
  • Stable when identities are recomputed. If InferenceX renames a field, or a change to the ingest tool changes how identifying fields or role keys are computed, the affected unit_ids or role keys change, and units would be redrawn: a held unit could become a fit unit. So such a change must ship an alias table from old to new unit_id and role key, and an aliased unit keeps its role. The alias table is generated, not written: CI runs the merge-base and candidate ingest tools on the same pinned source revision and pairs the identities each gives the same records. A change whose aliases would give one new unit or role key two different roles needs a new partition version, which a person approves. The ingest code detects such a change from the source's contract version (§12.8).

When a partition version is retired, its seed is published. The committed hash then lets anyone check that the split was drawn as claimed.

  • D8 A quantity BLIS simulates, such as prefix-cache hits or queueing, is never stored. A quantity that depends on the request stream but that BLIS does not simulate, such as speculative acceptance or expert routing balance, is a property of the workload. It is keyed by workload identity and never stored as a coefficient scoped only to a chip or model. Its value is taken from the command line if stated there, else from the scenario, else derived from the trace, else taken from the substrate's profile for that workload identity, and the Result's inputs record which supplied it (SIM-10). Speculative acceptance is keyed by the target model, the drafter, the speculative method, the number of speculative tokens K, the workload's category and thinking mode, and three collection settings: the engine that measured the value, the draft sampler (greedy or probabilistic), and the verifier. The verifier takes vLLM v0.33.0's values: standard, block or fly. Synthetic rejection sampling, in which the engine forces acceptance, is a realisation (below), not a verifier. The drafter is the model's own in-graph speculator, such as its MTP layers, or a separate drafter checkpoint with its own catalog entry. A profile states each collection setting as its source states it. A setting the source marks as documented carries the value that the connector or the engine fixes, such as standard for an unset verifier, and the profile states that value. A setting the source leaves at its engine's default, with no value, is stated as the marker default. A setting the source marks as unknown is unstated. At lookup, the engine states the run's resolved values and its own defaults at its release, read from its own configuration. The lookup only compares. A profile's default stands for the requesting engine's stated default when the profile's engine is the request's engine, and for no value otherwise. A field that neither side states is unstated, and an unstated field matches only an unstated one. A curve measured on one checkpoint is carried as measured on that checkpoint's own model when the catalog has that model. It may also be carried to another catalog model by a stated transfer, but only while no curve measures that model. A value stated on the command line, in the scenario or by the workload is used as stated. Such a value also says how its run realised acceptance: naturally, by verifying the drafts, or synthetically, by the engine forcing the acceptance. A value that gives the acceptance length AL but no per-position rates is spread over the K positions. A natural value takes the decay pi = qib for the rate at position i, where q makes the rates sum to AL − 1 and the exponent b is fitted to the substrate's measured curves; the substrate states one exponent per method and one fitted to every method, which serves a method with none of its own. A synthetic or unstated value takes the engine's minimum-variance schedule: rate 1 at each of the first ⌊AL − 1⌋ positions, the remainder at the next, and 0 after it. The fitted decay is an estimate, not a measurement; its coefficient method is calibrated (§9.2). It is not judged against held-out end-to-end runs until it passes the landing gate (VAL-6). It names the speculative method it was fitted for, and the Result records the schedule and the decay's method and exponent as an estimated substitution. The schedule changes how many tokens a request advances only in an engine that draws acceptance per step; an engine that does not advances each request by the mean acceptance length. A profile lookup, in the substrate's profiles or in a profile set the scenario names, may borrow when no measured profile has the run's exact key. It takes the closest measured one, in this order. First, the same target, drafter, method and collection settings at another K. Between measured values of K it interpolates linearly. Above the largest it takes the largest's value. Below the smallest it takes that profile's stated per-position rates for the first K positions. A profile that states none gives 1 + K(AL − 1)/K₀, where K₀ is its K. That figure cannot exceed what the profile's own rates would give, so it does not overstate drafting's gain. The lookup never extrapolates. Second, the same target, drafter and method under other collection settings: another engine, draft sampler or verifier, including a profile or request that leaves a setting unstated. It takes the profiles that differ in the fewest collection settings, then the lowest value at the run's K, found by the first step's rules. Third, another drafter of the same target, but only a profile measured with the run's speculative method on the run's engine, so that the drafter is the key field in which it differs from the run, apart from K and the draft sampler and verifier. It takes the lowest value at the run's K, found by the first step's rules, so that drafting's gain is not overstated. A profile of another drafter that also differs in the method or the engine is not a candidate, because the method and the engine can change acceptance by more than the drafter does, and no measurement supports a value borrowed across them. For example, a DSpark drafter on vLLM would take 4.05 from a DFlash drafter measured on SGLang, while internal deployment measurements of that DSpark drafter on vLLM give 2.72. When the only profiles of other drafters differ in method or engine, the lookup is refused, and the refusal names the nearest profile it declined and the key fields in which it differs. The run then states its acceptance in the scenario or on the command line. Fourth, the same method on another target whose graph records the same architecture. Every step keeps the category and thinking mode, apart from a fallback category the user requested. Two profiles that share the whole key but record different sampling settings, such as temperature, are not interchangeable, and an exact key found in two profile sets is ambiguous; the lookup refuses both. Any remaining tie breaks in an order the substrate's acceptance reference states, so the choice is deterministic. With no profile on any step, the run is refused. The Result records the profile used, the step, and each key field that differed.
