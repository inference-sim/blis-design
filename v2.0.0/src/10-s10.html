10The data ledger

10.1 Sources

The ledger (substrate/catalog/ledger/) lists every measured unit from every data source, with each unit's role. It holds these sources:

  • SemiAnalysis InferenceX: end-to-end serving benchmarks for vLLM, SGLang and other engines, plus collective benchmarks (CollectiveX), operator benchmarks (OperatorX), agent traces and speculative acceptance curves.
  • NVIDIA AISimulate: operator sweeps per chip, collected under vLLM, SGLang and TRT-LLM.
  • NVIDIA's forward-pass dataset on Hugging Face (nvidia/aisimulate-fpm-dataset, Apache-2.0): whole forward-pass timings per model, chip and layout.
  • Red Hat's configiq dataset on Hugging Face (redhat-performance/configiq-performance-upstream-data, CC-BY-4.0): aggregate end-to-end GuideLLM measurements of upstream vLLM releases, one row per model, accelerator, release, layout, workload and concurrency. It holds aggregates only: no per-request data, run identifiers, timestamps or engine command lines.

Any other source, such as an engine project's published performance runs or the team's own private runs, joins by the procedure of §12.2. Each source serves several purposes. The ledger lets each be used for all of them, and keeps any one data point from serving two purposes that must stay apart.

10.2 Units, identities and roles

A unit is the smallest piece of data the ledger assigns a role to:

  • one InferenceX benchmark run of one deployment and recipe fingerprint at one concurrency, with the measurement of each attempt that produced one;
  • one point of a CollectiveX or OperatorX run, such as one token count;
  • one point of an AISimulate sweep, such as one matrix shape;
  • a forward-pass cell;
  • one configiq row's configuration at one concurrency, with each measurement of it.

A point is a unit as the dashboard scores it, and has its unit's identifier. The identifier, unit_id, is the SHA-256 of a canonical JSON object holding only the source's own identifying fields. The JSON is UTF-8, with sorted keys and no spaces. Nothing from BLIS enters the identifier, so a BLIS change never changes a unit's identity.

Each source identifies a unit by its own fields, and nothing from BLIS enters the identifier.

Training data is every unit whose role is fit, select or validate, and all data from a source with no held-out roles. The held-out units are those whose role is held or anchor. Accuracy is reported only on held-out units (D9).

How roles are assigned

A unit's role is computed and never stored. Near-copies of one unit must share its role, or one could be fitted while its near-copy judges the fit. So the role is drawn per role key:

  • InferenceX end-to-end: the source, model, hardware, precision, framework, benchmark type and configuration hash. The key leaves out the recipe fingerprint, concurrency, measured date and benchmark run, so one deployment's sweep and its re-measurements share a role, whether or not each record carries a fingerprint.
  • CollectiveX, OperatorX and AISimulate: the run or file, so a whole sweep shares a role.
  • Forward-pass dataset: the source, revision, model, chip and layout.
  • configiq: every identifying field except the concurrency.

Every field of a role key is an identifying field, so a unit's identity fixes its role key. The role is HMAC-SHA-256(seed, role_key) mod 100, compared with cut-points fixed per source in the ledger. For example, a source might send 0 to 29 to fit, 30 to 39 to select, 40 to 49 to validate, 50 to 79 to held and 80 to 99 to anchor. The HMAC's message is the canonical JSON of the role key, and its digest is read as a big-endian unsigned integer. The seed is 32 random bytes from a cryptographic generator. It is a secret held only by the seed-holding jobs, and only its SHA-256 is committed. With 256 bits of entropy, the seed cannot be recovered from its hash. The ledger records who generated the seed, when, and who owns its rotation.

The draw is random by role key and controls no dimension. Role keys that differ only in precision, framework or configuration hash can fall on opposite sides, so the sibling of a held unit may be a fit unit. Held-out accuracy therefore measures generalisation across configurations of deployment families that the fit units already cover. Generalisation to a chip or model with no fit unit is measured by leave-one-out runs in the error job (VAL-5) and is published as such. The ledger report lists, for each source, how many role keys hold each role, by chip and by model family. A chip or model family with no held-out key is named there, so that a new partition version can address it.

What the ledger commits, under substrate/catalog/ledger/:

  • the sources, each pinned to an exact revision;
  • the units, by unit_id, identifying fields and role key;
  • the ingest report: for each source revision, the records read, those merged as duplicates, those joined into one unit, and those left out, each with its reason;
  • the cut-points and the partition version;
  • the legacy table and any alias tables (below);
  • the hash of the seed.

The source supplies the units; a pull request does not. The ingest tool generates the unit list from the pinned source revision, in one canonical form. CI regenerates the list and requires it to match byte for byte. Each measurement belongs to exactly one unit. The tool recognises a measurement by the SHA-256 of the canonical JSON of the record's measured values (for InferenceX, its metrics object). A record that reports an error, or whose measured values are empty, is left out and counted. The conclusion of the benchmark run, such as a failed or cancelled matrix, is recorded on the unit and does not remove it, because a run that fails in one job still writes real measurements from the others.

A source sometimes stores one measurement as several records, as when each attempt of a benchmark run becomes its own row. The ingest tool applies these rules:

  • Records with the same identifying fields and measured values are one unit. The tool keeps the record with the smallest source row id (for InferenceX, benchmark_results.id; for a file source, the path and then the line) and lists the others as duplicates. The choice cannot change the unit's identifier or role. It decides only which record's other fields, such as the image digest and server log, the unit carries; a field only a duplicate records comes from the duplicate with the smallest row id that records it.
  • Records with the same identifying fields and different measured values are one unit holding each measurement. Their spread is the measurement's own noise (COV-10).
  • The same measured values under two identities are one unit when the role keys are equal, under the identity with the smallest row id. When the role keys differ, they are left out, because they could let one measurement draw two roles.

The ingest report counts every record merged, joined or left out, so a pull request cannot re-add a known measurement under a new unit_id to get a new role draw.

The ledger never commits the role of a select, validate or held unit. At each release of inference-sim, a seed-holding release job writes three published lists, substrate/catalog/ledger/published/fit.yaml, anchor.yaml and report.yaml. These lists are runtime data, embedded with the rest of the catalog. The rest of the ledger is not.

Who may see which roles

InferenceX data are public. If every role were written down, anyone could find the held-out units and tune a change against them. So each job learns only the roles it needs:

  • fit, anchor and report members are published with each release, as lists of unit identifiers. Fitting scripts, people and agents read the fit list, and the dashboard shows the anchor points.
  • select members are visible only to the select job, which scores candidates and returns aggregates. validate members are visible only to the error job, which measures method error nightly (VAL-5). held members are visible only to the gate job (D7). Each runs in inference-sim for operator-level work and in accuracy-dashboard for whole-run work.

The published lists do not separate select, validate and held, so a change cannot be tuned against the held units without the gate job. Legacy sides (below) differ. The old FIT and HELD labels are public, so the fit-side units not on the fit list are exactly the select units, and the held-side units not on the anchor list are exactly the held units. The gate reports every held unit on a legacy side as a separate figure, marked as not blind.

Pull-request code never sees the seed

A candidate is code a pull request controls. In a job that held the seed, it could read the secret, or leak which units are held through its output. So every scoring run has two jobs:

  • The candidate job has no secret. It fetches its modules and the pinned scoring harness, then runs the candidate with no network on every unit not on the published fit, anchor or report lists. It writes one prediction per unit.
  • The seed-holding job runs only scorer code from main. It computes roles and reduces the predictions to aggregates. Each aggregate covers at least min_points role keys (COV-13); a smaller lane is merged with its neighbours or not reported.

A candidate could still learn which units are held by corrupting its predictions on chosen units and watching the aggregates move. So held-unit aggregates are returned only for a pre-registered change, or by the nightly and pre-release gate runs, and the gate job counts every evaluation made on each partition version. Each pre-registration commit gets one evaluation on held units. The ledger commits a budget of evaluations for each partition version; when the count reaches it, the following release uses a new partition version, which publishes the retired seed (below). Maintainer practice: the count of further evaluations of the same change is shown on the pull request and in the release notes. A pull-request job without a pre-registration may read only the published fit units, through the dashboard's scoring harness (§11.7). Its figures inform review and are never landing evidence. Anchor figures are public and can guide work, so only the prospective figure of D9 is claimed as out-of-sample.

Three properties of the rule

  • Append-only. Roles for new units are drawn inside the seed-holding jobs, the first time a unit appears and before any job uses it. An existing unit keeps its role unless a new partition version says otherwise. Maintainer practice: a maintainer with write access approves a new partition version.
  • Legacy units keep their old side. A partition made before the ledger existed is carried over through ledger/legacy-map.yaml. Each legacy unit keeps its old label, fit side or held side, and the keyed rule chooses only within that side: fit or select, held or anchor. A unit whose legacy records carry both labels takes the fit side, because data that was fitted on cannot judge a fit. A new unit whose role key holds legacy units takes their side, and the fit side if they hold both. A coefficient fitted from legacy records cites their units, and a release refuses it while any cited unit is in select; it is refitted from the fit list first (D1). The ingest tool generates the map and commits it with the legacy table.
  • Stable when identities are recomputed. If InferenceX renames a field, or a change to the ingest tool changes how identifying fields or role keys are computed, the affected identifiers change and units would be redrawn: a held unit could become a fit unit. So such a change ships an alias table from old to new unit_id and role key, and an aliased unit keeps its role. The alias table is generated: CI runs the merge-base and candidate ingest tools on the same pinned source revision and pairs the identities each gives the same records. A change whose aliases would give one new unit or role key two roles needs a new partition version. The ingest code detects such a change from the source's contract version (§12.8).

When a partition version is retired, its seed is published. The committed hash then lets anyone check that the split was drawn as claimed.

A frozen archive, such as InferenceX's database dump, owns the record ids up to its cutoff, and the live feed owns the ids above it. A row at or below the cutoff is never pulled again from the feed, because the two can report the same row's numbers differently.   • D8 A quantity BLIS simulates, such as prefix-cache hits or queueing, is never stored. A quantity that depends on the request stream and that BLIS does not simulate, such as speculative acceptance or expert-routing balance, is a property of the workload. It is keyed by workload identity, never by chip or model alone. Its value comes from the first of these that has it: the command line, the scenario, the trace, the substrate's profile for that workload identity. The Result's inputs record which one (SIM-10).
    • Key. Speculative acceptance is keyed by the target model, the drafter, the speculative method, the number of speculative tokens K, the workload's category and thinking mode, and three collection settings: the engine that measured it, the draft sampler (greedy or probabilistic) and the verifier (standard, block or fly, as the modelled commit defines them). Synthetic rejection sampling, in which the engine forces acceptance, is a realisation (below), not a verifier. The drafter is the model's own in-graph speculator, such as its MTP layers, or a separate drafter checkpoint with its own catalog entry.
    • Collection settings. A profile states each setting as its source does. A setting the source documents carries the value the connector or engine fixes, such as standard for an unset verifier. A setting the source leaves at the engine's default is the marker default. A setting the source marks unknown is unstated. At lookup the engine states the run's resolved values and its own defaults at the modelled commit, and the lookup only compares them. default stands for the requesting engine's default when the profile's engine is the request's engine, and for no value otherwise. An unstated field matches only an unstated one.
    • Models. A curve measured on one checkpoint is carried as measured on that checkpoint's own model when the catalog has it. A stated transfer may carry it to another catalog model, only while no curve measures that model.
    • Stated values. A value stated on the command line, in the scenario or by the workload is used as stated. It also says how its run realised acceptance: naturally, by verifying the drafts, or synthetically, by the engine forcing acceptance. A value that gives the acceptance length AL without per-position rates is spread over the K positions. A natural value takes the decay pi = qib at position i, where q makes the rates sum to AL − 1 and the exponent b is fitted to the substrate's measured curves. The substrate states one exponent per method, and one fitted to every method for a method with none. A synthetic or unstated value takes the minimum-variance schedule: rate 1 at each of the first ⌊AL − 1⌋ positions, the remainder at the next, and 0 after. The fitted decay is an estimate with the coefficient method calibrated (§9.2). It is not judged against held-out end-to-end runs until it passes the landing gate (VAL-6). The Result records the schedule and the decay's method and exponent as an estimated substitution. The schedule changes how many tokens a request advances only in an engine that draws acceptance per step; any other engine advances each request by the mean acceptance length.
    • Borrowing. When no measured profile has the run's exact key, the lookup takes the closest measured one and never extrapolates. It tries these steps in order.
