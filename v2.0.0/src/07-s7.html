7Fidelity to upstream code

7.1 What an engine port contains

An engine repository ports all of its upstream's code that decides what each step runs and what each request's KV cache costs. That code falls into four parts. Each surface-list item (§7.5) has one primary part, the one that owns most of its decisions. A feature whose code spans parts, such as speculative decoding, LoRA or HiSparse, is still one item, and it names the other parts it touches. The table names each upstream's classes at the release the engine repository pins; the names change between releases, the four parts do not.

7.2 The method

"Faithful to vLLM" means: give vLLM's own scheduler and BLIS's Go port the same inputs, and they make the same decisions at every step. To run vLLM's scheduler without GPUs, a test harness replaces only its environment. Everything else is vLLM's own code at a pinned commit. Figure 3 shows the arrangement.

7.5 The surface list: making gaps visible

The tiers test only ported code. To show what is not ported, each upstream-tracking repository generates a surface list (surface.json) from the pinned upstream's source. The generator reads the upstream's own plugin registration tables, so a new feature in an upstream release appears in the list without anyone remembering to add it.

UpstreamWhat the generator reads
vLLMconnectors registered with KVConnectorFactory (every registered name, with aliases, where one name maps to another's class, recorded as such); offload and tier types; KV-cache spec types and group roles registered with KVCacheSpecRegistry, read after its registration function runs, and the manager each maps to; speculative methods; scheduler policies; configuration classes. Metrics are not held in one registration table in vLLM; the generator finds every Prometheus metric constructor in the source.
SGLangtransfer backends (disaggregation/utils.py TransferBackend); HiCache storage backends; tree caches the selection code can choose, including those registered with register_radix_cache_backend; tree-core backends; allocator and memory-pool types; speculative algorithms; scheduling policies; ServerArgs groups; metric families; event types

Each item has one status (X9). The aim is that every item the llm-d stack uses is modelled. The other two statuses are exceptions, and each needs evidence a reviewer can check:

  • modelled, naming the oracle scenarios that cover it. This is the default goal for every item.
  • refused, meaning the engine refuses it by name until it is modelled. The item names its issue and the backlog counts what it blocks (§11.6). A refused item waits in the backlog, and the item that blocks the most dashboard points or published deployments is the next one modelled.
  • out of scope, for an item BLIS will not model. Only three reasons are allowed: the item runs only on hardware BLIS does not simulate (for example AMD-only or TPU-only); it does no work the simulator prices (for example a multimodal encoder when BLIS simulates text serving); or it is deprecated upstream and slated for removal. The reason names which of the three it is, with a citation to the upstream code or announcement. An item may be out of scope only while its weight (below) is zero. Otherwise it is refused, and appears in the backlog.

"Hard to port", "rarely used" and "needed later" are not reasons for either exception; they are priorities, which the weight and the backlog already express.

Each item also has a weight: how many distinct deployments in llm-d's published guides and model recipes use it, and how many accuracy-dashboard points it blocks. surface.json holds only statuses, because an engine repository cannot depend on the guides or the dashboard (X7). The guides commit is pinned once, in inference-sim's guides.lock. Each release records it in stack.json, and inference-sim coverage publishes each item's deployment count. The accuracy dashboard, which sits above every other repository, adds its own blocked-point counts to give the weights, and opens an issue against the engine repository for any out-of-scope item whose weight is not zero. The engine then marks the item refused. The count parses each rendered manifest's engine arguments with that engine's own argument parser. The weighted share of modelled items is published with every release (SIM-5), and an engine release may not lower it (X9). The list is also the reading list for an upgrade: the difference between two releases' lists is the new work.

7.6 Port a shared framework before the features built on it

Connectors, tiers and KV-cache managers are built on shared frameworks. In vLLM these are the connector base class; the offload spec, manager and tiering layers; and the KV-cache coordinator with the manager base class, which every spec type's manager extends. In SGLang they are the HiCache controller and storage interface, and the tree-cache interface with the allocator and memory-pool base classes. Porting one framework completely, with recorded traces of its contract, makes each further connector, tier or manager a smaller change. Without it, each one is a large port of its own. Engine repositories therefore port a framework as a unit before porting the features built on it.

A framework's interface is the abstract class or classes that its features implement or call. For the connector base it is the connector base class, for offload tiering the offloading manager and spec, and for HiCache the storage interface. A framework's traces are taken at that interface and are of two kinds. A recorded trace is the sequence of interface calls that a real feature makes while the oracle runs a scenario. The port receives the same calls, and its answer to each is compared with the upstream's. A direct trace is a sequence of calls made by a driver that the engine repository writes, including orderings that no existing feature makes. Recorded traces keep the call mix realistic. Direct traces test the contract itself, not one feature's use of it. A part of a framework that reads the clock is traced with the clock replacement that FID-1 lists. A part that does its work in threads, as HiCache's controller does its backups, loads and prefetches, is run by the step-driven runner of FID-1: each thread body runs unmodified, one loop iteration at a time, at the step boundary its manifest entry declares, so that its decisions are traced in a fixed order. When only some parts of a framework have traces, the surface list holds the parts as separate items, each with its own status.

7.7 Fidelity invariants

  • FID-1 The manifest lists every replacement. Any write the harness makes outside a listed site fails CI, and a changed list carries a new version. The configuration the oracle resolves equals, outside the fields the manifest lists, what the upstream's CUDA platform would resolve for the chip the scenario names. Restoring a CUDA value that depends on choosing a CUDA attention backend is a transcription (FID-8), checked against recorded CUDA start-up logs. Every read of the current platform reachable from ported code is listed in the manifest. Each read counts as one site: every call of a platform predicate, and every read of a platform attribute. A module constant computed from the platform at import, such as _is_cuda = is_cuda(), counts once at its definition and again at every read of the constant, so a read cannot hide behind a constant. Clock reads and thread starts reachable from ported code are listed the same way, one site per read or start. A thread start is not run as a thread. The step-driven runner replaces it: the thread's target, unmodified, runs synchronously, one iteration of its loop at the step boundary its entry declares ("thread body run synchronously at step k"), and the completion of a device stream or event it waits on is reported at that boundary too. Each start site is one listed environment entry naming its target and its boundary. The runner's scheduling rule is stated once, in the manifest, and no thread body is copied into the harness (FID-8).Checked by: oracle/check_mocks.py, from contracts/harness, in each engine repository; a generator in each engine repository that lists every such site reachable from ported code at the pinned release, and fails when a site has no manifest entry or a listed site no longer exists.
  • FID-2 The oracle runs in a locked Python environment at the pinned upstream commit, and every recorded trace records that commit, the lock file's hash, the scenario's hash, the seed and the manifest version.Checked by: oracle/check_lock.py and the trace provenance check.
  • FID-3 A recorded trace's decisions change only in a commit carrying a golden-reviewed: line that names the trace and gives the reason. Tools refuse to rewrite traces unless an explicit update flag is set.Checked by: oracle/check_goldens.py; the oracle runners refuse to write traces without the update flag.
  • FID-4 Every ported function is exercised by at least one recorded scenario.Checked by: coverage gate.
  • FID-5 A framework (connector base, offload tiering, HiCache) is marked modelled in the surface list only when it has recorded and direct traces at its own interface (§7.6). A feature built on the framework does not supply them. A part of a framework without those traces is a separate item with its own status. It is not marked modelled, whatever the status of the other parts.Checked by: a surface-list check that a framework marked modelled names recorded and direct traces taken at its interface, and that each part without them is a separate item that is not marked modelled.
  • FID-6 A property asserted about an engine port, such as a monotonicity law, is first run against the upstream oracle. It is adopted only if the upstream satisfies it on the oracle scenarios. A law about the cost model names the upstream behaviour it rests on.Checked by: the property tests run in the oracle tier before they run against the port.
  • FID-7 For every catalog model and each supported layout, the resident weights an engine reports in its PoolPlan (per-rank shape, stored data type and sharding, after the engine's weight post-processing) equal what the pinned upstream allocates. The graph's tensors equal the checkpoint's safetensors headers.Checked by: oracle tier T0 in each engine repository, run whenever a substrate release changes the catalog or the engine moves to a new upstream release.
  • FID-8 The harness may not contain a copy of an upstream decision function. A harness file with a Derived from header, or a function named like an upstream function, is refused unless the manifest declares it as a transcription.Checked by: oracle/check_mocks.py.
  • FID-9 The engine is tested as the simulator drives it, not only on its own. Each recorded trace also records the timed inputs the engine received: arrivals, completions, transfer ends and aborts. Replaying those inputs through inference-sim's driver into engine.Engine reproduces the trace's decisions step by step.Checked by: the coupled replay test in inference-sim's CI, over every engine repository's recorded traces.
  • FID-10 Every compared field and metric series takes its neutral value and at least one other value somewhere in the scenario set, so a comparison of it can fail. The comparison is two-sided: a field or series that appears on only one side is a mismatch.Checked by: a value-coverage report in each engine repository's CI, which fails on any field or series seen only at one value.
  • FID-11 The work a step shape asks the cost model to price equals what the pinned upstream launches for the same step, for each layer: the rows of every matrix multiply, each operation's FLOPs and bytes, the token count of every draft pass, and the context entries each context-dependent operation reads, bounded by its window where it has one. Rows and token counts match exactly; FLOPs and bytes match within a stated tolerance. FID-7 compares what is resident; this compares what runs.Checked by: an oracle comparison, run with T0 and on engine pull requests that change how step shapes are emitted. It executes the upstream forward pass on meta tensors, at the padded batch the upstream launches, under a PyTorch dispatch mode that counts each operation's rows, FLOPs and bytes, with the ranks under a fake process group. Each opaque custom operation, such as attention or a fused mixture of experts, is counted by a rule the manifest lists. Routed-expert rows are compared in total (tokens times experts per token), since routing depends on data. Context reads are counted from the upstream's own attention metadata: sequence lengths, block tables and windows. Known-bad inputs: a matrix multiply priced at fewer rows per token than the upstream runs, and a windowed gather priced over the whole context.
  • FID-12 A connector or storage backend in the pinned tree that calls a KV store package runs that package, and every service it calls that makes a decision BLIS models, at the versions the oracle's lock pins, as code under test. The manifest replaces only their clocks and the transport that carries bytes. The outside-service kind is allowed only for a service that makes no decision BLIS models, such as a tokenizer. Each trace records the package's version, and each call the adapter makes at kvstore.Store, with its answer (§6.5).Checked by: oracle/check_mocks.py, which fails on a replacement inside the package or its services other than a clock or the byte transport, with a replaced Mooncake store master as its known-bad input; oracle/check_lock.py, which fails when the package or a service is missing from the lock or a trace records another version; oracle/check_goldens.py, which fails a trace whose number of recorded calls differs from the number the oracle counts at the package's entry points in the same run.
