7Fidelity to upstream code

7.1 What an engine module models

An engine module models one upstream commit: a release tag, or any commit on the upstream’s main or a release branch. Its Upstream record names the commit and the release the commit descends from. A scenario names the commit by its full hash, or by a tag that the Upstream record lists as an alias of that commit; any other value is refused with the record’s aliases. A build runs one commit of each engine (LIF-6). The module ports all of the upstream code that decides what each step runs and what each request’s KV cache costs. Each surface-list item (§7.5) has one primary part, the one that owns most of its decisions. A feature whose code spans parts, such as speculative decoding, is still one item, and it names the other parts it touches. The table names examples of each upstream’s classes. The surface list (§7.5) is the authority at each commit.

Each part is ported framework first (§7.6). The surface list has a category for each part, so a model or configuration that needs an unported manager, tree cache or pool is refused by name and counted, and does not fail inside the engine. The tiers of §7.4 test the parts: scheduling by T2 and T3; KV-cache management by T2; transfer and tiering by T4 and T5; resolution by T1; lowering by T0, by the comparison of priced with launched work (FID-11) and by T3’s padding comparison. T6 checks the metrics and KV events of every part. T7 and T8 cover all four.

Engine upgrade. An engine upgrade moves a module from one commit to another by porting the diff of the code it already models. It regenerates the committed lists of §7.5 at the new commit, locks the oracle to that commit (FID-2) and runs every tier again (FID-14). Maintainer practice: a module is upgraded at each upstream release, and on demand when a scenario needs a later commit, which a maintainer with write access decides and records in an issue (§12).

Model support. Model support is work in an engine module for one model. It is needed only when the model brings engine-facing code that an upgrade does not port (§12.5).

Model backport. A model that lands upstream between upgrades can be supported at once by applying the upstream commits that add it onto the modelled commit. The Upstream record lists them. A backport carries model code only: it may change only the files under the upstream’s model-definition and model-configuration directories and its model-registry entry, which the Upstream record names. A commit that touches any other path is not a backport, and waits for an engine upgrade. A backport is dropped when the modelled commit contains it. It has no grade of its own: a run is graded by its commit distance from the modelled commit (§11.3).

Upgrade report. Each upgrade generates a report of what the new commit changes and which models it supports; its contents are in §12.4. Its model list is the difference between the architectures registered at the two commits. Each architecture has a status (§7.5).

A new engine, such as TRT-LLM, meets the same bar as vLLM and SGLang. It is a new directory under engines/. It ports the upstream’s scheduling and KV-cache code, and an oracle runs the upstream code to check the port. Where the upstream core is C++, the oracle drives that code through its bindings (FID-2), and the sites of FID-1 apply to the native code.

7.2 The method

A port is faithful to vLLM when vLLM’s own scheduler and BLIS’s Go port make the same decisions at every step, given the same inputs. To run vLLM’s scheduler without GPUs, a test harness replaces only its environment. Everything else is vLLM’s own code at the modelled commit. Figure 3 shows the arrangement. The same method applies to every engine.

7.5 The surface list: making gaps visible

The tiers test only ported code. To show what is not ported, each engine module generates a surface list (surface.json) from the upstream source at the modelled commit.

A model architecture is an item too: it is modelled when the catalog has a handler for it and T0 and FID-11 pass for it. A path by which the upstream serves a model that has no registered class, such as a generic fallback implementation, is an item of its own with a status, and a model that only that path serves is listed under that item in the upgrade report. Each item has one status (X9). Every item the llm-d stack uses is to be modelled. The other two statuses are exceptions, and each needs evidence a reviewer can check:

  • modelled, naming the oracle scenarios that cover it. This is the goal for every item.
  • refused: the engine refuses the item by name until it is modelled. The backlog counts what it blocks (§11.6), and the item that blocks the most dashboard points or published deployments is modelled next.
  • out of scope, for an item BLIS will not model. Only three reasons are allowed: the item runs only on hardware BLIS does not simulate (for example AMD-only or TPU-only); it does no work the simulator prices (for example a multimodal encoder when BLIS simulates text serving); or it is deprecated upstream and slated for removal. The reason names which of the three applies, with a citation. An item may be out of scope only while its weight (below) is zero. Otherwise it is refused.

“Hard to port”, “rarely used” and “needed later” are priorities, not reasons for either exception. The weight and the backlog express priority.

Each item also has a weight: how many distinct deployments in llm-d’s published guides and model recipes use it, and how many accuracy-dashboard points it blocks. surface.json holds only statuses, because an engine module cannot depend on the guides or the dashboard (X7). The guides commit is pinned once, in guides.lock, and inference-sim coverage publishes each item’s deployment count, parsed from each rendered manifest with the engine’s own argument parser. The accuracy dashboard adds its blocked-point counts. The weighted share of modelled items is published with every release (SIM-5), and an engine upgrade may not lower it (X9). The difference between two commits’ lists is the new work of an upgrade.

7.6 Port a shared framework before the features built on it

Connectors, tiers and KV-cache managers are built on shared frameworks. Porting one framework completely, with recorded traces of its contract, makes each further connector, tier or manager a smaller change. A module therefore ports a framework as a unit before the features built on it.

A framework’s interface is the abstract class or classes that its features implement or call. A framework’s traces are taken at that interface and are of two kinds. A recorded trace is the sequence of interface calls that a real feature makes while the oracle runs a scenario. The port receives the same calls, and its answer to each is compared with the upstream’s. A direct trace is a sequence of calls made by a driver the module writes, including orderings that no existing feature makes. Recorded traces keep the call mix realistic; direct traces test the contract itself. A part of a framework that reads the clock is traced with the clock replacement of FID-1. A part that does its work in threads, as HiCache’s controller does its backups, loads and prefetches, is run by the step-driven runner of FID-1, so that its decisions are traced in a fixed order.

7.7 Fidelity invariants

  • FID-1 The manifest lists every replacement. A write the harness makes outside a listed site fails CI, and a changed list carries a new version. Outside the listed fields, the configuration the oracle resolves equals what the upstream’s CUDA platform resolves for the chip the scenario names. The oracle selects the platform class of the scenario’s chip with faked device properties (capability and memory), so that the upstream’s own platform code makes the decision. A transcription (FID-8) is allowed only for a decision that cannot run without a device, and each is listed with the recorded start-up log entries that confirm it for every chip the scenarios name.
    Every read of the current platform reachable from ported code is one listed site: each call of a platform predicate, each read of a platform attribute and each read of a module constant computed from the platform at import, which also counts once at its definition.
    Clock reads, random draws, environment reads and thread starts reachable from ported code are listed the same way, in any language, native code included. A replacement of a site in native code is made at a link-time or preload interposer, a build flag or an injected interface, never by patching Python.
    A thread start is not run as a thread. The step-driven runner runs the thread’s target, unmodified, synchronously, one loop iteration at the step boundary its entry declares (“thread body run synchronously at step k”), and reports the completion of a device stream or event it waits on at that boundary. Each start site is one environment entry naming its target and boundary.    Checked by: oracle/check_mocks.py, from substrate/contracts/harness, in each engine module; a generator in each engine module that lists every such site reachable from ported code at the modelled commit, and fails when a site has no manifest entry or a listed site no longer exists.
  • FID-2 The oracle runs the upstream’s own code at the modelled commit, in a locked environment: Python packages for a Python upstream, and for a C++ upstream the upstream’s build driven through its bindings. Coverage of native code (T1) comes from an instrumented build, locked in the same way. Where the upstream implements one decision twice, for example a native core and a Python one, the Upstream record names the implementation the oracle runs as the one the upstream selects by default, and a differential test runs the oracle with each: the two traces are identical, or each difference is a listed divergence that names the implementation BLIS follows. Every recorded trace records the commit, the lock file’s hash, the scenario’s hash, the seed and the manifest version.Checked by: oracle/check_lock.py and a provenance check on every trace; the differential test between implementations, with a divergence between two cores as its known-bad input (X18).
  • FID-3 Maintainer practice: a recorded trace’s decisions change only after a maintainer has reviewed the change and its reason. The oracle runners refuse to write traces unless an explicit update flag is set.Checked by: oracle/check_traces.py compares each trace with a fresh oracle run.
  • FID-4 Every branch of every ported function is exercised by at least one recorded or fuzzed scenario (T8), or is listed with the reason that no input reaches it.Checked by: branch-coverage gate.
  • FID-5 A framework (connector base, offload tiering, HiCache) is marked modelled in the surface list only when it has recorded and direct traces at its own interface (§7.6). A feature built on the framework does not supply them. A part of a framework without those traces is a separate item with its own status, and is not marked modelled, whatever the status of the other parts.Checked by: a surface-list check that a framework marked modelled names recorded and direct traces at its interface, and that each part without them is a separate unmodelled item.
  • FID-6 A property asserted about an engine port, such as a monotonicity law, is first run against the upstream oracle. It is adopted only if the upstream satisfies it on the oracle scenarios. A law about the cost model names the upstream behaviour it rests on.Checked by: the property tests run in the oracle tier before they run against the port.

  • FID-11 The work a step shape asks the cost model to price equals what the upstream launches for the same step, for each layer: the rows of every matrix multiply, each operation’s FLOPs and bytes, the token count of every draft pass, and the context entries each context-dependent operation reads, bounded by its window where it has one. Rows and token counts match exactly. FLOPs and bytes match within a stated tolerance. FID-7 compares what is resident; this compares what runs.Checked by: an oracle comparison, run with T0 and on pull requests that change how step shapes are emitted.
