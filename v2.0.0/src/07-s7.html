7Fidelity to upstream code

7.1 What an engine module models

An engine module models one upstream commit: a release tag, or any commit on the upstream's main or a release branch. Its Upstream record names the commit and the release the commit descends from. A build runs one commit of each engine (LIF-6). The module ports all of the upstream code that decides what each step runs and what each request's KV cache costs. That code falls into four parts. Each surface-list item (§7.5) has one primary part, the one that owns most of its decisions. A feature whose code spans parts, such as speculative decoding, LoRA or HiSparse, is still one item, and it names the other parts it touches. The table below names each upstream's classes at the modelled commit. The names change between commits. The four parts do not.

Metrics are outputs of the parts that produce them. Each part is ported framework first (§7.6). In vLLM the KV-cache framework is the layer grouping, the coordinators and the manager base class. In SGLang it is the tree-cache interface and the allocator and memory-pool base classes. The tiers of §7.4 test the parts: scheduling by T2 and T3; KV-cache management by T2; transfer and tiering by T4 and T5; resolution by T1; lowering by T0, by the comparison of priced with launched work (FID-11) and by T3's padding comparison. T6 checks the metrics and KV events of every part. T7 covers all four.

Engine upgrade. An engine upgrade moves a module from one commit to another by porting the diff of the code it already models. It changes behaviour for every model. It regenerates fields.json, surface.json and kernel_impls.json at the new commit (§7.5), locks the oracle to that commit (FID-2) and runs every tier again (FID-14). Maintainer practice: a module is upgraded at each upstream release, and on demand when a scenario needs a later commit. A maintainer with write access decides an on-demand upgrade and records the decision in an issue. §12 gives the procedure.

Model support. Model support is work in an engine module for one model. It is needed only when the model brings engine-facing code that an upgrade does not port, which lives mostly in the model's own folder upstream. Three cases need it: a KV-cache layout the module has not seen, such as DeepSeek-V4's sliding-window cache and compressor; the model's own kernels, or a backend choice the module does not lower, such as fused attention kernels; and a new drafting method or scheduler hook. A model that brings none of these needs only a catalog entry (§12).

Model backport. A model that lands upstream between upgrades can be supported at once by applying the upstream commits that add it onto the modelled commit. The Upstream record lists them. A backport carries model code only, never scheduler, KV-cache or connector changes. It is dropped when the modelled commit contains it. It has no grade of its own: a run is graded by its commit distance from the modelled commit (§11.3).

Upgrade report. Each upgrade generates a report of the models the new commit supports. For each model it states:

  • whether the catalog has it;
  • whether it needs model support, and for what. This comes from the regenerated lists, where every new entry has a status (X9), and from the model's own code;
  • for each catalog chip, the coefficients it lacks: the entries a new primitive family needs before the model can run, and the kernels it would price below measured or calibrated (§9.2).

A new engine, such as TRT-LLM, meets the same bar as vLLM and SGLang. It is a new directory under engines/. It ports the upstream's scheduling and KV-cache code, and an oracle runs the upstream code to check the port. Where the upstream core is C++, the oracle drives that code through its bindings (FID-2).

7.2 The method

"Faithful to vLLM" means: give vLLM's own scheduler and BLIS's Go port the same inputs, and they make the same decisions at every step. To run vLLM's scheduler without GPUs, a test harness replaces only its environment. Everything else is vLLM's own code at the modelled commit. Figure 3 shows the arrangement. The same method applies to every engine.

7.4 Test tiers

Every tier is a behavioural test: it compares what the port does with what the upstream does, or checks a property of that behaviour. No tier asserts the text, order or hash of source (FID-13). Every engine module uses the same tiers. A procedure in §12 names which tiers must run again.

7.5 The surface list: making gaps visible

The tiers test only ported code. To show what is not ported, each engine module generates a surface list (surface.json) from the upstream source at the modelled commit. The generator reads the upstream's own registration tables, so a new feature in an upstream commit appears in the list without anyone remembering to add it.

Each item has one status (X9). Every item the llm-d stack uses is to be modelled. The other two statuses are exceptions, and each needs evidence a reviewer can check:

  • modelled, naming the oracle scenarios that cover it. This is the goal for every item.
  • refused: the engine refuses the item by name until it is modelled. The backlog counts what it blocks (§11.6), and the item that blocks the most dashboard points or published deployments is modelled next.
  • out of scope, for an item BLIS will not model. Only three reasons are allowed: the item runs only on hardware BLIS does not simulate (for example AMD-only or TPU-only); it does no work the simulator prices (for example a multimodal encoder when BLIS simulates text serving); or it is deprecated upstream and slated for removal. The reason names which of the three applies, with a citation to the upstream code or announcement. An item may be out of scope only while its weight (below) is zero. Otherwise it is refused.

"Hard to port", "rarely used" and "needed later" are priorities, not reasons for either exception. The weight and the backlog express priority.

Each item also has a weight: how many distinct deployments in llm-d's published guides and model recipes use it, and how many accuracy-dashboard points it blocks. surface.json holds only statuses, because an engine module cannot depend on the guides or the dashboard (X7). The guides commit is pinned once, in guides.lock in inference-sim, and inference-sim coverage publishes each item's deployment count. The count parses each rendered manifest's engine arguments with that engine's own argument parser. The accuracy dashboard adds its blocked-point counts. An out-of-scope item whose weight is not zero is marked refused. The weighted share of modelled items is published with every release (SIM-5), and an engine upgrade may not lower it (X9). The difference between two commits' lists is the new work of an upgrade.

7.6 Port a shared framework before the features built on it

Connectors, tiers and KV-cache managers are built on shared frameworks. In vLLM these are the connector base class; the offload spec, manager and tiering layers; and the KV-cache coordinator with the manager base class, which every spec type's manager extends. In SGLang they are the HiCache controller and storage interface, and the tree-cache interface with the allocator and memory-pool base classes. Porting one framework completely, with recorded traces of its contract, makes each further connector, tier or manager a smaller change. Without it, each one is a large port of its own. A module therefore ports a framework as a unit before the features built on it.

A framework's interface is the abstract class or classes that its features implement or call. A framework's traces are taken at that interface and are of two kinds. A recorded trace is the sequence of interface calls that a real feature makes while the oracle runs a scenario. The port receives the same calls, and its answer to each is compared with the upstream's. A direct trace is a sequence of calls made by a driver the module writes, including orderings that no existing feature makes. Recorded traces keep the call mix realistic. Direct traces test the contract itself, not one feature's use of it. A part of a framework that reads the clock is traced with the clock replacement of FID-1. A part that does its work in threads, as HiCache's controller does its backups, loads and prefetches, is run by the step-driven runner of FID-1, so that its decisions are traced in a fixed order. When only some parts of a framework have traces, the surface list holds the parts as separate items, each with its own status.

7.7 Fidelity invariants

  • FID-1 The manifest lists every replacement. A write the harness makes outside a listed site fails CI, and a changed list carries a new version. Outside the listed fields, the configuration the oracle resolves equals what the upstream's CUDA platform resolves for the chip the scenario names. Restoring a CUDA value that depends on choosing a CUDA attention backend is a transcription (FID-8), checked against recorded CUDA start-up logs. Every read of the current platform reachable from ported code is one listed site: each call of a platform predicate, each read of a platform attribute, and each read of a module constant computed from the platform at import (such as _is_cuda = is_cuda()), which also counts once at its definition. Clock reads and thread starts reachable from ported code are listed the same way. A thread start is not run as a thread. The step-driven runner runs the thread's target, unmodified, synchronously, one loop iteration at the step boundary its entry declares ("thread body run synchronously at step k"), and reports the completion of a device stream or event it waits on at that boundary. Each start site is one environment entry naming its target and boundary. The runner's scheduling rule is stated once, in the manifest, and no thread body is copied into the harness (FID-8).Checked by: oracle/check_mocks.py, from substrate/contracts/harness, in each engine module; a generator in each engine module that lists every such site reachable from ported code at the modelled commit, and fails when a site has no manifest entry or a listed site no longer exists.
  • FID-2 The oracle runs the upstream's own code at the modelled commit, in a locked environment: Python packages for a Python upstream, and for a C++ upstream the upstream's build driven through its bindings. Every recorded trace records the commit, the lock file's hash, the scenario's hash, the seed and the manifest version.Checked by: oracle/check_lock.py and a provenance check on every trace.
  • FID-3 Maintainer practice: a recorded trace's decisions change only after a maintainer has reviewed the change and its reason. The oracle runners refuse to write traces unless an explicit update flag is set.Checked by: oracle/check_goldens.py compares each trace with a fresh oracle run.
  • FID-4 Every ported function is exercised by at least one recorded scenario.Checked by: coverage gate.
  • FID-5 A framework (connector base, offload tiering, HiCache) is marked modelled in the surface list only when it has recorded and direct traces at its own interface (§7.6). A feature built on the framework does not supply them. A part of a framework without those traces is a separate item with its own status, and is not marked modelled, whatever the status of the other parts.Checked by: a surface-list check that a framework marked modelled names recorded and direct traces taken at its interface, and that each part without them is a separate item that is not marked modelled.
  • FID-6 A property asserted about an engine port, such as a monotonicity law, is first run against the upstream oracle. It is adopted only if the upstream satisfies it on the oracle scenarios. A law about the cost model names the upstream behaviour it rests on.Checked by: the property tests run in the oracle tier before they run against the port.
  • FID-7 For every catalog model and each supported layout, the resident weights an engine reports in its PoolPlan (per-rank shape, stored data type and sharding, after the engine's weight post-processing) equal what the upstream allocates at the modelled commit. The graph's tensors equal the checkpoint's safetensors headers.Checked by: tier T0 in each engine module, run whenever the catalog changes or the engine moves to a new commit.
  • FID-8 The harness may not contain a copy of an upstream decision function. A harness file with a Derived from header, or a function named like an upstream function, is refused unless the manifest declares it as a transcription.Checked by: oracle/check_mocks.py.
  • FID-9 The engine is tested as the simulator drives it, not only on its own. Each recorded trace also records the timed inputs the engine received: arrivals, completions, transfer ends and aborts. Replaying those inputs through the simulator's driver into engine.Engine reproduces the trace's decisions step by step.Checked by: the coupled replay test in inference-sim's CI, over every engine module's recorded traces.
  • FID-10 Every compared field and metric series takes its neutral value and at least one other value somewhere in the scenario set, so a comparison of it can fail. The comparison is two-sided: a field or series that appears on only one side is a mismatch.Checked by: a value-coverage report in each engine module's CI, which fails on any field or series seen only at one value.
  • FID-11 The work a step shape asks the cost model to price equals what the upstream launches for the same step, for each layer: the rows of every matrix multiply, each operation's FLOPs and bytes, the token count of every draft pass, and the context entries each context-dependent operation reads, bounded by its window where it has one. Rows and token counts match exactly. FLOPs and bytes match within a stated tolerance. FID-7 compares what is resident; this compares what runs.Checked by: an oracle comparison, run with T0 and on pull requests that change how step shapes are emitted. It executes the upstream forward pass on meta tensors, at the padded batch the upstream launches, under a PyTorch dispatch mode that counts each operation's rows, FLOPs and bytes, with the ranks under a fake process group. Each opaque custom operation, such as attention or a fused mixture of experts, is counted by a rule the manifest lists. Routed-expert rows are compared in total (tokens times experts per token), since routing depends on data. Context reads are counted from the upstream's own attention metadata: sequence lengths, block tables and windows. Known-bad inputs: a matrix multiply priced at fewer rows per token than the upstream runs, and a windowed gather priced over the whole context.
  • FID-12 A connector or storage backend whose decisions live in a package outside the engine's tree, such as a KV store, is refused by name until the package's code is modelled to the bar of FID-2. A setting that loads such code from outside the tree is refused as code_not_visible (§11.4).Checked by: the surface-list check of FID-5, with a connector that calls an unmodelled package as its known-bad input (X18): the engine must refuse it.
  • FID-13 Correctness and invariants are checked by behavioural tests: conformance, differential tests against the upstream through the oracle, mutation, metamorphic and property tests. A test that asserts source text, declaration order, a hash, or a golden used in place of a behaviour does not count towards any tier.Checked by: the mutation sweep (T7), which breaks a ported function's behaviour and fails the tier whose tests do not notice.
  • FID-14 An engine upgrade regenerates fields.json, surface.json and kernel_impls.json at the new commit, whatever kind of commit it is, locks the oracle to it, and runs every tier again. Every new entry gets a status (X9). A backport changes no trace of a model that does not use it.Checked by: each generator works at any commit and fails on a checkout that is not the Upstream record's commit; the completeness check fails on an entry without a status; a metamorphic test runs the oracle scenarios of other models with and without each backport and compares traces.
