13Automation: how the rules are kept

Rules are kept in three ways (§4.2). This section describes the first, automated checks, and the agent work that runs against them. Review, approval, merge, release and signing decisions are maintainer practice, kept with branch protection, required reviews and signed commits. No automated check reads a pull request’s title or body, and none polices process.

  1. Deterministic checks decide everything that can be decided mechanically and that protects the product’s correctness or accuracy: import-graph boundaries, conformance suites, differential, mutation, metamorphic and property tests, data validators, and the staleness of generated files. Given the same commit, a check gives the same answer.
  2. Agents do bounded work: porting a changed function, classifying a new field, fitting a coefficient. They work from the upgrade report or the requested scenario (§12), against the checks.
  3. Maintainers review, merge and release, and set direction.

13.1 The invariant registry

Every invariant in this document is a record in substrate/contracts/invariants/:

- id: SUB-6
  statement: The cost model resolves nothing; every default, backend choice,
             padding and capture decision arrives in the plan or step shape.
  scope: [substrate/kernel]
  checks:
    - test: TestKernelResolvesNothing
      known_bad: a plan that leaves a default unresolved
      runs: pull_request
  status: ci                      # ci | partial | none

The status partial means some of a rule’s checks are written and others are not. A rule that is a maintainer practice (§4.2) has no checks. Each check runs on pull_request, nightly or release, and names a known-bad input that must make it fail (X18).

A generator renders these records into a section of each repository’s AGENTS.md. A rendered copy that does not match its record fails CI.

13.2 Agent guidance

What a repository’s AGENTS.md holds. It is the first file an agent reads, so it is short. In this order it holds: what the repository is and owns, and what it must never hold (Table 1, §2.2); the rules that apply to a change here, rendered from the invariant registry; the commands that build, test and run every check, as CI runs them; what a change must also update (the README.md, a generated copy, the registry record); and where to look next. It states no version, count or list of supported features. It does not restate a rule that a check enforces and an agent cannot get wrong; it states the rules a check cannot decide.

Review questions. A rule that depends on judgement may carry a review question with a trigger: the paths it concerns, or a description of the change, such as “a floating-point reduction is added”. The review agent reads the diff against each trigger and, for each question that applies, answers yes or no in a review comment, with a reason and the files and lines that support it. A question is guidance for that review and never a check: no job fails because it is unanswered or answered in the unwanted direction. A maintainer reads the answers with the rest of the review.

13.3 On every pull request

CI runs per component directory, with path filters: a change runs the checks of the directories it touches, and the cross-directory checks (§3.4). The last column of Table 1 (§2.2) names each component’s checks.

  • A workflow starts on a pull request only when the code can have changed: opened, synchronize, reopened, and a change of base branch. Editing a pull request’s title or body starts nothing and changes no merge state, and no check reads that text.
  • The checks are required in branch protection (X17), so a pull request cannot merge while one fails.
  • A pull request that can change prices also generates the price-change report: each benchmark scenario’s step prices before and after the change.
  • Heavy checks (oracles, mutation sweeps, the byte gate) run only for the directory whose code they test. Whole-run accuracy gates run as §13.5 describes.

13.4 Every night

  • The nightly build builds and tests inference-sim at the head of its main branch and of each open release branch (§14.4), on three platforms, against the router fork commit each one pins. It checks the import graph against Table 1.
  • Full-data gates rerun the coefficient registry writers, the landing gates and fixture-agreement checks on the full data, which a pull request’s CI cannot hold.
  • Detectors poll upstream commits and releases and the data sources, and open an issue for a maintainer.
  • The dashboard scores, publishes coverage and grades, and updates the backlog.

13.5 Where accuracy gates run

An accuracy gate compares a candidate with held-out data (VAL-6). Where it runs depends on what it needs:

  • Operator-level gates need only the cost model and the coefficient registry, for example “does this attention coefficient predict the held-out sweep points?” They run in inference-sim’s gate job, which holds the role seed in a protected environment (D7).
  • Whole-run gates need engines and the simulator, for example “does this change improve end-to-end latency on held-out InferenceX deployments?” They run the dashboard’s scoring harness (§11.7), the only end-to-end scorer, at the release or commit the repository pins. A candidate job in the pull request’s own repository builds the candidate and runs the harness with no secret and a read-only token, on every unit not on the published fit, anchor or report lists, and writes one prediction per unit. accuracy-dashboard’s gate job holds the role seed (D7), runs only its own main, refuses predictions made by a harness commit other than one released from its main, reads them as untrusted input, reduces them to aggregates and reports the result on the pull request.

The gate compares two trees: the base, which is the pull request’s merge base, and the candidate, which is its head. Comparing against the merge base, not the last release, keeps unrelated changes already on main out of the comparison. Each tree’s catalog and coefficient registry are passed with --catalog and --registry.

  • If the pull request changes only files under substrate/catalog/ and substrate/registry/, both trees load under the released simulator’s validators, and the code outside those directories at the merge base is identical to the code of the release, the gate runs the released simulator twice, once per tree. No rebuild is needed. If main carries unreleased code changes, the next case applies, so the data are judged with the code they will ship with.
  • Otherwise, for example when the pull request changes the cost model or an engine module, or uses a data field the released simulator cannot read, the job builds one simulator from the base and one from the candidate, and each runs on its own tree.

Before a release is cut, the whole-run gate job runs once more, comparing the release candidate with the previous release on held units. A lane that gets worse by the test of VAL-6 fails the check, unless it is recorded as a defect in another term and approved (VAL-11). That final check covers changes that were each fine alone but interact. In every case the import graph holds (X7): the candidate job runs the pinned harness and imports none of its code.

The gate job runs on pull requests that carry a pre-registration, and again nightly on the full data. Any pull request, draft or not, may also run the harness on published units for review (§11.7); that run holds no seed and decides nothing.

13.6 Releases

inference-sim is the one tagged release (§14). Cutting it is maintainer practice (LIF-3). The generated inputs to a release are the list of pull requests merged since the previous release, the price-change report (§13.3) and stack.json (SIM-3).

accuracy-dashboard and blis-config-search each pin an inference-sim release and run nightly on the newest one. Neither cuts a release of its own.

13.7 What agents may and may not do

An agent works within the checks and never decides a merge or a release.
Agents mayAgents may not
Work an issue, an upgrade report or a requested scenario, in a branchEdit a recorded trace without the update flag and a review line; edit a generated file by hand
Port changed functions; classify fields and surface items; write tests; fit coefficients from fit units; draft pre-registrationsWeaken, skip or delete a check; change a success criterion after reading held-out data; change the ledger’s cut-points or partition version
Iterate until the checks passApprove a merge, cut a release, or review a change they wrote
Act as the review agent (§13.2)Load recorded traces, vendored data or data files into context, instead of the tool summaries

CI or permissions enforce most of the prohibitions. Two depend on the agent’s instructions and on review: working within the task, and not loading generated files into context.

  • Every check declares the paths it consists of: its test files, thresholds, fixtures and workflow file. A CI step fails on any new test skip, lint suppression or loosened threshold in them, unless a committed waiver file names the file and the reason; a maintainer reads that file in review.
  • Held-out data is never read before the success criterion is committed (§9, §10).
  • Trace and generated-file guards are CI checks.
  • Agent credentials have no permission to merge or tag.
