5Details of each component

Table 1 (§2.2) gives, for each component, what it owns, what it may import, what it must never contain and the check that enforces it. Paths that begin contracts/, catalog/, registry/, kernel/, validate/ or load/ are under substrate/ (§4).

5.1 The substrate

  • SUB-1 Packages under substrate/contracts import only the Go standard library, the YAML parser and each other. They change only compatibly: an interface never gains a method, optional abilities are separate interfaces, and new fields keep their zero-value meaning. An incompatible change is one pull request that changes the contract and every implementer together (§12.8). contracts/harness and contracts/conformance may also use golang.org/x/tools, at the version go.mod requires, for their analysis checks.Checked by: the import-graph check (X7); an API-compatibility check of the contracts packages against the commit of the newest inference-sim release. It runs apidiff at a pinned version through go run, in accept-break mode (naming its issue) for an incompatible change.
  • SUB-2 Every new or changed data field ships with its validator, a failing example for each way it can be wrong, and the JSON Schema the simulator prints for it; no separate reference page is kept (X29).Checked by: documentation-matches-types test; strict loaders; examples must validate.
  • SUB-3 The catalog holds declared facts only: figures read from a published source, each with a followable citation. Each model’s graph is generated from its vendor config.json and the safetensors headers of its checkpoint, and never edited by hand (SUB-15). A graph node exists only if it launches GPU work. No runtime code reads config.json, no model value is hard-coded in the cost model or an engine, and no setting asks the user to copy a value from a checkpoint.
    A scenario’s cluster names catalog entries for its chip, fabric and storage devices, and states what the user provisions: the node count, which nodes sit under each switch, each group’s uplink oversubscription, and the GPUs per node, GPUs per rack and host memory per node where the chip’s entry leaves them open. Where the entry states them, the scenario may omit or restate them; any other value is refused. A chip with no rack tier accepts no rack size. A different packaging of a chip is a catalog entry of its own, and states the host CPU of its nodes (§9). One function in contracts/spec resolves a cluster’s packaging, and every reader calls it (X15).    Checked by: deriver --check; the validators, including the packaging check and its test pair; a test that a run gives the same result when the vendor config.json files are removed; a lint for model-name literals in kernel/ and in engine lowering code. Review: that each citation supports its figure.
  • SUB-4 Every coefficient is generated by its family’s writer script, never edited by hand. It records its value, units, scope, method, sources and data units (§9).Checked by: writers --check on fixtures per pull request and on full data nightly.
  • SUB-5 Coefficients obey physics: no compute rate above the chip’s dense datasheet peak for the data type; no memory bandwidth above the datasheet peak for a working set larger than the L2 cache; at a fixed algorithm, topology tier and bytes per rank, a collective never gets faster as the group grows; no transfer rate above the catalog peak of the link a leg crosses.Checked by: property tests.
  • SUB-6 The cost model resolves nothing. Every default, backend, padding and capture decision arrives in the plan or step shape.Checked by: a lint that the cost model’s public functions accept only plans, step shapes, transfers, and catalog and coefficient registry handles; the perturbation test of SUB-11.
  • SUB-7 The cost model has a price for every primitive, and for every move form (§6.1) on every catalog device, link and NIC it can cross. When no fitted coefficient exists it uses the next source in a fixed order and records which (§9).Checked by: a completeness test over every primitive and chip, and every move form with every storage device, link and NIC.
  • SUB-8 A change to the substrate never breaks the data it releases: validators, deriver and writers all pass on the released tree.Checked by: those tools, run on every pull request.
  • SUB-9 Data is loaded the same way from a path or from the embedded copy: the same file patterns, the same validators (including the checks between the catalog and the coefficient registry), and the same content hash. Checked by: loading the embedded copy and an exported checkout of one commit gives identical data and hash.
  • SUB-10 contracts/conformance includes a set of unusual model shapes: every layer windowed, every layer recurrent, MLA only, a draft layer declared last, a single layer, and no attention. Every engine and the cost model either runs each one or refuses it with the upstream’s reason. No size or price is non-finite or zero where a positive value is required.Checked by: the conformance suite, run against the cost model and every engine.
  • SUB-11 Every field of PoolPlan, StepShape and plan.Transfer, and every coefficient family, changes some price when changed, or is listed as not yet priced with an issue. The lifecycle fields of engine.Transfer (ID, Request and Blocks) are never priced.Checked by: a perturbation test in kernel/; a ratchet on the not-yet-priced list, which may only shrink.
  • SUB-12 Every loader of a BLIS document refuses unknown keys, duplicate keys, numbers that do not convert exactly, non-finite numbers and recursive aliases. A declared field is used or refused, never dropped. Validation has two layers. The field layer holds the checks whose answer is the same under every engine commit; a field problem means the document is wrong. The engine layer is each engine module’s own refusal of what it cannot lower or run (SIM-9). It runs only when the field layer reports no error, and a refusal there may mean that the engine does not model the document yet. No rule set outside an engine module maps settings to lowering (X3).Checked by: a shared set of malformed documents in contracts/conformance run against every loader; SIM-11’s test of each declared field.
  • SUB-13 inference-sim is one Go module: no go.mod exists below the repository root, and the module zip’s files total under 100 MB uncompressed (Go’s limit is 500 MB).Checked by: a check that fails on a nested go.mod; a check of that total.
  • SUB-14 The memory breakdown closes. Every memory figure an engine’s upstream reports at start-up (weights, memory outside PyTorch’s allocator, peak activations, the CUDA-graph pool, and the memory left for KV) has one matching term, within a stated tolerance. Buffers and workspaces the engine chooses are PoolPlan fields, sized as the upstream sizes them. Memory the engine does not choose, such as the CUDA context and communication libraries, is a measured coefficient per chip and library version. Anything left over is a named term on a list that may only shrink. Each term states its basis: per rank, per node or per group (SUB-16). Host memory closes the same way: host-resident weights, the host KV tier and pinned buffers are PoolPlan figures, each stating whether the engines on a node share it. A shared figure counts once per node, and the node’s sum fits its host memory.Checked by: in each engine module, oracle tier T3 against the upstream’s buffer-sizing functions; in the substrate’s error job, a comparison of the total with recorded GPU start-up logs (ledger units with role validate); a start-up refusal when a node’s host-memory figures exceed its host memory.
  • SUB-15 A model graph holds only what the checkpoint states: the tensors, their shapes and stored data types, scale tensors, and the layer structure. Every graph field can be computed from config.json and the safetensors header of every checkpoint shard (no tensor data). The catalog’s deriver writes these facts and nothing else. How an engine shards, fuses, pads or repacks a tensor, its page size, and the nodes it emits under a layout are lowering, which lives only in engine modules (X3, §6.1).Checked by: a test that rederives every graph field from those inputs; the import-graph check of X3. The deriver records each header’s SHA-256 and the revision (X12).
  • SUB-16 Quantities carry units as types. Bytes, seconds, tokens, FLOPs, bytes per second and dimensionless ratios are distinct Go types in contracts/, as are per-rank, per-node and per-group amounts, so adding a byte count to a token count, or a per-rank amount to a per-group one, does not compile. A coefficient registry entry’s unit equals the unit its formula requires, checked at load. An efficiency lies in (0, 1]. A quantised format is one type (payload bits, scale bits, block shape) with one function for its stored bytes.Checked by: the compiler; a load-time unit check in the cost model; validator rules that catalog peaks are dense figures whose ratios between data types match the datasheet.
  • SUB-17 A transfer or collective names its endpoints by rank, and the cost model prices it over the path between them through the catalog’s links: the NVLink domain, the NIC and each switch tier. A collective that leaves its NVLink domain also reports the demand it places on each link during the step; that demand is reserved, and transfers share what remains.Checked by: a property test over random placements; the link-capacity test of SIM-13; a conformance case in which a move of a pool spanning nodes, stated as one entry per node, demands the sum of its entries’ bytes on a shared link, and a known-bad engine that states one endpoint for such a pool.
  • SUB-18 Provenance is recorded per field. A catalog field holds a datasheet figure, a published figure, or a measurement of one named device, and says which. A fitted or assumed value is a coefficient.Checked by: validator rules on catalog provenance fields.
  • SUB-19 Every document that crosses a repository boundary has one definition, in contracts/spec: the scenario, the deployment, the Result, and the per-point record the scoring harness writes. Each release publishes them as JSON Schema generated from the Go types. blis-config-search and accuracy-dashboard validate every document they read or write with inference-sim schema validate, which runs the Go validators (X15), and define none of their own. The per-point record is defined there although the dashboard writes it, because config search and the substrate’s gates read it.Checked by: a generator test that the published schemas match the Go types; schema validation in the applications’ CI; a lint that refuses a hand-written schema for these documents.
  • SUB-20 No price, size or engine decision depends on a free-text label. Every property a consumer branches on, such as whether an expert group is shared or routed, is a typed field with a closed set of values, derived from the checkpoint and checked at load. Names and roles kept for people to read change no output.Checked by: a perturbation test (SUB-11) that relabelling every documentation string changes no price, size or decision; a lint that refuses a comparison on a documentation-only string field outside tests.
  • SUB-21 Every move is priced by the form it states (§6.1), as legs over paths the catalog states, with the coefficients the coefficient registry holds for that form, device, link and chip. A form’s price never depends on an engine’s name or setting. A move whose form the plan or the catalog cannot make, such as ipc between GPUs on different nodes or gpudirect_storage with buffered IO, is refused by env.DemandFor, naming the form and the reason.Checked by: the perturbation test of SUB-11 on each form field; a test that a move stating no form gets the price §6.1 gives it; property tests in kernel/ that a pipelined move takes no less time than its slowest leg alone, that a move whose buffer holds one chunk takes the sum of its legs’ times for each chunk, that a move’s time never falls when a leg’s rate falls, and that, for whole logical blocks, the buffered price of a storage move is never below its unbuffered price; a property test in inference-sim of the two advance rules; a refusal test pair for each form (SIM-9); the completeness test of SUB-7.
  • SUB-22 The form a transport library chooses comes from one function in contracts/transport, over a table in catalog/transport keyed on the library, its version, its settings and catalog facts about the two ends (§6.1). Each table entry cites the library’s selection code at that version. A setting or combination the table does not cover is refused by name. No engine module or cost-model code chooses a library’s transport.Checked by: a table test against what each library reports choosing (UCX’s protocol report, NCCL’s debug log), recorded with ledger units per catalog chip and NIC; the catalog validators, which refuse an entry without a citation (SUB-3); a refusal test for an uncovered setting; a perturbation test that changing the engine kind changes no form; the review question of X2 for any entry that names an engine.

5.2 The engines

Each directory under engines/ is one engine module. It ports one engine’s scheduler, KV-cache managers, connectors, offload tiers, default resolution and lowering (§7.1), with the oracle, the Upstream record, fields.json and surface.json. It registers as an engine kind (vllm or sglang) with the upstream commit it models (LIF-5), implements engine.Engine, and emits PoolPlan and StepShape. The substrate defines the shape of a field list and holds no engine’s fields: inference-sim fields prints what the registered engine reports. A new engine is a new directory under engines/, held to §7. Shared oracle and provenance machinery comes from contracts/harness, never from another engine. An SGLang module’s KV events and metrics are byte-compatible with what llm-d’s SGLang adapter reads (SGL-5).

vLLM

  • VLM-1 Decisions match vLLM at the modelled commit, step by step, on every oracle scenario.Checked by: oracle tiers T0 to T6 (§7.4).
  • VLM-2 Every Go file states where it came from: derived from a vLLM path at a commit; a model backport, naming its upstream commits (§7); or original. Every ported file names a commit that the Upstream record lists, and no other.Checked by: a provenance lint.
  • VLM-3 The engine’s field list classifies every configuration field and every environment variable the modelled commit reads, including those the communication libraries it uses read, with exactly one of the statuses below. No other status is allowed unless a release plan allows one for a stated period (§1).
    A field has exactly one of three statuses, and each status records its evidence.
    StatusHolds whenEvidence recorded
    modelledThe port reads the field, and setting it changes a decision in a recorded trace, or a field of the emitted plan or step shape that the cost model prices (SUB-11).An oracle scenario that sets it and whose trace the port reproduces, or a test that finds the emitted plan or step shape equal to the upstream’s resolution; the value classes covered.
    proven inertNo value of the field changes a decision, a kernel choice or whether a configuration is accepted.A passing proof (T1, §7.4), with probe values that follow the same value classes.
    not modelledThe port does not read the field; or reads it but carries it to no decision, plan or step-shape field and has no inertness proof; or reaches only a plan or step-shape field on SUB-11’s not-yet-priced list.An open issue that names the field or its group, says what it does upstream, and why the port does not model it; for the not-yet-priced case, the issue of that list.
    Value classes. For a boolean or enumerated field, the values the evidence sets; for an ordered numeric field, the range the evidence sets, split at every threshold the upstream compares the field with. A field that can name code outside the modelled commit, such as a class or module path, is marked so. Each field also states its estimation rule (§11.2), or that it has none.Checked by: completeness check; inertness proofs (§7.4); a perturbation test over every field marked modelled; a check that every field has an estimation rule or says it has none; a check that fails a not-modelled entry whose cited issue does not list the field or gives no reason; a check that fails any field whose type can hold a class or module path and is not marked as able to name code.
  • VLM-4 surface.json lists every connector, offload tier, KV-cache spec type and its manager, speculative method, scheduler policy, metric family and KV-event type the modelled commit registers, each with a status (X9).Checked by: generator against vLLM’s own registration tables (§7.5).
  • VLM-5 No clock reads and no goroutines. Waiting is reported to the simulator as a time value.Checked by: the determinism test of X6 (identical traces with the clock shifted, under different thread counts and under a hostile goroutine scheduler); a lint for clock reads and goroutine starts.
  • VLM-6 A value of an enumerated setting, such as a connector, backend or policy name, runs only through the surface item that models it. Two values share code only where the upstream’s registration maps them to the same class, cited. Every value is either refused by name or produces its own trace.Checked by: dispatch generated from surface.json; a perturbation test per value.
  • VLM-7 Every KV-cache spec type and group role the modelled commit registers in the upstream’s KV-cache spec registry has a status in surface.json that X9 allows. For a modelled one, the manager that the registry maps it to is ported, with oracle scenarios that allocate, evict and free its blocks and, where the manager supports prefix caching, share a prefix between requests. A model whose layers need a refused spec type is refused before the run starts, naming the spec type. The grouping of layers into KV-cache groups and the per-group coordinators are ported once and serve every manager.Checked by: a generator over the upstream’s KV-cache spec registry (§7.5); a T2 scenario per ported manager; a start-up refusal test per refused spec type.
  • VLM-8 A step that consumes a layered transfer follows the timing rule of §6.2. Its wait points are the connector’s per-layer calls: one before each attention layer, waiting for that layer’s loaded KV, and one after it, starting that layer’s save.Checked by: the shared suite in contracts/conformance for the timing rule, with property tests that a layered step never ends before its compute alone would, nor after its compute and its whole transfer run in sequence; that, when every part arrives before the layer that waits for it, it ends with its compute slowed by layered_transfer_compute_efficiency while a part is in flight; and that a transfer with no parts leaves the step time unchanged. The oracle’s run for FID-11 configures the scenario’s connector with the metadata the scheduler built for each T4 or T5 step with layered parts, lists the connector’s device copies as transport in the manifest, and records the layer index of each wait and save with a hook; the port’s stated wait points are compared with them. Its known-bad input is the same run with no connector configured, which fails because no hook fired. SUB-11’s perturbation test covers the coefficient.

SGLang

  • SGL-1 The oracle drives SGLang’s own Python classes at the modelled commit, in a locked environment. Where the upstream offers several implementations of a decision, such as the Python and native radix-tree cores, the oracle runs every one. The traces are identical, or each difference is a listed divergence naming the implementation BLIS follows (the default installation’s).Checked by: the lock and trace-provenance checks of contracts/harness; a T2 differential case between the implementations.
  • SGL-2 Every Go file states its provenance, as for VLM-2.Checked by: the provenance lint of VLM-2, from the shared harness.
  • SGL-3 The field list covers every configuration field and every environment variable the modelled commit reads, under the rules of VLM-3. Defaults are resolved as SGLang’s own resolution hooks resolve them.Checked by: field-list completeness against SGLang’s argument definitions and environment variables; the T1 default-resolution tier.
  • SGL-4 surface.json lists every transfer backend, tree cache, tree core, allocator and memory-pool type, speculative algorithm, scheduling policy, metric family and KV-event type the modelled commit can select, each with a status (X9).Checked by: a generator that reads SGLang’s registration tables and selection code at the modelled commit (§7.5).
  • SGL-5 KV events are emitted exactly as SGLang emits them: one BlockStored per page, merged by SGLang’s event queue under the queue’s own conditions, and consecutive BlockRemoved events likewise. Every tree core merges alike (§6.4).Checked by: byte comparison with SGLang’s queued events for every tree core; a routing test at page size 1 and at 16 or more.
  • SGL-6 Every tree cache, tree core, allocator and memory-pool type the modelled commit can select has a status in surface.json that X9 allows. A modelled type has its Go counterpart, with oracle scenarios that insert, match, lock, evict and free through it. A configuration that selects a refused type is refused before the run starts, naming the type.Checked by: a generator that parses SGLang’s selection branches at the modelled commit, with an unlisted branch as its known-bad input (§7.5); a T2 scenario per ported type; a start-up refusal test for each refused type.
  • SGL-7 A step that consumes a layered transfer follows the timing rule of §6.2. Its wait point is HiCache’s per-layer completion count, which a KV pool waits on before it returns a layer.Checked by: the shared suite and property tests of VLM-8, and the oracle run of FID-11. For each scenario with a pending HiCache load, that run hooks the counter’s wait to record each layer index and compares the port’s stated wait points with them. Its known-bad input is the same run with no HiCache load pending, which fails because no wait fired.

5.3 The router fork

The router fork (inference-sim/llm-d-router, branch llm-d-r) is llm-d’s own router code made runnable in simulated time. It serves both engines through llm-d’s adapters. inference-sim imports from it only pkg/embed.New and the hosting contract.

The hosting contract. The hosting contract is the interface between the simulator (its sim/llmd package) and the fork’s pkg/embed. The fork owns it, with its conformance suite, in a directory of its own (blisembed/). The fork imports no package of any github.com/inference-sim/ module (X7), and inference-sim imports the contract through the one replace of X11, under the fork’s module path. SUB-1 and RTR-3 apply to it.

  • RTR-1 Upstream releases are merged into llm-d-r, never rebased. Fork pull requests land as merge commits. Commits written for BLIS follow X20; upstream history is merged as upstream wrote it.Maintainer practice (§4.2): the repository allows merge commits and forbids squash and rebase merging. The reviewer of an upstream merge confirms that the head contains the previous upstream base and adds no commit outside a release.
  • RTR-2 Every change the fork makes to an upstream file is one of eleven kinds, and nothing else:
    Every change to an upstream file takes the required form of one of eleven kinds.
    KindRequired form
    clock read or deadlinetime.Now, time.After or a context deadline becomes the runtime’s clock (rt.Now)
    timer or periodic worka goroutine looping on a ticker becomes rt.Every(ctx, name, interval, fn)
    goroutine or blocking waitgo f() becomes rt.Go(f); a blocking select becomes rt.Park(condition)
    random drawa draw from a global or unseeded source becomes a draw from a named stream, rt.Rand("<name>")
    iteration orderwhen hosted, a map listing that reaches a decision is sorted, or sorted and then shuffled from a named stream; when not hosted, upstream’s order is kept
    network callwhen hosted, an outbound HTTP call goes through hosting.Transport, which the host serves
    work orderingparallel or background work runs, when hosted, one item at a time in a fixed order; when not hosted, upstream’s concurrency is kept
    per-simulation statestate the upstream shares across the process, such as the picker’s tie-break counter, is kept per runtime when hosted (rt.Local)
    hosted substitutewhen hosted, a component is replaced by one with the same contract that the host can drive, such as a time-to-live cache on the runtime’s clock; or a path BLIS does not host is refused by name
    test adaptationan upstream test is changed only to follow a signature another allowed kind changed
    startup assemblythe runner is split so a host can build the router without servers or leader election
    No change alters a routing, admission, flow-control or scoring decision: no condition, weight, threshold, default or plugin choice.Checked by: a classifier in hack/hosting-lint that matches each hunk of the diff against the upstream release to a kind’s required form; a hunk that matches none fails CI. The differential test of X4 checks that decisions are unchanged, which catches a hunk the classifier misreads. Review question. Does this change only alter how the router is built or hosted, never which plugins run or what they decide? Applies when: a hunk is classified as startup assembly.
  • RTR-3 The hosting contract and its conformance suite are in the fork. pkg/embed.New passes the suite, and the contract changes only compatibly (SUB-1). An incompatible change lands in the fork first, in one pull request that changes the contract and its conformance suite; inference-sim then moves its pin (X11, §12.8).Checked by: the conformance suite and the API diff, both in the fork’s CI, against its own history.
  • RTR-4 A plugin type runs in BLIS only after an audit. The audit converts every baselined use inside that plugin (RTR-6). The fork’s audited list and BLIS’s allow-list change together.Checked by: a test in inference-sim that every allow-listed type is on the fork’s audited list.
  • RTR-5 The llm-d P/D sidecar is hosted under the same runtime interface, so P/D leg handling is llm-d’s code.Checked by: a test that P/D runs go through the hosted sidecar’s code and that the simulator holds no P/D leg logic of its own.
  • RTR-6 Every direct clock read, timer, goroutine, random draw, map-order dependence, network call and process-wide mutable state on a router path goes through the runtime interface, or is on the reviewed baseline. A use is on the baseline for one of three recorded reasons: it cannot affect a decision (a log, a metric, an order-free walk); it lies inside a plugin type BLIS refuses; or it lies on a path that pkg/embed.New never builds, such as the router’s servers. A use of the second kind is converted when its plugin is audited (RTR-4). The baseline grows only by review.Checked by: hack/hosting-lint, which type-checks the router packages, including package-level variables written after initialisation, and fails on any use not in the baseline or on more uses than it records. Review question. Does this baselined use stay off every decision path, lie only inside a refused plugin, or lie only on a path the embedding never builds? Applies when: an entry is added to the baseline.
  • RTR-7 Under the simulated runtime, at most one router goroutine runs at a time, and a goroutine gives way only in rt.Park. No lock is held across a call that can reach rt.Park. Channel and wait-group waits on decision paths become rt.Park (RTR-2). Decisions do not depend on the order in which goroutines runnable at one instant resume.Checked by: hack/hosting-lint, which fails on a lock held across a path to rt.Park and on an unconverted channel or wait-group wait on a decision path; a seeded test that permutes resumption order and compares decisions.

5.4 The simulator

The simulator is a discrete-event loop that runs engine modules, priced by the cost model, behind the hosted router, under a workload (§8). It reaches engines only through engine.Engine, at one build site, and builds the Environment they run against (§6.3). It emits Result documents and stack.json.

  • SIM-1 The engine is chosen by the scenario’s engine: {kind, version}. Any number of kinds may be registered, each modelling one upstream commit; a scenario naming another commit is refused (LIF-6). The version is the full commit hash or an alias that the Upstream record lists for that commit; any other value is refused, and the message lists the aliases.Checked by: tests that build two engine kinds in one binary and refuse a scenario naming an unmodelled commit.
  • SIM-2 No silent degradation: unsupported or ambiguous input is refused with a message; library code returns errors and never exits the process.Checked by: refusal tests.
  • SIM-3 Every release publishes stack.json: the commits of inference-sim and the router fork, the upstream commit each engine models, the Go toolchain version, and the llm-d guides commit.Checked by: a release check that stack.json matches the tagged build’s modules, toolchain, Upstream records and guides.lock.
  • SIM-4 The byte gate (a fixed scenario set whose output must not change in a refactor) runs on every pull request.Checked by: the byte gate job in CI.
  • SIM-5 Each release reports how much of the llm-d stack’s published configurations it can run, per engine (X9).Checked by: a release job that computes coverage from the llm-d guides commit pinned in guides.lock and each engine’s surface list, and publishes per-item deployment counts through inference-sim coverage. The dashboard adds its blocked-point counts (§7.5).
  • SIM-6 A run that names no catalog or coefficient registry uses the embedded copy. A run that names a path uses that directory instead, plus any overlays the overlay flags name. A path flag never overlays.Checked by: a test per case; the result records the data source.
  • SIM-7 Every run makes progress. Each request ends in one of the fates of §8.7 (DEV-9). An engine pauses only when it has a scheduled wake-up or nothing to do. It never has more steps in flight than PoolPlan.InFlight, its upstream’s pipeline depth (for example, one batch ahead under SGLang’s overlap scheduler), and never processes a step’s output before that step ends. A request that can never fit in the engine’s KV cache is refused at admission, with the upstream’s reason, and recorded; it is never retried forever.Checked by: a progress watchdog that fails a run when no request changes state for a set number of engine steps while work waits; a seeded property test over random pools and prompts, including the exact-fit and one-block-over cases, which are also oracle scenarios in each engine module.
  • SIM-8 Requests and sessions follow one written state machine, whose end states are the fates of §8.7 (DEV-9). Intermediate P/D states, such as waiting for decode KV, are states of the machine, each with edges to eviction and to an end state. Code that ends a request sets its fate before notifying anyone. Every round a session planned has exactly one fate. A request identifier is never reused within a run.Checked by: a transition-table test; the arrival-count check of DEV-9; an oracle scenario for identifier reuse per engine module.
  • SIM-9 Each refusal has two tests: the smallest configuration that triggers it, and the closest one that does not. The message names the field and value that caused it and what the user must change. A feature or plugin is refused only under the settings that reach code BLIS does not model. A configuration the upstream refuses at start-up is refused at start-up, naming the upstream’s condition: BLIS never simulates a deployment the upstream would not start, and a search never ranks one. A limit of the deployment is reported as one, never as a simulator error.Checked by: the refusal test pairs in inference-sim, each engine module and the router fork; for each upstream start-up refusal on a modelled path, a scenario that the oracle and BLIS refuse with the same condition (T1, §7.4); a message test per refusal.
  • SIM-10 Any option that changes a byte of the Result is recorded in the Result’s inputs. A cache key includes every input the cached value depends on.Checked by: a test per command-line option that toggles it and compares the recorded inputs.
  • SIM-11 Every field the simulator itself reads (scenario keys outside the engine and router blocks, trace headers, replay descriptors) is consumed, refused or inert, and says which. Engine and router blocks are classified only by their owners (X1). A consumed field changes some byte of the Result when it changes. One validator exists per kind of value (X15), and every input that carries that kind calls it, so a value refused on the command line is refused in a trace header too.Checked by: a test that toggles each consumed field in every input schema; a parity test that the same invalid value is refused through every input.
  • SIM-12 Each request’s tokens are counted once, in a token record the engine emits: prompt tokens, tokens served from the local and external caches, tokens computed, and tokens emitted. Session growth, trace export, latency metrics and the Result read it; none recomputes it. Counts per rank and per group are distinct types (SUB-16).Checked by: a test that every consumer reads the record; known-answer tests of every capacity function at parallel widths above one.
  • SIM-13 The traffic that overlapping transfers and step collectives place on a link never exceeds its capacity. inference-sim shares each link among them, as the one piece of resource arithmetic it owns (X3).Checked by: a property test over random placements, transfers and collectives.
  • SIM-14 Every cluster control loop that runs beside the router, such as an autoscaler or LoRA adapter placement, is a model component (§8.1): it acts only on published values (DEV-1, DEV-4). Each is listed in the generated list of control loops, with the upstream controller it models, if any. A Result that used one names it, with its validation status and evidence (§8.9).Checked by: a check that every configurable control policy has an entry in the list; a Result test that each active loop is named with its validation status.
  • SIM-15 For each part of a layered transfer (§6.2), the simulator sends the engine one transfer-complete message, timestamped when the part’s last byte arrives under the link sharing of SIM-13. It computes no step time from them.Checked by: a test that each part produces exactly one message at its arrival time and that a step’s end comes only from the engine’s own time advance; the coupled replay test (FID-9).
  • SIM-16 A scenario may state several deployments, each with its own model and pools. A request goes to the deployment whose model it names, and each deployment has its own hosted router (one per InferencePool) with its own state and named random streams (DEV-6), so a draw in one router never moves another. An endpoint’s lifecycle events reach only the router of its pool. A request naming no deployed model is refused, listing the deployed models. The Result gives each model its own reported values.Checked by: a test with two models in two pools: each request reaches its own pool; changing the second router’s configuration leaves the first model’s routing byte-identical; an endpoint removed from one pool is unknown to the other router; a request for an undeployed model is refused (SIM-9); a run and its replay agree.
  • SIM-17 A cluster may hold node pools of different chips. An instance is priced and sized by the variant of the pool it is placed in: its PoolPlan, KV budget, step limits and hourly cost all come from that pool’s chip, never from another pool’s. A variant is a scenario for that chip (the same model, the pool’s cluster.hardware), opened once per pool; a node pool whose chip has no variant is refused by name. Each instance is billed at the price of its pool, and two pools may share a chip at different prices.Checked by: a test with an H100 pool and an A100 pool under one workload: an instance in each reports its own pool’s KV budget, step time and price, and a pool with no variant is refused by name.
  • SIM-18 Engines that run a file-system secondary tier (fs) with one root_dir for the same model share one file system: a block file one engine publishes is a hit for every other engine of that model on that root_dir. A different root_dir or model is a different file system. inference-sim builds one store per (model, root_dir) pair and hands it to every engine of the model through ShareTierStorage. The tier has no capacity and never evicts.Checked by: a test with engines of two models and two root_dir values: a block file published by one engine is found by the engines of its model on its root_dir and by no other; and a test in engines/vllm in which a prompt one engine cascaded to the shared storage is loaded by a second engine, which computes only the tokens past the shared prefix.

5.5 blis-config-search

blis-config-search finds the best configuration for a goal, reproducibly, over engine settings and llm-d router configurations. It depends only on inference-sim, pinned by tag and commit (X11), and never reads catalog or coefficient registry files directly. It reads everything else through inference-sim commands: fields, catalog resolve, metrics, acceptance and schema.

  • CFG-1 One pin file names the simulator release, and every report states it. A committed report uses that release’s embedded data; exploratory runs with other data are labelled experimental and are never committed as reports.Checked by: scripts/test_build.py; workflows that stop if the cloned commit differs from the pin.
  • CFG-2 Everything after the specification is deterministic and generated. Comparisons between arms follow DEV-11.Checked by: scripts/test_experiment.py. Maintainer practice (§4.2): a committed report is the generator’s output, never edited by hand.
  • CFG-3 Settings are the named engine’s own settings, read from the simulator. No list of settings is copied by hand.Checked by: a check that every settings list comes from inference-sim fields at the pinned release and the repository holds no copy.
  • CFG-4 A specification ranks and checks configurations on any metric of the metric registry, at any scope (§8.7). An example is the p95 time to first token for the whole cluster. Every metric it uses has one definition in the metric registry, shared by the search, the ranking and the report (DEV-8), and every reported value states its metric, scope and aggregate. A run that is overloaded or incomplete is never ranked (DEV-10).Checked by: a specification check that every metric and scope it names is defined by the metric registry; the report schema, which requires each reported value’s metric, scope and aggregate.
  • CFG-5 A search varies only settings that the engine’s field list marks as modelled at the pinned release. A ranking states the least trusted coefficient method and, from the dashboard’s published summary at the pinned release, the grades of the dashboard points in the lanes it relies on; a recommendation in a lane with no G1 or G2 points is labelled an extrapolation, with that lane’s measured error. A speculative-decoding arm states its acceptance (D8). The value comes from the substrate’s profiles through inference-sim acceptance (D8’s lookup), or from another cited measurement. The report names the source and each key field that differs from the arm.Checked by: a specification check against inference-sim fields; the report schema.
  • CFG-6 Everything the pinned simulator can run is a knob a specification can sweep: each setting the engine’s field list marks as modelled, and each scenario field the simulator reads, such as pools, parallel layout, KV tiers, speculation, router plugins and workload. A knob that a search cannot vary is listed with its reason. The list is generated from the simulator at the pinned release, never written by hand (CFG-3).Checked by: a test that fails when a modelled setting or a scenario field has neither a sweep key nor a listed reason, with a scenario field added to the schema as its known-bad input.

5.6 accuracy-dashboard

accuracy-dashboard shows publicly how accurate BLIS is against measured ground truth, and how much of that ground truth it can score. It fetches the InferenceX runs and recorded configurations of the units the ledger lists. Its scoring harness is the single scorer (COV-1): it turns a measured run into a scenario, runs a given inference-sim build on it, and compares. The harness is a script, run at the accuracy-dashboard commit that a pin file names (§11.7, §13.5), so a gate and the dashboard compute a reported value the same way.

The dashboard depends only on inference-sim. It gets what it needs from these inference-sim commands: fields, ledger (the published fit and anchor lists), catalog resolve (an InferenceX model or chip name to a catalog identity, or none), coverage, invariants, metrics (DEV-8) and schema (SUB-19). Its secret-holding jobs also check out substrate/catalog/ledger at the commit they score and compare it with the ledger at the merge base (§3.3), because the select and held roles need the full ledger. Its invariants, COV-1 to COV-13, are in §11.9 with the design they enforce.
