5Each repository's design

Each card gives the repository's purpose, what it owns and must never hold, its interfaces, what triggers a change, how correctness is shown, and its own invariants.

blis-substrate

Purpose
The engine-independent foundation: the shared language, published facts, coefficients and the cost model.
Owns
Contracts and data types; validators; conformance suites; the engine harness; the catalog, including the data ledger; the coefficient registry; the cost model; the invariant registry.
Never holds
Any engine's name, version or policy outside tests; third-party raw data.
Interfaces
Packages under contracts/ are imported by every Go repository. The cost model, the data loader and the embedded data are imported only by inference-sim. Its data reaches a run either from a path or from the embedded copy (§3.3). Fitting scripts reach the cost model through inference-sim with --catalog and --registry, or in-process through kernel.Open, which uses the same loader and checks (SUB-9).
Triggers
A new model, chip or network; a dataset drop; an accuracy idea; a new capability's contract.
Correct when
Validators pass on the data being released, the cost model passes its laws and engine-neutrality checks, held-out accuracy does not get worse, and contracts changes only compatibly.
  • SUB-1 Packages under contracts/ import only the Go standard library, the YAML parser and each other. Between contract-change review sets they change only compatibly: an interface never gains a method, optional abilities are separate interfaces, and new fields keep their zero-value meaning. An incompatible change is allowed only as a contract-change review set (§12.8), which releases every implementer against it together. From v1 on such a set raises the substrate's MAJOR version. While the substrate is at v0 it raises MINOR, because Go treats every v0 version as one major. contracts/harness and contracts/conformance may also use golang.org/x/tools, at the version blis-substrate's go.mod requires, for their analysis checks.Checked by: import test; API-compatibility check of the contracts/ packages against the substrate commit the newest inference-sim release pins. The check runs apidiff at a pinned version through go run, as the router fork’s check does, in accept-break mode for a contract-change review set, which names the set’s issue. The tool is a step of the check and not a dependency: no package under contracts/ imports it and go.mod does not require it.
  • SUB-2 Every new or changed data field ships with its validator, a failing example for each way it can be wrong, and the JSON Schema the simulator prints for it (schema); no separate reference page is kept (X29).Checked by: documentation-matches-types test; strict loaders; examples must validate.
  • SUB-3 The catalog holds declared facts only: figures read from a published source, each with a citation a reader can follow. Each model's graph is generated from its vendor config.json and the safetensors headers of its checkpoint, and never edited by hand. A graph node exists only if it launches GPU work; a config field that changes no operation has no node. No runtime code reads config.json. No model value is hard-coded in the cost model or an engine, and no setting asks the user to copy a value from a checkpoint. A scenario's cluster names catalog entries for its chip, fabric and storage devices, and states what the user provisions: the node count, which nodes sit under each switch and how oversubscribed each group's uplink is, and the GPUs per node, GPUs per rack and host memory per node where the chip's entry leaves them open. Where the entry states them, as GB200 NVL72's does, the scenario may omit them or restate them unchanged, and any other value is refused. On a chip whose entry has no rack tier, the scenario may not state a rack size. On a chip that has one, the cluster's fabric is the network between racks. A different packaging of the same chip is a catalog entry of its own. One function in contracts/spec resolves a cluster's packaging from the scenario and the catalog, and every reader calls it (X15).Checked by: deriver --check; the validators, including the packaging check and its test pair; a test that no runtime package opens config.json; a lint for model-name literals in kernel/ and in engine lowering code. Review: that each citation supports its figure.
  • SUB-4 Every coefficient is generated by its family's writer script, never edited by hand. It records its value, units, scope, method, sources and data units (§9).Checked by: writers --check on fixtures per pull request, on full data nightly; provenance rules.
  • SUB-5 Coefficients obey physics: no compute rate above the chip's dense datasheet peak for that data type; no memory bandwidth above the datasheet peak for a working set larger than the chip's L2 cache; at a fixed algorithm, topology tier and bytes per rank, a collective never gets faster as the group grows; no transfer rate above the catalog peak of the link a leg crosses.Checked by: property tests.
  • SUB-6 The cost model resolves nothing. Every default, backend choice, padding and capture decision arrives in the plan or the step shape.Checked by: a test that the cost model's public functions accept only plans, step shapes, transfers, and catalog and coefficient registry handles.
  • SUB-7 The cost model has a price for every primitive it can be asked about, and for every move form (§6.1) on every catalog device, link and NIC it can cross. When no fitted coefficient exists it uses the next source in a fixed order, and records which one it used (§9).Checked by: completeness test over every primitive and every catalog chip, and over every move form with every catalog storage device, link and NIC.
  • SUB-8 A change to the substrate never breaks the data it releases: validators, deriver and writers all pass on the tree being released.Checked by: the validators, the deriver and every coefficient registry writer, run on every pull request.
  • SUB-9 Data is loaded the same way from a path or from the embedded copy: the same file patterns, the same validators (including the checks between the catalog and the coefficient registry), and the same content hash. The embedded patterns equal the loader's patterns.Checked by: A test that loads the embedded copy and an exported checkout of the same commit, and gets identical data and an identical hash; a test comparing the two pattern lists.
  • SUB-10 contracts/conformance includes a set of unusual model shapes: every layer windowed, every layer recurrent, MLA only, a draft layer declared last, a single layer, and no attention at all. Every engine and the cost model either runs each one or refuses it with the upstream's reason. No size or price may be non-finite or zero where a positive value is required.Checked by: the conformance suite, run in blis-substrate, blis-vllm and blis-sglang.
  • SUB-11 Every field of PoolPlan, StepShape and Transfer, and every coefficient family, changes some price when it is changed, or is listed as not yet priced with an issue. Here Transfer means the plan.Transfer that the cost model receives; the lifecycle fields of engine.Transfer (ID, Request and Blocks) are never priced. A setting that the engine resolves but the cost model never reads is a gap, and it is visible.Checked by: a perturbation test in kernel/; a ratchet on the not-yet-priced list, which may only shrink.
  • SUB-12 Every loader of a BLIS document refuses unknown keys, duplicate keys, numbers that do not convert exactly, non-finite numbers and recursive aliases. Every declared field is either used or refused, never dropped. Validation has two layers. The field layer holds the checks whose answer is the same under every engine release, and a field problem always means the document is wrong. The rule layer asks whether a named engine release would run the document as written, and runs only when the field layer reports no error; a rule problem may mean that the document is right and the rule needs extending.Checked by: a shared set of malformed documents in contracts/conformance, run against every loader; a test that every declared field is read.
  • SUB-13 blis-substrate is one Go module: no go.mod exists below the repository root, and the files in the module zip that Go fetches total under 100 MB uncompressed (Go's limit is 500 MB).Checked by: a check that fails on any nested go.mod; a check of that uncompressed total.
  • SUB-14 The memory breakdown closes. Every figure an engine's upstream reports about memory at start-up (weights, memory outside PyTorch's allocator, peak activations, the CUDA-graph pool, and the memory left for KV) has one matching term, within a stated tolerance. Buffers and workspaces the engine chooses are PoolPlan fields, sized by the engine as its upstream sizes them. Memory the engine does not choose, such as the CUDA context and communication libraries, is a measured coefficient per chip and library version. Anything left over is a named term on a list that may only shrink, never folded into another term. Each term states its basis: per rank, per node or for the group (SUB-16). Host memory closes the same way: the weights an engine keeps in host memory, its host KV tier and its pinned buffers are PoolPlan figures. Each states whether the engines on a node share it; a shared figure counts once per node. For each node, the sum fits the catalog's host memory.Checked by: in each engine repository, oracle tier T3 against the upstream's own buffer-sizing functions; in blis-substrate's error job, a comparison of the total with recorded GPU start-up logs, which are ledger units with role validate; a start-up refusal in inference-sim when a node's host-memory figures exceed its host memory.
  • SUB-15 A model graph holds only what the checkpoint states: the tensors, their shapes and stored data types, scale tensors, and the layer structure. Every graph field can be computed from config.json and the safetensors header of every checkpoint shard (the header only, no tensor data). How an engine shards, fuses, pads or repacks a tensor, which page size it uses, and which nodes it emits under a layout are lowering, and belong to the engine (X3). The engine reports the resident weights that result in its PoolPlan.Checked by: a test that rederives every graph field from those inputs; a check that graph vocabulary has no emit conditions. The deriver records each header's SHA-256 and the revision, under the same licence rule as config.json (X12).
  • SUB-16 Quantities carry units as types. Bytes, seconds, tokens, FLOPs, bytes per second and dimensionless ratios are distinct Go types in contracts/, and so are per-rank, per-node and per-group amounts, so adding a byte count to a token count, or a per-rank amount to a per-group one, does not compile. A coefficient registry entry's unit equals the unit the formula reading it requires, checked when the coefficient registry loads. An efficiency lies in (0, 1]. A quantised format is one type (payload bits, scale bits, block shape) with one function for its stored bytes.Checked by: the compiler; a load-time unit check in the cost model; validator rules that catalog peaks are dense figures and that their ratios between data types match the datasheet. The bounds on rates are SUB-5's.
  • SUB-17 A transfer or collective names its endpoints by rank, and the cost model prices it over the path between them through the catalog's links: the NVLink domain, the NIC and each switch tier. A collective's step time is set by the cost model. A collective that leaves its NVLink domain also reports the demand it places on each link during the step; that demand is reserved, and transfers share what remains.Checked by: a property test over random placements, in blis-substrate; the link-capacity test of SIM-13; a conformance case in which a move of a pool that spans nodes, stated as one entry per node, demands the sum of its entries' bytes on a shared link, and a known-bad engine that states one endpoint for such a pool.
  • SUB-18 Provenance is recorded per field, not per file. A catalog field holds a datasheet figure, a published figure, or a measurement of one named device, and says which. A fitted or assumed value is a coefficient, and belongs in the coefficient registry.Checked by: validator rules on catalog provenance fields.
  • SUB-19 Every document that crosses a repository boundary has one definition, in contracts/spec: the scenario, the deployment, the Result, and the per-point record the scoring harness writes. Each substrate release publishes them as JSON Schema, generated from the Go types. blis-config-search and accuracy-dashboard validate every document they read or write with inference-sim schema validate, which runs the Go validators (X15), and define none of their own. The published JSON Schema serves editors and structural checks. The per-point record is defined there too, although the dashboard writes it, because config search and the substrate's gates read it.Checked by: a generator test in blis-substrate that the published schemas match the Go types; schema validation in the applications' CI; a lint in the applications that refuses a hand-written schema for these documents.
  • SUB-20 No price, size or engine decision depends on a free-text label. Every property a consumer branches on, such as which attention node in the model graph reads a cache the plan sizes or whether an expert group is shared or routed, is a typed field with a closed set of values, derived from the checkpoint and checked at load. Names and roles kept for people to read change no output.Checked by: a syntax-tree lint in blis-substrate and each engine repository that refuses a comparison on a documentation-only string field outside tests; a perturbation test (SUB-11) that changing such a label changes no price.
  • SUB-21 Every move is priced by the form it states (§6.1), as legs over paths the catalog states, with the coefficients the registry holds for that form, device, link and chip. A move that states no form keeps the price it had before forms existed. A form's price never depends on an engine's name or setting. A move whose form the plan or the catalog cannot make, such as ipc between GPUs in different NVLink domains on different nodes, gpudirect_storage with buffered IO, or a staging buffer that is not among the plan's Buffers, is refused by env.DemandFor with a message that names the form and the reason.Checked by: the perturbation test of SUB-11, which changes each form field and expects a price to change; a test that every move stated without a form gets the price it got before; property tests in kernel/ that a pipelined move takes no less time than its slowest leg alone, that a move whose buffer holds one chunk takes exactly the sum of its legs' times for each chunk, that a move's time never falls when a leg's rate falls, and that, for requests that are a whole number of logical blocks, the buffered price of a storage move is never below its unbuffered price, because buffered IO adds a copy in host memory and moves the same bytes; a property test in inference-sim of the two advance rules; a refusal test pair for each form (SIM-9); the completeness test of SUB-7.
  • SUB-22 The form a transport library chooses comes from one function in contracts/transport, over a table in catalog/transport keyed on the library, its version, its settings and catalog facts about the two ends (§6.1). Each table entry cites the library's selection code at that version. A setting or combination the table does not cover is refused by name. No engine repository and no cost-model code chooses a library's transport.Checked by: a table test against what each library reports choosing: UCX's protocol selection report (UCX_PROTO_INFO=y) and NCCL's NCCL_DEBUG=INFO log, recorded with ledger units on each catalog chip and NIC; the catalog validators, which refuse an entry without a citation (SUB-3); a refusal test for an uncovered setting; the review question of X2 for any entry that names an engine.

blis-vllm

Purpose
vLLM's engine in Go, in the four parts of §7.1: the scheduler, engine loop and data parallelism; the KV-cache manager, its block pool and the managers for each KV-cache spec type; the KV connectors and offload tiering; and default resolution and lowering. It models one vLLM release at a time, and registers as engine kind vllm with that version. inference-sim pins one of its commits; a tag is optional (§14.1).
Owns
vLLM configuration, read verbatim; vLLM's default resolution; lowering a model graph to the kernels vLLM runs; emitting plans and step shapes; the oracle and its recorded traces; the field list and the surface list.
Never holds
Pricing arithmetic, coefficients or catalog facts; code from blis-sglang; the decisions of a KV store package, which it reaches through kvstore.Store (KVS-2).
Interfaces
Implements engine.Engine from contracts, which includes reporting its own field list; emits PoolPlan and StepShape; publishes fields.json and surface.json. The substrate defines the method and the shape of a field list, and holds no engine’s fields: a list depends on the engine and its release, and inference-sim fields prints what the registered engine reports without reading it.
Triggers
A vLLM release; a fidelity bug; a modelling gap at the top of the backlog.
Correct when
Every oracle tier matches vLLM at the pinned commit, every changed trace was reviewed, and the field and surface lists are complete.
  • VLM-1 Decisions match vLLM at the pinned commit, step by step, on every oracle scenario.Checked by: oracle tiers T0–T6 (§7.4).
  • VLM-2 Every Go file states where it came from: derived from a vLLM path at a release and commit; derived from a path in a package the oracle's lock pins, naming that package and version, for an adapter a connector imports from it (§6.5); moved from another repository; or original. At every commit of a branch that models a release, every ported file names that vLLM release, and no file names another. An adapter file derived from a package names both the vLLM release and the package version.Checked by: provenance test.
  • VLM-3 The engine’s field list classifies every configuration field and every environment variable the pinned release reads, including those read by the communication libraries it uses, as modelled, proven inert (with a passing proof), or not modelled (with an issue). No other status is allowed, except one a release plan allows for a stated time (glossary: Inert, unproven). A field is modelled when the port reads it and setting it changes a decision in a recorded trace, or a field of the emitted plan or step shape that the cost model prices (SUB-11). Its evidence is an oracle scenario that sets it and whose trace the port reproduces, or a test that sets it and finds the emitted plan or step shape equal to the upstream's own resolution. A field that reaches only a plan or step-shape field on SUB-11's not-yet-priced list is not modelled, and cites that list's issue. A field the port reads but carries to no decision, plan or step shape is proven inert or not modelled. A field marked modelled records the value classes its evidence covers: for a boolean or enumerated field, the values its evidence sets; for an ordered numeric field, the range its evidence sets, split at every threshold the upstream compares the field with, generated from the upstream's comparisons. The probe values of a proven-inert field follow the same classes. A field that can name code outside the pinned release, such as a class or module path, is marked so. A field marked not modelled cites an open issue that names the setting or its group, and says why the port does not model it, what the setting does upstream, and the milestone that models it or the reason it never will. Each field also states its estimation rule (§11.2), or that it has none.Checked by: completeness check; inertness proofs (§7.4); a perturbation test over every field marked modelled; a check that every field has an estimation rule or says it has none; a check that fails a not-modelled entry whose cited issue does not list the field or its group, or that cites no reason. A second check fails on any field whose type can hold a class or module path and is not marked as able to name code.
  • VLM-4 surface.json lists every connector, offload tier, KV-cache spec type and its manager, speculative method, scheduler policy, metric family and KV-event type the pinned release registers, each with a status (X9).Checked by: generator against vLLM's own registration tables (§7.5).
  • VLM-5 No clock reads and no goroutines. Waiting is reported to the simulator as a time value.Checked by: syntax-tree test.
  • VLM-6 A value of an enumerated setting, such as a connector, backend or policy name, runs only through the surface item that models it. Two values share code only where the upstream's own registration maps them to the same class, cited. Every value is either refused by name or produces its own trace.Checked by: dispatch generated from surface.json; a perturbation test per enumerated value.
  • VLM-7 Every KV-cache spec type and group role the pinned release registers in KVCacheSpecRegistry has a status in surface.json that X9 allows. For a modelled one, the manager that KVCacheSpecRegistry maps it to is ported, with oracle scenarios that allocate, evict and free its blocks and, where the manager supports prefix caching, share a prefix between requests. A model whose layers need a refused spec type is refused before the run starts, with a message naming the spec type. The grouping of layers into KV-cache groups at start-up, and the coordinators that run one manager per group, are ported once and serve every manager.Checked by: generator against KVCacheSpecRegistry (§7.5); a T2 scenario per ported manager; a start-up refusal test with a model that needs each refused spec type.
  • VLM-8 A step that consumes a layered transfer follows the timing rule of §6.2. Its wait points are the connector's per-layer calls: wait_for_layer_load before each attention layer, and save_kv_layer after it.Checked by: the shared suite in contracts/conformance for the timing rule of §6.2, with property tests that a layered step never ends before its compute alone would, nor after its compute and its whole transfer run one after the other; that, when every part arrives before the layer that waits for it, it ends with its compute, each layer slowed by layered_transfer_compute_efficiency for the time a part is in flight beside it; and that a transfer with no parts gives the step time it gave before; and the oracle's run for FID-11, which executes the upstream forward pass on meta tensors at the padded batch. For each T4 or T5 scenario with layered parts, that run configures the scenario's connector, gives it the connector metadata the scheduler built for that step, and lists the connector's device copies as transport in the manifest. A hook on the per-layer calls records the layer index of each wait and save, and the port's stated wait points are compared with them. Its known-bad input is the same run with no connector configured, which fails because no hook fired. The perturbation test of SUB-11 covers the coefficient.

blis-sglang

Purpose
SGLang's engine in Go, in the four parts of §7.1: the scheduler and its event loops; the tree caches, allocators and memory pools; the hierarchical cache (HiCache) and disaggregation transfer; and default resolution and backend selection. It models one SGLang release at a time, and registers as engine kind sglang with that version. inference-sim pins one of its commits; a tag is optional (§14.1).
Owns, never holds, interfaces
As blis-vllm, for SGLang. It imports nothing from blis-vllm; shared machinery comes from contracts/harness.
Triggers
An SGLang release; a fidelity bug; a gap at the top of the backlog.
Correct when
As blis-vllm. In addition, its KV events and metrics are byte-compatible with what llm-d's SGLang adapter reads.
  • SGL-1 The oracle drives SGLang's own Python classes at the pinned tag, in a locked environment, with the Python tree core of the radix cache selected.Checked by: the oracle's lock check and recorded-trace provenance check, from contracts/harness.
  • SGL-2 Every Go file states its provenance, as for VLM-2.Checked by: shared harness test.
  • SGL-3 The field list covers every configuration field and every environment variable the pinned SGLang release reads, under the rules of VLM-3. Defaults are resolved as SGLang's own resolution hooks resolve them.Checked by: the field-list completeness check against SGLang's ServerArgs and environment variables, and the T1 default-resolution tier.
  • SGL-4 surface.json lists every transfer backend, HiCache storage backend, tree cache, tree core, allocator and memory-pool type, speculative algorithm, scheduling policy, metric family and KV-event type the pinned release can select, each with a status (X9).Checked by: a generator that reads SGLang's registration tables and selection code at the pinned tag (§7.5), and a check that every item has a status.
  • SGL-5 KV events are emitted exactly as SGLang emits them: one BlockStored per page, merged in SGLang's event queue with the queue's last event when it has the same medium, LoRA adapter, block size, cache salt and session, and its parent hash continues that event's chain (mem_cache/events.py:140-170). Consecutive BlockRemoved events of the same medium are merged too. Both tree cores, Python and Rust, merge the same way (§6.4).Checked by: byte comparison with SGLang's queued events, for both tree cores; a routing test at page size 1 and at page size 16 or more.
  • SGL-6 Every tree cache, tree core, allocator and memory-pool type the pinned release can select has a status in surface.json that X9 allows. A modelled type has its Go counterpart, with oracle scenarios that insert, match, lock against eviction, evict and free through it. A configuration that selects a refused type is refused before the run starts, with a message naming the type.Checked by: a generator that parses SGLang's tree-cache, allocator and pool selection branches at the pinned tag, with an unlisted branch as its known-bad input (§7.5); a T2 scenario per ported type; a start-up refusal test for each refused type.
  • SGL-7 A step that consumes a layered transfer follows the timing rule of §6.2. Its wait point is HiCache's per-layer counter, which a KV pool's buffer accessor waits on before it returns a layer.Checked by: the shared suite in contracts/conformance for the timing rule of §6.2, with property tests that a layered step never ends before its compute alone would, nor after its compute and its whole transfer run one after the other; that, when every part arrives before the layer that waits for it, it ends with its compute, each layer slowed by layered_transfer_compute_efficiency for the time a part is in flight beside it; and that a transfer with no parts gives the step time it gave before; and the oracle's run for FID-11, which, for each scenario with a pending HiCache load, configures HiCache with that step's load and lists its device copies as transport in the manifest. A hook on the counter's wait records each layer index, and the port's stated wait points are compared with them. Its known-bad input is the same run with no HiCache load pending, which fails because no wait fired.

blis-kvstore

Purpose
The decisions of each KV store package (§2.2), in Go: what the store holds, where each object lives, what it evicts and when, and what it answers at its storage API. It has one package per store, such as the Mooncake store and LMCache, and each package models one release of its store.
Owns
One package per store, each with its Upstream record (the store's release and commit); each store's field list and surface list; the oracle that runs each store's own code and services, and its recorded traces.
Never holds
An engine's decisions, including the connector and the adapter that call the store (§6.5); pricing arithmetic, coefficients or catalog facts; a store that decides nothing, which is a catalog storage device.
Interfaces
Each package implements kvstore.Store (§6.5) and imports only packages under contracts/. No engine imports this repository. inference-sim builds each store the scenario's settings name: a store private to one engine instance is passed to that engine, and a shared store runs as its own component (§8.1). Each package publishes fields.json and surface.json.
Triggers
A release of a store it models; a fidelity bug; a store at the top of the backlog.
Correct when
Every store package matches its store's own code at the pinned release on recorded and direct traces, and every field list and surface list is complete.
  • KVS-1 Each store package models one release of its store. Its Upstream record names that release and its commit, every ported file names that release, and no file names another.Checked by: the provenance test from contracts/harness, as for VLM-2.
  • KVS-2 The repository imports only packages under contracts/. No engine module imports it. No store decision exists in another repository: the substrate and inference-sim hold none, and an engine repository holds only the connector and its adapter (X2, X3).Checked by: an import test here; the import test of X3 in each engine repository; a test in inference-sim that every kvstore.Store it builds comes from this module; the provenance case of X3 that refuses an engine-repository file derived from a store path other than the adapter; the review question under X3.
  • KVS-3 A store package's decisions match its store's own code at the pinned release, call by call, at kvstore.Store. The oracle runs the store's own code and every service it calls that makes a decision BLIS models, such as the Mooncake store's master or LMCache's controller, in a locked environment. It replaces only their clocks and the transport that carries bytes, each listed in its manifest (FID-1, FID-2). Its traces are of the two kinds of §7.6: recorded traces are the calls that each engine's oracle records into the store package (FID-12), and direct traces come from a driver this repository writes. A recorded trace changes only as FID-3 allows.Checked by: the store oracle, with oracle/check_mocks.py, oracle/check_lock.py and oracle/check_goldens.py from contracts/harness; a surface-list check that every store marked modelled names recorded and direct traces.
  • KVS-4 For each store, the release that each engine's oracle lock pins equals the release its store package models. An engine's surface item that reaches a store records that release. While an engine's lock pins another release, every item of that engine that reaches the store is refused by name, with a message that names both releases, and the other engine's items are unaffected.Checked by: a build check in inference-sim, which imports both engines and this module, that compares each engine's surface.json record with the store package's Upstream record; a refusal test with a mismatched release.
  • KVS-5 Each store package publishes a surface.json that lists every eviction policy, storage backend, placement strategy and replication mode its pinned release can select, each with a status (X9). The list's header names each file and function its generator parses at the pinned release.Checked by: a generator that parses the named sites, with an unlisted branch as its known-bad input; a check that fails when a named site does not exist at the pinned release; a check that every item has a status.
  • KVS-6 No clock reads and no goroutines. A lease or timeout runs on the simulated time passed in, and the store's own next event is reported through Next (§6.5), as for VLM-5.Checked by: syntax-tree test.
  • KVS-7 Each store package's fields.json classifies every setting its pinned release reads, from the engine process (configuration passed through the connector, environment variables, configuration files) and from the stores block, under the rules of VLM-3. An engine's field list marks each setting the store package reads, and cites that package's entry instead of classifying it twice.Checked by: the field-list completeness check of VLM-3, run against the store's own configuration parsing at the pinned release; a check in inference-sim that every setting an engine marks as read by a store package has an entry in that package's list.

llm-d-router fork (inference-sim/llm-d-router, branch llm-d-r)

Purpose
llm-d's own router code, made runnable in simulated time. It serves both engines through llm-d's own adapters.
Owns
Upstream llm-d code; the runtime interface ("seams") through which the router reads time, starts work, draws random numbers and makes calls; pkg/embed; the audited plugin list; the surface list of llm-d plugin types.
Never holds
Any change to a routing decision.
Interfaces
pkg/embed.New, which implements the contracts/embed router contract and is the only identifier BLIS imports.
Triggers
An llm-d release; a plugin a BLIS user needs.
Correct when
The default runtime reproduces upstream on recorded requests, upstream's own tests pass on the fork, every simulated-runtime decision is one the default runtime can make from the same recorded state, and the change-kind, hazard and API checks pass.
  • RTR-1 Upstream releases are merged into llm-d-r, never rebased. Fork pull requests land as merge commits. Commits written for BLIS follow X20; upstream history is merged as upstream wrote it.Checked by: commit checks, and a history check that the head contains the previous upstream base and adds no upstream commit outside a release. Maintainer practice (§4.2): the repository allows merge commits and forbids squash and rebase merging, a setting a person with write access keeps.
  • RTR-2 Every change the fork makes to an upstream file is one of eleven kinds, and nothing else:

inference-sim

Purpose
The simulator: a discrete-event loop that runs engines, priced by the substrate, behind the hosted router, under a workload.
Owns
The event loop, cluster and instance wiring, and workload generation and replay. Choosing between path and embedded data, and recording which was used. Engine selection, and the Environment the engines are built with (§6.3). Building each KV store the scenario's settings name, from blis-kvstore, and coupling each shared store into the model as a component (§6.5). Link sharing among transfers and the cross-domain traffic of step collectives (SIM-13). The command line, the Result document, and the byte gate.
Never holds
Engine behaviour; a KV store's decisions; routing policy; pricing; resource arithmetic, except sharing links among transfers and step collectives (X3, SIM-13); catalog or coefficient registry data except through the substrate module; a scorer that compares simulations with measured benchmarks, which belongs to accuracy-dashboard (§2.2).
Interfaces
Imports blis-substrate (the cost model, the data loader and the embedded data, besides contracts/), each engine module at one build site, blis-kvstore, and the router fork. Each engine module and the router fork models one upstream release, so a build runs one release of each engine and of llm-d (LIF-6). Emits Result documents and stack.json.
Triggers
A new commit on the main branch of any repository below it; a simulator feature.
Correct when
Determinism and replay tests pass, refactors are identical on the byte gate and the dashboard's corpus, validation changes carry held-out evidence, and verification changes that move outputs carry the price-change report and the scoring harness's figures on published units (X13).
  • SIM-1 The engine is chosen by the scenario's engine: {kind, version}. Any number of kinds may be registered, each at one upstream release; a scenario naming another release is refused (LIF-6). A scenario that still uses the field engine_version, from before engine: {kind, version} existed, is refused with a message that names the replacement.Checked by: tests that build two engine kinds in one binary, and that refuse any scenario using engine_version with a message naming engine: {kind, version}.
  • SIM-2 No silent degradation: unsupported or ambiguous input is refused with a message; library code returns errors and never exits the process.Checked by: refusal tests.
  • SIM-3 Every release publishes stack.json: the exact commit of every BLIS module, with its pseudo-version, and every upstream release it was built and tested with, the Go toolchain version, and the llm-d guides commit.Checked by: a release check that stack.json matches go list -m all, go version and guides.lock for the tagged build.
  • SIM-4 The byte gate (a fixed scenario set whose output must not change in a refactor) runs inside this repository.Checked by: the byte gate job in inference-sim's CI, on every pull request.
  • SIM-5 Each release reports how much of the llm-d stack's published configurations it can run, per engine (X9).Checked by: a release job in inference-sim that computes coverage from two inputs, the llm-d guides commit pinned in guides.lock (which stack.json records) and each engine's surface list, and publishes per-item deployment counts through inference-sim coverage. The dashboard adds its blocked-point counts to them (§7.5).
  • SIM-6 A run that names no catalog or coefficient registry uses the embedded copy. A run that names a path uses that directory instead of the embedded copy, plus any overlays the overlay flags name. A path flag never overlays.Checked by: tests for each case; the result records the data source.
  • SIM-7 Every run makes progress. Each request ends in one of the fates of §8.7 (DEV-9). An engine pauses only when it has a scheduled wake-up or nothing to do. It never has more steps in flight than PoolPlan.InFlight, which is its upstream's depth (in vLLM, max_concurrent_batches, config/vllm.py:577-587; in SGLang, one batch ahead under the overlap scheduler), and never processes a step's output before that step ends. A request that can never fit in the engine's KV cache is refused at admission by the engine, with the upstream's reason, and inference-sim records the refusal; it is never retried forever.Checked by: a progress watchdog that fails a run when no request changes state for a set number of engine steps while work is waiting; a seeded property test over random pools and prompts, including the exact-fit case and the one-block-over case. The capacity boundary cases are also oracle scenarios in each engine repository.
  • SIM-8 Requests and sessions follow one written state machine, whose end states are the fates of §8.7 (DEV-9). Intermediate P/D states, such as waiting for decode KV or transferring, are states of the machine, each with edges to eviction and to an end state. Code that ends a request sets its fate before notifying anyone. Every round a session planned has exactly one fate. A request identifier is never reused within a run.Checked by: a transition-table test; the arrival-count check of DEV-9; an oracle scenario for identifier reuse in each engine repository.
  • SIM-9 Each refusal has two tests: the smallest configuration that triggers it, and the closest one that does not. The message names the field and the value that caused it. A feature or plugin is refused only under the settings that actually reach the code BLIS does not model. A configuration the upstream refuses at start-up is refused at start-up, naming the upstream's own condition: BLIS never simulates a deployment the upstream would not start, and a search never ranks one. A refusal states what the user must change, and says that the deployment does not fit or is not supported when that is the cause; it never reports a limit of the deployment as an error in the simulator.Checked by: the refusal test pairs in inference-sim, each engine repository and the router fork; for each start-up refusal the upstream has on a modelled path, a scenario that the oracle refuses and BLIS refuses with the same condition (T1, §7.4); a message test for each refusal that wording names the field, the value and the cause.
  • SIM-10 Any option that changes a byte of the Result is recorded in the Result's inputs. A cache key includes every input the cached value depends on.Checked by: a test per command-line option that toggles it and compares the recorded inputs.
  • SIM-11 Every field the simulator itself reads (scenario keys outside the engine, router and stores blocks, trace headers, replay descriptors) is consumed, refused or inert, and says which. Engine, router and stores blocks are classified only by their owners (X1, KVS-7). A consumed field changes some byte of the Result when it changes. One validator exists per kind of value (X15), and every input that carries that kind calls it, so a value refused on the command line is refused in a trace header too.Checked by: a reflection test over every input schema that toggles each consumed field; a parity test that the same invalid value is refused through every input.
  • SIM-12 Each request's tokens are counted once, in a token record the engine emits: prompt tokens, tokens served from the local and external caches, tokens computed, and tokens emitted. Session growth, trace export, latency metrics and the Result read that record; none recomputes it. Counts per rank and per group are distinct types (SUB-16).Checked by: a test that every consumer reads the token record; known-answer tests of every capacity function at tensor-parallel and data-parallel widths above one.
  • SIM-13 The traffic that overlapping transfers and step collectives place on a link never exceeds its capacity. inference-sim shares each link among them, as the one piece of resource arithmetic it owns (X3).Checked by: a property test over random placements, transfers and collectives.
  • SIM-14 Every cluster control loop that runs beside the router, such as an autoscaler or the placement of LoRA adapters, is a component (§8.1): it acts only on published values (DEV-1, DEV-4). Each is listed in inference-sim's generated list of control loops, with the upstream controller it models, if any. A Result that used one names it and states its validation status and the evidence for it (§8.9).Checked by: a reflection test that every configurable control policy has an entry in the list of control loops; a Result test that each active loop is named with its validation status.
  • SIM-15 For each part of a layered transfer (§6.2), the simulator sends the engine one transfer-complete message, timestamped when the part's last byte arrives under the link sharing of SIM-13. It computes no step time from them.Checked by: a test in inference-sim that each part produces exactly one message at its arrival time, and that a step's end is taken only from the engine's own time advance; the coupled replay test (FID-9).
  • SIM-16 A scenario may state several deployments, each with its own model and pools. A request goes to the deployment whose model it names, chosen by the model alone, and each deployment has its own hosted router (one per InferencePool) with its own state and its own named random streams (DEV-6), so a draw in one router never moves another. An endpoint's lifecycle events reach only the router of its pool. A request that names no deployed model is refused by name, with the models the scenario deploys. The Result reports figures per model, and a scenario with one deployment runs and reports exactly as it did before.Checked by: a test in inference-sim with two models in two pools: each request reaches its own pool; changing the second router's configuration leaves the first model's routing byte-identical; an endpoint removed from one pool is unknown to the other router; a request for an undeployed model is refused with its message; a run and its replay agree. The refusal has the two tests of SIM-9 for the refusal.
  • SIM-17 A cluster may hold node pools of different chips. An instance is priced and sized by the variant of the pool it is placed in: its PoolPlan, KV budget, step limits and hourly cost all come from that pool's chip, never from another pool's. A variant is a scenario for that chip (the same model, the pool's cluster.hardware), opened once per pool; a node pool whose chip has no variant is refused by name. Two pools may share a chip and differ in price; each instance is billed at the price of the pool it sits in.Checked by: a test in inference-sim with an H100 pool and an A100 pool under one workload: an instance in each reports its own pool's KV budget, step time and price, and a pool with no variant is refused with its name.
  • SIM-18 Engines that run a file-system secondary tier (fs) and name one root_dir for the same model read and write one file system, as vLLM instances over one shared file system do: a block file one engine publishes is a hit for every other engine of that model on that root_dir. A different root_dir, or a different model, is a different file system, since block files of two models are not interchangeable. inference-sim builds one store for each (model, root_dir) pair of a run and hands it to every engine of the model through the engine's ShareTierStorage; an engine never makes a store of its own for a root_dir it shares. The tier has no capacity and evicts nothing, as vLLM's fs tier has none (fs/manager.py).Checked by: a test in inference-sim with engines of two models and two root_dir values: a block file published by one engine is found by the engines of its model on its root_dir and by no other; and a test in blis-vllm in which a prompt one engine cascaded to the shared storage is promoted and loaded by a second engine, which computes only the tokens past the shared prefix.

blis-config-search

Purpose
Find the best configuration for a goal, reproducibly, over vLLM or SGLang settings and llm-d router configurations.
Owns
Experiment specifications, deterministic sweeps, ranking, and reports.
Never holds
Copied lists of settings; invented settings; results written by hand.
Interfaces
Depends only on inference-sim, pinned by tag and commit. It reads settings lists and plugin parameters through inference-sim fields, catalog identities through inference-sim catalog resolve, metric definitions through inference-sim metrics, acceptance profiles through inference-sim acceptance, a cluster's resolved packaging through inference-sim catalog resolve, and the schemas of its inputs and outputs through inference-sim schema. Its scripts never read catalog or coefficient registry files directly.
Triggers
A new experiment; a simulator release.
Correct when
Every specification validates and runs, the same specification on the same pins gives an identical report, and every ranking follows the output analysis of §8.8.
  • CFG-1 One pin file names the simulator release, and every report states it. A committed report uses that release's embedded data; exploratory runs with other data are labelled experimental and are never committed as reports.Checked by: scripts/test_build.py; workflows that stop if the cloned commit differs from the pinned one.
  • CFG-2 Everything after the specification is deterministic and produced by a bot. Comparisons between arms follow DEV-11.Checked by: scripts/test_experiment.py; reports arrive only through the bot's pull request.
  • CFG-3 Settings are the named engine's own settings, read from the simulator. No list of settings is copied by hand.Checked by: a check that every settings list is read from inference-sim fields at the pinned release, and that the repository holds no copy.
  • CFG-4 A specification ranks and checks configurations on any metric of the metric registry, at any scope (§8.7). Examples are the p95 time to first token for the whole cluster, the largest p99 time to first token over instances, and output tokens per second per accelerator for one pool. Every metric it uses has one definition in the metric registry, shared by the search, the ranking and the report (DEV-8), and every figure states its metric, scope and aggregate. A run that is overloaded or incomplete is never ranked (DEV-10).Checked by: a specification check that every metric a specification names is a metric registry identifier and every scope is one the metric registry defines; the report schema, which requires each figure's metric, scope and aggregate; regression tests.
  • CFG-5 A search varies only settings that the engine's field list marks as modelled at the pinned release. A ranking states the least trusted coefficient method and, from the dashboard's published summary at the release its pin file names, the grades of the dashboard points in the lanes it relies on, and a recommendation in a lane with no G1 or G2 points is labelled an extrapolation, with that lane's measured error. A speculative-decoding arm states its acceptance in its scenario (D8). The value comes from the substrate's profiles, read through inference-sim acceptance, which runs D8's lookup, or from another cited measurement. The report names the source and each key field in which it differs from the arm.Checked by: a specification check against inference-sim fields; the report schema.
  • CFG-6 Everything the pinned simulator can run is a knob a specification can sweep: each setting the engine’s field list marks as modelled, and each scenario field the simulator reads, such as pools and their hardware, parallel layout, KV tiers and connectors, speculation, router plugins and workload. A knob that a search cannot vary is listed with its reason, such as a value fixed by the deployment being searched. The list of knobs is generated from the simulator at the pinned release, never written by hand (CFG-3).Checked by: a generated knob table, built from inference-sim fields and the scenario schema of the pinned release; a test that fails when a modelled setting or a scenario field has neither a sweep key nor a listed reason, with a scenario field added to the schema as its known-bad input.

accuracy-dashboard

Purpose
Show publicly how accurate BLIS is against measured ground truth, and how much of that ground truth it can score, for every engine, engine version, chip, model and layout.
Owns
Fetching InferenceX runs and their recorded configurations for the units the ledger lists; the end-to-end scoring harness, which is the single scorer (COV-1) and turns a measured run into a scenario, runs a given simulator build (a release, or a commit of a branch or pull request) on it, and compares; closeness grades; coverage; the blocker backlog; and the website. The harness is a script, run from a release or from any commit a lower repository pins, and is what whole-run accuracy gates run (§13.5), so a gate and the dashboard compute a figure the same way.
Never holds
Its own list of which settings are modelled; translation of settings, except the stand-ins the engine's estimation rules state; a published figure computed on points used for fitting.
Interfaces
Depends only on inference-sim: its releases for the published dashboard, and the unreleased commits a pull request names for review and gate runs. Its seed-holding jobs also check out blis-substrate/catalog/ledger at the substrate commit the build uses, and compare it with the ledger at the merge base (§3.3), because computing select and held roles needs the full ledger. It gets everything else from seven inference-sim commands:
  • fields prints each engine's field list;
  • ledger prints the published fit and anchor unit lists;
  • catalog resolve maps an InferenceX model or chip name to a catalog identity, or reports that none exists;
  • coverage prints each surface item's deployment count in llm-d's guides;
  • invariants prints the invariant registry at the substrate version inference-sim pins;
  • metrics prints the metric registry (DEV-8);
  • schema prints the JSON Schema of every document BLIS reads and writes, and schema validate checks a document with the Go validators (SUB-19).
It imports no other BLIS module.
Triggers
A simulator release, picked up by the next nightly run (new ledger units and catalog entries arrive this way); predictions files posted by candidate jobs of lower repositories, collected by a scheduled or dispatched workflow on its own main. A new InferenceX dump is scored once the substrate release that embeds its anchor list, and the inference-sim release that pins it, exist.
Correct when
Every anchor unit has a grade, refactors leave scores identical, and coverage and the backlog are published.

Its invariants, COV-1 to COV-12, are in §11.8 with the design they enforce.
