12Triggers

A trigger is an outside event that requires work. Each trigger has one playbook, with the same fields every time:

  • how the trigger is detected;
  • a preflight that computes the scope before any work starts;
  • the steps;
  • the checks that must pass;
  • what done means;
  • the expected size of the work.

Figure 5 shows which repositories each trigger touches.

12.1 A new model on existing capabilities

Detected
A request; a new model appearing in InferenceX data with no catalog entry, which the dashboard's backlog lists; or a drafter that a catalog model's InferenceX deployments run and the catalog lacks, which the §12.2 poll reports.
Preflight

inference-sim onboard --plan <hf-repo@revision> <scenario>… answers, for each requested engine, layout and cluster:

  • Is there a graph handler for the architecture?
  • Does the graph vocabulary cover it?
  • Does the engine lower every primitive?
  • Which coefficients would come from which method (§9)?
  • Is the router configuration hosted?

If anything other than a catalog entry or a coefficient is missing, the request becomes a new-capability trigger (§12.7) for that part.

Steps
  1. Add the vendor config.json at a full revision hash, and model.yaml; generate graph.yaml. If the architecture is new, add a graph handler.
  2. List the model's drafters in its model.yaml: its graph's own speculator, and each separate drafter entry, which names its target. Include every drafter its InferenceX deployments run, and onboard each separate one as a model. A drafter whose method the engine does not run is a new-capability trigger (§12.7).
  3. Where the preflight shows coefficients below rank 1, fit them if fit data exists. Otherwise keep the less trusted value (the one with the larger rank number).
  4. Merge the change into blis-substrate's main branch. The release bot moves inference-sim's pin to that commit.
Checks
Validators; deriver --check; coefficient registry property tests; a run of each requested layout; held-out accuracy for any of the model's held units.
Done when
  • T-M1 One pull request in blis-substrate, plus the bot's version bump. No engine, router or simulator code changed.
  • T-M2 Every requested layout runs, or the preflight names why not.
  • T-M3 Every coefficient the model uses has a method, and the method mix is reported.
Size
One pull request. An agent working this trigger opens only blis-substrate.

12.2 A data drop

Detected
A scheduled job polls each source: new InferenceX dump tags, run ids and acceptance curves, new AISimulate commits, new forward-pass dataset revisions. It opens a pull request when one appears. It also reports each drafter that a catalog model's InferenceX deployments run and the catalog lacks (§12.1).
Preflight
A ledger diff: new, changed and removed units per source and engine. The seed-holding release job adds which coefficient families gain fit units.
Steps
  1. Pin the new revision in the ledger's sources file.
  2. Commit the new units. Their roles are drawn by the seed-holding jobs the first time those jobs see them, before any use (D4).
  3. Refit only the families whose fit data changed. A refit that uses new units waits for the substrate release whose release job publishes their fit list. Each refit follows §12.3.
  4. Regenerate the acceptance profiles. A new curve is carried, with its drafter, when its model and drafter resolve in the catalog; one that does not is skipped with a stated reason (D8).
Done when
  • T-D1 No existing unit changed role.
  • T-D2 Every new unit has exactly one role.
  • T-D3 The revision is pinned by hash.
  • T-D4 Coverage and grade changes per lane are reported.
Size
One ledger pull request, plus one per refitted family.

12.3 An idea to improve accuracy

Detected
A person or an agent proposes it, usually from the top of the backlog.
Preflight

A pre-registration file, committed before any held-out data is read. It states:

  • the hypothesis;
  • the layer it changes: a coefficient, a method, a pricing form, or engine behaviour;
  • the target lanes;
  • the sources and lanes whose select and held units will be used (the jobs choose the units themselves);
  • the success criteria;
  • the predicted dashboard change.
Steps
  1. Make one change per pull request.
  2. Evaluate candidates by path. A writer script puts each candidate coefficient registry in its own directory, and the select job scores each one with --registry <dir> (§13.5). A data-only candidate needs no rebuild.
  3. Choose among candidates using select units only.
  4. Evaluate once on held units, in the gate job (§13.5).
  5. Land the change if the criteria pass. Otherwise commit the negative result as a note.
Done when
  • T-A1 Results on held units exist only as outputs of the gate job, run after the pre-registration commit (D7).
  • T-A2 Held-out error and distribution distance did not get worse on any lane, judged by the paired interval of VAL-6, and improved on the target lane.
  • T-A3 After release, the dashboard change is within the predicted range, or the miss is recorded.
  • T-A4 A failed idea leaves a committed note with its evidence, so it is not tried again blindly.
Size
One change in the repository that owns the layer. A bundle of several ideas is refused.

12.4 A vLLM or SGLang release

Detected
The engine repository's release watcher, a scheduled job, watches the upstream's final release tags (release candidates are ignored, §14.1) and opens an upgrade pull request with the preflight attached.
Preflight

Three generated reports:

  • The surface diff: new, removed and changed connectors, tiers, KV-cache managers, speculative methods, policies, configuration fields, defaults, metrics and event types (§7.5).
  • The field demand: for each new or changed field, how many dashboard points set it and to which values, which the dashboard posts on the upgrade pull request from its published blocked-point counts, as it does for surface weights (§7.5). A field the data use most is modelled first, over the range of values the data use.
  • The source diff: for each ported Go file, its Derived from header names an upstream file, so the tool lists every ported function as unchanged, changed (with the upstream diff) or removed. It also lists kernel implementations whose selection changed.

An agent working the upgrade reads these reports, not the whole upstream.

Steps
  1. Cut the release branch release-<old> from main, so fixes to the old release can still ship (§14.4).
  2. On main, update the Upstream record, the oracle's pinned commit and lock file, and run all tiers.
  3. Re-port only the changed functions. Delete code for anything the new release removed.
  4. Classify every new surface item and configuration field.
  5. Regenerate the recorded traces that changed. Each one gets a golden-reviewed: line with its reason.
  6. Merge the upgrade into the engine repository's main branch. The release bot moves inference-sim's pin to that commit in a MINOR release (§14.1). Scenarios naming the old release are then refused with the message of LIF-6.
  7. For each kernel implementation whose selection changed, the substrate gets a coefficient by the methods of §9. A transferred value states its transfer rule (§9.2).
Done when
  • T-E1 Changes are confined to three places: the engine repository; the simulator's version bump, in which the release bot rewrites engine.version in the byte-gate and example scenarios and a person reviews the byte-gate changes; and the coefficients the preflight named.
  • T-E2 Every ported file names the new release, and no code for the old release remains on main.
  • T-E3 The surface list and field list are complete for the new release.
  • T-E4 Every changed trace carries its review line.
  • T-E5 The replacement manifest is unchanged, or bumped with a reason.
  • T-E6 The new inference-sim release refuses scenarios naming the old release with the message of LIF-6. The release that message names lists the old release in its stack.json, and its tagged build reproduces its own recorded byte-gate output.
Size
Proportional to the number of changed ported functions and new surface items, not to the size of the engine.

12.5 An llm-d release

Detected
A scheduled job in the fork watches llm-d's release tags.
Preflight

hack/upstream-merge-report lists:

  • conflicts with files the fork changes;
  • new clock, goroutine, random or map-order uses on decision paths;
  • new or renamed plugin types and parameters;
  • changed per-engine metric mappings and KV-event adapters;
  • changed resource definitions.
Steps
  1. Cut release-<old> from llm-d-r (§14.4).
  2. Merge the release into llm-d-r (not a rebase).
  3. Route every new hazard site through the runtime interface, or add it to the baseline on review (RTR-6). Each change to an upstream file must be of an allowed kind (RTR-2).
  4. Audit new plugin types, or leave them refused.
  5. Merge the upgrade into the fork's llm-d-r branch once the fork's own checks pass, after re-applying any hosting change the merge conflicted with (T-R1). The fork's merge does not wait for the rest of BLIS.
  6. If the release changes the metrics or KV events llm-d reads from engines, check that each engine still emits exactly what its upstream release emits. Change an engine only where llm-d's new mapping exposes something the port omits but its upstream emits. Where llm-d reads something the modelled engine release does not emit, BLIS reproduces the mismatch, and the release notes name it.
  7. Move inference-sim's replace line to that commit, and update its plugin allow-list in the same pull request. If an upstream behaviour change breaks inference-sim tests while the fork's own checks pass, for example a change to how a picker breaks ties, that pull request waits. The release watcher opens an issue that names the upstream change and the failing tests, and tags the owners of inference-sim and the fork, who decide whether the tests or the expected results change.
Done when
  • T-R1 Every existing hosting change survives the merge unchanged, or is re-applied with a reason.
  • T-R2 Every changed hunk in an upstream file is of an allowed kind, and the hazard lint passes. The release notes report how many upstream lines the fork changes, as a measure of merge cost.
  • T-R3 No unaudited plugin type is reachable from a shipped scenario.
  • T-R4 Both engines' metric and KV-event mappings are exercised by tests, and each engine still emits exactly what its upstream release emits.
  • T-R5 Upstream's own tests pass on the fork, and the differential test of X4 passes against the new upstream release.
Size
One fork pull request and one version-bump pull request, plus engine pull requests when llm-d changes what it reads from engines.

12.6 A new engine

Steps
Create blis-<engine> from contracts/harness: the provenance check, the no-clock check, the trace and manifest checkers, and the Upstream record. Generate its surface list first, so the scope is known before porting starts. Implement engine.Engine and plan emission, then register the engine kind in inference-sim. This is how blis-sglang starts (§14.3), and how TRT-LLM would start later.
Done when
T-N1 The substrate changes only by adding to contracts. T-N2 Every surface item has a status.

12.7 A new capability

Detected
The top of the backlog, or a refused surface item that a user needs.
Steps
  1. An additive contracts change, if one is needed.
  2. Each engine either implements the capability with traces, or refuses it by name. Where the capability rests on a framework (§7.6), port the framework first.
  3. An engine-independent pricing form in the cost model, if one is needed.
  4. Coefficients by the methods of §9.
  5. Wiring in inference-sim.
Done when
T-B1 The capability is engine-independent in the substrate. T-B2 Each engine models it or refuses it by name. T-B3 It is one capability per review set, never bundled with a model.
