6The boundary between engines and the cost model

6.1 The rule

Only an engine repository knows its upstream, so only it works out the engine's behaviour: defaults, backend choices, padding and graph-capture sizes. It hands the cost model three plain objects, described in physical units (bytes, tokens, ranks), never in an engine's vocabulary: a PoolPlan, a StepShape, and, for each KV move, an engine.Transfer whose Move field states the move in physical units: the catalog device, the node and rack that send and receive, and the direction. The cost model never sees an engine's settings and never applies an engine's rules (SUB-6). A release plan may relax this rule for one named input while settings resolution moves into engine lowering: the cost model may read the typed engine-settings carrier (contracts/kernel/enginesettings, Inputs.Engine and the code that reads them) as a transitional input. The relaxation lets nothing new in: no engine default, spelling or backend choice is added to the substrate while it lasts. It ends when engine lowering resolves every setting and the substrate receives only the plan, the step shape, transfers and operation facts. The plan names the relaxation, the date the maintainer approved it and the milestone at which it ends (X2, SUB-6).

The forms a move takes. Many KV moves are not a plain copy over one link. A move from storage can pass through a staging buffer in host memory, or go straight to the GPU; a move to a peer instance can cross NVLink, PCIe, an RDMA network or a TCP network, from GPU or host memory at either end; a storage device can sit on the node or across the network. So the Move also states its form, from the closed list below, and these fields of plan.Transfer:

  • the memory at each end: GPU, host, or a named catalog storage device;
  • for a storage device reached over the network, or a move between nodes, the protocol: RDMA or TCP;
  • for a copy between GPU and host memory, the copy mechanism: the GPU's copy engines, or a copy kernel that runs on its streaming multiprocessors;
  • the staging buffer, if the bytes pass through one, and the chunk size the move is pipelined in;
  • for storage, whether IO is buffered (through the operating system's page cache) or unbuffered (O_DIRECT), and whether the upstream syncs a write to the device before it counts the write as done;
  • the size of one request, and how many requests the engine keeps in flight;
  • the bytes it registers with the network for the first time.

A move that states no form is priced as env.DemandFor priced it before forms existed: its Kind and Tier select copy for host memory, storage for a storage device, and the network form its endpoints imply for a peer. So no earlier move changes price (SUB-1). The engine states the form, as its upstream's code and configuration choose it. Where a transport library makes that choice, as UCX does under NIXL and NCCL does for its own transfers, the engine gets it from one table in contracts/transport, described below. The cost model never picks a form and never falls back from one form to another (SUB-6).

The cost model prices each form as a sequence of legs. A leg is a copy over one path that the catalog states: within a node, the link between a GPU and host memory, host memory itself, the NVLink domain, the PCIe path between two devices, or a storage device's own link; between nodes, the NIC at each end and each switch tier between them (SUB-17). A PCIe path between two devices is priced through the host. One leg of b bytes, sent as n requests with q in flight, takes ⌈n/q⌉ × base latency + b / rate, with the rate held to the catalog peak of the leg's link (SUB-5). A memory layout, such as SGLang's layer_first or page_first, reaches the price only through the request size and count it gives. This section defines each coefficient family; how a value is obtained follows §9.

NIXL's storage plugins map to forms by what they do: its GDS plugin to gpudirect_storage; its POSIX plugin to storage or staged_storage; its object plugin, which moves bytes through host memory with an S3 client, to storage or staged_storage over tcp. A storage device reached over the network, such as a network file system, an object store or 3FS, is a catalog storage device with a network attachment: the catalog states the rack or switch it hangs from, or that it sits outside the cluster behind a stated uplink. Its coefficients are its own.

Staging. Any form may name a staging buffer in host memory, which adds a leg between the buffer and the GPU at each end that uses one. This is how a peer pull from GPU memory over TCP, or an RDMA move whose GPU memory is not registered with the NIC, is stated. The buffer is one of the plan's Buffers, so its size is the size the upstream allocates. A move with more than one leg goes through its buffer in chunks of the size the engine states. If the buffer holds two chunks or more, the legs overlap: the move takes the first chunk's time through every leg, plus the slowest leg's time for each later chunk. If it holds one chunk, each chunk passes through every leg before the next starts, so the legs run one after the other. When the upstream keeps the bytes in a tier between two legs, as vLLM's CPU tier sits between GPU memory and its secondary tiers, those are two moves, each reported on its own: here, a copy and then a storage move.

Buffered and unbuffered IO. Unbuffered IO (O_DIRECT) goes between the device and the buffer. The operating system requires each request to be aligned to the device's logical block size, a catalog fact, so each request is rounded up to it. Buffered IO also copies the bytes through the page cache, so the storage leg carries one more copy in host memory, priced at host_copy_rate. A buffered read is priced as a read from the device. A buffered write is done when its bytes are in the page cache, unless the move states that the upstream syncs it, citing the call, in which case it is done when the device write is. The device write that follows, the page cache's writeback, is demand on the device's link that continues after the move ends, and the simulator shares it like any other. A read that the page cache would serve without the device depends on what the node read and wrote before, which no engine decides and no price holds. That hit is not priced. This is a stated limit of this section, with an open issue in blis-substrate.

Who chooses the transport. Some forms are chosen by a transport library rather than by the engine's own code. Under NIXL, UCX picks cuda_ipc, rc, tcp or cuda_copy from the hardware it finds and from settings such as UCX_TLS. NCCL picks a peer, shared-memory or network path from its own topology search and from settings such as NCCL_P2P_LEVEL. That code is neither engine's, so no engine repository ports it (VLM-2), and the cost model may not resolve it (SUB-6). The choice is split in two. The table is data: entries in catalog/transport, keyed on the library and its version, the library settings the engine's field list classifies (VLM-3), and catalog facts: whether the two ends share a node or an NVLink domain, the NIC, and whether it supports GPUDirect RDMA. Each entry gives the form, cites the library's selection code at that version (SUB-3), and names no engine (X2). The selection is one function in contracts/transport, which reads the table through an optional interface that inference-sim's Environment also implements, so the contract grows compatibly (SUB-1) and engines still import only contracts/. The engine passes the library, its settings and the endpoints, and states the form the function returns. A setting or a combination the table does not cover is refused by name (SUB-22).

How the simulator advances a move. The cost model returns the bytes each leg places on each link, and the move's fixed latency: its base latencies, the pipeline's first chunk, and any registration. The simulator shares each link among the moves on it (SIM-13). A pipelined move then advances at the rate of its slowest leg after sharing, and a move whose buffer holds one chunk at 1 / Σ(1 / ri), where ri is each leg's rate after sharing. Both rules are part of the link sharing that X3 allows the simulator (SUB-21).

6.2 The plan and the step shape

Both are defined in contracts/engine. Every field added later must keep its zero value meaningful, so the contract only grows (SUB-1).

// PoolPlan is fixed for the life of one engine pool.
type PoolPlan struct {
    Hardware string         // catalog chip name
    Fabric   string         // catalog network name; "" on one node
    Layout   Layout         // tensor, pipeline, data, expert and context parallel widths, and rank placement
    Layers   []LoweredLayer // one entry per (layer, primitive)
    KV       []KVGroup      // per cache group: bytes per page, tokens per page, full or sliding window
    KVBudget []int64        // bytes per rank available for KV, one value per pipeline stage
    Tiers    []KVTier       // the KV tiers below GPU memory, as the engine resolved them
    Graphs   GraphPolicy    // CUDA-graph buckets, keyed by token count or by batch size
    Drafts   DraftPolicy    // speculative decoding: chain length, or tree (top-k × steps)
    DraftLayers []LoweredLayer // the draft model's own layers, lowered like the target's
    Host     HostPlan       // per-request and per-token host work (admission, sampling, detokenizing)
    Weights  []ResidentTensor // per rank: shape, stored data type and sharding, after weight post-processing
    Buffers  []Buffer       // engine-chosen buffers and workspaces, sized as the upstream sizes them
    InFlight int            // most steps in flight at once; 1 without asynchronous or overlap scheduling
}

type LoweredLayer struct {
    Layer      int          // index in the model graph
    Stage      int          // pipeline stage that runs it
    Primitive  string       // from a fixed list: "attention.decode", "gemm", "moe.grouped_gemm", "all2all", …
    KernelImpl KernelImpl   // what executes it; the registry looks coefficients up by this
    Shape      PrimitiveShape
    Collective *Collective  // group, bytes, and whether it crosses nodes
}

type KernelImpl struct {
    Library  string         // from a fixed list in contracts, e.g. a named attention library
    Variant  string         // the library's own exported kernel name; an engine's backend names map to it in the engine's lowering
    CodeHash string         // hash of source and target GPU architecture, or of a binary library (below)
}

type KVTier struct {
    Device   string         // catalog device name, e.g. host DRAM, local NVMe
    Bytes    int64          // capacity per rank, as the engine sized it
    Shared   bool           // one copy per node rather than one per rank
}

// StepShape is one engine step on the data-parallel ranks that run in lockstep, already padded by the engine.
type StepShape struct {
    Mode      StepMode      // Mixed, ExtendOnly, DecodeOnly, Verify, Prebuilt or Idle
    Ranks     []RankStep    // per data-parallel rank in the lockstep group: each request's scheduled and cached tokens
    Padded    []PaddedShape // per rank: the shape actually launched (graph bucket, padding)
    Drafts    DraftShape    // tokens drafted and verified this step
    Stage     int           // pipeline stage; 0 without pipeline parallelism
}

Prebuilt is SGLang's P/D decode merge: KV arrived from the prefill pool, so the step runs no forward pass. It still has scheduler and host cost, which the cost model prices.

PaddedShape also records how the step launches: a full CUDA-graph replay, a piecewise replay with some layers run eagerly, or a fully eager run. These have different costs, so the engine states which one applies.

These definitions imply six rules:

  • The engine pads the batch, and the cost model prices the padded shape. vLLM pads in its model runner, to token-sized graph buckets and data-parallel padding rules. SGLang captures decode graphs by batch size. Each engine reports the shape it launches in Padded. When data-parallel ranks run in lockstep, padding depends on every rank's tokens in the same step, so a StepShape describes all the ranks that run in lockstep. The engine decides which ranks those are. In vLLM v0.32.0, data-parallel ranks run in lockstep only for mixture-of-experts models; for a dense model each rank is an independent engine (v1/engine/core.py:1473-1481), so its StepShape has one rank.

  • The engine names the exact kernel implementation. SGLang, for example, picks an attention backend per chip and model, and forces a page size of 64 for FlashMLA (arg_groups/overrides.py:1146-1154). The engine's lowering records that choice in KernelImpl, and the coefficient registry prices that exact implementation.

    The coefficient registry's lookup key uses a hash of the kernel's source (the kernel hash, CodeHash), not a package version. Engines pin library versions in their lock files (vLLM v0.32.0 pins flashinfer-python==0.7.0.post1), and those versions move often without changing a given kernel. A coefficient lists the kernel hashes it is valid for. A version bump that leaves a kernel unchanged therefore needs no substrate change. A kernel whose source changed gets a new key, and the substrate must supply a value for it (§9). Libraries shipped only as binaries, such as cuBLAS, cuDNN and FlashInfer's precompiled kernels, are keyed by the SHA-256 of the shipped library file together with the target GPU architecture. For a kernel built from source, the hash covers the source and the target GPU architecture. A compiler or CUDA toolkit change can change a kernel's speed without changing its source; the engine records the toolkit version with each kernel implementation, and the coefficient registry treats a toolkit change like a library change that leaves the source alone: the entry stays, and the landing gate (VAL-6) shows whether the old value still holds. Each engine release ships a generated table, kernel_impls.json, of every kernel implementation it can emit, for its pinned library versions and for every library version seen in InferenceX runs. Runtime tuning (autotuned launch configurations, library heuristics, and tuned-configuration files such as vLLM's per-GPU fused-MoE configurations) is part of the implementation's measured behaviour, not a separate key. If a lookup has no entry for an exact implementation, the cost model takes the most trusted entry §9.2 offers for that chip, at worst the primitive family's roofline or assumed entry, and the price records that method (VAL-3). Kernels that ship inside an engine, such as vLLM's custom all-reduce, use the library names vllm-csrc and sglang-kernel. These are library names, and the engine-name check (X2) allows them as such.

  • The engine decides which KV blocks move between tiers, and the substrate prices each move. Which blocks move between GPU memory, host memory and storage, when, and under which policy, is engine behaviour: vLLM's offloading connector and tiering factory, SGLang's HiCache. The engine reports each move as an engine.Transfer. The cost model turns each transfer into a demand: bytes per link, from catalog device facts and coefficient registry tier coefficients. The engine returns its transfers to the simulator with each step. The simulator asks env.TransferDemand(engine.Plan(), t.Move) for each one, through env.DemandFor, which returns the bytes each link must carry. env.DemandFor first refuses a transfer whose report and Move disagree, or that its plan cannot make. An engine that starts a transfer implements engine.Planned, whose Plan() returns the PoolPlan the transfer is priced against. The engine states a peer's node and rack from the request (engine.Request.Peer), which a host must set on a request that pulls KV from a peer. The simulator fills in nothing. Two limits are deferred to M3. A plan.Transfer has one sender and one receiver, so for a pool that spans nodes the engine states the node that holds the tier, and the cost model prices that node's link (blis-substrate#48). A plan.Transfer has one token count, so the blocks each KV cache group moves, which differ in a hybrid model, are not stated (blis-substrate#49).
  • Sharing a link over time is the simulator's job. A transfer can span many steps, and several transfers can share one link. Dividing a link's bandwidth among concurrent transfers depends on when they happen, so it belongs to the simulator's event loop. This is the one place the simulator does resource arithmetic, and X3 states it as the only exception. Everything else about tiers comes from the engine or the cost model: capacity, bytes per block, and which blocks move.

  • A transfer can be consumed layer by layer, overlapped with the step that uses it. In vLLM v0.32.0, every attention layer calls the connector's wait_for_layer_load before it runs and save_kv_layer after (model_executor/layers/attention/kv_transfer_utils.py:15-60). Of the registered connectors, the LMCache connectors, when LMCache's use_layerwise is set, and MoRIIOConnector do work there (kv_connector/v1/lmcache_connector.py:163-183, kv_connector/v1/moriio/moriio_connector.py:373-390); the others return at once. In SGLang v0.5.23, HiCache loads host KV one layer at a time, and each KV pool's buffer accessor waits on a per-layer counter before it returns a layer (managers/cache_controller.py:83, LayerDoneCounter; mem_cache/memory_pool.py:2852-2880). The engine states this with the field Parts of engine.Transfer. Each part is one plan.Transfer with the range of layers it carries, numbered within the pipeline stage that runs them, and, for a load, the layer whose compute waits for it, or, for a save, the layer after whose compute it may start. The engine also states whether the step's end waits for its layer-wise saves. A step whose launch mode, as PaddedShape records it, does not run the per-layer calls states no parts, and the engine cites the upstream condition. These wait points are engine behaviour, placed as the upstream's code places them.

    The cost model sizes each part from the plan's KV groups and prices it as a move (§6.1). It returns the step's compute time per layer with its StepEstimate. A layer that runs while a copy is in flight beside it runs at a share of its rate, the coefficient layered_transfer_compute_efficiency, keyed on chip, link and copy mechanism (copy engine or copy kernel), and measured by timing a layer's kernels with and without a concurrent copy of each mechanism. The simulator moves each part over its links, shared as for any transfer, and sends the engine a transfer-complete message for each part when it arrives (SIM-15). The engine ends the step, as it combines pipeline stages: layer i starts when layer i−1 has ended and every part it waits for has arrived, the step ends when its last layer ends, or later if it waits for its saves, and each arrival recomputes the engine's time advance (§8.3). This timing rule is the same for every engine and is checked by one suite in contracts/conformance; VLM-8 and SGL-7 add only each engine's wait point. A transfer with no parts is consumed whole, as before.

  • The engine combines pipeline stages. With pipeline parallelism the engine emits one StepShape per stage. The cost model prices each stage alone. How stages overlap, and where bubbles occur, is the engine's batch-queue behaviour, so the engine combines the stage times and reports them to the simulator.

6.3 How an engine is built: two phases

An engine cannot size its KV cache without knowing how much memory the model's weights, activations and buffers take. That is the cost model's arithmetic. The cost model, in turn, cannot price a step without the engine's plan. inference-sim breaks the loop by giving the engine an environment when it builds it:

// contracts/engine: what an engine may ask of the substrate while it is built and run.
type Environment interface {
    Graph(model string) (*model.Graph, error)          // the catalog's model graph
    Chip(name string) (*hardware.Chip, error)          // catalog hardware facts
    Memory(partial PoolPlan) (kernel.MemoryBreakdown, error) // weights, activations, buffers; per stage
    Price(plan PoolPlan, step StepShape) (kernel.StepEstimate, error)
    TransferDemand(plan PoolPlan, t plan.Transfer) (kernel.TransferDemand, error) // t is an engine.Transfer's Move; plan is the engine's Plan()
    Acceptance(model, drafter, workload string) (acceptance.Profile, error)
}

// engine.New builds an engine for one pool.
func New(spec Spec, env Environment) (Engine, error)

Here plan.Transfer is the move as the cost model receives it: the tokens moved, the node and rack at each end, the direction, and the catalog device of a tier. Each end is a plan.Endpoint, a node and a rack, both numbered within the pool the end belongs to: the node from the pool's first node, the rack from its lowest rack. It is defined in contracts/engine/plan, with PoolPlan. The simulator takes plan from engine.Plan() and t from the Move of each transfer the engine returns.

A move that spans nodes, and a move in a hybrid model. Two facts about a real move do not fit one pair of endpoints and one token count, so plan.Transfer has two optional fields for them.

Node moves. A pool may span several nodes. An offload job or a pull then runs on every worker of the pool, and each node's workers move their own share of the KV at the same time. The engine states this with Nodes, a list of plan.NodeMove. Each entry is one node's move: the node and rack it starts from, and the node and rack it lands on, numbered as in the paragraph above. Every entry moves the move's tokens, for its own node's share of the KV. The cost model finds the bytes of each entry from the plan, as the KV of the ranks that sit on that node. It prices each entry over its own path, as it would a move on its own, and adds the results into one demand: a link that two entries use carries the sum of their bytes, and each node's NIC carries only its own. The entries run together, so the move's fixed latency is the largest of theirs, not the sum. This is how two nodes behind one oversubscribed uplink load that uplink twice. An entry that leaves and lands on the same node uses no NIC (SUB-17). When Nodes is empty, the move is the single From and To, priced over one node's links. When it is not empty, From and To are the first entry, and the engine's report is refused if they differ from it.

Group sizes. A hybrid model keeps several KV cache groups, and the groups hold different numbers of blocks: a sliding-window group keeps only its window, a full-attention group keeps every token. A move may therefore carry a different token count for each group. The engine states it with Groups, a list of plan.GroupMove: the index of a KV group in the plan's KVGroups, and the tokens that group moves. The cost model rounds each group up to the pool's page size and sums the groups' bytes. Tokens stays the largest count among the groups, and the report is refused if any group's count exceeds it. When Groups is empty, one count, Tokens, applies to every group, as before.

Both fields are additive and optional (SUB-1). An engine that states neither is priced exactly as it was. An engine whose upstream moves bytes per node, or per group, states the fields, so that no per-engine pricing hook is needed beside env.DemandFor: the host prices every move through that one call. The conformance suite has a two-node pool and a two-group hybrid model, and a known-bad engine that reports one endpoint for a pool that spans nodes and gets a price that is too low for it.

Construction then runs in two phases:

  1. Plan. The engine resolves its configuration and lowers the model into a partial PoolPlan, one whose KV budget is still empty. The partial plan carries the engine's own profiling step shape (in vLLM, the shape its memory profiling run uses; in SGLang, the shape behind its reserve formula) and the set of graphs it will capture. The engine states the resident weights and the buffers it chooses in the partial plan. env.Memory sums their bytes, and sizes the activations of the profiling shape and the graph pools. Choosing the profiling shape is engine policy; the cost model only sizes the shape it is given. The engine then applies its upstream's budget rule, such as vLLM's gpu_memory_utilization or SGLang's mem_fraction_static, and fills in KVBudget.
  2. Run. Each step, the engine forms a StepShape and asks env.Price for its time.

inference-sim implements Environment using the substrate's cost model and data loader. Engines therefore import only packages under contracts/, yet run against the released catalog, coefficient registry and cost model. Engine tests use a small reference implementation in contracts/conformance, which prices from fixed test values.

6.5 The KV store contract

A KV store package (§2.2) is reached through one contract, kvstore.Store in contracts/kvstore. The contract sits at the store's storage API, the calls the store offers to whatever uses it: for LMCache, its cache engine (lmcache.v1.cache_engine.LMCacheEngine); for the Mooncake store, its client's put, get, exist and remove. It does not sit at the connector. The adapter between an engine and that API decides which tokens a request saves and loads, and when, using the engine's own scheduler types, so it is engine behaviour (X3). vLLM v0.32.0 can run either its own copy of the LMCache adapter or the one the lmcache package ships, chosen by use_native (kv_connector/v1/lmcache_connector.py:88-108). Either way the engine repository ports the adapter, and the file names where it came from (VLM-2).

// contracts/kvstore: a KV store's storage API, as an adapter calls it.
type Op int // Exist, Get, Put, Remove, Pin or Unpin

type Location struct {
    End    plan.Endpoint // node and rack (§6.3)

}
type Memory struct {
    Kind   MemoryKind // a closed set: GPU, Host or Device

}

    Pool    int // the pool's index in the scenario
    Replica int // the engine instance within the pool
}
type Request struct {
    Op    Op
    Keys  [][]byte // the store's own object keys, as the adapter computes them
    Bytes []int64  // per key, for Put

}
type PutOptions struct {
    Replicas  int        // copies the store keeps; 0 means the store's own default
    Preferred []Location // where the caller asks the store to place them, in order; empty for none
}
type Answer struct {
    Found  []bool          // per key: present (Exist, Get), accepted (Put, Remove), held (Pin, Unpin)
    Holder []Location      // per key, for Exist and Get: where the object is
    Moves  []plan.Transfer // every byte the store's client moves for this request, replicas included
    Ready  int64           // microseconds after the request until the caller may continue
}
type Store interface {
    Handle(now int64, caller Instance, r Request) (Answer, error)
    Advance(now int64) ([]plan.Transfer, error) // the store's own timed work up to now: leases, eviction, write-behind
    Next() int64                                // the time of its next own event; -1 when it has none
}

A store may hold an object pinned between a lookup and the read that follows, as LMCache does, so that no eviction falls between them; Pin and Unpin say so, and a trace shows each. A put carries the replica count and preferred placement the client sends, as the Mooncake store's does. The caller is a typed instance, never a free-text label (SUB-20). Each later addition to the contract keeps its zero value meaningful (SUB-1).

Private and shared stores. A store's settings say whether it serves one engine instance, as LMCache's local CPU and disk backends do, or several, as the Mooncake store's master and LMCache's remote and peer backends do. A private store is part of its engine's component: inference-sim builds it and passes it in the engine's Spec, and the engine calls it directly. A shared store is a component of its own (§8.1). Its behaviour comes from blis-kvstore, and inference-sim only couples it into the model. An engine sends a shared store each Request as a message and receives the Answer as a message, Ready microseconds later (DEV-1). Where the upstream's call blocks, the engine waits for the answer; where it does not, the engine goes on. Each engine declares which for each call site (DEV-3). At a blocking site, such as the Mooncake store's exist call while the scheduler counts the tokens it can load, the port splits its transition there: it sends the request, ends the transition, and resumes from that point on the answer. Because Ready may be zero, the engine and the store form a zero-time cycle; its declared bound is one round trip per blocking call site per step (DEV-5). Requests that reach a store at one instant are handled in the order of the message key (§8.2), never in the order the simulator happened to run the senders. A store's own timed work, such as a lease that expires, is its internal event, and its time advance is Next.

Moves. Every byte a request moves is in its Answer, and the engine that sent it states each one as a move (§6.1). Bytes the store moves on its own, such as the Mooncake store copying an object to storage, or LMCache writing to a remote backend after the request has returned, come from Advance. inference-sim prices them through the cost model against a plan that names only the chip and fabric of the nodes at each end, and shares their links like any other transfer (SIM-13).

Settings. A setting that the engine process reads, such as vLLM's kv_connector_extra_config or LMCache's environment variables and configuration file, stays in the engine block, where the upstream reads it (X1). A store service that runs as its own process, such as the Mooncake store's master, is configured in the scenario's stores block, one entry per service, in the service's own flag names. The store package's field list classifies both kinds (KVS-7).
