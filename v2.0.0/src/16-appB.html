BGlossary

Each term is defined once, here, and used in one sense throughout.
AgentAn AI coding agent that does one scoped task in a branch (§13.7).
Agent guidanceA rule an agent follows on every change it writes or reviews, rendered into each repository’s AGENTS.md (§4.2, §13.2).
AnchorA ledger unit with the role anchor: the units on which the dashboard reports public accuracy. Only anchor units are scored for publication (§10.2, COV-2).
Batch meansA way to estimate the uncertainty of a steady-state figure from one long run: cut it, after warm-up, into equal consecutive batches, and treat each batch's mean as one observation (§8.8).
Blocker backlogThe ranked list, per engine, of everything that lowers coverage or grade: refused surface items, not-modelled fields, coefficients below rank 1 and unpriced execution modes. Each entry shows how many points it blocks or demotes (§11.6).
Byte gateA fixed set of scenarios whose output must stay byte-identical across a refactor.
Candidate jobThe half of a scoring run that runs the candidate's code, with no seed and no network, and writes one prediction per unit (§10.2).
Coefficient registryThe substrate’s fitted and assumed coefficients, each with its provenance, in substrate/registry/ and read with --registry (§3.3, §9). Distinct from the invariant registry and the metric registry (§1).
Commit distanceHow far a run’s engine commit is from the modelled one, counted from their merge base: commits apart, and releases apart where the two commits are in different releases (§11.5). A run on the modelled commit has distance zero.
Common random numbersUsing the same random streams in two runs that are being compared, so their difference reflects the configuration, not chance (§8.4).
ComponentA part of the BLIS code with one owner: a directory of inference-sim, or a separate repository. Table 1 (§2.2) lists them and says what each may import. Not to be confused with a model component.
Confluent transitionA component's change of state when its own event and a message fall at the same instant (§8.1).
Conformance suiteA test suite in contracts/conformance that any implementation of a contract must pass.
Content hashThe SHA-256 of a sorted list of every data file's own SHA-256 and relative path (§3.3). Equal hashes identify equal data.
Cost modelThe code in substrate/kernel/ that prices a step from the plan, the step shape, the catalog and the coefficient registry.
CUDA graphA recorded sequence of GPU launches that replays quickly but only for fixed batch shapes, so engines pad a batch up to the next recorded shape.
DCODeveloper Certificate of Origin: a Signed-off-by line by which the person who takes responsibility for a commit certifies it. Encouraged, not checked (X20).
DeploymentA serving configuration, as a scenario's deployment document states it (SUB-19). For InferenceX, one role key covers one deployment under one benchmark type (§10.2): one model on one chip, at one precision, under one framework and configuration hash.
DEVSThe Discrete Event System Specification, Bernard Zeigler's formalism for discrete-event models, whose terms §8 uses.
Distribution distanceHow far BLIS's predicted latency distribution is from the measured one, beyond the mean. The landing gate uses the largest absolute relative error across the p50, p90 and p99 of time to first token and of time per output token. The coefficient registry's fitting principles define it exactly.
DrafterWhat proposes speculative tokens for a target model: the model's own in-graph speculator, such as its MTP layers, or a separate drafter checkpoint with its own catalog entry, such as an EAGLE3, DSpark or DFlash model. It is distinct from vLLM's draft_model method, which is one way of running a separate checkpoint (D8).
Engine block, router blockThe parts of a scenario that hold the engine's own configuration and llm-d's own configuration, copied verbatim from what the upstream accepts.
Engine kindWhich engine a scenario uses: vllm or sglang.
Engine moduleA directory under engines/ that ports one upstream engine at one commit: its scheduler, KV-cache management, defaults and lowering, with its oracle and its Upstream record (§5.2, LIF-5).
Engine upgradePorting the diff of the code an engine module already models (scheduler, KV-cache manager, connectors, defaults, lowering) from one upstream commit to another. It changes behaviour for every model (§12.4).
EnvironmentThe interface through which an engine asks the substrate for model graphs, chip facts, memory sizes and prices (§6.3).
Exactly pinned, experimentalA run is exactly pinned when the simulator is an inference-sim release tag or a full commit, its stack.json names the router fork commit and each engine’s modelled commit, its catalog and coefficient registry hashes equal the embedded hashes of that commit, and it uses no overlay and no uncommitted change. Any other run is experimental. Only exactly pinned results are published.
Experimental frameThe recorded description of what a run measures: its input generator, initial state, phases (warm-up, measured window, drain), stop rule, acceptance conditions and metric definitions (§8.6).
Extrapolated, unidentifiedFlags on a lookup or coefficient. Extrapolated: used outside the range of inputs its fit covered. Unidentified: its fit data do not determine its value. Both lower its rank for VAL-3 (§9.3, VAL-10).
FateHow a request ended: completed, dropped with a reason, timed out, in flight or queued at the horizon, or not started. Written once per request (DEV-9).
Field listThe generated list (fields.json) of every configuration field and environment variable an upstream commit reads, each with a BLIS status (VLM-3).
FLOPsFloating-point operations.
FunnelThe count of units at each stage from a source to scored, reported for each scored source (§11.6).
Gate job, select job, error jobThree of the seed-holding jobs. The gate job and the select job score candidates on held and select units respectively; the error job measures each method's error on validate units. Each runs in blis-substrate for operator-level work and in accuracy-dashboard for whole-run work. All three return only aggregate results (§10.2, §13.5).
GEMMGeneral matrix multiply.
GradeG1 to G5: how closely BLIS reproduces a dashboard point, judged by its engine commit, its configuration and the methods of the coefficients that price it (§11.3).
Graph handler, graph vocabularyA graph handler is catalog code that builds one model family’s graph from its config.json. The graph vocabulary is the set of node kinds a graph may use (SUB-15).
HeadlineThe dashboard’s published accuracy figure, computed from anchor units only (§11).
HeldA ledger unit with the role held: used only to judge an accuracy change at its landing gate, in the gate job, never listed publicly (§10.2, VAL-6).
Held-out unitA ledger unit whose role is held or anchor. Accuracy is reported only on held-out units (D9); every other unit is training data.
HiSparseHierarchical sparse attention for sparse-MLA models, in vLLM and SGLang. Host memory holds each request's whole KV cache; GPU memory holds the pages the sparse indexer selects, plus the newest tokens. In vLLM it is a connector, a coordinator and three KV-cache managers (source, hot and resident).
HMACA keyed hash. Without the key (here, the seed) the output cannot be predicted.
Holm correctionA way to test many lanes at once while keeping the chance of any false failure at the stated level (VAL-6).
HorizonThe simulated time at which a run stops, if its stop rule names one (§8.6).
Hosting contractThe interface between the simulator and the router fork’s embedded router: clock, runtime, sessions and KV events. The router fork owns it, with its conformance suite, so the fork depends on no BLIS module (RTR-3, §5.3).
In-flight depthThe most engine steps that run at once, PoolPlan.InFlight: 1 without asynchronous or overlap scheduling (SIM-7).
Inert, unprovenA temporary field status allowed only by a release plan: a field believed to have no effect, whose proof is still to come.
Internal event, external eventA component's change of state at a time it scheduled for itself (internal), or on a message from another component (external) (§8.1).
Invariant registryThe records of every invariant in this document: statement, checks and status, in substrate/contracts/invariants/ (§13.1). Each repository’s AGENTS.md section is generated from it.
ISL, OSLInput and output length of a request, in tokens.
Kernel hashCodeHash: the hash that identifies a kernel implementation, of its source and target GPU architecture, or of a binary library (§6.2).
Kernel implementationThe library, variant and kernel hash (CodeHash) that execute one primitive. The coefficient registry looks coefficients up by it.
Known-bad inputAn input that a check must reject. Each check in the invariant registry names one (X18).
KV cacheThe stored attention keys and values of each request. A KV connector moves it between machines; KV tiering moves it between GPU memory, host memory and storage.
KV-cache manager, KV-cache specIn vLLM, the code that decides which blocks a request's KV cache holds, which prefix blocks it shares and which blocks are evicted. At start-up the model's layers are grouped, and each group has a KV-cache spec, such as full attention, sliding window or Mamba state. KVCacheSpecRegistry maps each spec type, or a group's role, to a manager; one manager may serve several spec types. A coordinator runs one manager per group (§7.1).
Landing gateThe accuracy check a coefficient or pricing change must pass to merge (VAL-6).
LaneA group of results judged apart. For a coefficient it is the kernel implementation the coefficient is fitted on, and the landing gate judges each lane (VAL-6). The dashboard reports in the same way for points that share an engine, modelled commit, chip, model and layout.
LayoutHow a model is split across GPUs: the tensor, pipeline, data, expert and context parallel widths, and where each rank is placed.
LedgerThe committed list of every measured unit from every data source, with the rule that gives each unit a role (substrate/catalog/ledger/, §10).
llm-d stackllm-d's router in front of vLLM or SGLang engines, as llm-d's published guides deploy it.
LoweringTurning a model’s architecture into the concrete operations one engine runs on one layout: which attention backend, which fused operations, which data types, which page size, how it shards and pads. It lives only in engine modules (SUB-15, §6.1).
Maintainer practiceA rule about process (review, approval, merge, issue handling, pull-request text, release notes, signing) that a maintainer with write access keeps with standard git and GitHub mechanisms such as branch protection, required reviews and signed commits. It is written as “Maintainer practice:” and has no check (§4.2).
ManifestThe list of everything the oracle replaces.
Memory poolIn SGLang, a store of KV cache or recurrent state in GPU memory, or, for HiCache, in host memory. A separate allocator hands out its slots or pages. Each attention layout (full attention in its MHA and MLA forms, sliding window, Mamba, hybrid, sparse) has its own pool type (§7.1).
Message classOne of a fixed order of message kinds, used with time, sender and the sender's send count to order messages at one instant (§8.2)
Metric registryThe list in contracts/ of every metric's definition: formula, statistic, population, window and unit (§8.7, DEV-8).
MLAMulti-head latent attention: attention that stores a compressed latent instead of full keys and values.
Model backportUpstream commits that add one model, applied onto the modelled commit and listed in the Upstream record. It carries model code only, never scheduler, KV-cache or connector changes, and is dropped when the modelled commit contains it (§12.5).
Model componentA part of the simulated system with its own state, changed only by its own internal events and by messages from other model components: an engine instance, the router, a link, or a client (one source in the workload generator) (§8.1). This is the DEVS sense, and differs from a component of Table 1.
Model supportWork in an engine module for one model, needed only when the model brings engine-facing code that an engine upgrade does not port, such as a new KV-cache layout, its own kernels or a new drafting method (§12.5).
Modelled commitThe upstream commit an engine module models. A build runs one modelled commit of each engine (LIF-5, LIF-6).
MoEMixture of experts.
MooncakeA KV transfer and storage system, used by vLLM connectors and as SGLang’s default P/D transfer backend.
MSER-5A warm-up rule: batch the output series in fives and cut where the variance of the remaining mean is smallest (§8.8).
MTPMulti-token prediction: a speculative-decoding method where extra model layers draft the next few tokens.
Named substitutionA value that no record of the run holds, stated on the point with the value used and its source. It lowers the grade. An estimated substitution is a named substitution whose value comes from a stated rule and not from a record (D10).
NIXLNVIDIA's library for moving KV caches between machines. vLLM's NixlConnector, the P/D connector llm-d's guides use most, is built on it.
Not blindA held-side figure from a unit whose label predates the ledger, so that the unit may have influenced earlier choices. The gate reports each such unit as a separate figure for as long as such units are used (§10.2).
Offered loadRequests arriving per second, set by the workload rather than by the system's response.
Onboarding a modelOne to three pieces of work, after any engine upgrade the model needs: a catalog entry, always; model support, when needed; and coefficients, only for a new primitive family (§12.1).
OracleThe harness that runs the upstream's own code with its environment replaced, and records its decisions.
Output functionWhat a component sends, evaluated just before an internal or confluent transition (§8.1).
OverlayA directory given with --catalog-overlay or --registry-overlay. Each entry replaces the entry with the same identity in the data in use, or is added if none exists (§3.3).
P/DPrefill/decode disaggregation: one pool of engines processes prompts (prefill), another generates tokens (decode), and the KV cache moves between them.
Paired bootstrapA way to put an interval on the difference between a candidate's error and the base's error on the same units, by resampling the units and recomputing the difference. The landing gate fails a lane only when the whole interval lies above zero (VAL-6).
Parallel DEVSThe form of DEVS in which all outputs at an instant are collected before any component changes state (§8.2).
Partition versionA numbered version of the ledger's role assignment. A new version is needed to change any existing unit's role.
Perturbation testA test that changes one field and checks that some price, decision, or field of the emitted plan or step shape changes (SUB-11, VLM-3).
Pin, re-pinTo require an exact commit or release of another module in go.mod; to update that requirement.
PointOne InferenceX unit as the dashboard grades it, G1 to G5 (§11.3): one benchmark run of one deployment and recipe fingerprint at one concurrency.
PoolA group of engine instances that share one configuration and layout, such as the prefill pool or the decode pool in P/D. Each pool has one PoolPlan.
PoolPlan, StepShape, TransferThe three objects an engine hands the cost model: a plan per engine pool, the shape of each step, and one transfer per KV move (§6.1, §6.2).
Pre-registrationThe file of an accuracy change, committed before any held-out data is read, that states what the change will be judged on (§12.3).
Price-change reportA report, generated for every release and every pull request that can change prices, of each benchmark scenario’s step prices before and after the change (§13.3).
PrimitiveOne kind of work the cost model prices: an attention step, a matrix multiply, a collective, a memory transfer.
Primitive familyThe coefficients that price one kind of primitive, such as dense GEMM, decode attention or all-reduce (VAL-2).
Profile likelihoodA way to find a fitted coefficient's interval by refitting the others at each candidate value (VAL-10).
Progress watchdogA check that fails a run when no request changes state for a set number of engine steps while work is waiting (SIM-7).
Quarantine listThe list of tests that fail on the main branch, each with an owning issue and an expiry date; listed tests do not block merges until they expire (X25).
Radix cache, tree cache, tree coreSGLang's prefix cache: a tree of token sequences whose nodes hold KV cache, so that requests sharing a prefix reuse it. A tree cache is any implementation of SGLang's tree-cache interface; the default is the unified radix cache, and others can be registered. A tree core is the tree's own data structure inside the unified radix cache, implemented in Python and in Rust (§7.1).
RatchetA count that CI allows to fall but never to rise.
Recorded traceThe oracle's output for one scenario at one upstream commit, reviewed and committed. The commit marker golden-reviewed: keeps an older name for the same thing.
Release branchA branch release-vX.Y of inference-sim, cut when an engine module moves to a new upstream commit, and kept for fixes to the commit the last release ran (§14.4).
ReplicationOne run of a scenario with its own scenario seed. Several replications give a confidence interval (§8.8).
ResultThe structured output of one run, written as JSON, including everything the run used (§3.3).
Review questionA yes/no question, attached to a rule, that the review agent applies to a pull request and answers in a review comment with the files and lines that support the answer (§13.2). It is guidance and never a check: it fails no CI job.
Review setThe pull requests that make up one change: one in inference-sim, and one in the router fork when the hosting contract changes (§12.8).
Role keyThe fields of a data unit that decide its role, so near-copies of one measurement share a role (§10.2).
RooflineAn estimate of a primitive's time as the larger of its compute time at peak FLOPs and its memory time at peak bandwidth.
Router tableThe substrate’s map from a router a run used to the nearest policy llm-d’s router offers (§11).
Runtime interface (seams)The points where the router fork reads time, starts work, draws random numbers or makes calls, so BLIS can supply simulated versions.
ScenarioThe YAML file a user gives BLIS: the engine and router configuration, the cluster, the workload and the seed.
Scoring harnessThe accuracy dashboard's tool that turns measured benchmark runs into scenarios, runs a given simulator build, and compares. The only end-to-end scorer (§11.7).
Seed-holding jobOne of the four kinds of CI job that hold the role seed: the release job, the select job, the error job and the gate job. They run only code from main, never a pull request's code. Only these can compute select, validate and held roles (§10.2).
Selected-version lintA check that reads the versions Go actually chose for a build (go list -m all), not the versions written in go.mod.
Simulated runtimeThe router fork's runtime when BLIS hosts it: clock, timers, randomness and goroutines driven by simulated time (§7.3).
SliceThe points that share an attribute value, such as one chip. Below min_points no aggregate is shown (COV-13).
stack.jsonThe record, published with each inference-sim release, of its own commit, the router fork’s commit, the upstream commit each engine module models, its Go toolchain version and its llm-d guides commit (SIM-3).
SubstrateThe engine-independent foundation: the substrate/ directory of inference-sim (§3).
Surface listThe generated list of every feature an upstream commit offers, each with a BLIS status.
Terminating run, steady-state runA run that ends by its stop rule (terminating), or one that measures a system after it has settled (steady-state) (§8.8).
Time advanceHow long until a component's next internal event, given its state (§8.1).
Token recordThe per-request counts an engine emits: prompt tokens, tokens served from local and external caches, tokens computed and tokens emitted (SIM-12).
TP, DP, EPTensor, data and expert parallelism.
Training dataEvery unit whose role is fit, select or validate, and all data from sources with no held-out role (§10.2).
TriggerAn outside event that starts BLIS work, such as a new upstream release or a new model (§12).
TRT-LLMNVIDIA’s TensorRT-LLM serving engine. A new engine of this kind meets the same bar as vLLM and SGLang, with its C++ code checked through bindings (§7).
Unit, roleA unit is the smallest piece of data the ledger tracks. Its role says what it may be used for.
Upgrade reportThe report an engine upgrade generates: the surface diff, the field demand, the source diff and, for each model the new commit supports, whether the catalog has it, whether it needs model support and which coefficients it lacks (§12.4).
UpstreamThe project BLIS reproduces: vLLM, SGLang or llm-d.
Upstream recordThe Upstream value in an engine module’s provenance.go: the upstream commit the module models, the release that commit descends from, and any listed model backport (LIF-5).
Validity domainThe range of models, chips, layouts, concurrencies, sequence lengths and replica counts that held-out data cover (§8.9).
Verification, validationChecking that the simulator does what its model says (verification), and checking that the model matches the real system (validation) (§8.9).
Warm-upThe stretch at the start of a steady-state run that is discarded because the system has not settled (§8.8).
Workload identityThe key under which a workload-dependent quantity, such as speculative acceptance or expert routing balance, is stored (D8).
