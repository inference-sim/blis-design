What an engine pin guarantees

An engine release, like any software, can ship with a bug or a gap that is found later. That is expected: the fix is a later commit on the same branch, and the next inference-sim release pins it the same way as any other.

When an inference-sim release pins a commit of blis-vllm or blis-sglang, that commit:

  • models the upstream release its Upstream record names, at the commit that record names, and no other release;
  • passed that release's oracle tiers, its field list and surface list checks, and every ci invariant (LIF-3);
  • differs from the commit the previous release pinned, on the same upstream release, only by BLIS-side changes: bug fixes, newly modelled features or plugins, contract or substrate updates. They may change prices or decisions. The inference-sim release notes list the pull requests merged between the two commits, say whether prices or decisions changed, and include the price-change report (§13.3);
  • holds only files ported from that upstream release or original to BLIS. Nothing is kept for an older release.

An engine module has no version number of its own. Its identity is its Upstream record and its commit. The pseudo-version Go derives for a commit only orders commits; its numbers come from an older tag and say nothing about the release modelled. Only inference-sim imports an engine module, and it pins the exact commit (LIF-2). If an upstream reaches v2, the module path gains /v2, as Go requires.

Upstream versions

Release candidates (vLLM's v0.33.0rc0, SGLang's v0.5.3rc0) are not modelled; an engine module models final releases only. A post release (SGLang's v0.5.6.post1) or a four-part version (vLLM's v0.10.1.1) is named in the Upstream record and in engine.version exactly as upstream writes it; no tag has to encode it.

A detail of Go's version ordering

To Go, -blis.N is a pre-release suffix. So v0.32.0-blis.1 sorts before v0.32.0. Among suffixed tags, v0.32.0-blis.2 sorts before v0.32.0-blis.10, and both sort before v0.32.1-blis.1. go get …@latest also prefers any plain release over every pre-release. This is Go's own ordering (golang.org/x/mod/semver) and the behaviour of go get.

Three rules follow:

  • Engine modules and the router fork never tag a plain v<upstream>; an optional tag always has a -blis.N suffix, with N from 1. The pseudo-version of a commit sorts after every tag that is its ancestor, so a pin to a new commit outranks the tags made before this rule.
  • Pins name exact commits. The release bot never resolves @latest, and a lint checks the version each build actually selects, not the text of go.mod (LIF-2).
  • A plain tag made before this rule stays, because tags are never moved or deleted (LIF-1). It makes @latest wrong for that module, and a module that requires it outranks every -blis.N tag and the pseudo-versions after them in version selection. A retract line does not fix this: retractions never change version selection, and Go reads them only from the latest release version, which is the plain tag itself. An exclude line in inference-sim's go.mod does, because Go applies the main module's excludes to the whole build (X11).

14.2 Lifecycle invariants

  • LIF-1 A tag names one commit forever, and a pinned commit stays on its branch forever. Tags are never moved or deleted; a mistake gets a new tag. A main or release branch that an inference-sim release pins is never rewritten.Checked by: the release bot, which confirms at each release that the tag is an annotated tag on the checked commit and that every pinned commit is on its branch. Maintainer practice (§4.2): a tag rule on v* in inference-sim blocks updating and deleting a tag, and branch protection blocks force-pushes to main and release branches in every repository.
  • LIF-2 In every build, each BLIS module resolves to the exact commit the release records in stack.json, and the router fork resolves to the commit stack.json records through inference-sim's one replace directive (X11). inference-sim's own substrate requirement equals the version its build selects, so no engine or router release can change the simulator's data. One Go toolchain version is named in contracts/toolchain, at the substrate version inference-sim selects. No module BLIS writes declares a go version above it. Every CI job sets GOTOOLCHAIN=local and installs exactly that version, so no build downloads a toolchain. The router fork's go line follows upstream llm-d; when upstream raises it, the release bot raises the toolchain file first, in the same review set. Documented version strings are generated (X23).Checked by: selected-version lint (go list -m all), which for the router reads the replace target that go list -m -json reports, not the placeholder version on the require line; a check that every module in go list -m -json all declares a GoVersion no higher than contracts/toolchain; a CI step that fails if go version differs from it; the pre-release test of every engine and router package against the simulator's selected versions (§3.2).
  • LIF-3 Only the release bot cuts releases. The one required release is inference-sim's, cut from a commit where every ci invariant passed, with every pin on a commit where the pinned repository's ci invariants passed. If the bot is unavailable, a person with write access to inference-sim may follow the documented manual procedure (§13.6); a manual tag is an annotated tag on the checked commit, recorded in the release notes.Checked by: the bot’s own check of every ci invariant at each commit it releases or pins; a nightly check, in inference-sim, that every tag made by a person is annotated and listed in its release notes. Maintainer practice (§4.2): inference-sim’s settings let only the release bot and people with write access create tags.
  • LIF-4 Release notes are generated (§13.3). For each repository the release pins, they list the pull requests merged between the commit the previous release pinned and the commit this one pins.Checked by: the release bot, which writes the notes from the release's changes.
  • LIF-5 An engine module, or the router fork, models one upstream release. A tag is optional. If one is made, it is v<upstream>-blis.N, v<upstream>-post.K.blis.N for a post release, or v<upstream>-rev.W.blis.N for a four-part version, with N from 1, and no plain upstream tag is made; every tag stays (LIF-1). In an engine module, the Upstream record names that release and commit, every ported file names that same release, and no code for another release remains. An adapter file derived from a package the oracle's lock pins also names that package's version (VLM-2). Release candidates are not modelled. The package that runs the modelled release depends on no package that exists only for another release.Checked by: a test that lists the dependencies of the engine's entry package with go list -deps and fails on any package kept for another release; a nightly tag check in the repository (format, N one above the previous tag on the same upstream release, no plain tag); in engine modules, the provenance test, which refuses a ported file that names another release.
  • LIF-6 Each inference-sim release runs exactly one upstream release of each engine, of llm-d and of each KV store blis-kvstore models, and lists them in stack.json. A scenario whose engine.version names a different upstream release is refused, with a message naming the release it asked for, the one this build runs, and the newest inference-sim release that runs the one it asked for, or says that none does. The llm-d release is not stated by scenarios; it is the one stack.json lists.Checked by: a refusal test per engine kind; a check that the message's release names match stack.json history.
  • LIF-7 A deprecated feature is removed by the first inference-sim release after its deprecation that may break compatibility: a MAJOR release, or a MINOR release while inference-sim is at v0. A repository below inference-sim, which has no releases of its own, removes it in the commit that release pins; an engine module also removes deprecated code when main moves to a new upstream release. Removal takes with it every code path, flag, field, test and document that existed only for that feature. Each deprecation is recorded where the feature is defined (a command's or flag's deprecation notice, or a // Deprecated: comment) with the release that deprecated it. Nothing in this design depends on a deprecated feature, and no repository keeps code that none of the binaries BLIS ships can reach.Checked by: the release bot, which refuses a MAJOR inference-sim release, or a MINOR one at v0, that still contains, in inference-sim or in a commit it pins, a feature deprecated in an earlier release; a whole-program dead-code check (Go's deadcode), run in stack CI's workspace from the main packages of every binary BLIS ships, with test files not counted as reaching code. Upstream files in the router fork, and the interfaces in contracts/, are exempt.

14.3 blis-sglang

blis-sglang does for SGLang what blis-vllm does for vLLM. It models one SGLang release, pinned by tag and commit. The pin must be exact, because SGLang's main moves fast and often rewrites core components, such as the allocator, between releases. Its first release and stages are in the release plan.

14.4 Release branches

Each upstream-tracking repository has a main branch (llm-d-r in the router fork) that models the newest upstream release BLIS supports. When BLIS moves to a new upstream release, two branches are cut:

  • in the upstream-tracking repository, release-<upstream>, for example release-0.32.0, from the last commit that modelled the old release;
  • in inference-sim, release-vX.Y, from its last release that ran the old upstream release.

A fix needed on the old release is made first on the main branch if the main branch needs it too, then cherry-picked to the release branch; otherwise it is made on the release branch alone. The fix is shipped by a PATCH release from inference-sim's release branch, which pins the fix's commit on the engine's release branch. A commit on a release branch alone reaches no user, because every inference-sim release pins exact commits.

Only the inference-sim release before the newest one is supported this way. Both release branches close when inference-sim next moves an engine or llm-d to a new upstream release.
