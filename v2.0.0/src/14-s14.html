14Versions and releases

This design has its own version number. The rule for numbering and tagging it is in the README of blis-design, and is stated nowhere else. This section is about the versions of the code the design describes.

14.1 Version schemes

An engine module models one upstream commit: a release tag, or any commit on the upstream’s main or a release branch (LIF-5). inference-sim is the one tagged release. Every other repository is pinned by commit.

Only inference-sim has release versions; everything else is identified by a commit.

What a release guarantees about an engine module

An upstream commit, like any software, can ship with a bug or a gap found later. The fix is a later commit on the same branch, and a later release contains it like any other change.

A release of inference-sim, for each engine module:

  • models the upstream commit its Upstream record names, and no other;
  • passed that commit’s oracle tiers, its field list and surface list checks, and every invariant whose registry status is ci (§13.1);
  • differs from the previous release that models the same commit only by BLIS-side changes: bug fixes, newly modelled features, contract or substrate updates. They may change prices or decisions. The release notes list the pull requests merged between the two releases, say whether prices or decisions changed, and include the price-change report (§13.3);
  • holds only files ported from that commit or original to BLIS.

The pseudo-version Go derives for a router fork commit only orders commits; its numbers come from an older tag and say nothing about the llm-d release modelled. If an upstream reaches v2, the module path gains /v2, as Go requires.

A detail of Go’s version ordering

To Go, -blis.N is a pre-release suffix. So vA.B.C-blis.1 sorts before vA.B.C, and go get …@latest prefers any plain release over every pre-release. This is Go’s own ordering (golang.org/x/mod/semver). Three rules follow for the router fork:

  • It never tags a plain v<upstream>; an optional tag always has a -blis.N suffix, with N from 1.
  • Pins name exact commits. A lint checks the version each build actually selects, not the text of go.mod (LIF-2).
  • A plain tag made earlier stays, because tags are never moved or deleted (LIF-1). It makes @latest wrong for that module. A retract line does not fix this, because Go reads retractions only from the latest release version, which is that tag. An exclude line in inference-sim’s go.mod does, because Go applies the main module’s excludes to the whole build (X11).

14.2 Lifecycle invariants

  • LIF-1 A tag names one commit forever, and a pinned commit stays on its branch forever. Tags are never moved or deleted; a mistake gets a new tag. A main or release branch that a release pins is never rewritten.Maintainer practice (§4.2): a tag rule on v* in inference-sim blocks updating and deleting a tag, and branch protection blocks force-pushes to main and release branches in every repository.
  • LIF-2 In every build, the router fork resolves to the commit stack.json records, through inference-sim’s one replace directive (X11). One Go toolchain version is named in substrate/contracts/toolchain. No module BLIS writes declares a go version above it. Every CI job sets GOTOOLCHAIN=local and installs exactly that version, so no build downloads a toolchain. The router fork’s go line follows upstream llm-d; when upstream raises it, a maintainer raises the toolchain file first, in the same change. Documented version strings are generated (X23).Checked by: selected-version lint (go list -m all), which for the router reads the replace target that go list -m -json reports, not the placeholder version on the require line; a check that every module in go list -m -json all declares a GoVersion no higher than contracts/toolchain; a CI step that fails if go version differs from it; a test of every engine and router package against the versions the simulator selects.
  • LIF-3 A maintainer with write access cuts each inference-sim release, from a commit where every required check passed, with an annotated tag on that commit. The release notes list the pull requests merged since the previous release and the price-change report, and name the upstream commit each engine module models (SIM-3).Maintainer practice (§4.2): inference-sim’s settings let only people with write access create tags; branch protection requires the checks before a merge; the maintainer writes the notes from the generated list and report (§13.6).
  • LIF-5 An engine module models one upstream commit. Its Upstream record names that commit and the release it descends from, every ported file names that same commit, and no code for another commit remains except a model backport the record lists (VLM-2). An adapter file derived from a package the oracle’s lock pins also names that package’s version. The package that runs the modelled commit depends on no package that exists only for another commit.Checked by: a test that lists the dependencies of the engine’s entry package with go list -deps and fails on any package kept for another commit; the provenance lint, which refuses a ported file that names another commit; the oracle tiers, which run the modelled commit (§7.4).
  • LIF-6 Each inference-sim release runs exactly one upstream commit of each engine and one llm-d release, and lists them in stack.json. engine.version is a full commit hash, or a release tag that the Upstream record lists as an alias of its commit. A scenario whose engine.version names a different commit is refused, with a message naming the commit it asked for, the aliases the Upstream record lists, the one this build runs, and the newest release that runs the one it asked for, or saying that none does. The llm-d release is not stated by scenarios; it is the one stack.json lists.Checked by: a refusal test per engine kind; a check that the message’s commit names match stack.json history.
  • LIF-7 A deprecated feature is removed by the first release after its deprecation that may break compatibility: a MAJOR release, or a MINOR release while inference-sim is at v0. An engine module also removes deprecated code when it moves to a new upstream commit. Removal takes with it every code path, flag, field, test and document that existed only for that feature. Each deprecation is recorded where the feature is defined (a command’s or flag’s deprecation notice, or a // Deprecated: comment) with the release that deprecated it. Nothing in this design depends on a deprecated feature, and no directory keeps code that none of the binaries BLIS ships can reach.Checked by: a whole-program dead-code check (Go’s deadcode) from the main packages of every binary BLIS ships, with test files not counted as reaching code; upstream files in the router fork, and the interfaces in contracts/, are exempt. Maintainer practice (§4.2): the maintainer cutting a MAJOR release, or a MINOR one at v0, reads the deprecation notices and removes the features they name.

14.3 The SGLang engine module

engines/sglang does for SGLang what engines/vllm does for vLLM. It models one SGLang commit, which stack.json records. The commit is exact, because SGLang’s main moves fast and often rewrites core components, such as the allocator, between releases.

The module’s surface list records each setting, its default and the behaviour it selects at the modelled commit, and the upgrade report regenerates it (§7.5, §12.4). This design states no setting or default of one commit. A run’s resolved defaults are compared with the modelled commit’s (SGL-3).

It does not port SGLang’s own router. In the llm-d stack, llm-d is the router.

14.4 Release branches

inference-sim has a main branch, which models the newest upstream commit of each engine BLIS supports, and release branches release-vX.Y. When an engine module moves to a new upstream commit, inference-sim cuts release-vX.Y from its last release that ran the old commit.

A fix needed on the old commit is made first on the main branch if the main branch needs it too, then cherry-picked to the release branch; otherwise it is made on the release branch alone. A PATCH release from the release branch ships it. Only the release before the newest is supported this way. The release branch closes when inference-sim next moves an engine or llm-d to a new upstream commit.

The router fork keeps a branch release-<llm-d release> for the same purpose, cut from the last commit that modelled the old llm-d release, and the release branch of inference-sim pins it.
