8Simulation method

BLIS is a discrete-event simulator. Its clock is virtual time: it jumps from one event, such as a request arriving or a step ending, to the next, and never follows the wall clock. Between events, state either stays fixed or changes at a known constant rate. This section states the rules a run follows, whatever engine it runs: which part of the system may change state and when, how events at one instant are ordered, how random numbers are drawn, which part of a run is measured, how results are analysed, and how the model is verified and validated. It takes its terms from Parallel DEVS, the Discrete Event System Specification of Bernard Zeigler. The table gives each term and its meaning in BLIS.

8.1 Model components and how they couple

Each model component changes its state only through its three transitions, and sends messages only through its output function. The output function runs on the state just before an internal or confluent transition, and every message it sends carries that instant’s time. An external transition sends nothing. A model component that must answer at once, as the router answers a request, schedules an internal event with a time advance of zero and sends its answer in the next round of the same instant (§8.2).

A link is the one model component whose state changes between events. Its state is the set of transfers in progress and the bytes each has left, and its time advance is the earliest time a transfer finishes under the current sharing. Every start or end of a transfer, and every step that starts or ends a cross-domain collective, is an event that recomputes the rate of every other transfer on the link.

Model components interact only through messages, and none reads another’s state. The router learns about an engine only through the metrics and KV events the engine sends, at the times it sends them, after the delay the deployment’s scrape and event-delivery settings impose. So each model component can be tested alone and then together.

Within a model component, nothing depends on goroutine scheduling, the system clock or the order of iteration over a map. Concurrency inside a model component, such as the router’s background work, runs on the simulated runtime, which serialises it (RTR-7).

8.2 One instant

Many events fall at one simulated instant, for example a step ending as a metrics scrape is due. An instant is a sequence of rounds. BLIS processes each round as Parallel DEVS defines an instant, in three phases:

  1. Every model component whose internal event falls at this instant runs its output function.
  2. Each model component receives the bag of every message addressed to it at this instant. BLIS sorts the bag by the key below, so a transition that reads it in order is deterministic.
  3. Each model component then makes exactly one transition: confluent if it had both an internal event and messages, internal if only the first, external if only the second.

So no model component sees another’s state change from the same round before making its own. A message produced in round r is delivered in round r+1 at the same time, and a model component whose transition leaves a time advance of zero is imminent in round r+1. The instant ends when a round has no imminent model component and no message. The router’s zero-time answer to a request is thus delivered in the round after the request, and is not reordered against messages of the earlier round. A message is keyed (time, round, class, sender, the sender’s own count of messages sent). An internal event is keyed (time, round, class internal, the model component’s index, its count of internal events). A model component’s index is its position in the scenario’s declared order, never a map or hash order, so renaming an instance leaves the Result unchanged. The order of internal events at one instant has no effect, because all outputs are gathered before any transition. The class is a fixed order of message kinds, such as "transfer complete" before "new request". Each class’s position is stated with its reason, and a change to the order is a change to the model (§8.9). The key has no global counter, so it depends on what each sender has done, not on the order in which the simulator scheduled things. Two messages with the same key are a defect.

A model component’s confluent transition says what it does when its own event and a message coincide. For an engine it follows from where the upstream’s loop reads its input queue, not from a choice BLIS makes, except where that order is a race between threads. A request that arrives while a step runs waits until the engine next reads its input. Under vLLM’s asynchronous scheduling, on by default, the next batch is scheduled while the current one runs, so a request arriving during step N usually first joins step N+2. Without it, the request can join step N+1. Each engine declares, for each kind of external input, the step boundary at which it takes effect and whether it arrives during a step or as one ends (DEV-3). Where the upstream’s order is a race, the declaration says so and names the order BLIS uses.

A value one model component publishes for others, such as an engine’s metrics, carries its time and a publication sequence number, and a reader that caches it keys the cache on both.

8.3 Time and progress

Simulated time is an integer number of microseconds. A duration that the cost model prices or a link computes is converted to microseconds once, by one rule: round to the nearest microsecond, with a minimum of one microsecond for any positive duration, so that rounding never creates a zero-time cycle. A link keeps each transfer’s remaining bytes as integers and carries the rounding remainder to its next event, so that the bytes moved are conserved. Two events that rounding makes simultaneous are ordered by the key (§8.2). Arithmetic whose result reaches the order of events or the Result gives the same bits on every supported platform (X6).

The future event list is a priority queue of internal events, ordered by time and then by the key (§8.2). A model component changes its own next event only by recomputing its time advance after a transition. The event it no longer wants is marked stale by a generation number, and dropped when it reaches the front of the queue, so it cannot affect the result wherever it sits.

Simulated time must advance: only finitely many events may happen in any finite stretch of simulated time. Every cycle of model components that can pass messages in zero time contains a model component with a positive time advance, or a declared bound on the rounds it may take in one instant. An engine step that changes no state is an error unless the engine scheduled it as a wake-up, or it is an idle or dummy step the upstream runs, such as vLLM’s dummy batches on idle data-parallel ranks of a mixture-of-experts model, which the engine declares.

8.4 Random numbers and determinism

Every random draw comes from a substream named by model component, purpose and entity: for example, client 3, prompt length, request 17. The substream’s seed is the SHA-256 of the scenario seed and that name. Streams for different seeds are treated as independent. The generator’s name and version are part of the experimental frame, because a new generator changes every draw. So request 17 of client 3 gets the same prompt length whatever happened to requests 1 to 16, in every configuration.

A run is determined by its scenario, seed and build: the same three give the same Result on every supported platform, because nothing in a run reads the wall clock, goroutine order, map order or an unnamed random source (X6).

The named substreams give common random numbers: two runs that differ only in configuration give the same requests the same random inputs. Their outputs are then usually positively correlated, so the difference between them varies less from seed to seed and needs fewer runs to estimate. It is not free of noise. Some draws depend on how the system responds, for example a retry after a timeout, or a router’s tie-break. They use their own substreams and do not line up between configurations. Comparisons therefore still need replications and intervals (§8.8).

8.5 Input models

Every distribution the workload generator draws from names its family, its parameters, how they were estimated, and the trace they were estimated from, and is compared with held trace data by the two-sample Kolmogorov-Smirnov distance, which must not exceed a bound stated with the distribution (for example 0.02 at samples above 10,000). The Result’s frame report includes a quantile-quantile comparison. Any significance level used is Holm-corrected over the distributions tested. Where a dependence matters, it is modelled, not assumed away: output length against prompt length, the burstiness of arrivals, and the structure of sessions.

A trace records the causes of each arrival, not only its time: which session a request belongs to, and how long the client waited after the previous response. Replaying a trace under another configuration recomputes the arrivals that depend on earlier completions. A replay of fixed timestamps has no random input, so its reported values have no replication interval unless the trace is resampled.

8.6 The experimental frame

A run measures something only relative to its experimental frame. In BLIS the frame is one document, recorded in every Result:

  • the generator: the workload and its input models (§8.5), or a trace to replay, with its seeds;
  • the initial state: empty caches, or caches warmed by a stated rule;
  • the phases: warm-up, measured window and drain, each defined by a rule. The measured window is the stretch whose requests and tokens form every reported value. A request belongs to the window by its arrival time, and latency statistics are taken over those requests, including those that finish during the drain. Throughput counts tokens by their emission time within the window. The frame records both rules, and a source whose client uses another rule is simulated with its rule, which the point names;
  • the stop rule: a request count, a horizon (a simulated time at which the run stops), or both;
  • the acceptance conditions under which the run counts for this frame, such as achieved concurrency within a tolerance of the target, and few enough requests unfinished at the horizon;
  • the metric definitions (§8.7).

A run that fails its acceptance conditions produces no reported value. If any replication of a point fails, the point is not scored, and it is not scored on the replications that passed; the Result states how many failed. Running a scenario, exporting its trace and replaying the trace under the same configuration gives an identical Result. A converted workload keeps the properties named in DEV-7.

8.7 What a metric means

Every metric that is reported, compared, ranked or used in a service-level check has one definition, with an identifier, in the metric registry in substrate/contracts/ (DEV-8): its formula, its statistic (a mean or a percentile), its population (requests, tokens or steps), its window and its unit. It covers latency (time to first token, time per output token, inter-token latency, end-to-end latency, scheduling and queueing delay), throughput (per second, and for tokens also per accelerator), interactivity (output tokens per second per request), goodput and service-level attainment. Time to first token, time per output token and inter-token latency follow the benchmark clients BLIS is compared with: time per output token excludes the first token and is averaged per request, and inter-token latency is pooled over tokens. A definition is never inferred from a field’s name.

A reported value is a metric at a scope: the whole cluster, one pool, or one instance. The scope selects the population; the formula, statistic, window and unit are unchanged. A reported value that aggregates over scopes, such as the largest p99 time to first token over instances, names the scope and the aggregate. Two reported values are compared only when their metric, scope and aggregate are all the same (DEV-8), and a report or ranking states all three for every reported value it shows.

A request’s fate is how it ended: completed; dropped, with a reason; timed out; in flight at the horizon; queued at the horizon; or not started. It is written once, at one place in the code, and every latency sample is derived from it. A request that emitted no token gives no token-latency sample. The generator keeps its own count of arrivals, and conservation compares that count with the sum of fates, so a counting error in the fates cannot hide behind the same error elsewhere.

A request in flight or queued at the horizon has an unknown latency that is at least what it has waited. A latency statistic states how it treats such requests: excluded, with their count beside it, or counted at their waiting time so far as a lower bound. A percentile is not reported when more requests are unfinished than the percentile leaves room for.

A quantile is reported only when the sample is large enough for it, and with an interval from the order statistics (minimum sample, §11.8).

8.8 Output analysis

A simulation’s outputs are estimates, and are analysed as estimates. A run is either terminating, measuring a fixed amount of work such as a benchmark of a set number of prompts at a set concurrency, or steady-state, measuring a system that has settled.

  • A terminating run discards nothing at its start, unless the measured run did. Where it has random input, its estimate is the mean over several independent replications (runs with different scenario seeds), with a confidence interval from the spread between them. InferenceX benchmarks are terminating runs. Their frame copies the measured run’s start state, stop rule and requests (COV-12), so seeds vary only what the requests do not fix.
  • A steady-state run discards a warm-up, the stretch at the start where the system is still filling. MSER-5 finds its length: it picks the cut that minimises the estimated standard error of the mean of the remaining series, with the cut limited to the first half of the run. It is applied to the series averaged over the replications, for each output series, including the prefix-cache hit rate, which often settles later than queue lengths. The warm-up is the largest cut over the series. The estimate comes from replications, or from batch means: one long run, after warm-up, split into 20 batches. The lag-1 autocorrelation of the batch means must be below 0.1; otherwise the batch is doubled, and if no batch size meets it the run is classed incomplete. A percentile gets its interval from replications, each holding enough samples for that percentile, never from batch means.
  • A run whose measured window shows a trend has not settled. If the backlog grows, the system is overloaded: its latency values describe a transient and are not reported. Its departure rate is reported as saturation throughput only if the departure rate itself shows no trend.

Independence assumptions. An interval is valid only as far as these hold. Replications are independent, because each has its own scenario seed (§8.4). Observations inside one run are not independent, because successive latencies are correlated through the queue, so no interval treats them as independent. Draws for different clients and entities are independent unless the workload models a dependence (§8.5). The cost model adds no random term to a step’s time. A run’s randomness comes from named substreams only: the workload’s draws, the router’s tie-breaks and draws, and any declared stochastic model of infrastructure, such as node-provisioning and instance-loading delays or KV-tier latency jitter. The Result's frame lists each, and a reported interval states which of them it covers. Two runs with the same seed are identical, not independent.

Replications and confidence. Replications start at five and continue until the interval is narrower than a stated fraction γ of the estimate, or a stated limit is reached, in which case the width reached is reported. The target is adjusted to γ′ = γ / (1 + γ), because a stopping rule on the interval width otherwise lets the interval under-cover; the stopping rule is part of the procedure that DEV-11 tests. A reported interval states its level, its method (replication means or batch means), the number of replications, and which uncertainty it covers. A comparison of two configurations uses the differences between paired replications that share common random numbers (§8.4). It has three outcomes: better, worse, or not distinguished. One configuration is better only when the whole interval of the difference lies beyond a stated margin. Not distinguished includes the case called equivalent, where the whole interval lies within the margin. A search that compares many configurations controls the chance of a false winner across all its comparisons, and re-estimates the winner on fresh seeds, because the best of many noisy estimates is biased upward.

The interval covers the randomness of the workload. The model’s own uncertainty is separate: its coefficients have intervals (VAL-10) and its methods have measured errors (VAL-5). A recommendation is reported with a sensitivity run, in which the coefficients it depends on most are moved across their intervals, and states whether the ranking changes. Byte identity shows that a refactor changed nothing. It does not show that a reported value is right.

8.9 Verification and validation

BLIS checks two different things. Verification asks whether the code does what the simulation model says (the simulation model is BLIS’s description of the serving system; it is not a language model). Its checks are the oracle tiers (§7.4), the conservation of requests, determinism, the byte gate and the relations of DEV-14. Validation asks whether the model matches the real system for its intended use. Its checks are held-out accuracy against measured benchmarks, through the dashboard’s scoring harness (§11.7), and the validity of its rankings. Both rest on a record of assumptions: each engine module and each cost-model form lists in its manifest what it does not model and why that is believed not to matter. Maintainer practice: at each engine upgrade a reviewer reads the event trace of a standard scenario for plausibility and records the review in the upgrade report.

Validation has three levels, and a point reports every level its source records.

  • Aggregate. The metrics of §8.7, scored by error, accuracy and quantile error (§11.8).
  • Distribution. Where the source records per-request data, the simulated and measured distributions of each metric, scored by distribution distance (§11.8).
  • Event. Where the source records per-request data, simulated and measured requests are paired by request identity and compared on per-request latency error, completion order (Kendall’s tau within each concurrency level), per-request prefix-cache hit length, per-tier KV hits and, for a P/D point, the start and end of each transfer. Runs with equal means and quantiles can still order completions and hit the prefix cache differently; only this level shows it.

A source that records aggregates only is validated at the first level and says so.

A change is a verification change when it must leave the model’s behaviour unchanged: a refactor, a speed-up, or a fix that makes the code match an oracle or a written rule. It is a validation change when it changes what is modelled: a pricing form, a coefficient, how links are shared, an input model, a timing rule such as the scrape delay, or the order of classes at one instant. A change that is both is split. A verification change that moves a reported value carries the evidence X13 asks of it.

The model’s validity domain is the range of models, chips, layouts, concurrencies, sequence lengths and replica counts its held-out data cover. It includes a (model, chip) pair only if some fit unit covers that pair, so a held point on a pair with no fit unit lies outside it. Held-out error measures generalisation across the configurations of a deployment family; generalisation across a chip or a model is measured by the leave-one-out runs of VAL-5. Every Result states whether its scenario lies inside the domain. Behaviour that appears only at cluster scale, such as router decisions across many replicas or contention on shared links, is verified against upstream code but not validated until measured cluster runs exist. Where measurements at several sizes exist, the simulated curve across sizes is compared with the measured curve, not only single points. When BLIS models a policy, such as an autoscaler or a saturation detector, its output states whether that policy has been validated, and against what.

Validity for decision use. BLIS ranks configurations, and a small error does not guarantee a correct ranking, because errors of opposite sign reverse an order. A source with several measured configurations of one workload and model reports ranking validity (§11.8) for each workload, beside accuracy. A Result of blis-config-search states the tau of the nearest validated workload.
