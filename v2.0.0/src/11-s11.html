11Accuracy coverage

When inference-sim releases, the accuracy dashboard scores the new release at its next nightly run, with no change to its own code. The dashboard scores every anchor unit, and grades how close each comparison is. InferenceX often runs older, nightly or custom engine builds, so a perfect comparison is not always possible.

11.1 Why settings must not be classified by the dashboard

A dashboard that keeps its own table of which engine settings are modelled will disagree with the engine. The engine changes, and the table does not. The release plan's background shows what that cost. So the dashboard never classifies a setting. The engine repository does, in its field list (VLM-3), and the dashboard reads that list.

11.2 Four steps for scoring a point

  1. State. The dashboard copies the run's recorded engine configuration and environment variables, unchanged, into the scenario's engine block. A run records its configuration in several places: the launch configuration, the arguments the engine logs as passed, the configuration it logs as resolved, and lines it prints about values it chose. The first two record the values passed; the last two record the values resolved. The dashboard reads every one, and a value any of them records is recorded by the run, so it is copied rather than estimated (X19). The engine block holds the values the run passed; a field the run records only as resolved is copied as resolved. This applies to a field the engine models or proves inert; for any other field the resolved value is the engine's own choice, not a setting the run made, so it is recorded on the point and not stated in the scenario, and the field's estimation rule applies only to a value the run passed. A resolved value that differs from a passed one is not a conflict, because the engine resolves its settings: the engine repository must reproduce that resolution. Where the run logs a resolved value that differs from the engine repository's resolution of the passed value, the point is G2, names the field, and the difference goes to the backlog as a fidelity defect. Two sources that record the same stage, such as the launch configuration and the logged passed arguments, with different values are a conflict, and the point is G5 with the reason value_conflict. The dashboard translates nothing, apart from the estimates of the next step. The one exception is engine.version: it is set to the engine release that the scoring inference-sim release runs, and the run's own release is recorded on the point (§11.5). A recorded field that the modelled release does not have would be refused (X1), so the point is G5 with the reason field_not_in_release, naming the field. A workload-dependent value the run records, such as the mean acceptance length its engine logs, is copied into the scenario as stated (D8). One it does not record is taken from the substrate's profiles, and is not an estimate under the next step. With no profile either, the point is G5 with the reason value_not_recorded.
  2. Estimate. When the run did not record a value the simulation needs, such as the maximum model length, or used a setting BLIS does not model, such as an unsupported quantisation format, the dashboard applies the engine's estimation rule for that field. Each engine repository writes these rules in its fields.json, beside each field's status: one of: leave the field unset, so the engine resolves the upstream's default (X19); a stated setting that stands in for an unmodelled one, with the reason; or none. An estimation rule may state when the stand-in is exact: preserves, a sentence naming what the upstream resolves identically, and valid_when, a list of clauses; the stand-in is exact for a recorded value when at least one clause holds, and a clause holds when every key in it holds. A value for which no clause holds is not stood in for: the point is G5 with the reason field_not_modelled. Absent valid_when, the rule applies to every value. The dashboard holds no rules of its own. A rule applies in two cases: the run did not record the value, or the run passed a setting the engine does not model. A rule never replaces the recorded value of a field the engine models or proves inert: that value is carried into the scenario as stated. For a setting the engine does not model, the rule's stand-in, or leaving the field unset, takes the place of the recorded value in the scenario, and the point names the field, the recorded value and what stood in for it. A not-modelled field that the engine reads and prices when it is stated is a status to correct, either to modelled with its evidence or to refused when stated (VLM-3); the rule does not stand in for that. Every estimate is named on the point and makes it G2; a field with no estimation rule makes the point G5, with the reason value_not_recorded for a missing value or field_not_modelled for an unmodelled setting.
  3. Decide. For each field, the engine's own fields.json says whether it is modelled, proven inert or not modelled. The dashboard keeps no table of its own.
  4. Price. The engine lowers the configuration to kernel implementations. For each implementation the cost model uses the most trusted available entry, the one with the smallest rank number (§9.2), and the point records which methods were used.

A gap at Estimate is a missing estimation rule, and a gap at Decide is porting work, both in the engine repository. A gap at Price is a value below rank 1. All three go to the backlog.

11.4 Reasons a point is not scored (G5)

  • code_not_visible: the run loaded code BLIS does not have. That is a class, module or plugin that a configuration field or plugin entry point names and the pinned upstream release does not ship, such as an out-of-tree connector, scheduler, worker or logits processor, or a patched private build. This reason takes precedence over field_not_modelled.
  • router_unsupported: the run was measured behind a router BLIS does not host, and the router table has no entry for it or says that no llm-d policy is close enough. BLIS hosts only llm-d's router (X4) and never simulates another, so such a point stays in the coverage counts as not scored. The router table (catalog/routers in blis-substrate) lists each router BLIS does not host, by the mode and session-affinity setting a run used, with the llm-d policy it maps to, or an explicit statement that no llm-d policy is close enough, and the evidence for the match or the mismatch: a citation of both routers' code or documentation at the revisions the runs used. A run whose recipe names a router build by version, not by commit, is covered by an entry that lists that version with every commit it could have been built from (a nightly of a development branch: the first-parent commits of its UTC date; a release: the commit of its tag), and only if each file that decides the mode is, at every one of those commits, either one blob or blobs with one normal form. The normal form removes logging statements, a binding that only carries a value to a removed statement, an unread element of a tuple binding and blank lines, and nothing else; the entry records each blob's normal-form digest and a script in the substrate recomputes it from the router's history. Where a file differs by more, the build is not covered. An entry maps a router to an llm-d policy only with that evidence; a router and mode with no such entry stays router_unsupported. A point behind a router the table maps is G2 (§11.3), never G1, and it is never presented as if llm-d had routed the run. Hosting another router would add an upstream to this design.
  • value_not_recorded: the result depends on a value the run did not record. It becomes G2 when an estimation rule in the engine's fields.json covers the value (§11.2).
  • field_not_modelled: the run sets a field the engine classifies as not modelled, and the field has no estimation rule, or its rule does not cover the recorded value. It clears when the field is modelled or gains a rule.
  • field_unclassified: the engine has not classified a field the run sets, or its repository publishes no field list yet. It is a blocker-backlog entry, cleared when an engine release classifies the field or publishes the list.
  • engine_unsupported: no BLIS engine repository exists for the run's engine, as with TRT-LLM.
  • chip_not_modelled: the run's chip is one the release does not model, such as AMD's MI300X, MI325X and MI355X, which are out of scope until after M4. The reason cites the issue that scopes the chip. The point stays in the ledger and in the coverage counts, and is not scored.
  • Order of reasons. A point's first reason, the one the coverage and the backlog count it under, is taken in this order: the scope reasons first, chip_not_modelled and then not_in_catalog, because a missing chip or model is a gap BLIS can close and the backlog shows it as such; then every other reason in the order listed here. The point keeps all its reasons.
  • topology_unsupported: the run was measured on a deployment the scoring harness cannot write as a scenario: several engines, as in a prefill and decode split or a run across nodes, where it builds one colocated pool. It is a blocker-backlog entry, cleared when the harness can write that topology.
  • not_in_catalog: the run's model or chip has no catalog entry yet. This is a model-onboarding trigger (§12.1), and the backlog counts it.
  • field_not_in_release: the run sets a configuration field that the engine release inference-sim runs does not have. It clears when inference-sim moves to a release that has the field.
  • value_conflict: two sources that record the same stage of one field, such as the launch configuration and the logged passed arguments, give different values (§11.2). This is a data issue, reported to the source.
  • build_unparseable: the run's recorded engine build cannot be read. This is a data issue, reported to the source.
  • measurement_contaminated: the run's server log shows that the measurement is not of the scenario it is labelled with. Today there are two subjects, request_count_mismatch and requests_failed, for a vLLM single-turn point. The benchmark client sends 10 times the concurrency in measured requests and 2 times the concurrency in warm-up requests to the server whose log the run keeps, so a clean log holds exactly 12 times the concurrency of completed client requests: only responses the server answered with success (HTTP 200) are counted, because a request answered with another status, such as a rejected or unknown-route probe, is not a request of the run. A log that holds a different count is another run's: two servers that shared a host and a port have split each other's clients, and the queue behind the measured latencies is the other run's. A log that holds more requests is still clean when the extra requests cannot overlap the timed ones, as when an accuracy evaluation ran on the same server before or after the benchmark; the check is that the engine's periodic statistics split the log into stretches separated by an idle interval, and one stretch holds exactly the client's count. A log with fewer completed requests is never clean. A run whose responses mostly failed, with more failed responses than completed ones, is not a completed run either, and is not scored: it is named requests_failed(N of M completed). Otherwise the reason names both counts, request_count_mismatch(expected N, logged M). The rule reads the log and the concurrency only, never a prediction or an error, and is applied to every vLLM single-turn point that has a server log, whatever its model, chip or split. A point with no server log, a log with no request lines, an agentic or prefill and decode point, and an SGLang point are not judged: SGLang's logs count launcher probes, so an exact count is not a test there. It is a data issue, reported to the source, and clears when the point is measured again on a server of its own.
  • blis_refused: the simulator refused the scenario the harness wrote from the run's recorded values, and said why. The subject is the simulator's own message, with this run's paths removed. The point stays in the coverage counts as not scored, and the backlog counts it. Two things are not this reason and are faults of the run (COV-8): a simulator that exits with no message of its own (a crash), and a Result the harness cannot read or that is incomplete. A replay that exceeds the runner's memory or time is a limit of the runner, not this reason: the point is listed as failed and the night is not stopped. The reason is a named fact about the point and is never a grade. The substrate's per-point record (SUB-19) carries the same closed list of reasons and must list this one; it does not yet (inference-sim/blis-substrate#403). A refusal code that the nightly has not met before is published like any other and listed in the summary's new_refusal_codes, so that a person reads it; the night warns and does not stop.

11.5 One simulator release scores every point

Each inference-sim release runs one upstream release of each engine (LIF-6). The dashboard scores all points with one inference-sim release at a time (COV-9). A point measured on that engine release can be G1 or G2. A point measured on another release is scored on the release inference-sim runs, and graded G3 or G4 by how much of the ported code differs (§11.3). So every point is priced by the same substrate and engine code, and a substrate improvement reaches every point without a backport.

The previous inference-sim release's scores stay published with it, so a reader can compare a point on its own engine release across BLIS releases.

11.6 The blocker backlog

Every night the dashboard publishes a ranked list, per engine, of everything that lowers coverage or grade:

  • refused surface items;
  • not-modelled fields;
  • coefficients below rank 1;
  • unpriced execution modes.

Each entry shows how many points it blocks or demotes. Engine and substrate work is chosen from the top of this list, and each entry maps to one playbook (§12).

11.7 The scoring harness, and who may run it

The dashboard's scoring harness is the one place where a simulation is compared with a measured end-to-end benchmark (§2.2). It takes three inputs: a simulator build (an inference-sim release, or a commit of a branch or pull request), the catalog and coefficient registry it should load (embedded, or paths), and a set of ledger units. It turns each unit's recorded run into a scenario as §11.2 describes, runs the simulator, and compares. It writes the same per-point records and aggregates, whoever runs it.

The harness is named by its accuracy-dashboard commit; the dashboard cuts no release. It is run as a script on a runner that builds the simulator, not as a container image. A repository whose pull requests run it pins that commit in one pin file, as it pins any dependency, and the release bot moves the pin. Every figure records the harness commit that produced it (X8).

Anyone may run it, at any stage of a change: on a feature branch, on a draft pull request, or on a pull request under review. What changes with the stage is which units it may read, because only seed-holding jobs may see select, validate and held units (D7):

Examples are a harness that stops at its recorded request count, or runs no warm-up by default. A blank value in a column that the source extracts from the run's command line means the value was not recorded, never that the engine's default applied. The achieved concurrency in the simulation matches the measured one within a stated tolerance. Each lane is scored on its percentiles and a distribution distance, not only on its mean. Where the digests are unrecorded, that mean is used only if the measurements agree with each other: their completed-request counts, and each compared metric, within 20% of the mean. Otherwise the point is G5 value_conflict, and its measurements are reported to the source.
