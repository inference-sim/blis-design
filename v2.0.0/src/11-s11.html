11Accuracy coverage

When inference-sim releases, the accuracy dashboard scores the new release at its next nightly run, with no change to its own code. It scores every anchor unit and grades how close each comparison is. InferenceX often runs older, nightly or custom engine builds, so an exact comparison is not always possible. BLIS maximises the share of points scored, their accuracy and their closeness to the run, and COV-15 makes this an obligation of every release.

11.1 Why settings must not be classified by the dashboard

A dashboard that keeps its own table of which engine settings are modelled will disagree with the engine. The engine changes, and the table does not. So the dashboard never classifies a setting. The engine module does, in its field list (VLM-3), and the dashboard reads that list.

11.2 Four steps for scoring a point

  1. State. The dashboard copies the run's recorded engine configuration and environment variables, unchanged, into the scenario's engine block. A run records its configuration in several places. The launch configuration and the logged passed arguments hold the values passed. The logged resolved configuration, and the lines the engine prints about values it chose, hold the values resolved. A value any of them records is recorded by the run, so it is copied and not estimated (X19). The engine block holds the values passed. A field the run records only as resolved is copied as resolved when the engine models it or proves it inert; for any other field the resolved value is the engine's own choice, and it is recorded on the point and not stated in the scenario. A resolved value that differs from a passed one is not a conflict, because the engine module must reproduce the engine's resolution. Where the run logs a resolved value that differs from the module's resolution of the passed value, the point is G2, names the field, and the difference goes to the backlog as a fidelity defect. Two sources that record the same stage with different values are a conflict, and the point is G5 with the reason value_conflict.
    The dashboard translates nothing, apart from the estimates of the next step. The one exception is engine.version, which is set to the commit the scoring release models; the run's own commit is recorded on the point (§11.5). A recorded field that the modelled commit lacks is refused (X1), so the point is G5 with the reason field_not_in_release. A workload-dependent value the run records, such as the mean acceptance length its engine logs, is copied as stated (D8). One it does not record is taken from the substrate's profiles and is not an estimate under the next step. With no profile either, the point is G5 with the reason value_not_recorded.
  2. Estimate. When the run did not record a value the simulation needs, such as the maximum model length, or passed a setting BLIS does not model, such as an unsupported quantisation format, the dashboard applies the engine's estimation rule for that field. Each engine module writes these rules in its fields.json, beside each field's status. A rule is one of: leave the field unset, so the engine resolves the upstream's default (X19); a stated setting that stands in for an unmodelled one, with the reason; or none. A rule may state when the stand-in is exact: preserves, a sentence naming what the upstream resolves identically, and valid_when, a list of clauses. The stand-in is exact for a recorded value when at least one clause holds, and a clause holds when every key in it holds. A value for which no clause holds is not stood in for, and the point is G5 with the reason field_not_modelled. Absent valid_when, the rule applies to every value. The dashboard holds no rules of its own. A rule never replaces the recorded value of a field the engine models or proves inert. For a setting the engine does not model, the stand-in, or leaving the field unset, takes the place of the recorded value, and the point names the field, the recorded value and what stood in for it. A not-modelled field that the engine reads and prices when stated is a status to correct, to modelled with its evidence or to refused when stated (VLM-3); the rule does not stand in for it. Every estimate is named on the point and makes it G2. A field with no rule makes the point G5 (§11.4).
  3. Decide. For each field, the engine's own fields.json says whether it is modelled, proven inert or not modelled. The dashboard keeps no table of its own.
  4. Price. The engine lowers the configuration to kernel implementations. For each implementation the cost model uses the most trusted entry the registry has for the chip (§9.2), and the point records which methods were used.

A gap at Estimate is a missing estimation rule, and a gap at Decide is porting work, both in the engine module. A gap at Price is a value below the most trusted method. All three go to the backlog (§11.6).

11.3 Closeness grades

The commit distance of a run is the pair of counts of commits from the merge base of its engine commit and the commit the scoring release models to each of the two, with the releases whose tags lie between them. Every point gets exactly one grade: the highest-numbered (least close) grade whose conditions apply. Grades are computed from data alone, so a condition the data cannot decide is never assumed to hold: a G1 is published only for a point whose every condition was evaluated.

Five grades, G1 to G5, say how closely a simulated point matches the run it is compared with.

A grade orders commit closeness first. A run of a model whose code was backported onto the modelled commit (§12.5) has no grade of its own: it is graded by commit distance like any other. A point simulated through the router table is graded and counted in coverage, and its accuracy has a figure of its own that is never pooled into the headline, because its error measures the substitution as well as BLIS (COV-11).

value_conflictTwo sources that record the same stage of one field give different values (§11.2). This is a data issue, reported to the source.The source corrects the record.
build_unparseableThe run's recorded engine build cannot be read. This is a data issue, reported to the source.The source corrects the record.
measurement_contaminatedThe run's server log shows that the measurement is not of the scenario it is labelled with. The rule applies to a vLLM single-turn point that has a server log. The benchmark client sends 10 times the concurrency in measured requests and 2 times in warm-up requests, so a clean log holds exactly 12 times the concurrency of completed client requests; only responses answered with success (HTTP 200) count. A log with a different count is another run's, as when two servers shared a host and a port and split each other's clients. A log with extra requests is still clean when they cannot overlap the timed ones, as when an accuracy evaluation ran on the same server before or after the benchmark: the engine's periodic statistics split the log into stretches separated by an idle interval, and one stretch holds exactly the client's count. A log with fewer completed requests is never clean. A run with more failed responses than completed ones is named requests_failed(N of M completed); any other mismatch is request_count_mismatch(expected N, logged M). The rule reads the log and the concurrency only, never a prediction or an error. It is a data issue, reported to the source.The point is measured again on a server of its own.
blis_refusedThe simulator refused the scenario the harness wrote from the run's recorded values, and said why. The subject is the simulator's own message, with this run's paths removed. The backlog counts it. Faults of the run and limits of the runner are not this reason (COV-8). The substrate's per-point record (SUB-19) carries the same closed list of reasons.The simulator accepts the scenario.

Order of reasons. A point's first reason, the one coverage and the backlog count it under, is the first that applies in the order of the table. The scope reasons come first, because a missing chip or model is a gap BLIS can close and the backlog shows it as such. The point keeps all its reasons.

11.5 One simulator release scores every point

Each inference-sim release models one upstream commit of each engine (LIF-6). The dashboard scores all points with one inference-sim release at a time (COV-9). A point measured on the modelled commit can be G1 or G2. A point measured on another commit is scored on the modelled commit and graded G3 or G4 by how much of the ported code differs (§11.3). So every point is priced by the same substrate and engine code, and a substrate improvement reaches every point without a backport.

The previous release's scores stay published with it, so a reader can compare a point on its own engine commit across releases.

11.6 Coverage and the blocker backlog

Coverage is reported as a funnel for each scored source, so every loss is a stated number. For InferenceX and configiq, at each release, the funnel counts:

  1. the rows the source holds;
  2. its units;
  3. the units in scope, which are those not chip_not_modelled;
  4. the units with recoverable inputs;
  5. the units scored;
  6. the units scored in each grade.

It also lists the top blockers, ranked by the points each one alone holds back and, for a coefficient below the most trusted method, by the share of predicted time it prices. A source used for training only reports a training funnel: the rows held, the units, the units with recoverable inputs and the units used in a fit.

No age limit applies (COV-2). Older runs count in the headline at their own grade, in the same funnel, and are not split off. The grade already says how closely a point matches what BLIS ran, and the same-commit figure is one slice away (COV-13).

Inputs are recovered from the most durable record a source offers: a server log kept by the source's API; a job log while its host keeps it, otherwise the recipe or script at the run's commit; the archive for a measurement the live feed no longer serves because a newer measurement superseded it. Inputs that a source deletes after a retention period are archived privately as they are pulled and never committed (D6), so a point stays scorable after the source deletes them. A point whose inputs are gone is G5 value_not_recorded, naming the missing record.

Every night the dashboard publishes a ranked list, per engine, of everything that lowers coverage or grade: refused surface items, not-modelled fields, coefficients below the most trusted method, and unpriced execution modes. Each entry shows how many points it blocks or demotes. Engine and substrate work is chosen from the top of this list, and each entry maps to one procedure (§12).

11.7 The scoring harness, and who may run it

The dashboard's scoring harness is the one place where a simulation is compared with a measured end-to-end benchmark (§2.2). It takes three inputs: a simulator build (an inference-sim release, or a commit of a branch or pull request), the catalog and coefficient registry it should load (embedded, or paths), and a set of ledger units. It turns each unit's recorded run into a scenario as §11.2 describes, runs the simulator, and compares. It writes the same per-point records and aggregates, whoever runs it.

The harness is named by its accuracy-dashboard commit; the dashboard cuts no release. It is run as a script on a runner that builds the simulator, and a repository whose pull requests run it pins that commit in one pin file, as it pins any dependency. Every figure records the harness commit that produced it (X8).

Anyone may run it, at any stage of a change. The stage decides which units it may read, because only seed-holding jobs may see select, validate and held units (D7):

What the scoring harness may read and report depends on who runs it.

A figure computed on a branch is labelled with its build and its data, as every Result is (X8), and is labelled experimental unless both are exactly pinned and no overlay was used. It can be posted on a pull request and is never published as BLIS's accuracy.

11.8 Accuracy statistics

Every reported value and every gate uses these definitions. No other section defines them.

One definition of error, accuracy, distance and interval serves every figure the dashboard publishes and every gate.
TermDefinition
ErrorThe error of a point on a metric is |simulated − measured| / measured, the absolute relative error. The signed relative error is published beside it as bias. Gates compare absolute errors only (VAL-6). A point whose measured value is zero is not scored on that metric.
AccuracyThe accuracy of a set of points on a metric is the median of their errors, with the mean and the 90th percentile beside it. Each role key counts once: the dashboard first averages the errors of a key's points, and weighs the keys equally.
Quantile errorThe error of a stated quantile (p50, p90 or p99) of a latency metric, simulated against measured.
Minimum sampleA quantile q of n measured requests is scored only when n ≥ 10 / (1 − q): 20 for p50, 100 for p90, 1,000 for p99. A smaller sample marks that quantile not scored, and every statistic skips it. A scored quantile is published with a distribution-free interval from the order statistics.
Distribution distanceWhere per-request data exist, the Wasserstein-1 distance between the simulated and the measured per-request samples of a metric, divided by the measured mean. Where a source records aggregates only, the mean of the quantile errors at p50, p90 and p99, labelled quantile error and not distance.
IntervalEvery aggregate accuracy figure shows a 95% interval from a cluster bootstrap: each resample draws role keys with replacement and takes all of a key's points. A comparison of two releases shows the interval of the paired difference on the points both score. A gate resamples the same way (VAL-6).
SlicesA slice view does not correct its intervals for the number of slices viewed. It ranks slices only by a Holm-corrected comparison with the headline.
Ranking validityFor the measured configurations of one workload and model: Kendall's tau between the simulated and the measured rank of the configurations on each metric, and the regret, which is the measured loss of the simulated best against the measured best.

  • COV-13 Accuracy is sliceable by any recorded attribute. Every scored point carries its attributes, and the dashboard filters and groups by any of them, recomputing every aggregate from the points that remain. The attributes are: source and role; model, precision, chip, node count and interconnect; engine, engine commit and commit distance; topology (TP, DP, EP, P/D pools), speculative method, offload and KV tiers, and router; workload type, input and output lengths, concurrency, arrival process and prefix sharing; measured date; source revision (archive or live feed); grade, and each substitution named on the point. Each slice shows its point count, its number of role keys and its coverage beside its accuracy, with the intervals of §11.8. min_points is 10 role keys: it counts distinct role keys, not points. The point rows stay visible at every count. No aggregate accuracy figure is shown below min_points, at any level from the headline to a drilled-in slice, and an aggregate not shown is excluded from every verdict. The dashboard shows the count in its place, and the per-point table states the rule.Checked by: the summary schema, which requires the attributes and a count with every aggregate; a test that every filter recomputes its aggregates from the remaining points; a test that no aggregate renders under min_points at any level, that ten points from two role keys render none, and that the per-point rows still do.
