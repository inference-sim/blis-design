9Getting a value for every coefficient

9.1 The aim

The cost model needs a coefficient for every primitive on every chip: an attention rate, a GEMM efficiency curve, a collective’s latency. Fitted measurements will never exist for every combination, and a refusal for a missing coefficient would lower coverage where a sound estimate exists. So every primitive gets a value, and every value records how good it is.

9.2 Sources, in order of preference

For each lookup (primitive, kernel implementation, chip, and where relevant data type and group size) the cost model uses the entry with the smallest rank number. When the coefficient registry has no exact entry, the lookup falls back down the ranks to the most trusted entry the registry has for that chip, and the point names the method (VAL-3).

Seven methods rank a coefficient from fitted to assumed, and the cost model takes the most trusted one available.
RankMethodWhere the value comes fromExample
1measuredfitted to microbenchmarks of this exact kernel implementation on this chip, with held-out error reportedattention decode rate for one library on H200, fitted to AISimulate sweeps
2calibrateda formula with physical structure, such as a roofline, whose one or two efficiency factors are fitted to composite data (end-to-end runs or whole forward passes) for this implementationa GEMM ramp shaped by FLOPs and bytes, with a fitted efficiency ceiling
3transferredmeasured on a closely related implementation or chip, and moved here by a stated rulean all-reduce coefficient measured on H100, moved to H200 by the ratio of the two chips’ measured link bandwidths
4literaturea figure from published work, cited exactlyan achieved bandwidth fraction reported by the GPU kernel’s authors
5vendor_speca datasheet figure used directly, nominal rather than achieveda link’s rated bandwidth, before any efficiency is measured
6rooflinecomputed from catalog facts alone: the larger of FLOPs over peak compute and bytes over peak bandwidth, times a default efficiency taken from the same primitive family on other chips of the same generation where there are anya new chip with datasheet figures but no measurements
7assumeda stated assumption with a reason, such as an upper bound"charge at most 5 µs of host time per request for scheduling", with the reason for the bound

A primitive family is the set of coefficients that price one kind of operation, such as dense GEMM, decode attention or all-reduce. Rank 6 needs a FLOP and byte formula for the primitive and at least one measured chip in its family to borrow an efficiency from. Most compute and memory primitives have both. Host CPU overheads, collective latency floors and the routing imbalance of expert all-to-all do not. For those families, and for every new family, the substrate MUST carry a rank-7 assumed value for every catalog chip, so that the cost model can always produce a price (VAL-2). New entries are required only for a new primitive family. For any other model or engine commit, fitted entries raise accuracy; where the ledger holds fit units for a family on a chip and the lookup is served at rank 3 or lower, the lookup is listed as fit_available (VAL-2). The point’s grade (§11) reports the trust in a price.

What a coefficient is keyed by. A kernel coefficient is keyed by the kernel implementation that runs, so data from one engine fits another’s value wherever both run the same implementation. The implementation’s identity includes the hash of the tuned configuration (an autotuned or per-device configuration file) that the engine’s lowering selects for the plan’s shape, data type and device, because a changed file changes speed while the kernel’s source stays the same. An engine-path cost (host time, scheduler time, launch cost, CUDA-graph replay) is keyed by the identity of the code that does the work, and by the host CPU of the node where it was measured. The code identity is the hash of the normalised bodies of the functions in the call closure that the engine’s code_paths.json lists. The oracle’s call trace generates the closure, which covers ported callees and the module constants and field defaults read on the path, and the diff generator of FID-14 produces it at any commit. Normalisation removes comments, docstrings and logging only; an annotation that defines a field stays. The engine module supplies the identity in its plan (§6.2), and the substrate stores it as an opaque key, so no engine name appears in substrate (X2). Engines or commits with the same code identity share an entry. A commit whose code differs has no exact entry and falls back as above (VAL-8); an upgrade writes a transferred entry from the previous identity for each identity it changes (§12.4), so the coefficient survives at rank 3 until it is refitted. A lookup whose host CPU differs from the entry’s is transferred, with the rule of scaling by the ratio of the catalog’s single-thread scores of the two CPUs, or assumed.

When a transfer is valid. A transferred entry names its source chip and its rule. If the source and the destination chip differ in generation (in tensor-core instruction set or data-type support), the rule must be one that VAL-5 has validated for that pair of generations; otherwise the entry ranks as roofline.

Measured or calibrated. A value is measured when its data units are microbenchmarks of exactly this kernel implementation on this chip, and calibrated when they are composite and a factor of a structured formula is inferred from them. Every value is stored, roofline values included, as a coefficient registry entry written by a writer script. The cost model only looks values up.

9.3 How the quality of a less trusted value is tracked

Every coefficient records its method (VAL-1) and every price records the methods it used (VAL-3). Each method’s typical error is measured and published as VAL-5 states.

  • Replacement. For each lookup there is at most one entry per rank. Replacing a measured value with a newly measured one is a normal accuracy change, with held-out evidence. Removing a more trusted entry otherwise needs a supersedes: record (VAL-4).
  • Backlog. Every value below rank 1 appears in the blocker backlog (§11.6), weighted by how many points it prices and by the share of their predicted time it prices (VAL-3).
  • Extrapolation. A fitted entry records the range of inputs its data covered (VAL-10). A lookup outside that range is extrapolated: it keeps the entry’s value, but for VAL-3 it ranks with transferred, so the price and the point’s grade show that the value is used where it was never measured.

    Checked by: schema rules in substrate/validate, including that a not_charged entry cites an FID-11 case.
  • VAL-2 For every primitive family and every catalog chip, some rank has a value: a family without a roofline formula, and every new family, has an assumed entry for every catalog chip. A missing measured value never causes a refusal, and the point names the method used. Where the ledger holds fit units for a family on a chip and a lookup there is served at rank 3 or lower, the lookup is listed as fit_available in the backlog, and a release carries no such entry unless a fit was attempted and failed identifiability (VAL-10) or the landing gate (VAL-6).Checked by: completeness test over every primitive and catalog chip (SUB-7); the backlog generator, which marks fit_available, and the release candidate check, which fails on an unexplained entry.
  • VAL-3 Each price records, among the coefficients it used, the least trusted effective rank and the share of its predicted time priced at each rank, and names its method and any flag. An extrapolated lookup counts as transferred, and an unidentified entry as assumed (VAL-10). A not_charged entry that does not meet VAL-1 counts as assumed, and every not_charged entry appears in the backlog and in the point’s record.Checked by: step-time result fields; checked in kernel tests, including that the shares sum to one.
  • VAL-4 Each lookup resolves to one entry per rank, and the entry with the smallest rank number is used. Flags do not change which entry is chosen, only how the price reports it. Where several entries of one rank match a lookup at different scopes, one written order of precedence over every scope dimension (chip, model, layout widths, node) picks one, whatever order the entries were loaded in. Two matching entries that the precedence does not order are refused at load, and a price’s provenance names every matching entry it displaced. Maintainer practice: a more trusted entry is removed only with a supersedes: record citing a defect, in a pull request a maintainer with write access approves.Checked by: a validator rule that refuses unordered matches; a cost-model test that resolves every pair of scope kinds in both load orders and agrees with the validator (X15).
  • VAL-5 Using data units with role validate (§10), the error of measured and calibrated entries is the held-out error of the fit on the same chip. The error of transferred, literature, vendor_spec, roofline and assumed entries is measured by leaving one chip out and applying the method to that chip’s units. Each is published per primitive family as an accuracy (§11.8). The rank order of §9.2 is a default: when these errors, with the interval of VAL-6, show that a method of lower rank has a smaller typical error than one of higher rank on a family, a validation change revises the order for that family. Transfer and roofline errors are published apart for same-generation and cross-generation cases, with leave-one-generation-out where the catalog holds at least two generations. A cross-generation figure is never presented as the typical error of a method; the first chip of a generation has no same-generation neighbour, so its error is the cross-generation figure.Checked by: nightly error job.
  • VAL-6 A change to a measured or calibrated value passes the landing gate. Its pre-registration is committed first and holds the fit and held-out split, the success criteria, a non-inferiority margin d for each criterion (no larger than the margin in the invariant registry, which only falls) and the name of the gate’s bootstrap substream (X6).
    • Split. The split is taken along a dimension the term must generalise across (a chip, a model, a parallelism or a kernel shape; for a whole-run gate, the deployment, so that every row of one deployment falls on one side), never by random rows. Training and held-out error are reported apart, because a fit quoted on its training data alone is not a result.
    • Lane. A lane is a group of held-out points judged together: for a kernel coefficient, the kernel implementation it is fitted on; for a whole-run change, the points that share an engine, modelled commit, chip, model and layout, as the dashboard groups them (§11). A lane with fewer than min_points role keys is merged as D7 says, and the merged lane is the unit judged.
    • Criteria. The criteria are held-out error and distribution distance (§11.8). Both are absolute, so the paired difference cannot reward swapping a positive error for a negative one. Neither may get worse on any lane, and both must improve on the target lane.
    • Interval. For each lane and criterion the gate computes, on that lane’s held units, the difference of the candidate’s error minus the base’s. The candidate and the base run each unit with the same scenario seeds and the same number of replications, which the Result records. The interval is a one-sided 95% BCa bootstrap interval from 10,000 resamples. Each resample draws role keys with replacement and takes all of a key’s units, because the units of one key are near-copies with correlated errors. The resamples come from the substream the pre-registration names. The Holm correction is applied over every lane and criterion judged.
    • Decision. A lane passes when the upper end of its adjusted interval is below d. The target lane passes only when the upper end is below zero. At a release, the gate also compares the candidate with the best published release on each lane in the same way (§13.5), so that a series of small passes cannot add up to a loss.
    • Reach. Every changed entry is selected by a lookup in at least one operator-level or whole-run gate run. An entry no gate run selects, such as a coefficient for a chip with no held data, is reported as unjudged, and a maintainer decides whether it lands. A whole-run lane that gets worse does not by itself fail a change whose operator-level held-out check passed: the gate records the regression as a defect in another term (VAL-11), and a maintainer decides whether the change lands. Figures come from a script.
    Checked by: on fixtures per pull request, full data nightly; operator-level gates in substrate/validate, whole-run gates in accuracy-dashboard’s gate job (§13.5); a simulated lane in which every role key holds five perfectly correlated units gives an interval no narrower than that of one unit per key; a lane with a known regression larger than d fails, and a lane with only a small, noisy sample cannot pass by having a wide interval.
  • VAL-7 A coefficient is a measured constant of a law the kernel evaluates, not a correction for one model. The one exception is a coefficient scoped to a single model, which marks a cost that the cost model’s general forms do not yet explain, and names the missing form. The coefficient registry’s ratchet is the largest number of such coefficients it may hold, and a test fails when the count is above it. The ratchet only goes down. Maintainer practice: a maintainer may approve a raise in a pull request that names the general form each added coefficient stands in for, and the issue that will lower the ratchet again. The coefficient registry holds the current number.Checked by: ratchet test.
  • VAL-8 A lookup matches a coefficient only for the exact kernel implementation that runs, or, for an engine-path cost, the exact code identity that does the work (§9.2). A value taken from a different implementation or identity is a transferred entry (D5). A coefficient fitted at one engine commit is an exact entry at another only when the code identity is the same; otherwise it carries as the transferred entry that the upgrade writes (§9.2). Every coefficient registry entry is selected by a lookup on the conformance scenarios, or its kernel hash appears in the kernel_impls.json of the commit some engine module of a supported inference-sim release models.Checked by: the cost model’s lookup, which has no fallback to a sibling implementation other than the ranked fallback of §9.2; a test in the simulator’s package, the one place that may import both the coefficient registry and the engine modules, that lists entries matching neither condition, which are removed.
  • VAL-9 A coefficient states what its measurement includes: device time only or host issue time as well, captured or eager execution, and which harness collected it. The formula that reads it states the same, and the two must agree. A formula that needs both device and host time reads two coefficients, never one that mixes them.Checked by: a validator rule matching each coefficient’s measurement boundary with the boundary its reading formula declares.
  • VAL-10 A measured or calibrated entry records the interval its fit supports (95%, by a bootstrap that resamples whole sweeps, meaning files or runs, or by profile likelihood) and the range of inputs its fit data covered: shapes, token counts, ranks, chip and kernel. A price that reads an entry outside that range records the lookup as extrapolated, which ranks it with transferred for VAL-3 (§9.3). An entry whose interval is unbounded, or wider than the width the entry states relative to the scale of its value (for a signed coefficient, relative to the range of the prediction it feeds), is unidentified: its data do not determine it. It ranks with assumed for VAL-3 and keeps its method and citations (D1).Checked by: validator rules on the interval and range fields; a test that extrapolated lookups report it; the fitting scripts’ identifiability check.
  • VAL-11 An operator-level check judges a pricing form; an end-to-end check judges how forms combine. A form that passes its operator-level held-out check but makes end-to-end error worse shows that another term is wrong. The disagreement is recorded as one defect, in the other term. The end-to-end figure is not used to reject the form that passed, or to keep a known error. No coefficient or form is kept because it cancels another error. Maintainer practice: a reviewer asks of a pricing change whether it is kept or rejected because it offsets an error elsewhere.Checked by: a lint that refuses comments or entries marked as a known over-charge or under-charge without a linked defect.
