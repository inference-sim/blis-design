9Getting a value for every coefficient

9.1 The aim

The cost model needs a coefficient for every primitive on every chip: an attention rate, a GEMM efficiency curve, a collective's latency. Fitted measurements will never exist for every combination. If a missing coefficient caused a refusal, coverage would fall even where a sound estimate exists.

The aim is that every primitive gets a value, and every value records how good it is.

9.2 Sources, in order of preference

For each lookup (primitive, kernel implementation, chip, and where relevant data type and group size) the cost model uses the entry with the smallest rank number:

RankMethodWhere the value comes fromExample
1measuredfitted to microbenchmarks of this exact kernel implementation on this chip, with held-out error reportedattention decode rate for one library on H200, fitted to AISimulate sweeps
2calibrateda formula with physical structure, such as a roofline, whose one or two efficiency factors are fitted to composite data (end-to-end runs or whole forward passes) for this implementationa GEMM ramp shaped by FLOPs and bytes, with a fitted efficiency ceiling
3transferredmeasured on a closely related implementation or chip, and moved here by a stated rule, such as a ratio measured on a third chipan all-reduce coefficient measured on H100, moved to H200 by the ratio of the two chips' measured link bandwidths
4literaturea figure from published work: a paper, a vendor whitepaper, or a library's benchmark, cited exactlyan achieved bandwidth fraction reported by the GPU kernel's authors
5vendor_speca datasheet figure used directly, nominal rather than achieveda link's rated bandwidth, before any efficiency is measured
6rooflinecomputed from catalog facts alone: the larger of FLOPs over peak compute and bytes over peak bandwidth, times a default efficiency taken from the same primitive family on other chipsa new chip with datasheet figures but no measurements
7assumeda stated assumption with a reason, such as an upper bound"charge at most 5 µs of host time per request for scheduling", with the reason for the bound

A kernel whose source did not change needs no transfer: it keeps the same kernel hash, and so the same entry.

Rank 6 needs a FLOP and byte formula for the primitive and at least one measured chip in its family to borrow an efficiency from. Most compute and memory primitives have both. Some do not: host CPU overheads, collective latency floors, and the routing imbalance of expert all-to-all. For those, and for any brand-new primitive family, the substrate MUST carry a rank-7 assumed value for every catalog chip, so that the cost model can always produce a price (VAL-2). Only the trust in that price varies, and the point's grade (§11) reports it.

How to tell measured from calibrated. A value is measured when its data units are microbenchmarks of exactly this kernel implementation on this chip. It is calibrated when its data units are composite, such as end-to-end runs or whole forward passes, from which a factor of a structured formula is inferred.

Every value is stored. Every value of every rank, roofline values included, is a coefficient registry entry written by a writer script. The cost model only looks values up. That keeps every price traceable to a committed entry.

9.3 How the quality of a less trusted value is tracked

  • Labelling. Every coefficient records its method, and every price records the methods of the coefficients it used.
  • Error measurement. Each method's typical error is measured by leaving one chip out: for chips that have a measured value, compute each less trusted method's estimate as if the measurement did not exist, and compare. That error is published per method and per primitive family.
  • Replacement. For each lookup there is at most one entry per rank, and the cost model uses the most trusted one, the entry with the smallest rank number. Removing a more trusted entry (one with a smaller rank number) needs a supersedes: record that cites a defect issue, such as a measurement found to be wrong. That record triggers a review question. Replacing a measured value with a newly measured one is a normal accuracy change, with held-out evidence.
  • Backlog. Every value below rank 1 appears in the blocker backlog (§11.6), weighted by how many points it prices.

Extrapolation. A fitted entry records the range of inputs its data covered (VAL-10). A lookup outside that range is extrapolated: it keeps the entry's value, but for VAL-3 it ranks with transferred, so the price and the point's grade show that the value is used where it was never measured.

9.4 Invariants

  • VAL-1 Every coefficient records exactly one method from the list in §9.2, or not_charged, with the sources that method needs:
    MethodRequired sources
    measured, calibratedthe data units it was fitted to
    transferredthe source coefficient and the transfer rule
    literaturean exact citation

    Checked by: schema rules in blis-substrate/validate.
  • VAL-2 For every primitive family and every catalog chip, some rank has a value. A missing measured value never causes a refusal.Checked by: completeness test over every primitive and catalog chip (SUB-7).
  • VAL-3 Each price records, among the coefficients it used, the least trusted effective rank, and names its method and any flag. An extrapolated lookup counts as transferred, and an unidentified entry as assumed (VAL-10).Checked by: step-time result field; checked in kernel tests.
  • VAL-4 Each lookup resolves to one entry per rank, and the entry with the smallest rank number is used; flags do not change which entry is chosen, only how the price reports it. Where several entries of one rank match a lookup at different scopes, one written order of precedence over every scope dimension (chip, model, layout widths, node) picks one, whatever order the entries were loaded in. Two matching entries that the precedence does not order are refused at load, and a price's provenance names every matching entry it displaced. A more trusted entry is removed only with a supersedes: record citing a defect issue, in a pull request that the reviewer with write access approves.Checked by: validator check against the previous release, plus review guidance for the review agent; a validator rule that refuses unordered matches; a cost-model test that resolves every pair of scope kinds in both load orders and agrees with the validator (X15).
  • VAL-5 The typical error of each method is measured by leaving one chip out, and published per primitive family, using data units with role validate (§10).Checked by: nightly job.
  • VAL-6 A change to a measured or calibrated value passes the landing gate. The fit and held-out split and the success criteria are committed first. The split is taken along a dimension the term must generalise across (a chip, a model, a parallelism or a kernel shape; for a whole-run gate, the deployment, so that every row of one deployment falls on one side), never by random rows, and training and held-out error are reported apart; a fit quoted on its training data alone is not a result. Held-out error and distribution distance must not get worse on any lane, and must improve on the target lane. For each lane the gate computes, on that lane's held units, the paired bootstrap interval of the candidate's error minus the base's error. A lane fails only when that whole interval lies above zero, with the Holm correction for the number of lanes compared. The target lane passes only when its whole interval lies below zero. Every changed measured or calibrated entry is selected by a lookup in at least one operator-level or whole-run gate run. An entry no gate run selects, such as a coefficient for a chip with no held data, is reported as unjudged and lands only with a person's approval. Figures come from a script. A whole-run lane that gets worse does not by itself fail a change whose operator-level held-out check passed: the gate records the regression as a defect in another term (VAL-11), and the change needs a person's approval.Checked by: on fixtures per pull request, full data nightly; operator-level gates in blis-substrate, whole-run gates in accuracy-dashboard's gate job (§13.5).
  • VAL-7 A coefficient is a measured constant of a law the kernel evaluates, not a correction for one model. The one exception is a coefficient scoped to a single model, which marks a cost that the cost model's general forms do not yet explain. It names the missing form. The registry's ratchet is the largest number of such coefficients it may hold, and a test fails when the count is above it. The ratchet only goes down, with one exception. A pull request may raise it, as a recorded exception, when three things hold. First, each coefficient the raise adds names the general form it stands in for. Second, the pull request records the raise and names the issue that will lower the ratchet again. Third, a maintainer approves the raise in that pull request. This invariant states no number: the registry's ratchet holds the current one.Checked by: ratchet test.
  • VAL-8 A lookup matches a coefficient only for the exact kernel implementation that runs. A value taken from a different implementation is a transferred entry (D5). A coefficient fitted on one engine release carries to another only when every function on the term's code path is unchanged between them, shown by a per-function diff that ignores comments, type annotations and logging. Every coefficient registry entry is selected by a lookup on the conformance scenarios, or its kernel hash appears in the kernel_impls.json of an engine release that some supported inference-sim release pins.Checked by: the cost model's lookup, which has no fallback to a sibling implementation; a test that lists entries matching neither condition, which are removed in the next substrate release.
  • VAL-9 A coefficient states what its measurement includes: device time only or host issue time as well, captured or eager execution, and which harness collected it. The formula that reads it states the same, and the two must agree. A formula that needs both device and host time reads two coefficients, never one that mixes them.Checked by: a validator rule matching each coefficient's measurement boundary with the boundary its reading formula declares.
  • VAL-10 A measured or calibrated entry records the interval its fit supports (95%, by bootstrap or profile likelihood) and the range of inputs its fit data covered: shapes, token counts, ranks, chip and kernel. A price that reads an entry outside that range records the lookup as extrapolated, which ranks it with transferred for VAL-3 (§9.3). An entry whose interval is unbounded, or wider than half its value, is flagged unidentified: its data do not determine it, and it ranks with assumed for VAL-3, while keeping its method and its citations (D1).Checked by: validator rules on the interval and range fields; a test that extrapolated lookups report it; the fitting scripts' identifiability check.
  • VAL-11 An operator-level check judges a pricing form; an end-to-end check judges how forms combine. A form that passes its operator-level held-out check but makes end-to-end error worse shows that another term is wrong. The disagreement is recorded as one defect, in the other term. The end-to-end figure is not used to reject the form that passed, or to keep a known error. No coefficient or form is kept because it cancels another error.Checked by: review guidance for the review agent; a lint that refuses comments or entries marked as a known over-charge or under-charge without a linked defect. Review guidance. Is this change kept or rejected because it offsets an error elsewhere? Expertise: expertise in the changed directory. Applies when: a pricing change lands or is rejected with end-to-end evidence that contradicts its operator-level evidence.
