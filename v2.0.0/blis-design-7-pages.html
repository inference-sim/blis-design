The BLIS design in seven pages

This summarises the BLIS target design for engineers who know llm-d and vLLM and are about to change code. The design is the authority, and each claim below links to the section that states it. Terms are defined in the glossary (Appendix B), and Appendix C maps v1.0.0 rule identifiers to this version.

What BLIS is, and the ideas behind it

BLIS simulates an LLM serving cluster. It runs the router of llm-d, hosted in simulated time with no change to any routing decision, and Go ports of the vLLM and SGLang engines (§5.2). A cost model built from published hardware facts and fitted coefficients prices every step (§6.1). The design rests on these ideas:

  • One repository, inference-sim, holds everything built into the simulator. Every fact and every kind of work has one owner, and import-graph checks keep the boundaries (§2.2).
  • Engines hand the cost model a fully resolved description of what runs. Lowering lives only in engine modules (§6.1).
  • An engine module models an upstream commit, and every feature of that commit has a status (§7.5).
  • Every coefficient lookup has a value labelled by its method, and falls back to the most trusted entry the coefficient registry has (§9.2).
  • Accuracy is reported only on held-out units; settings come from each run’s records (§10.4).

The components

To place a fact, ask what it depends on. An engine’s upstream commit, such as vLLM’s default gpu_memory_utilization: the engine module. An llm-d release: the router fork. The simulator’s own design: the simulator. Otherwise it is true of the hardware, the model, the physics or the data, and the substrate owns it. H200 memory bandwidth is catalog data; the speed of one attention kernel on H200 is a coefficient in the registry; a user’s scorer weights stay in the scenario, copied verbatim. A change to the substrate passes one test: would a second engine need the same edit? If not, it belongs in an engine module (§2.2).

The parts of the substrate change together, so a model’s data, coefficients and cost-model change is one pull request and one release (§3.1). Contracts change only compatibly (§5.1). Data reaches a run by a path (--catalog, --registry), which replaces the embedded copy, or from the copy compiled into the release. A path lets a recalibration candidate be scored with no rebuild. Each run records which it used, and a path load and an embedded load of the same commit give the same data and content hash (§3.3).

The boundary between engines and the cost model

Only an engine module knows its upstream, so only it works out defaults, backend choices, sharding, fusion, padding and graph-capture sizes. That work is lowering. The catalog’s deriver writes checkpoint facts only, and no rule set outside an engine module maps settings to lowering (§6.1). The engine hands the cost model three objects in physical units (§6.2):

  • PoolPlan, fixed for the life of one pool: hardware, parallel layout, the lowered layers with the kernel implementation of each, the KV groups and budget, lower tiers, graph and draft policies, host work, resident weights, buffers, and steps in flight.
  • StepShape, one step across the data-parallel ranks in lockstep, already padded as the upstream pads it, with a mode (mixed, extend-only, decode-only, verify, prebuilt or idle).
  • engine.Transfer, one KV move, which the cost model turns into bytes per link.

An engine cannot size its KV cache without the cost model’s memory arithmetic, and the cost model cannot price a step without the engine’s plan. An Environment, supplied by the simulator, breaks the loop. In the plan phase the engine resolves its configuration, lowers the model into a partial plan, asks the Environment for the memory that weights, activations and buffers take, and applies its upstream’s budget rule. In the run phase it forms a step and asks for its price (§6.3).

The engine pads, and the cost model prices the padded shape. A kernel coefficient is keyed by the kernel implementation that runs, identified by a hash of its source, so a library version bump that leaves a kernel unchanged needs no substrate change. An engine-path cost (host, launch, graph replay) is keyed by the identity of the code that does the work, supplied by the engine module and stored as an opaque key, so no engine name appears in the substrate (§9.2). The engine decides which KV blocks move between tiers, and the substrate prices each move over paths the catalog states. The simulator shares each link among overlapping moves, the one resource arithmetic it owns (§6.2). Engine differences, such as step modes and page size, each have a place in the contract (§6.4).

Engines model an upstream commit

An engine module models one upstream commit: a release tag, or any commit on the upstream’s main or a release branch. Its Upstream record names the commit and the release it descends from. A build runs one commit of each engine, and a scenario naming another is refused (§7.1). Three kinds of work are distinct.

  • An engine upgrade moves a module from one commit to another by porting the diff of the code it models. It regenerates the field, surface and kernel lists at the new commit, locks the oracle to it, and runs every tier again (§12.4).
  • Model support is work in one module for one model, needed only when the model brings engine-facing code that an upgrade does not port: a new KV-cache layout, its own kernels, or a new drafting method or scheduler hook (§12.5).
  • A model backport applies the upstream commits that add a model onto the modelled commit, and lists them in the Upstream record. It carries model code only, never scheduler, KV-cache or connector changes. It is dropped when the modelled commit contains it, and has no grade of its own: a run is graded by its commit distance (§7.1).

Each upgrade generates a report: the surface diff, the field demand, the source diff and, for each model the new commit supports, whether the catalog has the model, whether it needs model support and for what, and, for each catalog chip, the coefficients it lacks and the kernels it would price below measured or calibrated (§7.1). Simulating the requested scenario, and the upgrade report, show what a new model lacks (§12.1). Maintainer practice: a module is upgraded at each upstream release; a maintainer with write access decides an on-demand upgrade and records it in an issue (§7.1). A new engine, such as TRT-LLM, meets the same bar as vLLM and SGLang: a new directory under engines/ that ports the upstream’s scheduling and KV-cache code, checked by an oracle that runs the upstream code, through its bindings for C++ (§12.6).

Fidelity to upstream code

An engine module ports four parts of its upstream: scheduling; KV-cache management; KV transfer and tiering; resolution and lowering (§7.1). A port is faithful when the upstream’s own scheduler and the Go port, given the same inputs, make the same decisions at every step. To run the upstream without GPUs, a harness replaces only its environment (GPU, clock, transport, environment settings, hardware platform, outside services), and a manifest lists every replacement. A recorded trace changes only after a maintainer has reviewed it (§7.2, §7.7). Every engine module runs the same tiers (§7.4):

Tests are behavioural: conformance, differential, mutation, metamorphic and property tests. A test of source text, declaration order, hashes or recorded outputs used in place of behaviour counts towards no tier (X13, §7.4). The surface list shows what the tiers do not test. Its generator reads the upstream’s own registration tables, so a new feature appears unprompted. Each item has one status. Modelled is the goal. Refused means the engine refuses it by name, with an issue, and the backlog counts what it blocks. Out of scope is allowed for three reasons only: the item needs hardware BLIS does not simulate, it does no work the simulator prices, or it is deprecated upstream (§7.5). A configuration field is modelled, proven inert with a passing proof, or not modelled with an issue (§5.2). A point whose run loaded code the upstream does not ship is not scored (§11.4). Shared frameworks are ported before the features built on them (§7.6). The router fork changes upstream files only in a fixed list of kinds, none of which alters a routing decision (§5.3).

Simulation method

BLIS takes its terms from Parallel DEVS, the Discrete Event System Specification. Model components (an engine instance, the router, a link, a client) interact only through timestamped messages, and none reads another’s state (§8.1). A time advance is the time of an engine’s next scheduled wake-up; a step ending is an internal transition, a request arriving an external one, and both at one instant a confluent one. A link’s state changes at a constant rate between events; each start or end of a transfer recomputes the rate of the others (§8.1). An instant is processed in three phases. Output functions run; each model component receives all the messages addressed to it at that instant, sorted by (time, round, class, sender, the sender’s own send count), with no global counter; each makes exactly one transition (§8.2). Each engine declares the step boundary at which each external input takes effect (§8.2).

Time is an integer number of microseconds. Only finitely many events may happen in finite time, so every zero-delay cycle contains a model component with a positive time advance or a declared bound (§8.3). Every random draw comes from a substream named by model component, purpose and entity, seeded from the scenario seed. Runs that differ only in configuration give the same requests the same inputs, but some draws depend on the system’s response, so comparisons need replications (§8.4).

The experimental frame is one document recorded in every Result: the generator and seeds, the initial state, the phases, the stop rule, the acceptance conditions and the metric definitions. Run, export and replay under the same configuration give an identical Result (§8.6). Every metric has one definition in the metric registry. A request’s fate (completed, dropped, timed out, in flight at the horizon, queued at the horizon, or not started) is written once, and every latency sample derives from it (§8.7).

Outputs are estimates. A terminating run is estimated from the mean of replications, starting at five, with a confidence interval. A steady-state run discards a warm-up found by a stated method, and a growing backlog means overload, so no latency value is reported. A comparison of two configurations is better, worse or not distinguished (§8.8). The interval covers workload randomness, and a reported value says whether it also covers the coefficients’ uncertainty. Every Result states whether its scenario lies inside the held-out data’s validity domain (§8.9). Verification asks whether the code does what the model says; validation asks whether the model matches the real system. A change that is both is split (§8.9).

Coefficients, the ledger and accuracy

When the coefficient registry has no exact entry, the lookup falls back down the ranks to the most trusted entry for that chip. Some rank has a value for every primitive family and chip, so a missing measurement never causes a refusal. New entries are required only for a new primitive family (§9.2). Each price records the least trusted method it used, and a lookup outside the range a fit covered ranks with transferred (§9.3, §9.4). A change to a measured value passes a landing gate: criteria committed first, then held-out error not worse on any lane (a group of held-out points judged together) and better on the target lane (§9.4). No rule requires a new GPU or cluster experiment. A measurement no source holds is priced by the fallback, down to a roofline or an assumed entry, and the entry is replaced when data appears (§10.4).

The ledger assigns each unit one role: fit, select, validate, held, anchor or report. The role is computed from the partition secret per group of near-copies, so near-copies cannot fit and judge. Only the fit, anchor and report lists are published. Results on select, validate and held units are aggregates, from jobs that hold the partition secret and never run a pull request’s code (§10.2). Accuracy is reported only on held-out units, those with the role held or anchor. Every source that is not held out is training data. A new source draws training roles only, split among fit, select and validate, and gains held-out roles only through a new partition version. Each run’s settings come from its own records: workload, cluster, GPU type, model and engine settings. A value no record holds is a named substitution on the point, and it lowers the grade (§10.4).

Scoring a point has four steps. State: copy the run’s recorded configuration verbatim. Estimate: apply the engine’s own rule for a value the run did not record. Decide: read each field’s status from the engine’s field list. Price: use the most trusted entry (§11.2). Grades follow commit distance, the distance between the run’s engine commit and the commit the scoring release models. G1: the same commit, and every condition for exactness holds. G2: as G1, with named substitutions. G3 and G4: another commit, with the ported code unchanged or changed. G5: not scored, for a listed reason. A condition the data cannot decide is never assumed to hold (§11.3). One simulator release scores every point (§11.5). Coverage is a funnel for each scored source, with no age limit on scoring, and a backlog ranks what lowers coverage or grade (§11.6). Accuracy is sliceable by any recorded attribute, and below a minimum number of role keys no aggregate is shown (§11.9). Anyone may run the scoring harness on any branch, but a reported value computed on a branch is labelled with its build and data and is never published as BLIS’s accuracy (§11.7).

Procedures

Each recurring trigger has one procedure with its components, steps and a list of what done means (§12).

How rules are kept, and how releases work

A rule is one of three kinds (§4.2). An automated rule is a deterministic check that protects the product’s correctness or accuracy: an import-graph lint, a conformance, differential, mutation, metamorphic or property test, a data validator, or a build-staleness check. A maintainer practice is a rule about process: review, approval, merge, issue handling, pull-request text and release notes. A maintainer with write access keeps it with standard git and GitHub mechanisms (branch protection, required reviews, signed commits). No program audits it. Agent guidance is followed by an agent that writes or reviews a change. A review finding ends fixed, filed as an issue, or rejected with a reason (§4.1). The checks that run on pull requests, releases and nightly are in §13.

Versions are written in one place (§4.1). inference-sim is the only tagged release; every other repository is pinned by commit (§14.1). Each release records in stack.json the upstream commit each engine models and the router fork commit, and the applications pin a release by tag and commit (§3.3). Lifecycle rules are in §14.1 and §14.2.

Working in a component

Each component’s rules are in §5.1 to §5.6. A contributor meets these first:

  • Engine modules. Each registers as an engine kind with the upstream commit it models, and publishes a field list and a surface list. Every Go file states its provenance. The port has no clock reads and no goroutines; waiting is reported to the simulator as a time value (§5.2).
  • The router fork. It is merged from each llm-d release, never rebased, owns the hosting contract and imports no BLIS code (§5.3).
  • The simulator. The engine is chosen by the scenario’s engine: {kind, version}. Unsupported or ambiguous input is refused, naming the field and the value. A fixed set of scenarios, the byte gate, must stay byte-identical across a refactor (§5.4).
  • The applications. Settings come from the simulator’s field list, never a hand-kept copy (§5.5). The dashboard is the only scorer (§5.6).

Rules a contributor must keep in mind

  • X1 Users configure BLIS with the upstream’s own configuration; an unknown or unsupported field is refused by its upstream name (§4).
  • X7, X2 One owner for each fact; dependencies point one way; the substrate contains no engine name (§4, §2.2).
  • X3, SUB-6, SUB-15 Engine behaviour and lowering live only in engine modules; the cost model resolves nothing; the deriver writes checkpoint facts only (§6.1).
  • X5, VLM-1 Fidelity is shown against the upstream’s own code (§4, §5.2).
  • X9 Every upstream feature has exactly one status (§7.5).
  • X13 Every behaviour change has a test that fails without it; tests assert behaviour (§4).
  • X8, D9 Every number is reproducible, and accuracy is reported only on held-out units (§4, §10.4).
  • D10, D11, VAL-2 Settings come from the run’s own records; no new GPU or cluster experiment is needed, because every lookup has a value and every price names its method (§10.4).
